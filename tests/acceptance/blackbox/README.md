# 黑盒套件 — 真实 agentgateway 上的认证、授权与凭证注入

> **性质**：黑盒回归，不是验收。`tests/acceptance/acceptance_matrix.csv` 的 95 条用例与六个 STD-CP 门禁保持 `NOT_RUN`。用例编号沿用 PoC 阶段的 `P1-*`。
> **结果**：agentgateway 1.7.0 上 91 个用例，90 PASS、1 FAIL，694 项检查（2026-11-18 加了 `P1-CO-01` 至 `08` 和 `P1-OA-01` 至 `08`，2026-11-19 加了 `P1-CO-09`）。FAIL 的是 `P1-SS-04`：网关自己仍然接受带两个 `Host` 头的请求，处置见"未解决"。证据：`evidence/p1-run-agentgateway-1.7.0.json`。
> **环境**：agentgateway **1.7.0**，即 `deploy/agentgateway/agentgateway.lock.json` 锁定的构建（上游容器镜像里的那个二进制，镜像按摘要锁定；二进制取出来在本机直接运行，不在容器里；它的 SHA-256 记在证据里，每次运行前按锁定文件核对，对不上就不运行）、本仓库的 `gateway-authz`、Mock 本地 Broker、Mock Provider，全部在本机回环地址。只测这一个构建。网关到 `gateway-authz`、Broker 到 `gateway-authz` 两段是双向 TLS，证书由每次运行临时生成的 CA 签发。
> **PDP 是本仓库的 `cmd/gateway-authz`，带 `acceptance` 标签构建**：产品代码加上本套件用的控制接口（看它收到了什么、让它答 500、变慢、放行却不给凭证、撤销账户）。跑的不是产品构建。它从文件读登记表和凭证，撤销表是为这次运行写的一个文件；已部署的 Gatekeeper 没有被调用，调用方 Token 是用每次运行临时生成的密钥签的。
> **名字还没改**：下文、用例标题、证书和端口名里的"Gatekeeper""PDP"，指的都是这个进程。PoC 阶段这个位置上是一个 Python Mock（`mock_gatekeeper.py`，已删除，见基线标签 `baseline-v1.0-poc`）。

## 回答了什么问题

G04 §4 要求用 PoC 比较三种凭证返回模式，G04 §9 列了 PoC 必须证明的结论。本 PoC 的回答：

| 问题 | 结论 | 依据 |
|---|---|---|
| agentgateway 能否按请求注入由 PDP 选定的第三方凭证（模式 A）？ | **能**。HTTP ExtAuthZ 的允许响应带 `Authorization` 头，网关按 `includeResponseHeaders` 把它（且只把它）写到上游请求。 | `P1-AZ-01/02/04`、`P1-CR-01` |
| 两租户、两账户能否隔离？ | **能**。租户身份取自已验签 JWT；蓝租户请求绿账户被拒；撤销蓝账户后下一个蓝请求即被拒，绿不受影响。 | `P1-AZ-03`、`P1-RV-01` |
| 调用方能否伪造租户或可信上下文？ | **不能**。伪造的 `x-idp-*`、`X-Tenant-ID` 到不了 PDP；PDP 看到的是网关按 JWT 声明和路由常量写入的值。 | `P1-AZ-05` |
| 内部 JWT 会不会到第三方？第三方凭证会不会回到调用方？ | **都不会**。Provider 只收到 Provider 凭证；PDP 收不到调用方 JWT，也收不到任何 Bearer 凭证；网关整轮运行的日志里没有 Provider 凭证、调用方 JWT 或密钥。 | `P1-CR-01/02/03/04` |
| 网关到 PDP 能否用工作负载 mTLS，PDP 能否据此只认网关？ | **能**。网关出示自己的证书，并且只接受工作负载 CA 为指定名字签发的 PDP 证书；PDP 从已验证的客户端证书取调用方身份。没有证书或证书来自别的 CA，连 TLS 都建立不了；同一信任域里不是网关的工作负载（业务应用、本地 Broker）拿到 401，拿不到凭证。冒充 PDP 的服务（名字对、CA 不对）收不到网关的任何请求。 | `P1-AZ-11`、`P1-CR-03`、`P1-TL-01` |
| PDP 故障时是否默认拒绝？ | **是**。PDP 返回 500、超时、进程不在，请求都没有到达 Provider。 | `P1-FC-01/02/03` |
| 拿一次创建调用的客单号，只凭日志能不能对上这次调用的两头？ | **放行的调用能；被拒绝的调用凭判定编号能**。放行的：网关访问日志里有且只有一行带这个客单号，同一行有 `gateway-authz` 给的判定编号、租户、承运商应答里的处理号；`gateway-authz` 的日志里有且只有一行带同一个判定编号。被拒绝的：403 的应答头和正文里有判定编号，网关那一行有同一个，`gateway-authz` 有一行拒绝带着它；那一行取不到请求正文，没有客单号。见下面"一次调用对得上"。 | `P1-CO-01` 至 `09` |
| 调用方能不能分清策略拒绝和问不到 PDP？ | **能，靠状态码和正文**。策略拒绝仍是 403，正文是 PDP 的原因。超时、进程不在、证书不被接受，以及模式 B 的 Broker 不在，是网关自己的 503，正文里没有判定；PDP 自己答的 500 和"定不了"原样到达。网关日志里这两类 503 不再是 `reason=ExtAuth`。见下面"失败从哪来"。 | `P1-FO-01/02` |
| Provider 会不会收到调用方自己加的请求头？ | **不会，只收到登记过的**。六条路由用同一份名单重建请求头。没登记的不到；登记过的到，凭证仍是那一个 `Authorization`。见下面"请求头只放行登记过的"。 | `P1-HD-01/02/03/04` |
| 非幂等写会不会被网关重放？ | **不会**（未配置重试策略时）。上游超时返回 504、上游断连返回 503，Provider 各只收到一次。 | `P1-WR-02/03` |
| 固定凭证（模式 C）够不够？ | **只够单账户**。跑得通，但两个租户以同一个账户到达 Provider。 | `P1-MC-01` |
| 模式 B（本地 Broker/Sidecar）？ | **跑得通，隔离、撤销、默认拒绝与模式 A 相同**。Gatekeeper 只被问决策，它发出的任何内容里都没有 Provider 凭证；凭证由 Broker 从本地存储取出，只走回环。代价见下面"三种取凭证方式的比较"。 | `P1-MB-01/02/03/04` |
| `backendAuth.key.expression` 比复制响应头更好吗？ | **能用，结果相同，没有观察到安全上的差别**。 | `P1-KX-01/02/03` |
| 撤销能不能由产品构建自己的入口来做，重启之后还在不在？ | **能，还在**。撤销者的工作负载身份向 `gateway-authz` 发一个请求，下一个请求在四种路由上都被拒绝，另一个账户不受影响；别的身份（包括拿得到凭证的网关）改不了也读不到；重启之后账户仍被拒绝，代次接着数；撤销文件读不成时 `gateway-authz` 不启动，网关拒绝全部请求。见下面"撤销：经产品自己的接口"。 | `P1-RV-02/03/04/05` |
| 凭证不是 Bearer 令牌，而是一个固定令牌加每个请求一个随机数时，还走得通吗？ | **走得通，网关注入的方式不用改，要改的是后端上那条规则认的前缀**。Provider 收到的是该租户自己账户的 `Hc-OweDeveloper 账号;令牌;随机数`，随机数次次不同；换掉令牌文件，下一个请求用的就是新令牌，`gateway-authz` 不重启。见下面"不是 Bearer 的凭证"。 | `P1-DT-01/02/03/04/05` |
| 凭证是向令牌端点取的 OAuth2 访问令牌时，能不能按账户隔离、缓存、过期前换新，取不到时拒绝？ | **能，对着替身令牌端点**。两个账户各拿各的令牌；连着要只取一次，并发要也只取一次；过期之前换新；令牌端点连不上、超时、答错时调用方得到 503 `CREDENTIAL_UNAVAILABLE`、Provider 什么都收不到，缓存里还没到期但该换新的令牌也不拿来顶；换客户端密钥不用重启；被撤销的账户拿不到缓存里的令牌；日志和应答里没有客户端密钥和令牌。没有对着真的令牌端点。见下面"OAuth2 客户端凭证"。 | `P1-OA-01` 至 `08` |
| 换了配置文件之后，能否确认这个实例上生效的是哪一份？ | **单个实例上能**。换文件不用重启，约 0.3 秒生效；加载不了的文件被整份拒绝，网关报告失败和原因，继续用上一份。网关报告的运行配置（`/config_dump`）算出的摘要随配置变，文件换回后回到原值。多个实例之间的情况在 `tests/integration/kubernetes` 里。注意事项见下面"配置回读"。 | `P1-RB-01/02` |
| 发布器能否从别的机器读到这些，又不把网关的管理地址交出去？ | **能**。网关另开一个要客户端证书的监听，只认发布器的身份，只把这两个 GET 转给本机的管理地址。管理地址上别的东西（关停、改日志级别、调试、写配置）在这个监听上一概没有；别的调用方连回应都得不到。 | `P1-RB-03` |

## 三种取凭证方式的比较

| | 模式 A：复制响应头 | 模式 A：`key.expression` | 模式 B：本地 Broker | 模式 C：固定凭证 |
|---|---|---|---|---|
| 按租户选账户 | 能 | 能 | 能 | 不能 |
| Provider 凭证经过哪里 | Gatekeeper 的响应 → 网关 | 同左 | Broker 本地存储 → 回环 → 网关；不出现在 Gatekeeper 的任何响应里 | 网关上的文件 |
| Gatekeeper 的接口 | `/v1/extauthz/check` | 同左，响应不变 | `/v1/egress/authorizations/decision`，只回决策和凭证句柄 | 不调用 |
| 多出来的东西 | 无 | 无 | 一个进程、一份本地凭证存储、一段回环通信 | 无 |

`key.expression` 的做法：ExtAuthZ 的 `metadata` 把 PDP 响应里的 `authorization` 头读进 `extauthz.credential`，再由 `backendAuth.key.expression` 写到上游请求，不再用 `includeResponseHeaders`。这条路由的写法是先在单独的试验里试出来的，试验中看到三点（不在证据文件里；证据文件证明的是现在这条路由的行为）：

- backend 上的 `authorization` 规则**先于** `backendAuth` 执行。照搬模式 A 路由上"必须有 `Authorization` 头"的规则，每个请求都会被拒（这时头还没写上）；要改成判断 `extauthz.credential`。写错的后果是全部拒绝，不是放行。
- 不加这条规则时，PDP 放行却没给凭证的请求会被不带凭证地转发，与"默认配置不安全的地方"第 3 项相同。
- `metadata` 也读得到响应体（`json(response.body)`），所以凭证可以不放在头里。契约目前规定凭证正文不出现在任何响应体里，本 PoC 没有改这一点。

模式 B 跑下来暴露的三件事：

- **回环端口上，密钥文件是唯一的屏障**。Broker 在回环地址上监听，网关用一个密钥文件证明自己；本机任何能读到这个文件的进程都能向 Broker 要到凭证（`P1-MB-04` 的对照项）。真实部署要靠 Unix Socket 或 Pod 内网络隔离，这一点没有测。
- **多了一处持有凭证的地方**。Broker 的本地存储里有该网关池用得到的全部账户凭证，它如何下发、轮换、吊销，设计里还没有。
- **决策契约缺一个字段**。`DecisionRequest` 原先没有地方放"调用方 Token 是为哪个环境签发的"，Broker 无从转达，PDP 也就拒绝不了 PROD Token 用在 TEST 池上。已在 `contracts/gatekeeper/openapi.yaml` 里加上可选的 `token_environment`（提案）。

## 不是 Bearer 的凭证：固定令牌加每个请求一个随机数

[ADR-0011](../../../docs/adr/ADR-0011.md) 第 3 条的做法，对着替身跑。有的 Provider 要的 `Authorization` 不是 `Bearer 令牌`，而是 `Hc-OweDeveloper 账号;令牌;随机数`：账号和令牌是固定的，随机数每个请求一个。`gateway-authz` 从第二个凭证文件（`--developer-tokens`）读账号和令牌，每次放行时现做随机数，把整段值放进允许响应的 `Authorization` 头。网关一侧仍是模式 A 的复制响应头，路由是 `mockcarrier-parcels-get-developer-token`。

- **网关上要跟着改的只有一处**：后端上"PDP 放行却没给凭证就拒绝"的那条规则（"默认配置不安全的地方"第 3 项）认的是凭证的第一个词。这条路由上它是 `Hc-OweDeveloper `；照搬 `Bearer `，这条路由的请求全部被网关拒绝。对照里把它改回 `Bearer `，`P1-DT-01/03/04/05` 都不通过；把这条规则整条去掉，`P1-DT-02` 不通过。`tests/contracts` 另有一条检查，拿路由上的这个词和 `gateway-authz` 源码里的那个词对。
- **调用方塞不进自己的凭证**（`P1-DT-02`）。调用方在自己的 Token 旁边再放一个 `Authorization: Hc-OweDeveloper …`：放在 Token 后面，PDP 给了凭证时请求照常转发，Provider 收到的只有 PDP 给的那一个；PDP 没给凭证时网关照样答 403，Provider 什么都没收到。放在 Token 前面，两种情况网关都答 401。两种顺序下 Provider 都没有收到调用方放的那个值。
- **换令牌不用重启**（`P1-DT-04`）。把令牌文件换掉（写新文件再改名），下一个请求带的就是新令牌，`gateway-authz` 还是同一个进程。换上去的文件读不成，或者带着 Bearer 文件里已经有的句柄，整份不要，继续用上一份，两种路由都不受影响；`gateway-authz` 各记一行，里面没有账号和令牌。
- **日志**（`P1-DT-05`）。网关和 `gateway-authz` 两边的日志里都没有账号、令牌，也没有这种认证头的值，包括凭证没给出来和令牌文件读不成时写的那些行。
- **替身比文档严一点**。Mock Provider 对这条路由按文档查头的格式（不对 403，账号或令牌不对 401），并且同一个随机数只收一次。承运商的文档说的是以后的版本会限定随机数不能重复；替身现在就拒，重发的头在这里看得出来。对照里把随机数改成固定的，`P1-DT-01/03/04/05` 都不通过。

对照（2026-11-18，改完跑一遍整套再改回）一共七处，每一处都有 `P1-DT` 用例不通过，别的用例都不受影响：上面两处配置；随机数固定；令牌文件不重读；读不成的文件把表清空；重读时把凭证写进日志；Bearer 文件里已有的句柄在令牌文件里照收。

这一段证明的是本仓库这一侧：`gateway-authz` 做出来的头经网关原样到了替身。承运商的沙箱没有被调用，替身接受不等于承运商接受。

## 撤销：经产品自己的接口

[ADR-0012](../../../docs/adr/ADR-0012.md) 的做法。`P1-RV-01` 和各种路由上的撤销用例，用的是验收构建才有的控制接口。`P1-RV-02` 至 `05` 走的是产品构建里就有的那条路：`gateway-authz` 带着 `--revocations`（保存撤销表的文件）和 `--revoker-identity`（唯一能改它的工作负载身份）启动，撤销者用为这次运行签发的证书向 `/v1/egress/revocations` 发请求。

- **撤销即时生效，四种路由都一样**（`P1-RV-02`）。撤销蓝账户之后的下一个蓝请求，在 Bearer 路由、开发者令牌路由、`key.expression` 路由和模式 B 路由上都是 403 `ACCOUNT_REVOKED`，Provider 一个都没有收到；绿账户照常。重复撤销什么都不变，代次不动。账户名打错了（登记表里没有这个账户）是 422，不是一次什么都没拦住的成功。恢复之后蓝账户放行。表里记着是哪个身份撤的、为什么；`gateway-authz` 的日志里也有这一行。
- **只有撤销者能改，也只有它能读**（`P1-RV-03`）。网关、本地 Broker、业务应用、发布器，和带着验收控制口令的操作者，各试了读表、恢复、撤销别的账户，都是 401，应答里没有表的内容，表和代次没有变。没有客户端证书、或者证书是别的 CA 签的撤销者，没有 HTTP 应答。反过来，拿撤销者的证书去调 ExtAuthZ 得到 401，要不到凭证。
- **重启之后还在**（`P1-RV-04`）。撤销之后把 `gateway-authz` 停掉再起来，换了一个进程：第一个蓝请求仍是 403 `ACCOUNT_REVOKED`，应答里的代次是重启之前的那个数，不是 0；表里仍记着是谁、为什么。
- **撤销文件读不成就不启动**（`P1-RV-05`）。文件不在、被截断、没有写表、别人可读，四种情况 `gateway-authz` 都以退出码 1 结束，说出是撤销文件的哪种毛病，不监听。这期间一个从没有被撤销过的账户的请求也被网关拒绝，Provider 没有收到。文件放回去之后它照常启动，原来的撤销仍然有效。文件不在不等于"没有撤销"：没有撤销是一份写着空表的文件。

**经操作员的命令走**（`P1-RV-06` 至 `11`，[ADR-0012](../../../docs/adr/ADR-0012.md) V1.2）。同一个接口，由产品自己的客户端来调：套件现场用 `go build` 构建 `gateway-control`（产品构建，不带标签），用这次运行签发的撤销者证书跑 `revoke`、`restore`、`revocations`，对着套件里那个真的 `gateway-authz`。命令只做一次请求，不重试；标准输出一行 JSON，标准错误一句话，退出码见 `gateway-control revoke --help`。

- **撤销**（`P1-RV-06`，12 项）。`revoke`：退出码 0、结局 `REVOKED`、`changed` 为真、代次加一；下一个蓝请求在 Bearer 路由和模式 B 路由上都是 403 `ACCOUNT_REVOKED`，Provider 一个都没收到，绿账户照常。`revocations` 读到的表里有这个账户，带着原因和撤销者的身份，与经接口读到的相同。再 `revoke` 一次：退出码 0，`changed` 为假，代次不动。`gateway-authz` 的日志里记了谁撤销的、为什么。
- **恢复**（`P1-RV-07`，7 项）。`restore`：退出码 0、结局 `LIFTED`、代次再加一；下一个蓝请求照常到达 Provider；`revocations` 读到的表是空的（`"revoked_accounts":[]`）。再 `restore` 一次：退出码 0，`changed` 为假，代次不动；日志里有恢复的那一行。
- **不是撤销者，不认识的账户**（`P1-RV-08`，14 项）。发布器、网关、业务应用、本地 Broker 的证书各跑 `revoke`、`restore`、`revocations`：都是 `NOT_REVOKER`、退出码 3、HTTP 401，输出里没有表的内容，也没有任何账户的状态；表和代次没有变，蓝账户仍被拒绝，绿账户没有被撤销。登记表里没有的账户（`account-bleu`）：`UNKNOWN_ACCOUNT`、退出码 3、HTTP 422，说明名字多半敲错了，什么都没有变。
- **问不到**（`P1-RV-09`，8 项）。`gateway-authz` 停掉时 `revoke` 和 `revocations` 都是 `UNKNOWN`、退出码 5，没有状态码，标准错误说请求可能到了也可能没到、再跑一次同样的命令是安全的、读到表之前不要当作已经撤销、没有自动重试。`gateway-authz` 起回来之后表里没有这个账户，代次与之前相同（这一次确实没到）。撤销者证书是别的 CA 签的、或者校验服务端用的名字不对，TLS 建不起来，同样是 `UNKNOWN`、退出码 5，表没有变。
- **生效但没有写下去**（`P1-RV-10`，10 项）。把保存撤销文件的目录（套件的 `.run`）改成不可写，再 `revoke`：`REVOKED_NOT_WRITTEN`、退出码 7、HTTP 500，应答里是现在生效的状态（已撤销，代次加一）；标准错误说账户现在被拒绝、`gateway-authz` 重启之后就不是了、要去查文件为什么写不了、修好之后再跑一次同样的命令。账户此刻确实被拒绝（403 `ACCOUNT_REVOKED`），文件里却还没有它。目录改回来之后再跑同一条命令：退出码 0，`changed` 为假，代次不变，文件里有了这个账户、谁撤销的、为什么。恢复写不下去时：`LIFT_NOT_WRITTEN`、退出码 3，标准错误说没有恢复、账户仍被撤销，蓝请求仍被拒绝；目录改回来之后再跑一次，`LIFTED`。这一例要求运行套件的用户受文件权限约束（不是 root），否则用例写明做不了并不通过。
- **输出里没有证书和私钥**（`P1-RV-11`，6 项）。上面各例里命令打印的全部内容、`gateway-authz` 的日志和网关的日志里，没有 PEM 头，也没有这次运行签发的任何一把私钥或证书的正文行。

这一组的结局和退出码与 Go 单元测试（`cmd/gateway-control/revoke_test.go`，对着要求客户端证书的 `httptest` TLS 服务器）一一对应；Go 里还有黑盒造不出的：没有配置撤销者（404）、请求不合格式（400）、应答看不懂的各种样子、不跟随重定向、超时、连接中途断掉。

验收构建的控制接口现在改的是同一个文件。黑盒原有的用例和期望都没有动。

对照（2026-11-18）一共十处，每一处都有 `P1-RV-02` 至 `05` 里的用例不通过：文件不在时当成空表；别人可读的文件照收；撤销只在内存里、不写文件；读文件时代次回到 0；谁有工作负载证书都能改；网关也能改；登记表里没有的账户也能撤销；判定读的和接口改的不是同一张表；改动不记日志；重复撤销算成一次改动。"判定读的和接口改的不是同一张表"那一处，原有的四个撤销用例也跟着不通过。

没有试过的：断电（试的是进程重启）；多于一个 `gateway-authz` 实例；写不下去只试了目录不可写这一种（磁盘满、文件系统只读没有试）。

## 一次调用对得上

开发计划 3.3，对着替身的这一部分。目标：拿一次创建调用的客单号（请求正文里的 `ReferenceId`），只凭日志找到网关的那一行、`gateway-authz` 的那一次判定，以及承运商应答里的处理号（`Data.ProcessCode`）。

做法：配置顶层 `frontendPolicies.accessLog.add` 往网关访问日志的每一行加四个字段，值是 CEL 表达式（老的 `config.logging.fields` 已弃用，没有用）。问 PDP 的五条路由各在 `protocol.http.metadata` 里把 `gateway-authz` 放行时给的应答头 `X-Idp-Decision-Id` 读成 `extauthz.decision_id`；`metadata` 只在放行时求值，所以被 PDP 拒绝的调用没有它，日志字段改为“有 `extauthz.decision_id` 就取它，否则取应答头 `x-idp-decision-id`”。`gateway-authz` 拒绝时（做出了判定的拒绝）也在应答头和正文里给判定编号，网关把 PDP 的拒绝原样转给调用方，这个头就在应答里。Mock Provider 的创建应答带承运商那样的 `Succeeded` 和 `Data.ProcessCode`、`Data.ReferenceId`（请求带字符串 `ReferenceId` 时）。

| 字段 | 值从哪来 |
|---|---|
| `authz_decision_id` | 放行的：`gateway-authz` 的应答头 `X-Idp-Decision-Id`，由 `metadata` 读成 `extauthz.decision_id`。被 PDP 拒绝的：同一个应答头，直接从应答里取。表达式 `has(extauthz.decision_id) ? extauthz.decision_id : response.headers["x-idp-decision-id"]`；两样都没有（问不到 PDP，或还没走到判定就被挡下）时这个字段不出现。Provider 写不进去：正文进不了表达式，Provider 应答里的这个头在六条后端路由上都被 `responseHeaderModifier.remove` 去掉（`P1-CO-08`） |
| `tenant_ref` | 已验签 JWT 里的租户。表达式 `jwt.tenant_id` 在日志里能用（不问 PDP 的路由上也有，`P1-CO-08`） |
| `provider_reference_id` | 请求正文的 `ReferenceId` |
| `provider_request_id` | 应答正文的 `Data.ProcessCode` |

后两个字段要网关为了写日志缓冲并解析正文，并把两个业务单号写进日志；这是仓库所有者 2026-11-18 定的。两个表达式只在值是 1 到 64 位 `A-Za-z0-9._-` 的字符串时写它，是别的字符串时写 `(malformed)`；值不是字符串（数字、对象）时求不出来，这个字段不出现。原因：日志把引号、换行、制表符转义，一次请求仍是一行，但长度不设限，5000 个字符照写。这个格式是为替身写的，换成真的承运商时，在 3.2 的配置里照它的格式定。

用例（`P1-CO-01` 至 `09`）：

| 用例 | 检查的是 |
|---|---|
| `P1-CO-01` | 一次带客单号的创建调用：只从客单号出发，网关日志正好一行；有判定编号、租户、处理号、路由名；`gateway-authz` 正好一行，放行，路由、租户、操作相符；替身收到了请求 |
| `P1-CO-02` | 两个租户各一次：各对到各自的判定编号和处理号，不串 |
| `P1-CO-03` | Broker 路由和另外三条问 PDP 的 GET 路由：有判定编号，能对到判定方的日志，没有客单号和处理号字段。Broker 那条对到的是 Broker 向 `gateway-authz` 问的那一次（`/v1/egress/authorizations/decision`，调用者是 Broker 的身份），不是网关问的 |
| `P1-CO-04` | 客单号带引号和换行、5000 个字符、是数字、是对象、是空串：日志只多一行，写的是 `(malformed)`（数字和对象时没有这个字段），替身收到的正文与发出的一致，调用方照常得到应答 |
| `P1-CO-05` | 应答里的处理号带引号、换行、超过 5000 个字符：日志只多一行，写的是 `(malformed)`，调用方收到的应答没有被改 |
| `P1-CO-06` | 被拒绝的调用（没有授权的租户、被撤销的账户）：调用方得到 403；应答头 `X-Idp-Decision-Id` 和正文的 `decision_id` 是同一个编号；网关那一行的 `authz_decision_id` 是它；`gateway-authz` 的日志里正好一行拒绝带着它；Provider 没收到请求；网关那一行没有客单号。另有：问不到 PDP（它不在）时，网关自己答 503，应答里没有判定编号，那一行没有 `authz_decision_id` |
| `P1-CO-07` | 正文里别的字段放像令牌的串、请求带着 JWT：网关和 `gateway-authz` 这几次的日志里没有那些串、JWT、Provider 凭证和密钥 |
| `P1-CO-08` | Provider 伪造判定编号。正文里伪造（不问 PDP 的 rates 路由）：那一行没有 `authz_decision_id`。应答头里伪造 `X-Idp-Decision-Id`：不问 PDP 的 rates 路由上，那一行没有 `authz_decision_id`，调用方的应答里没有这个头；问 PDP 的 tracking 路由上放行之后伪造，那一行的 `authz_decision_id` 仍是 `gateway-authz` 给的那个，调用方的应答里没有这个头 |
| `P1-CO-09` | Broker 路由上被拒绝的调用（别的租户的账户、被撤销的账户）：调用方得到 403 和 PDP 的原因码，Provider 没收到请求；应答头 `X-Idp-Decision-Id` 和正文的 `decision_id` 是同一个编号；网关那一行的 `authz_decision_id` 是它，网关只写了一行；`gateway-authz` 的日志里正好一行拒绝带着它，端点是 `/v1/egress/authorizations/decision`、调用者是 Broker 的身份（是 Broker 问的那一次，不是网关问的）。另有：`gateway-authz` 不在、Broker 问不到判定时，调用方得到 Broker 的 503 `GATEKEEPER_UNAVAILABLE`，应答头和正文里没有判定编号，网关那一行没有 `authz_decision_id` |

实测到的限度，都是 1.7.0 上的行为：

- **被拒绝的调用靠判定编号对，不再靠路由、租户和时间。** `gateway-authz` 做出了判定的拒绝（策略拒绝、账户被撤销、定不了的 503）在应答头 `X-Idp-Decision-Id` 和 403/503 的正文 `decision_id` 里给编号，和它日志里那一行是同一个；网关写日志时从应答头取。没走到判定的（调用者身份不对、可信上下文有歧义）没有编号，也不另造。防伪造：回退到应答头有一个风险，Provider 也能写这个头（没有去掉时它到得了调用方，也读得到日志里）。所以六条后端路由（含不问 PDP 的 rates）的 `responseHeaderModifier.remove` 都列了 `x-idp-decision-id`，上游应答里的这个头一律去掉；PDP 的拒绝由网关直接转答、不经过上游，不受影响。回退因此只可能取到 PDP 的头（`P1-CO-08`；`tests/contracts` 检查六条路由写法一样）。
- **被拒绝的那一行仍没有从请求正文取的字段**（只有租户和判定编号）：被拒绝的请求那一行取不到请求正文，这是 1.7.0 的行为（`P1-CO-06`）。
- **正文太大时取不到**：约 3MB 的试过取不到；上限在哪里没有量。取不到只是没有这个字段，请求和应答照常透传。正文不是 JSON、没有这个字段、没有正文（GET）也一样。
- **没有 `traceparent` 时网关不自己生成 trace id**；带了，日志里有 `trace.id`，转给上游的是同一个 trace id 加新的 span id。**ExtAuthZ 的请求里没有 trace 信息**，所以 `gateway-authz` 的日志里没有 trace id。这次不处理，完整的 Trace 在第 5 节。
- Broker 那条路由上，网关日志里的判定编号是 Broker 问 `gateway-authz` 得来的那一个，Broker 把它放在自己的应答头里转给网关（Mock Broker 也这样做，放行和拒绝时都放，拒绝时正文里也有 `decision_id`）；真的 Broker 要照这个做，否则这条路由上没有判定编号。Broker 路由上被拒绝的调用，凭判定编号对得上（`P1-CO-09`，2026-11-19 补）：Broker 把 `gateway-authz` 给的编号放进自己 403 的应答头和正文，网关那一行有它，`gateway-authz` 有一行拒绝带着它；Broker 自己没问到判定的 503（`GATEKEEPER_UNAVAILABLE`）没有编号。Broker 自己挡下的另外两种（本机调用者不对的 401、可信上下文有歧义的 403）也没有编号，`P1-MB-04` 看了前一种，后一种没有用例。
- 没有对着承运商沙箱试过：处理号的真实格式不知道。

## 失败从哪来

问 PDP 的五条路由（含模式 B）上，`failureMode` 从 `deny` 改成 `denyWithStatus: 503`。`deny` 时问不到 PDP，调用方得到的也是 403，和策略拒绝一样。

- **策略拒绝**（`P1-FO-01`）仍是 403，正文是 PDP 的 `reason_code`。试的是蓝租户申请绿账户，`ACCOUNT_NOT_GRANTED`。
- **PDP 自己答了的，原样到调用方**。它答 500，调用方得到 500。它被问到了但定不了（开发者令牌文件里没有这个账户的凭证，`P1-FO-02`），调用方得到 503，正文是 PDP 的 `INDETERMINATE` / `CREDENTIAL_UNAVAILABLE`，不是 403；另一个有凭证的账户照常。两种情况下 Provider 都没收到这个请求。
- **问不到 PDP**，网关自己答 503，正文里没有 `result` 和 `reason_code`，请求不转发。试过的是：超过网关给 PDP 的 1 秒还没答、PDP 进程不在、PDP 端口上的证书网关不接受（冒充的服务一个请求都没收到）。写、`key.expression`、开发者令牌三条路由在 PDP 不在时同样是这个 503。模式 B 在本地 Broker 不在时也是。

`P1-FC-01` 至 `03` 和 `P1-TL-01` 的期望没有改，仍是拒绝并且不转发。变的是它们记下的状态：问不到的时候从 403 变成 503。

网关自己的访问日志分不开"问不到"和"PDP 答了定不了"这两条 503（观察，不是检查）。记下来的都是 info、`reason=DirectResponse`，没有 `error` 字段。`deny` 的时候，问不到是一条 error、`reason=ExtAuth`。调用方靠正文区分；要知道 PDP 有没有被问到，看 `gateway-authz` 自己的日志。

另外试过、不在检查里的：这个二进制接受 `denyWithStatus: 200`，然后对一个没有转发的请求答 200；状态写成 `99` 时它退回 403。评审配置钉在 503，`tests/contracts` 对过。`failureMode: allow` 会在没问到 PDP 时继续往下走，要靠后端"必须有凭证"的那条规则才拒绝。

对照（2026-11-18，改完跑一遍整套再改回）一共七处。六处改 `failureMode`，每一处 `P1-FO-01` 都不通过，`tests/contracts` 也不通过：跟踪、写、模式 B、开发者令牌四条路由改回 `deny`；跟踪路由改成 `allow`；五条路由都改成 `denyWithStatus: 500`。`gateway-authz` 在定不了的时候改答 403，`P1-FO-02` 不通过。

## 请求头只放行登记过的

G03 §5 要求只传播 Provider 允许的头。原先只按名字删（下面第 5 项），调用方自己加的头仍会到 Provider。现在每条后端在凭证写上之后，用同一段表达式重建请求头：

```text
request.headers.filterKeys(k, k in ["accept", "authorization", "content-type", "idempotency-key", "traceparent", "x-client-trace"])
```

名字是小写，写成大写一个都匹配不上。`authorization` 在名单里，是因为这段表达式在"必须有凭证"的规则和 `backendAuth` 之后才执行，这时这个头只可能是 PDP 给的凭证。`Host` 和框住正文的头是网关自己的，不在名单里。

- **登记过的到得了**（`P1-HD-01`）。`Accept`、`Idempotency-Key`、`X-Client-Trace` 原样到 Provider。`Traceparent` 到了，里面仍有调用方的 trace id；网关可以改这个值。`Authorization` 是该账户的凭证。
- **没登记的不到**（`P1-HD-02`）。`X-Evil-Probe` 一类头不到 Provider。`Cookie` 和 `X-Forwarded-For` 仍被按名字删掉。
- **六条路由同一份名单**（`P1-HD-03`）。每条都带上 `User-Agent`、`Accept-Encoding`、`Accept-Language`、`Baggage` 和没登记的头。Provider 收到的都在名单里，或是网关自己的，并且只有一个凭证。
- **绕不过去**（`P1-HD-04`）。值不是 UTF-8、名字换了大小写、把头名写进 `Connection`、登记过的头发两次、Token 后面再放一个 `Authorization`。Provider 剩下的仍是名单里的头，和那一个账户的凭证。

求值不了的表达式不拦截。证据的 `allow_list_expression_that_cannot_be_evaluated` 记的是：把六处表达式都换成网关不认识的函数之后，`--validate-only` 仍接受；请求得到 200；没登记的头全部到了 Provider；按名字删的那些没有到；除了请求行，网关没有别的日志。所以按名字删除留着，六条路由用同一段文本（`tests/contracts` 对过），`P1-HD-03` 每条路由都发一次。

对照（2026-11-18，改完跑一遍整套再改回）一共十处。九处有 `P1-HD` 用例不通过，`tests/contracts` 也不通过：三条路由各自去掉名单；六条路由的表达式改成求值不了；名单里加进没登记的头；去掉 `idempotency-key`；`x-client-trace` 写成大写（这一处 `P1-CR-01` 和 `P1-FP-02` 也不通过）；名单里加进 `user-agent` 和 `baggage`；名单里去掉 `authorization`（凭证到不了 Provider，大量原有用例一起不通过）。唯一黑盒没抓住的是跟踪路由上去掉按名字删除、名单还留着：那些头本来就不在名单上，Provider 仍收不到。这一处 `tests/contracts` 不通过。按名字删除单独起作用，是在表达式求值不了的时候，记在上面的观察里。

## 配置回读

G03 要求发布之后逐个实例回读，确认生效的是批准的那一份（`GW-FR-014`、`GW-FR-041`）。网关的管理地址上有两个接口用得上：`/api/runtime` 的 `configReload` 说最近一次加载文件成没成功，`/config_dump` 给出它实际在用的配置。`P1-RB-01/02` 在被测的那个网关上换文件再换回来，看这两个接口怎么说。用的时候要知道：

- **单看 `synchronized: true` 不够**。`configReload` 只有 `synchronized` 和 `lastError` 两个字段，没有版本号，也没有加载时间；文件已经换了而网关还没重载的那一刻，它同样是 `true`。"这一份已经生效"要两条同时成立：`/config_dump` 的摘要等于期望值，并且 `synchronized` 为 `true`。
- **`/api/config/effective` 不能用来确认**。它显示的是磁盘上的文件，文件被拒绝时照样显示被拒绝的内容（`P1-RB-02` 的 `api_config_effective_shows_the_rejected_file`）。
- **期望的摘要要从网关那里取**。`/config_dump` 是网关内部的表示，不是文件原文，不能拿文件的哈希去比；要先让一个实例加载这份文件，取它的摘要作基准。单独试过（不在证据里）：一份只有两条路由的小配置，在重新启动的另一个实例上摘要相同；这里的评审配置，空闲时、有流量前后、隔几秒之后摘要都相同，`/config_dump` 的内容里没有那次运行的任何凭证或私钥。跨实例比对时要去掉 `config` 段再算：那一段里有随运行环境变的值（比如工作线程数跟着 CPU 限额走），见 `tests/integration/kubernetes/README.md` 第 4 点。
- 拒绝是整份的：被拒绝的文件里即使有没问题的路由，也不会生效。
- **摘要里有什么、没有什么**（单独试过，不在证据里）。`/config_dump` 里有路由、策略、后端、监听地址，有 `backendTLS` 引用的证书和 CA 的正文，有 JWKS 里各把密钥的 `kid`。没有私钥，没有凭证文件的内容，没有 JWKS 的密钥本身。所以：换了证书，摘要会变；JWKS 里同一个 `kid` 换了一把密钥，或者固定凭证文件换了内容，摘要不变。按地址取 JWKS 时，身份提供方加一把密钥，摘要也跟着变，哪怕没有任何发布。拿摘要跨实例、跨时间比对时要先把证书正文换成占位，JWKS 要随配置一起下发，见 ADR-0010 第 6、8 条。

**回读口**（`P1-RB-03`）。上面两个接口都在管理地址上，而管理地址不能离开回环（见下面第 7 项）。发布器在别的机器上，要读到它们，走的是评审配置里的另一个监听（`27619`）：

- 监听带 TLS，并要求客户端证书（`tls.root` 指向工作负载 CA）。没有证书、证书来自别的 CA，握手就失败。
- `frontendPolicies.networkAuthorization` 只放行发布器的身份（证书里的 SPIFFE ID）。同一个 CA 签发的其它工作负载，包括网关自己、Broker、业务应用，连接被直接断开。
- 这个监听上只有一条路由：`GET /config_dump` 和 `GET /api/runtime`，路径精确匹配，转给本机的管理地址。读到的内容与直接问管理地址相同。
- 管理地址上别的路径和方法在这里都是 404：关停、改日志级别、写配置、调试和性能分析接口、界面。出站路由不在这个监听上，回读路由也不在收业务请求的监听上。

这是让网关代理它自己的管理地址。上游文档没有把这写成一种用法；换版本时由 `P1-RB-03` 把关。

## 默认配置不安全的地方

下面九项**不配置就是不安全的**，都是跑出来的，不是读文档读出来的。"不处理时的默认行为"每次运行都在被测的这个二进制上重新观察：`run.py` 在跑用例之前，把评审过的配置去掉下面各项的处理，用它启动网关两次，一次不给会话密钥（第 6 项），一次给了密钥看它放过什么（其余各项），把看到的记在证据的 `agentgateway.start_without_session_key_rewrites_config_file` 和 `agentgateway.unmitigated_defaults` 里（各项后面括号里是对应的字段）。它们是观察值，不是检查项：换了版本后默认行为变了不算失败，但要回头看对应的处理是否仍然需要、是否仍然够用。处理之后的效果由用例检查。第 1、2 项最初是第一次运行的失败项；第 3、4 项是随后对照 G03 §5 把期望收紧才暴露的。现在的 `agentgateway.poc.yaml` 已逐项处理。

1. **Host 原样转发**（`host_header_the_provider_received`）。上游收到的是调用方发来的 `Host: egress-api.idp.test`。必须为每条路由配置 `urlRewrite.authority`。
2. **路径不做规范性检查**（`request_targets_on_the_route_without_a_pdp`）。`%252e%252e`（双重编码）、`%00`、`;x=1` 被原样转发到上游。现在由两层拦截：路由 `authorization` 规则只放行由非保留字符组成、段不以点开头的路径；`gateway-authz`（`internal/egressauthz/domain`）用同一条规则。无 PDP 的模式 C 路由证明了网关这一层单独有效。带 ExtAuthZ 的路由上 PDP 先被调用，这些请求是被 PDP 拒绝的。
3. **PDP 放行但没给凭证时，请求照样转发**（不带任何凭证；`pdp_allows_without_a_credential`）。现在在 backend 上加了 `authorization` 规则，没有 `Authorization` 头就由网关拒绝。
4. **Provider 的 `Location`、`Set-Cookie` 原样回给调用方**（`provider_answers_302_with_a_cookie`）。网关不跟随 302，但会把跳转目标和 Cookie 交给调用方。现在用 `responseHeaderModifier.remove` 去掉。
5. **调用方的 `Cookie`、`X-Forwarded-*`、`Forwarded` 原样传给 Provider**（`caller_headers_the_provider_received`）。现在用 `requestHeaderModifier.remove` 去掉。
6. **没有会话密钥时，网关启动会改写自己的配置文件**。`config.session.key` 未设置时，网关生成一个密钥并写回启动它的那个文件。第一次在 1.7.0 上运行时，仓库里受版本管理的 `agentgateway.poc.yaml` 就这样被加了三行（已还原，没有提交）。对按摘要审批、部署后回读对账的配置发布（G03）来说，这意味着运行中的文件不再是批准的那个文件，而且里面多了一个密钥。处理：用环境变量 `SESSION_KEY` 提供密钥，实测可阻止改写；`run.py` 另外只让网关从 `.run/` 下的副本启动，仓库里的文件它碰不到。`P1-CF-01` 检查网关运行时所用的文件与仓库里的逐字节一致；证据的 `start_without_session_key_rewrites_config_file` 记录了不提供密钥时的实际行为（`true`）。第 7 项的 `storage.mode: readOnly` 是第二道：有了它，即使没有密钥网关也不往文件里写（证据的 `start_without_session_key_rewrites_config_file_with_storage_read_only` 为 `false`，由 `P1-CF-02` 检查）；这时会话 ID 不加密，网关会记一条警告，所以密钥仍然要给。另外两个单独试过、不在证据文件里的观察：配置文件只读时网关只记一条警告然后照常启动；`session.key: disabled` 这个写法配置校验接受，本套件没有用它。
7. **管理接口能改运行中的配置，还会改写配置文件**（`write_through_the_admin_api`）。网关的管理地址上有一套给自带 UI 用的接口。默认的存储模式下，向它发一个 PUT（`/api/config/resources/...`）就能给运行中的配置加资源，网关还把改动写回启动它的那个文件。评审配置里管理地址只绑了回环，但本机任何进程都够得着；而 G03 要求运行配置只有发布器一个来源，G01 的 `GW-FR-046` 要求限制原生管理 UI 的写路径。处理：`config.storage.mode: readOnly`。同样的 PUT 得到 403，网关报告的运行配置（`/config_dump`）和文件都不变（`P1-CF-02`）。这一项和 `config` 段的其它设置一样，只在启动时读取。**`readOnly` 管的只是配置的写入**：设了它之后，向管理地址发 `POST /quitquitquit` 照样关停网关，`POST /logging?level=…` 照样改日志级别（单独试过，不在证据里）。上游的安全策略也写明管理接口不是一道面向不可信调用方的边界。所以管理地址只能留在回环上，不能为了回读把它开给别的机器；回读另走一个监听，见上面的"回读口"。
8. **收业务请求的监听默认开在本机所有网卡上**（`callers_listener_bound_to`）。不写 `bindAddress` 时端口监听的是 `*`，谁连得到这台机器，谁就能绕过前置组件直接连网关。处理：`bindAddress: 127.0.0.1`。监听只在回环上，从本机的另一个地址连它会被拒绝，前置组件成了别的机器进来的唯一入口（`P1-NL-01`）。管理、指标、就绪端口本来就绑在回环上；评审配置里唯一对外的端口是回读口。这个字段从 1.6.0 起就有（上游发布说明），本文件原先说"配置 Schema 没有监听器的绑定地址字段"，那是错的。
9. **调用方自己加的请求头会到达 Provider**（`unregistered_caller_headers_the_provider_received`）。不重建请求头时，没有被第 5 项按名字删掉的头（如 `X-Evil-Probe`）原样到上游。处理：每条后端用同一份名单重建请求头，见上面"请求头只放行登记过的"。`P1-HD-01` 至 `04` 检查处理之后的效果。名单求值不了的时候这一项失效，第 5 项仍在，见那一节。

## 未解决

- **`P1-SS-04` FAIL：带两个 `Host` 头的请求被接受**（RFC 9112 §3.2 要求 400）。网关用第一个做路由，第二个不会到达上游；上游 `Host` 已被第 1 项改写，所以没有形成越权，但请求本身应当被拒。配置层面没有办法：配置 Schema 里没有相关开关；CEL 规则里也识别不出来，`request.headers["host"]` 取不到值，`request.host` 只反映第一个（这是单独试验的结果，不在证据文件里）。这个用例保留为 FAIL，因为它记录的是网关自身的行为。处置分两头：
  - **前置组件**。在网关前面放了一个 nginx 1.30.6（`front.nginx.conf`，监听 `127.0.0.1:27620`，转发到 `27611`）。经它发送时，两个 `Host`（顺序正反、两个相同、写请求）和没有 `Host` 的请求都由 nginx 自己答 400，网关日志里没有新增记录，PDP 和 Provider 什么也没收到（`P1-FP-01`）。另外三个用例确认加了这一跳之后原有性质不变：租户隔离、Provider 收到的头和请求体、401/403/404（`P1-FP-02`）；Provider 变慢或断连时写请求只到达一次，nginx 没有重放（`P1-FP-03`）；指定上游和路径变形仍然到不了 Provider，nginx 把路径原样交给网关，拒绝它们的仍是网关和 PDP，只有 `%00` 是 nginx 直接拒的（`P1-FP-04`）。**限制**：其余用例仍直接打网关端口。这个端口现在只绑回环（上面第 8 项），别的机器连不上它，只能经前置组件进来；同一台机器上的进程仍然可以直接连它。Kubernetes 上对应的做法是把前置组件和网关放在同一个 Pod 里，Pod 对外只有前置组件的端口，见 `tests/integration/kubernetes`。这里验证的是这一个 nginx 版本加这份配置，正式的入口组件要重新跑。
  - **上游**。在只有两条路由、没有任何策略的最小配置上单独复现过：网关按第一个 `Host` 路由，后端只收到第一个，第二个被丢弃；没有 `Host` 的请求网关会答 400。也就是说网关自己前后一致，风险出在它前面有一个按另一个 `Host` 做判断的组件时。报告在 `docs/upstream/UPSTREAM_REPORT_duplicate_host.md`，**已于 2026-11-11 提交，上游还没有答复**；agentgateway 的 `SECURITY.md` 要求拿不准是否属于安全问题时走私下报告，所以走的是私下渠道（公告 `GHSA-gccc-c8q8-cjmm`，只有报告方和上游维护者能打开）。
- **mTLS 证明的是"谁在调用 PDP"，不是"调用方 Token 里写了什么"**。租户和服务身份仍然是网关转述的：PDP 相信它们，是因为对面是网关。网关被攻破等于这些声明可以伪造，这一点 mTLS 不改变。
- **规范路径规则很严**：不允许 `%`，所以路径段里不能有需要编码的字符。真实 Provider 的 Operation 如果需要，得按 Operation 单独登记放宽，不能全局放开。

## OAuth2 客户端凭证：向令牌端点取令牌

[ADR-0011](../../../docs/adr/ADR-0011.md) 第 4 条的做法，对着替身令牌端点跑。`gateway-authz` 从第三个凭证文件（`--oauth-clients`）读每个账户的令牌端点、客户端标识、客户端密钥和 `key_version`，用 `client_credentials` 加 HTTP Basic 去取访问令牌，按账户缓存，把 `Bearer 令牌` 放进允许响应的 `Authorization` 头。取到的是 Bearer 令牌，所以**没有加网关路由**，用现有的 `tracking.get` 那条问 PDP 的 Bearer 路由；登记表里那条路由多了两个租户、各带一个账户（`tenant-oauth-1`/`account-oauth-1`、`tenant-oauth-2`/`account-oauth-2`），原有租户和账户没有动。账户放进已有的租户会让它们有两个账户、"唯一获授账户"的选择失效，所以用了新租户。替身令牌端点是 Mock Provider 的一个路径（`/oauth/token`），同一个进程、同一个端口：核对 Basic 里的客户端和密钥，给每个客户端发各自的令牌并记住它属于哪个账户，Provider 的业务端点收到这样的令牌时认它、在应答里说出账户，过了寿命就不认；用例通过 `/admin/oauth/config` 控制它的寿命、延迟和故障，通过 `/admin/oauth` 读每个客户端被取了几次、各次用的是哪一个密钥。令牌端点的请求不进 `/admin/hits`。

这八个用例排在最后。每个用例开头把客户端文件换成一份 `key_version` 新的，`gateway-authz` 因此认为键都变了、缓存是空的，没有哪个用例从前一个留下的缓存开始。

- **各拿各的**（`P1-OA-01`）。两个账户的请求到 Provider 时各带着发给自己客户端的令牌；令牌端点各被问一次，带着文件里写的 `scope`（`account-oauth-1` 的是两个记号 `parcels.read parcels.write`，替身报告它收到的整串，与文件里的一致）和 `audience`。
- **缓存与换新**（`P1-OA-02`、`03`）。连着五个请求只取一次。寿命设成五秒：两秒时还是第一枚，4.7 秒（最后十分之一里）的请求用的是新的一枚，第二次取发生在第一枚的五秒之内。
- **并发**（`P1-OA-04`）。令牌端点慢 0.4 秒，十二个请求同时来，全部 200，令牌端点只被问一次，十二个请求用的是同一枚。
- **取不到**（`P1-OA-05`）。十三种做法：状态 500、401，重定向（不跟随，禁止目标什么都没收到），`token_type` 不对、没有、没有 `expires_in`、为 0、是字符串，令牌为空，不是 JSON，JSON 数组，连接被掐断，超过超时才答；另有一个没人监听的端口。每一种：调用方得到 503、`INDETERMINATE`、`CREDENTIAL_UNAVAILABLE`，Provider 什么都没收到；超时的那种约 0.8 秒就拒绝；端点恢复之后下一个请求照常。另造了一条：先取到一枚，等它进入该换新的最后十分之一、令牌端点同时坏掉，两个请求都被拒绝，而那一枚在 Provider 那里还没过期（直接拿它去问 Provider 得到 200）；端点恢复后用的是新的一枚。
- **换密钥**（`P1-OA-06`）。令牌端点只认新密钥之后，把客户端文件换成新密钥加新 `key_version`：下一个请求就是用新密钥取了新令牌，替身报告那一次用的是第二个密钥，没有拒绝过一次；`gateway-authz` 同一个进程。换上去的文件不合格（非回环的明文 `http`、别人可读）时，继续用上一份，缓存的令牌照用，令牌端点没有再被问，`gateway-authz` 各记一行。
- **撤销**（`P1-OA-07`）。令牌已缓存，撤销账户：403 `ACCOUNT_REVOKED`，Provider 没收到，令牌端点没有再被问；恢复之后用的是缓存里原来那一枚。
- **日志和应答**（`P1-OA-08`）。网关的日志、`gateway-authz` 的日志、这几个用例里调用方得到的全部应答（成功的、被拒绝的、被撤销的）里，没有客户端密钥、替身发过的任何访问令牌和 Basic 头；`gateway-authz` 的日志里有每次取令牌的行（句柄、类别、用时、`expires_in`），没有令牌端点应答的正文。

文件写得不对时不启动（权限不是 0600、非回环的明文 `http`、句柄与另一个文件重复、`--oauth-timeout` 不合法），黑盒里没有对应的用例：第一步的同类检查（开发者令牌文件）也没有另起进程做，所以这几条只在 Go 单元测试里（`cmd/gateway-authz` 的 `TestOAuthFlagsRefuseToStart`、`oauthclient` 的文件测试）。

这一段证明的是本仓库这一侧：取令牌、缓存、拒绝和不泄露，对着一个按 RFC 6749 回答的替身。令牌端点是回环上的明文 HTTP，不是真的令牌端点，也没有 HTTPS 的场景。

## 没有覆盖

`gateway-authz` 跑的是验收构建，登记表、凭证和撤销表都来自为这次运行写的文件，撤销者的证书也是为这次运行签发的（没有真实身份源、授权库、Secret Manager；Provider 的令牌端点只有 `P1-OA-*` 用的那个替身），没有调用已部署的 Gatekeeper；Provider 是回环 Mock，开发者令牌那条路由的对端也是它，承运商的沙箱没有被调用；本地 Broker 是 Mock，存储是一个 JSON 文件。mTLS 只在网关到 PDP、Broker 到 PDP 两段上是真的，CA 和证书每次运行临时生成：没有 SPIFFE Workload API，没有证书轮换和吊销；调用方到网关、网关到 Provider 是明文 HTTP。单进程，没有限流、负载；多副本和配置的滚动替换在 `tests/integration/kubernetes` 里，用的是一份没有 JWT 和 ExtAuthZ 的小配置。回读口只在这一个实例上、用为这次运行现做的发布器证书试过；这套用例里没有发布器，真的发布器（`cmd/gateway-control`）在 `tests/integration/compose` 里对着一份没有 JWT 和 ExtAuthZ 的小配置跑。没有 gRPC ExtAuthZ、决策缓存、CONNECT、gRPC 上游、HMAC 签名、对 Provider 的 mTLS；没有 DNS 重绑定和网络层出口 ACL。完整列表在证据文件的 `scope_limits`。

## 运行

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt   # 一次
.venv/bin/python tests/acceptance/blackbox/run.py                                   # 锁定的 agentgateway；约 30 秒；没有 FAIL 才返回 0
.venv/bin/python tests/acceptance/blackbox/run.py --agentgateway /path/to/agentgateway   # 锁定的那个二进制放在别处时
.venv/bin/python tests/acceptance/blackbox/run.py --check-evidence                  # 不运行；证据是不是当前这些文件跑出来的
```

需要 Go 工具链：脚本每次都用 `go build -tags acceptance` 把 `cmd/gateway-authz` 构建到 `.run/` 下再启动它。

只跑 `deploy/agentgateway/agentgateway.lock.json` 锁定的那个 agentgateway 构建：上游容器镜像里的二进制。第一次先运行 `.venv/bin/python tests/acceptance/blackbox/pin.py --fetch`，它按摘要拉镜像、取出二进制、核对后放到 `~/.local/opt/agentgateway/<版本>/agentgateway`。不带 `--agentgateway` 时先找这个路径，没有再找 `PATH` 上的 `agentgateway`；找到的二进制要与锁定文件里的版本、提交和 SHA-256 都一致，否则脚本拒绝运行（`pin.py`，`--agentgateway` 指定的也一样）。证据文件是 `evidence/p1-run-agentgateway-<版本>.json`，只有锁定版本的这一份。

脚本先检查端口段是否空闲、用 `--validate-only` 校验配置，再启动五个进程和一个 nginx 容器，跑完全部停掉。跑用例之前，网关还会被短暂地另外启动四次：用去掉处理的配置启动两次（见"默认配置不安全的地方"），一次不给会话密钥，一次观察它放过什么；再用评审过的配置、不给会话密钥启动一次；再用评审过的配置、把请求头名单换成一段求值不了的表达式启动一次（见"请求头只放行登记过的"）。四次都从 `.run/` 下的临时文件启动，观察完就停掉，用例不对着它们跑。nginx 需要本机有 docker：镜像是 nginx 官方的非特权版本，按摘要固定（见 `run.py` 的 `FRONT_IMAGE`），本地没有时会拉取一次；容器以非 root、只读根文件系统、不带任何 capability 运行，用宿主机网络，只监听回环。docker 或镜像不可用时脚本拒绝运行，不会跳过那四个用例。网关从 `tests/acceptance/blackbox/.run/` 下的配置副本启动，会话密钥经环境变量 `SESSION_KEY` 提供（原因见上面第 6 项）。每次运行生成新的 JWT 签名密钥、会话密钥、工作负载 CA 与证书、Mock 凭证，放在 `tests/acceptance/blackbox/.run/`（已忽略），不写入证据。

## 文件

- `agentgateway.poc.yaml`：原生配置。六条出站路由（两条模式 A，一条模式 B，一条模式 C，一条用 `key.expression` 的模式 A，一条凭证不是 Bearer 令牌的模式 A），外加回读口和它的一条路由。
- `pin.py`：按 `deploy/agentgateway/agentgateway.lock.json` 找到并核对 agentgateway 二进制，`--fetch` 时从锁定的镜像里把它取出来；联调套件（`tests/integration/gatekeeper/`）和 Kubernetes 套件（`tests/integration/kubernetes/`）也用它。
- PDP 不在这个目录里：是仓库根下的 `cmd/gateway-authz`，双向 TLS，按客户端证书里的身份决定谁能调哪个端点；实现了 `contracts/gatekeeper/openapi.yaml` 的 `/v1/extauthz/check`（模式 A）、`/v1/egress/authorizations/decision`（模式 B）和改撤销表的 `/v1/egress/revocations`。本套件用的控制接口在 `cmd/gateway-authz/hooks_on.go`，只有带 `acceptance` 标签的构建里才有。
- `mock_broker.py`：Mock 本地 Broker。`pki.py`：每次运行的 CA、证书和 TLS 连接；证书里有网关、Broker、发布器、撤销者等几个工作负载身份。
- `mock_provider.py`：记录收到的每个请求；按 Bearer 令牌认账户，`/v1/parcels/` 下按 `Hc-OweDeveloper 账号;令牌;随机数` 认，同一个随机数只收一次。`/oauth/token` 是替身令牌端点（`P1-OA-*`）。`policy.poc.json`：四个租户四个账户的授权数据（两个是 `P1-OA-*` 用的）。
- `front.nginx.conf`：前置 nginx 的配置。给 agentgateway 上游的报告（英文，含最小复现）在 `docs/upstream/`。
- `run.py`：用例与期望。`evidence/p1-run-agentgateway-<版本>.json`：最近一次运行的逐项检查与观察值，含二进制、锁定文件与配置的 SHA-256。

## 期望是怎么定的

期望取自 G01/G03/G04，写在 `run.py` 里，不达标记 FAIL，不改期望迁就结果。运行历史：

1. 第一次运行 37/39。失败的是 Host 转发和路径绕过（上面第 1、2 项），据此改了网关配置和 PDP 参考实现。
2. 随后对照 G03 §5 **收紧**了三处期望（无凭证时必须由网关拒绝、`Location` 不得回给调用方、`X-Forwarded-*` 不得传给 Provider），并新增 `P1-SS-04`。收紧后暴露出第 3、4 项和重复 `Host` 的问题；第 5 项的处理与检查是同时加上的。
3. 在 1.6.0 上定格为 39/40。
4. 把同一份配置和同一套用例原样拿到 1.7.0 上：同样是 39/40，失败的同样是 `P1-SS-04`。这次运行暴露了第 6 项，据此新增 `P1-CF-01`，并把网关改为从副本启动、经环境变量拿会话密钥。
5. 两个版本定格为 40/41。
6. 网关到 PDP 的共享密钥换成双向 TLS，`P1-AZ-11`、`P1-CR-03` 的期望随之收紧（原来查"没有密钥就 401"，现在查"没有证书连不上，证书身份不是网关就 401"），新增 `P1-TL-01`、`P1-CR-04`；加入模式 B（`P1-MB-01..04`）和 `key.expression` 路由（`P1-KX-01..03`）。新增的 9 个用例在 `run.py` 里第一次运行就全部通过；在此之前，mTLS 和 `key.expression` 的配置写法已经在单独的试验里试过。当时 1.7.0 为 49/50，1.6.0 为 46/47 加 3 个 SKIP。
7. 为 `P1-SS-04` 加了前置 nginx 和 `P1-FP-01..04`。`P1-SS-04` 本身没有动，仍然 FAIL。新增的 4 个用例第一次运行就通过；之后只给 `P1-FP-01` 加了一条对照检查（单个 `Host` 的请求确实会在网关日志里留下记录），用来说明"网关日志没有新增"这条检查不是空的。当前 1.7.0 为 53/54，1.6.0 为 50/51 加 3 个 SKIP。

8. PDP 从 Python Mock 换成本仓库的 `gateway-authz`（Go，验收构建）。网关配置里只改了注释，用例和期望没有动。换完第一次运行 37/54：`run.py` 直接调 PDP 时从来不发 `Host` 头，Python Mock 不在乎，Go 的 HTTP 服务端按 RFC 9112 §3.2 答 400，于是控制接口全部失效，靠它们注入故障和读取记录的用例跟着失败。改的是 `run.py` 的客户端（补上 `Host` 头），不是期望。之后两个版本的结果与换之前逐项相同：1.7.0 的 282 项检查、1.6.0 的 260 项检查，没有一项变化。一个不在检查里的差别：网关到 `gateway-authz` 协商出的是 HTTP/2，到 Python Mock 时是 HTTP/1.1（证据的 `gateway_authz.http_versions_seen_from_the_gateway`）。
9. `gateway-authz` 加了可选的一步：登记表放行之后再向 Gatekeeper 的 PDP 确认账户授权。黑盒套件不启用它（不带 `--gatekeeper-url`），`run.py`、配置和期望都没有动；因为服务的源码变了，两个版本各重跑一次，逐项结果与上一份证据相同。启用这一步时的表现在 `tests/integration/gatekeeper/` 里测。
10. 目标版本只留一个：agentgateway 锁定为 1.7.0（`deploy/agentgateway/agentgateway.lock.json`），1.6.0 不再测，它的证据文件已从目录里删除（git 历史里还有）。`run.py` 启动网关前按锁定文件核对二进制。原先单独放着、只有 1.7.0 接受的 `key.expression` 路由并进了 `agentgateway.poc.yaml`，"二进制不接受就记 SKIP"的分支随之去掉。用例和期望没有动。重跑后仍是 53/54，282 项检查的结果与上一份 1.7.0 证据逐项相同。
11. 前五项默认行为改为每次运行都观察并记进证据（`agentgateway.unmitigated_defaults`），不再靠 PoC 早期在 1.6.0 上的观察；在 1.7.0 上五项都与原先的描述一致。为了能观察到第 4 项里的 Cookie，Mock Provider 的 302 响应加了 `Set-Cookie`。`P1-SS-02` 的期望原文本来就写着不把 Provider 的 Cookie 交给调用方，但此前 Mock 不发 Cookie，这半句没有被检查到；现在补了一条检查（`Set-Cookie not passed to the caller`）。其余用例和期望没有动。重跑后仍是 53/54；除新增的这一条外，282 项检查的结果与上一份证据逐项相同。
