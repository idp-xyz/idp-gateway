# 在 Kubernetes 上发布配置：不可变的快照，滚动替换

[ADR-0010](../../../docs/adr/ADR-0010.md) 提议数据面用 standalone 模式的 agentgateway。在 Kubernetes 上，一份快照是一个不可变的 ConfigMap，一个网关池是一个 Deployment；发布就是把 Deployment 指到新快照的 ConfigMap 上，由它滚动替换副本。这里在本机的一个 kind 集群里验证这套做法。

> 这是机制验证，不是验收，通过不改变验收矩阵里任何用例的 `NOT_RUN`。  
> 集群只有一个节点。配置是一份只有几条路由的小文件；没有 JWT、ExtAuthZ 和凭证，那些在黑盒套件里。

## 怎么跑

```bash
tests/integration/kubernetes/stack.sh up                 # 建集群，约半分钟
.venv/bin/python tests/integration/kubernetes/run.py     # 约三分钟；第一次要拉三个镜像，再多一分多钟
tests/integration/kubernetes/stack.sh down               # 删除集群和它的 kubeconfig
```

需要 kind、kubectl、docker，以及本机已有的节点镜像 `kindest/node:v1.35.0`（本机到不了 Docker Hub）。

- 集群叫 `idp-gateway-k8s`。它的 kubeconfig 只写在 `.run/kubeconfig`（已被 git 忽略）；脚本不读也不改 `~/.kube/config`，不动本机上别的 kind 集群。
- 用到三个镜像，都按摘要引用，由集群节点自己去拉：锁定的上游 agentgateway 镜像（摘要取自 `deploy/agentgateway/agentgateway.lock.json`）、与黑盒套件相同的前置 nginx、一个带 Python 的工具镜像。节点要够得着 `cr.agentgateway.dev` 和 `public.ecr.aws`。
- `run.py` 只动 `egress-test` 这一个命名空间，每次从头建起。证书每次运行现做，跑完删除。
- 发布前的离线加载在本机起一个容器，临时占用回环上的 `27619`，所以不能和黑盒套件、Gatekeeper 联调同时跑。

## 部署的样子

每个网关 Pod 里两个容器：

| 容器 | 是什么 | 端口 |
|---|---|---|
| `front` | nginx，与黑盒套件同一个镜像、同一份配置，只换了端口。Pod 上收业务请求的只有它 | 8080 |
| `agentgateway` | 锁定的上游镜像。收业务请求的监听只绑回环；管理、指标只绑回环；另开一个回读口 | 8081（回环）、15000 和 15020（回环）、8443（回读口）、15021（就绪探测） |

- **快照**：ConfigMap `agentgateway-snapshot-<内容摘要的前 12 位>`，`immutable: true`。
- **Deployment**：`maxSurge: 1`、`maxUnavailable: 0`、`minReadySeconds: 3`。Pod 模板里写着它用哪一份快照。
- **终止的先后**：`front` 先等 8 秒再停止接新连接，等的是端点被摘除；网关收到终止信号后 12 秒内照常接 `front` 转来的请求，之后只把在途的做完，最迟 45 秒；Pod 的宽限期 60 秒。
- **证书**：一个 Secret，里面是回读口的服务端证书、网关去问 PDP 用的客户端证书和 CA。发布器的证书不在网关 Pod 里。
- 另有一个工具 Pod 和一个回话的后端。工具 Pod 扮演发布器，也扮演别的工作负载；`probe.py` 是它跑的脚本。

## 结果

2026-11-11，Kubernetes v1.35.0（kind v0.31.0，单节点），agentgateway 1.7.0（锁定摘要的上游镜像），三个副本：4 个用例全部通过，同一份脚本连跑两轮都是 4/4。逐项结果写在 `.run/result.json`，不入库。

| 用例 | 内容 | 结果 |
|---|---|---|
| K8-01 | 三个副本从同一份快照启动。跑的是锁定摘要的镜像。发布器的证书从另一个 Pod 经回读口读到每个副本：配置已加载，存储模式 `readOnly`，摘要相同，并且等于发布前在集群外算出的期望值。回读口上没有管理地址的其它接口，也不回答别的调用方。从另一个 Pod 连不上网关的业务监听、管理端口和指标端口。带两个 `Host` 头的请求在 `front` 就被拒绝。快照的 ConfigMap 改不了 | PASS |
| K8-02 | 发布一份多一条路由的快照：全部副本被滚动替换，期间就绪的副本不少于 3 个，没有一个请求失败；每个副本的摘要等于新快照的期望值；上一份快照的 ConfigMap 还在 | PASS |
| K8-03 | 一份网关加载不了的快照：集群外的加载先拒绝它并给出原因。硬发下去：第一个新 Pod 里的网关退出，Pod 不就绪，滚动停住；原来的副本一个没少、没有重启、照常服务，没有请求失败。指回上一份之后恢复，原来的副本没有被重建 | PASS |
| K8-04 | 回滚到更早的那份快照：同样是一次滚动，没有请求失败，摘要回到那份快照的期望值 | PASS |

## 看清的事

### 1. 三个副本十来秒换完，期间没有请求失败

| | 第一轮 | 第二轮 |
|---|---|---|
| 从发布到滚动完成（`K8-02`） | 12.2 秒 | 11.2 秒 |
| 从回滚到滚动完成（`K8-04`） | 11.6 秒 | 10.3 秒 |
| 滚动完成之后，旧 Pod 全部退出（`K8-02`） | 又过 13.5 秒 | 又过 13.5 秒 |

流量由工具 Pod 经 Service 发出：每秒 20 个快请求，每个一条新连接；另有两条线各自接连发耗时 2 秒的请求。两轮、四次滚动，一共 2540 个快请求和 130 个慢请求，全部得到 200。

脚本定稿之前还跑过三轮，用例相同、检查项少几条：也都是 4/4，滚动用时 9.7 到 13.1 秒，同样没有失败的请求。

没丢请求靠的是上面那组终止时限。默认设置下，网关收到终止信号立刻不再接新连接，5 秒后切断在途的请求（单独试过，不在这套用例里）。这里的 8 秒、12 秒、45 秒是为这套用例取的，没有对着真实的请求时长调过。

### 2. 加载不了的快照，在两个地方被挡住

- **发布之前**。发布器用同一个镜像在集群外加载这份快照。加载不了，进程以非零码退出并说出原因，这份快照就不该往下发。
- **硬发下去**。新 Pod 里的网关起不来：它启动时遇到加载不了的文件就退出。Pod 不就绪，`maxUnavailable: 0` 让滚动停在这第一个 Pod 上。原来的副本没有被碰过。

### 3. 期望摘要可以在集群外算出来

每个副本经回读口报告的摘要，等于发布前在集群外加载同一份快照得到的摘要。集群外那次加载是一个 docker 容器，用的是另一套证书。两边相等有两个条件：

- 算摘要时去掉 `config` 段。两边这一段不同的项是 `dns`：解析器的配置随环境变。上一版套件还量到过工作线程数随 CPU 限额变。
- 算摘要时把证书正文换成占位。配置里有一条形状与真实的池相同的路由，带着去问 PDP 用的客户端证书和 CA；它们的正文在 `/config_dump` 里。不换成占位，集群里和集群外的摘要就不同，`K8-01` 里有一项检查专门确认这一点。

### 4. 回读不用进容器，也进不去

上游镜像里没有 shell，`kubectl exec … sh` 起不来。回读走的是网关自己的回读口：拿发布器的证书，从另一个 Pod 连 Pod 地址上的 8443。同一个 CA 签发的其它工作负载、不带证书的、别的 CA 的证书，都得不到回应；回读口上也没有关停、改日志级别这些接口。写法与黑盒套件的 `P1-RB-03` 相同。

### 5. Pod 对别的工作负载只开三个端口

从另一个 Pod 连网关 Pod：`front` 的 8080、回读口 8443、就绪探测口 15021 连得上；网关的业务监听 8081、管理 15000、指标 15020 被拒绝。业务请求进来只有 `front` 这一条路，而网关自己会接受的那种带两个 `Host` 头的请求（黑盒套件的 `P1-SS-04`），在 `front` 得到的是 400。

## 为什么不就地改 ConfigMap

这套用例的上一版（提交 `128ca4a`）测的是另一种做法：一个池一个 ConfigMap，发布就是改它的内容，等 kubelet 把它同步进各个 Pod，网关各自重载。它跑得通，当时量到的是：

- 变更要 24 到 84 秒才到 Pod（kubelet 默认每分钟同步一次），同一次变更里各副本先后相差 4 到 17 秒。
- 一改，这个池的全部副本都会换上，中途停不下来，池内分不了批。
- `config` 段的设置只在启动时读取，改了它还得另外滚动重启一次：两类变更，两套做法。
- 遇到加载不了的文件，运行中的副本会拒绝它、继续用上一份，看上去没事。但此后任何一个副本重启、任何一次扩容，新进程读到的都是那份坏文件，起不来。

所以 ADR-0010 改成了现在的做法。它的代价也写在 ADR 里：每次发布都重启这个池的每一个网关进程。

## 没有覆盖的

- 多节点、节点或 kubelet 故障、Pod 被驱逐；自动扩缩、PodDisruptionBudget、NetworkPolicy。
- 带 JWT、ExtAuthZ 和真实 PDP 的配置。JWKS 随快照下发也没有在这里跑：黑盒套件里 JWKS 是文件，但这里的快照只有一个配置文件。
- 长连接和流。这里最长的请求是 2 秒；SSE、gRPC 流、WebSocket 在滚动时会怎样没有测。
- 发布器本身。这里是脚本直接 `kubectl apply`；发布器的证书怎么签发和轮换、它怎么得到各个 Pod 的地址，都没有设计。
- 证书轮换。单机上试过，证书文件换了网关会重读；集群里 Secret 换了之后的情况没有测。
- 上游的 standalone Helm chart。这里的清单是自己写的。
- arm64。
