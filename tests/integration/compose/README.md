# 单机上的一个池：发布时换掉挂载目录里的文件，启动时先对账，容器死了由看守起回来

运行平台的第一期是单机上的 docker compose（[ADR-0010](../../../docs/adr/ADR-0010.md) 第 10 条）。单机上一个池只有一个网关实例，没有别的副本可以轮着换，所以发布不重启网关：发布器把网关容器挂载的目录里的配置文件整份换掉，网关自己重载，发布器再经回读口确认它在跑的是哪一份。这里在本机用 docker compose 验证这套做法。

跑的池就是正式的部署文件（[`deploy/compose`](../../../deploy/compose/README.md)）描述的那一个，所以也验证部署文件本身：启动的先后，启动时对不上会怎样，停；以及守着这个池的看守。

> 这是机制验证，不是验收，通过不改变验收矩阵里任何用例的 `NOT_RUN`。  
> 配置是一份只有几条路由的小文件；没有 JWT、ExtAuthZ 和凭证，那些在黑盒套件里。`SH-01` 到 `SH-08` 由这个脚本扮演发布器，看的是网关和这种发布方式本身；`SH-09` 到 `SH-11` 跑的是真的发布器 `cmd/gateway-control` 的三条命令：`publish`、`reconcile`、`restart`；`SH-12` 到 `SH-14` 看部署文件，里面有发布器的第四条命令 `place`；`SH-15` 是网关自己的一个性质；`SH-16` 到 `SH-19` 看看守，也就是第五条命令 `keep`：真的看守在本机上跑着，脚本去杀容器、杀发布器、绕过发布器写文件。`SH-20` 读看守给出的指标；`SH-21` 起一个真的 Prometheus，装着部署目录里的告警规则。`SH-22` 看出口的规则在这个池里是不是真的装上了；它排在 `SH-15` 后面跑。  
> "断电"是把三个常驻容器同时强行杀掉来模拟的。真的重启一台机器没有做过。部署目录里的两个 systemd 单元没有装到哪台机器上跑过：看守在这里由脚本直接起，不经 systemd。

## 怎么跑

```bash
.venv/bin/python tests/integration/compose/run.py     # 十分钟左右；自己起，跑完自己拆
python3 tests/integration/compose/units.py            # 一分钟左右；两个 systemd 单元之间的关系，见第 14 点末尾
```

`run.py` 需要 docker、docker compose 和 Go（脚本现场构建 `cmd/gateway-control`）。

- compose 项目叫 `idp-gateway-compose`。脚本只动它的容器和网络，以及一个叫 `idp-gateway-compose-scratch` 的临时容器。只有 `SH-19` 例外：它起的池用的是部署文件自己写的项目名 `idp-gateway-pool`，装在 `.run/deployed` 里。这台机器上已经有叫这个名字的项目时，这一条不动它，直接记为不通过；拆的时候脚本只删项目目录是 `.run/deployed` 的容器。
- 用到四个镜像，都按摘要引用，本机没有时由 docker 去拉：锁定的上游 agentgateway 镜像（摘要取自 `deploy/agentgateway/agentgateway.lock.json`）、与黑盒套件相同的前置 nginx、装出口规则用的那个带 iptables 的镜像、一个带 Python 的工具镜像。
- 占用本机回环上的 `27618` 到 `27620`，所以不能和黑盒套件、Gatekeeper 联调、Kubernetes 套件同时跑。
- 证书每次运行现做，跑完删除。逐项结果写在 `.run/result.json`，不入库。

## 部署的样子

脚本跑的是 `deploy/compose/compose.yml` 本身，只另外套上这个目录里的 `echo.yml`（多一个会回话的后端）；部署文件要的变量由脚本现填。部署文件里的七个服务（启动的先后见第 11 点和第 16 点）：

| 服务 | 是什么 | 端口 |
|---|---|---|
| `netns` | 什么都不做，只占着网络命名空间和本机上的两个端口。`front` 和网关都接在它里面（相当于 Kubernetes 上的同一个 Pod），两个可以各自重启 | 8080 映射到本机回环的 27620，8443 映射到 27619 |
| `place` | 跑完就退出：`gateway-control place`。网关启动之前，把记录的那一份放回配置目录。不接任何网络 | 没有 |
| `egress` | 跑完就退出：`pin-egress.sh once`。网关启动之前，在 `netns` 的网络命名空间里装上出口的规则 | 没有 |
| `agentgateway` | 锁定的上游镜像。收业务请求的监听、管理、指标和就绪端口都只绑回环；另开一个回读口 | 8081、15000、15020、15021（回环）；8443（回读口） |
| `confirm` | 跑完就退出：`gateway-control reconcile`，从 compose 的网络上读回读口。它的退出码是 0，`front` 才启动 | 没有 |
| `front` | nginx，与黑盒套件同一个镜像，配置的各条指令也相同，只差两个地址。对外收业务请求的只有它 | 8080 |
| `egress-watch` | 常驻：`pin-egress.sh watch`，每两秒把同一套规则重装一遍，配置里多出来的后端靠它放行。与 `netns` 共用 PID 命名空间。看守不数它 | 没有 |

另有 `echo`（`echo.yml`）：路由的后端，8000，只在 compose 的网络里。它不属于部署文件。

- **启动**：`docker compose up -d`。`netns` 和 `place` 一起开始，后面四个（`egress`、网关、`confirm`、`front`）按上表的顺序一个等一个（第 11 点）；`egress-watch` 在 `egress` 跑完之后启动，别的都不等它。七个容器都写明了不设重启策略。
- **配置**：本机上的一个目录，只读挂进网关容器。挂的是目录，不是 `config.yaml` 这一个文件。
- **发布**：发布器在这个目录里写一个临时文件，落盘，再改名盖掉 `config.yaml`。改名是原子的，网关读到的要么是旧的整份，要么是新的整份。
- **回读**：发布器从本机连回读口，出示自己的客户端证书，读 `/config_dump` 和 `/api/runtime`。写法与黑盒套件的 `P1-RB-03` 相同。发布器的证书不在网关容器里。
- **证书**：另一个只读挂载的目录，里面是回读口的服务端证书、网关去问 PDP 用的客户端证书和 CA。
- 七个容器的根文件系统都只读。装出口规则的两个（`egress`、`egress-watch`）以 root 运行，只有 `NET_ADMIN` 一个 capability；其余五个不带任何 capability。网关以运行脚本的那个本机用户的身份运行；会话密钥经环境变量 `SESSION_KEY` 给。它和 `front` 的停止时限设的都是 60 秒（`stop_grace_period`）。
- **真的发布器**（`SH-09` 到 `SH-11`）：`gateway-control` 直接在本机上运行，与脚本是同一个用户。`publish` 和 `restart` 用本机的 docker 命令另起一个临时容器做离线加载；那个容器的回读口映射到本机回环的 27618，挂的证书目录是另外现做的一套（另一个 CA），比池的那个多一个文件。`restart` 还用 docker 命令重启网关容器。`reconcile` 不用 docker。发布器在配置目录里留两个自己的文件：锁文件 `.config.yaml.lock` 和记录 `.config.yaml.confirmed`（第 9 点）。
- **`place` 和 `confirm` 两步**跑的是同一个 `gateway-control`：脚本把它构建成静态链接的，部署文件把它挂进 nginx 的那个镜像里跑，身份也是运行脚本的那个本机用户。发布器的证书只挂给 `confirm`。
- **看守**（`SH-16` 到 `SH-19`）：`gateway-control keep` 直接在本机上运行，由脚本起，不经 systemd，与脚本是同一个用户。它跑 docker compose 时用的项目名、两个 compose 文件（部署文件和 `echo.yml`）和变量文件由参数给它，与脚本自己跑 docker compose 时给的相同。`SH-19` 不给这些：两个 systemd 单元里写的命令原样在一个放着 `compose.yml` 和 `.env` 的目录里跑，像装好的机器上那样，那个池没有 `echo`。看一眼和对账的间隔在多数步骤里设得比默认的短（第 14 点）。

## 结果

2026-11-12，docker 29.8.1（WSL2 里的 Ubuntu 24.04，不是 Docker Desktop），compose 5.5.1，agentgateway 1.7.0（锁定摘要的上游镜像），Go 1.26.8：19 个用例、212 项检查全部通过，同一份脚本连跑三轮都是 19/19，每轮 574 到 583 秒。第 14 点引用的数字出自这三轮。`units.py`（systemd 255）是 6 个用例、21 项检查，全部通过，68 秒。

2026-11-17 加上告警的两个用例之后，同一台机器上连跑三轮，都是 21/21，每轮 669 到 686 秒。跑之前时钟已对准（内核 tick 10000，单调时钟按硬件速度走）。`GatewayKeeperDown` 从看守停下到响，三轮是 61.1、61.1、61.0 秒；套件接受的是 60 到 75 秒。更早那一轮量到 56 秒，是这台机器的单调时钟被调慢了，不是规则从第一次抓取失败提前响。第 14 点的数字没有换。`units.py` 仍是 6/6。

| 用例 | 内容 | 结果 |
|---|---|---|
| SH-01 | 用部署文件启动一个池。目录里还没有记录时 `docker compose up -d`：`place` 没有可放的（`NO_RECORD`），网关照样从目录里的文件起来；`confirm` 没有可对的（`UNCONFIRMED`），命令以非零码结束，`front` 没有启动，业务端口上没有人应答。之后脚本单独把 `front` 起起来：到 `SH-08` 为止由脚本扮演发布器，这个池一直没有记录。网关跑的是按摘要引用的锁定镜像，报告的版本和提交与锁定文件一致；七个容器都没有重启策略。发布器从本机经回读口读到：配置已加载，存储模式 `readOnly`，摘要等于发布前在另一个容器里算出的期望值。本机上只映射了业务端口和回读口，都只在回环上，占着它们的是 `netns`；从同一个网络上的另一个容器，连不上网关的业务监听、管理、指标和就绪端口。`place` 不接任何网络，发布器的证书只挂给 `confirm`。带两个 `Host` 头的请求在 `front` 就被拒绝。回读口不回答别的调用方，上面也没有管理地址的其余接口 | PASS |
| SH-02 | 发布一份多一条路由的快照：改名换文件，网关报告的摘要变成新快照的期望值，新路由生效；网关还是那个容器、那个进程；期间没有一个请求失败 | PASS |
| SH-03 | 一份网关加载不了的快照：离线加载先拒绝它并给出原因。硬换上去：网关经回读口报告加载失败和原因，在跑的仍是上一份，被拒绝的文件里的路由没有生效，没有重启，没有请求失败。把上一份放回去之后报告加载成功 | PASS |
| SH-04 | 回滚到更早的那份快照：同样是换文件，摘要回到那份快照的期望值，没有重启，没有请求失败 | PASS |
| SH-05 | 对照：另起一个网关容器，只把 `config.yaml` 这一个文件挂进去。就地改写这个文件，容器里看得到；写临时文件再改名，本机上的文件已经是另一份，容器里的网关 5 秒后还在跑原来那份 | PASS |
| SH-06 | 一份只在 `config` 段与上一份不同的快照：期望摘要相同。换上去之后路由部分生效、网关报告加载成功，`config` 段却仍是启动时的值。重启网关容器之后才是新值；重启时在途的请求做完了，`front` 没有动 | PASS |
| SH-07 | 重启网关时新来的请求被拒绝多久。没有在途的请求时重启一次；有两个各还剩 3 秒左右的在途请求时再重启一次：在途的请求都做完了，它们做完之前新来的请求全部被拒绝 | PASS |
| SH-08 | 网关解析配置文件之前先做环境变量替换。另起一个网关容器加载一份正文里带 `$` 的文件：`$名字` 换成了那个容器里环境变量的值，`${名字:-默认值}` 在没有这个变量时换成默认值，`$$` 成了一个 `$`，反斜杠不起转义的作用，后面不跟名字的 `$` 原样留着。`$SESSION_KEY` 一样被换：会话密钥进了运行配置，从回读口读得到。引用一个没有的环境变量，整份文件加载失败，离线加载也拒绝它 | PASS |

## 看清的事

### 1. 改名换文件，0.3 秒左右生效，期间没有请求失败

三轮里从改名到回读口报告出结果，一共量了 12 次：0.29 到 0.36 秒。

流量从本机经 `front` 的端口发出：每秒 20 个快请求，每个一条新连接；另有两条线各自接连发耗时 2 秒的请求。三轮里换文件的三个用例（`SH-02` 至 `SH-04`，共 12 次换文件）期间一共 1300 个快请求和 78 个慢请求，全部得到 200。

这不是碰巧。上游在锁定提交上的源码（`crates/agentgateway/src/util.rs`、`state_manager.rs`）里，配置文件是一个普通文件时网关监视的是这个文件本身，变化先攒 250 毫秒；文件被改名替换之后它重新加载，并对新文件重新建立监视。上游自己有一条"反复改名替换之后仍然重载"的测试（`file_config_reloads_after_repeated_rename_replacement`）。

网关刚启动的头几毫秒是例外：这时换上去的文件它可能看不到。在套件自己的池上、套件之外单独量的（空闲机器）：`docker restart` 网关，从 docker 报出 start 事件算起隔一段时间，照发布器的做法（临时文件加改名）换上另一份，然后经回读口看 12 秒，一共 43 次。

- 隔约 5 毫秒，5 次：3 次网关启动时读到的就是新的那一份（0.05 秒后回读口报告的已经是它）；2 次读的是旧的，之后 12 秒一直报告旧的。
- 隔约 8 毫秒，4 次：4 次都一直报告旧的。
- 隔 11 毫秒到 1 秒，34 次：全部重新加载，换文件后 0.26 到 0.33 秒生效。

没加载的那 6 次，把同一份再放一遍（再改名一次），0.27 到 0.33 秒后都加载了。原因看上去是启动时读过文件之后、开始监视之前的那一小段，这只是从外面量出来的，没有对着上游源码核实；换 agentgateway 的版本时要重看。

### 2. 加载不了的文件在两个地方被挡住，但不能让它留在盘上

- **发布之前**。发布器用同一个镜像另起一个容器加载这份快照。加载不了，进程以非零码退出并说出原因，这份快照就不该往下发。
- **硬换上去**。0.3 秒后网关经回读口报告这次加载失败和原因（与离线加载给出的原因相同），继续用上一份；整份文件都不生效，里面没有毛病的那条路由也不生效。

第二种情况下网关看上去没事，但这时目录里的文件是坏的那一份，网关在跑的是上一份。它一旦重启（崩溃、主机重启、换镜像），读到的就是那份坏文件，起不来：离线加载那一步看到的正是网关启动时遇到这份文件就退出。所以发布器读到"加载失败"之后要把上一份放回去，不能停在这里。放回去 0.3 秒后网关报告加载成功。

真的发布器做的就是这两步，见第 8 点。它自己死在这两步之间时怎么办，见第 9 点。

### 3. 要挂目录，不能只挂 `config.yaml`

只挂一个文件时，容器拿到的是那个文件本身，而不是"目录里叫这个名字的文件"。发布器改名换上去的是另一个文件，容器里的还是原来那个：`SH-05` 里本机上的文件已经换了，网关 5 秒后仍在跑旧的，也不报错。就地改写同一个文件容器里倒是看得到（0.29 到 0.35 秒后重载），但就地改写不是原子的，网关可能读到写了一半的文件。

### 4. `config` 段的改动要重启网关，回读的摘要看不出来

`config` 段的设置只在启动时读取。`SH-06` 换上一份只改了 `config` 段里一项的文件：网关报告加载成功，路由部分也确实换了，那一项却还是启动时的值。摘要是不含 `config` 段的（见第 6 点），所以这份快照和上一份的期望摘要相同，回读看不出 `config` 段有没有生效。发布器得自己比：新快照的 `config` 段和网关启动时用的那份不一样，这次发布就要重启网关。

真的发布器比的是两边 `/config_dump` 里的 `config` 段：离线加载这份快照得到的，和池里的网关报告的。不一样，`publish` 就不发布，结局是 `RESTART_REQUIRED`，并列出不同的项；这种快照由 `restart` 发布（第 10 点）。`dns` 和工作线程数这两项随运行环境变，不比。

### 5. 单机上重启网关，新来的请求被拒绝；拒绝多久取决于在途的请求还要多久

单机上只有这一个实例，重启期间新来的请求没有别处可去：`front` 连不上网关，答 502（应答正文是 nginx 自己的错误页）。三轮里量到的：

| 重启时在途的请求 | 重启命令用时 | 每秒 20 个的快请求里得到 502 的 |
|---|---|---|
| 没有（`SH-07`） | 0.31、0.31、0.27 秒 | 3、3、3 个 |
| 两个，各还剩 1 秒左右（`SH-06`） | 1.20、1.18、1.16 秒 | 21、20、20 个 |
| 两个，各还剩 3 秒左右（`SH-07`） | 3.18、3.18、3.19 秒 | 58、60、61 个 |

网关收到终止信号就不再接新连接，等在途的请求做完才退出；在途的请求都做完了，没有被切断。所以新请求被拒绝的时间，差不多就是在途的请求里最长的那个还要多久；没有在途的请求时是 0.15 秒左右（更忙的那一轮是 0.4 秒）。

它最多等多久由 `connectionTerminationDeadline` 定，这里设的是 45 到 49 秒（用例拿这一项当那种只在启动时生效的设置来改）；等得最久的一次是 13 秒左右（`SH-11`，第 10 点）。45 这个数是从 Kubernetes 套件沿用的，没有对着真实的请求时长调过。在单机上它有两头：定得长，重启时新请求可能被拒绝得久；定得短，在途的请求会被切断。

### 6. 期望摘要可以在另一个容器里算出来

池里的网关经回读口报告的摘要，等于发布前另起一个容器加载同一份快照得到的摘要；那个容器用的是另一套证书。两边相等的条件与 Kubernetes 套件里看到的相同：算摘要时去掉 `config` 段（两边不同的项是 `dns`），并把证书正文换成占位。

发布器（Go）和这个脚本（Python）各自实现了这个算法。`SH-09` 里两边对同一个网关算出的摘要相同。

### 7. 网关解析配置文件之前，先拿环境变量替换正文里的 `$名字`

锁定的版本读到配置文件之后、解析之前，把整份正文过一遍替换（上游 `crates/agentgateway/src/types/local.rs` 的 `expand_env`，用的是 `shellexpand`）。用的是加载这份文件的那个进程的环境。替换在解析之前，所以不分键、值还是注释；上游为此专门绕开了自己那行写模式地址的注释。`SH-08` 里看到的：

| 正文里写的 | 网关拿到的 |
|---|---|
| `$HOSTNAME` | 这个环境变量的值（容器的主机名） |
| `${NO_SUCH_VARIABLE:-fallback}` | 没有这个变量，是 `fallback` |
| `$$HOSTNAME` | `$HOSTNAME`：`$$` 是字面的 `$` |
| `\$HOSTNAME` | 反斜杠加上环境变量的值：反斜杠不起转义的作用 |
| 后面不跟名字的 `$` | 原样 |
| `$NO_SUCH_VARIABLE` | 整份文件加载失败：`error looking key 'NO_SUCH_VARIABLE' up: environment variable not found` |
| `$SESSION_KEY` | 会话密钥 |

用例之外单独试过的：`${名字}` 同样被换；`$1` 被当成名字叫 `1` 的变量，没有这个变量，整份文件加载失败。

这对发布意味着三件事：

- **带这种写法的快照不是自成一体的。** 同一份文件，离线加载的容器里和池里的网关上可以是两份不同的配置，期望摘要就说明不了什么；也可以一边加载得了、另一边加载不了。
- **会话密钥可以被写进运行配置。** 会话密钥是经环境变量给网关的。快照里写一个 `$SESSION_KEY`，它就成了运行配置里的一个值，能读回读口的都读得到。
- **值里一个没有转义的 `$` 能让整份文件加载不了。** 正则替换里的 `$1` 就是。以后由 RouteIntent 编译出配置时，值里的 `$` 要写成 `$$`。

所以发布器拒绝正文里带这类引用的快照，结局是 `REFUSED`，不加载，也不碰池。它查的是正文的字面，比网关认的宽：`$` 后面跟着字母、数字、下划线、非 ASCII 字节或 `{` 的都算，`$$` 成对跳过。它只管得了经它发布的文件；它依据的是锁定版本的写法，换版本时要重新确认（`deploy/agentgateway/README.md`）。

### 8. 真的发布器对着真的网关

`SH-09` 到 `SH-11` 跑的是 `gateway-control`，对着前面的用例用的同一个池。它有五条命令：`publish` 发布一份快照，网关不重启（本点）；`reconcile` 对账（第 9 点）；`restart` 发布一份要重启网关才能全部生效的快照（第 10 点）；`place` 在网关启动之前把记录的那一份放到位，由部署文件在启动时跑（第 11 点）；`keep` 是常驻的看守（第 14 点）。前四条做完就退出。

`publish` 发布一份快照时依次做：

1. 正文里有对环境变量的引用：拒绝（第 7 点）。
2. 用同一个镜像另起一个临时容器加载这份快照，得到期望摘要。网关加载不了，或加载出来存储模式不是 `readOnly`：拒绝。
3. 经回读口读池里的网关。它上一次加载失败，或存储模式不是 `readOnly`：池不干净，不发布。它的构建与离线加载的不同：要重启，不发布。
4. 目录里放着的不是记录里的那一份（第 9 点）：池不干净，不发布，要先对账。只有一种情况它自己补得上：放着的正是要发布的这一份，网关也报告它在生效，这时只补记。
5. 这份快照的 `config` 段与池里的网关启动时的不同：要重启，不发布（第 4 点）。
6. 目录里已经是这份快照、网关也报告它在生效：什么都不写。否则把文件换上去（临时文件、落盘、改名），等网关经回读口报告期望摘要，然后把这一份记成这个池上最后一次得到确认的。
7. 没有生效（网关报告加载失败，或 10 秒内没有报告期望摘要）：把上一份放回去，再等网关报告它在跑的又是发布之前的那一份。

前四条命令的结果都以 JSON 写到标准输出，退出码说明池现在的状态（`keep` 的输出和退出码见第 14 点）：

| 结局 | 退出码 | 哪条命令 | 池 |
|---|---|---|---|
| `ACTIVE` | 0 | `publish`、`restart` | 这份快照正在生效，并且记下来了 |
| `IN_SYNC` | 0 | `reconcile` | 就是记录的样子，什么都没有写 |
| `IN_PLACE` | 0 | `place` | 目录里放着的是记录的那一份：本来就是，或者刚放回去。网关在跑什么，它没有看 |
| `NO_RECORD` | 0 | `place` | 没有记录，没有可放的，什么都没做 |
| `REFUSED`、`POOL_NOT_READY` | 3 | `publish`、`restart` | 没有被碰过 |
| `RESTART_REQUIRED` | 3 | `publish` | 没有被碰过 |
| `UNCONFIRMED` | 3 | `reconcile` | 没有可以拿来对的记录，什么都没做 |
| `RESTORED` | 4 | 前三条都有 | 发布时：换上去过，没有生效，上一份已经放回去并得到确认。对账时：池和记录对不上，记录的那一份已经放回去并得到确认 |
| `UNKNOWN` | 5 | 这四条都有 | 没能确认网关在跑的是哪一份。发布时：换上去过，没有生效，也没能确认放回去了。对账时：记录的那一份在目录里，却没能读到网关在跑它。`place`：记录的那一份没能放回去 |
| `RESTART_PENDING` | 6 | `reconcile` | 文件和运行配置都对得上，网关的启动设置却不是确认时的那一套；要重启（第 10 点） |
| 没有结局，出了错 | 1 | | 配置没有被动过，原因在标准错误上 |
| 没有结局，命令行写得不对 | 2 | | 什么都没做 |

`UNKNOWN` 不是成功也不是失败：先看网关是不是还在跑，再对一次账。

三轮里看到的（`SH-09`）：

- **发布一份新快照**：发布器用了 2.28、2.00、1.98 秒。其中要另起一个容器做离线加载；换上文件之后它至少等 1 秒才认读到的结果，因为网关攒 250 毫秒才重载，新旧两份的运行配置相同时，更早读到的"已生效"说明不了它加载过新文件。期间 486 个快请求和 26 个慢请求全部得到 200，网关没有重启。
- **一份离线加载得了、池里加载不了的快照**：它引用的一个文件只在离线加载那边的证书目录里有。发布器换上去，读到网关报告加载失败，把上一份放回去，前后用了 3.06、2.99、3.18 秒；这期间 546 个快请求和 30 个慢请求全部得到 200。它给的原因是池里的网关自己说的：`routes[4]: read resource file /work/tls/only-in-staging.crt at line 65 column 3`。离线加载通过不等于池里加载得了，兜底的是放回去这一步。
- **被叫停时先把上一份放回去**。脚本等发布器把一份没有毛病的快照换上去，立刻给它发 SIGTERM。它没有立刻退出：把上一份放回去，等网关报告在跑的又是发布之前的那一份，然后以 `RESTORED` 结束，原因写的是 `interrupted while waiting for the gateway: context canceled`。SIGINT 和 SIGHUP 走的是同一段代码；`publish` 上没有另发，`SH-11` 给 `restart` 发的是 SIGINT。
- **池不干净时它不动手**。脚本绕过发布器往目录里放了一份坏文件，网关正报告加载失败：发布器的结局是 `POOL_NOT_READY`，那份坏文件它没有动。把池收拾回来是 `reconcile` 的事（第 9 点）；这一条里是脚本自己把上一份放回去的。
- **同一个池同时只有一次发布**。晚到的那次以退出码 1 结束，什么都没做。互斥靠配置目录里的一个锁文件 `.config.yaml.lock`；它一直留在目录里，网关不受它影响。五条命令占的是同一把锁；实际跑过的是两次 `publish` 同时进行，锁被占着时的 `place`（`SH-13`，占着锁的是脚本），以及锁被脚本或一次带重启的发布占着时的看守（`SH-16`、`SH-17`），别的组合只有单元测试。
- **用过之后不留东西**：临时容器不在了，放候选配置的目录是空的，配置目录里除了配置文件只有锁文件和记录。

### 9. 发布器死在半路：记录，和对账

发布器被叫停时会先把上一份放回去（第 8 点）；被强行杀掉（SIGKILL、断电、机器重启）时来不及。它要是死在换上文件之后，目录里留下的就是一份没有人确认过的文件：网关加载得了，池就在跑一份没人确认过的配置；加载不了，网关下次重启就起不来（第 2 点）。要收拾，先得知道该放着的是哪一份。

**记录。** 每次发布得到网关确认之后，发布器把配置目录里的一个文件 `.config.yaml.confirmed` 整份换掉（做法与换配置文件相同）。这个文件只有属主能读写，里面是：

- 得到确认的那份快照的全文和它的 SHA-256；
- 网关当时报告的运行配置摘要，和它的构建（版本、提交）；
- 网关当时的启动设置，也就是 `/config_dump` 的 `config` 段，除去随运行环境变的 `dns` 和工作线程数。每一项只记值的 SHA-256，不记值：对账只要知道它们变没变，而这些值有一部分取自网关进程的环境；
- 记下的时刻。

它和配置文件在同一个目录里，所以也只读地挂进了网关容器；里面除了快照的全文只有几个摘要。它是单机下发这一层自己的东西，只有最后一条，只说"这个目录里该放着哪一份"。它不是发布的记录：发布过哪些、谁批准的，不在这里。

第一次对一个还没有记录的池动手之前，`publish` 和 `restart` 先把当时放在那里的文件和网关当时报告的记成第一条，这一条不带启动设置。这样第一次发布做到一半死了，也知道该放回哪一份。记下的内容只有单元测试核对过。

有了记录：

- **`publish` 和 `restart` 动手之前先核对。** 目录里放着的不是记录的那一份（上一次发布没有做完，或者有人绕过发布器写了这个文件），它们不动手，结局是 `POOL_NOT_READY`，原因里说要先对账。
- **没做完的发布有两条出路。** 再发布同一份：放着的正是它、网关也报告它在生效，`publish` 只补记，不再写文件，结局 `ACTIVE`。或者对账，把它收回去。
- **`gateway-control reconcile` 对账**：拿记录去对池现在的样子。它不做离线加载，不用 docker；依据是记录，不是重新算出来的期望值。

| 目录里的文件 | 网关 | 对账做什么 | 结局 |
|---|---|---|---|
| 是记录的那一份 | 报告在跑的是它 | 什么都不写 | `IN_SYNC` |
| 不是记录的那一份，或者没有文件 | 不论报告什么，读不到也一样 | 把记录的那一份放回去，等网关报告在跑的是它 | `RESTORED`；等不到是 `UNKNOWN` |
| 是记录的那一份 | 报告上一次加载失败，或者在跑的不是它 | 再放一次：换文件会让网关重新加载。等法同上 | 同上 |
| 是记录的那一份 | 读不到 | 不写，等到时限 | 读到了按上面几行办；一直读不到是 `UNKNOWN` |
| 是记录的那一份 | 报告加载成功，但构建不是做记录时的那个 | 什么都不做：摘要里有版本，两个构建的没法比 | `UNCONFIRMED` |
| 没有记录 | | 什么都不做 | `UNCONFIRMED` |

文件和运行配置对上之后（本来就对上的，和放回去之后对上的都算），它再比启动设置。不是确认时的那一套，说明网关带着别的文件重启过：结局改成 `RESTART_PENDING`，列出不同的项。对账自己不重启网关，也不启动网关。

三轮里看到的（`SH-10`；最后一条在 `SH-11`）：

- **池就是记录的样子**：0.01 秒，`IN_SYNC`，文件没有被重写。
- **发布器刚把一份没有毛病的快照换上去就被 SIGKILL**。文件留在那里，网关加载了它，新路由已经在答话；记录里仍是上一份。这时发布另一份：`POOL_NOT_READY`，文件它没有动。对账：把记录的那一份放回去，1.07、1.06、1.06 秒之后以 `RESTORED` 结束（其中 1 秒是换上文件之后至少要等的），没有人确认过的那条路由没有了。期间 426 个快请求和 24 个慢请求全部得到 200，网关没有重启。
- **同样被杀掉之后，把同一份快照再发布一次**：`ACTIVE`，文件没有再写，记录跟上了。
- **有人绕过发布器放了一份网关加载不了的文件**：对账把记录的那一份放回去，`RESTORED`，原因里带着网关自己说的那句话。
- **有人把配置文件删了**：网关不退出，报告 ``failed to read from file `config/config.yaml`: No such file or directory (os error 2)``，继续跑原来那份。对账把文件放回去，`RESTORED`。文件被删过之后网关仍然看得到它变了：之后的发布照常生效。
- **发布器在离线加载时被 SIGKILL**：留下一个临时容器和一个放候选配置的目录；池没有被碰过，对账是 `IN_SYNC`。下一次发布先把这两样清掉，照常成功。
- **网关带着一份坏文件重启，起不来**（坏文件是脚本放的，网关容器是脚本重启的）。这时对账：记录的那一份放回去了，可是读不到网关，等满时限（这一次设的是 3 秒），结局是 `UNKNOWN`。再对一次：文件已经是对的，它不再写，等满时限，仍是 `UNKNOWN`。脚本把网关容器起起来之后，网关读到的是放回去的那一份，对账是 `IN_SYNC`。
- **带重启的发布做到一半被 SIGKILL**：对账之后是 `RESTART_PENDING`，见第 10 点。

要知道的：

- **平时对账的是看守**（第 14 点），默认一分钟一次。发布器被强行杀掉而机器没有重启时，留在目录里的那份没人确认过的文件要到看守下一次对账才被收回去；在那之前，`publish` 和 `restart` 会拒绝动手，网关加载得了那份文件的话在跑的就是它。看守没有在跑时，没有谁会自动去对账：启动一个池时部署文件会对一次（第 11 点），平时要有人来跑 `reconcile`，或者再跑一次启动命令（第 12 点）。
- **对账会把绕过发布器的改动收回去。** 这是它的本意：这个目录只有发布器写。
- **对账不启动网关，也不重启网关。** 网关没有在跑时它只管把文件放对。
- **记录读不成样子时前四条命令都停下来。** 文件坏了，或者是更新的版本写的格式：退出码 1，什么都不做，要人来看。`place` 遇到一份坏了的记录在 `SH-13` 里跑过，其余只有单元测试。看守这时对不了账：它把这件事写出来，不动文件，下一眼再试（只有单元测试）。
- **记录跟着配置目录走。** 目录没了，记录也没了；这时对账是 `UNCONFIRMED`，下一次发布把当时放在那里的当成起点。

### 10. 带重启的发布：先换文件，网关加载得了再重启

`config` 段与网关启动时不同的快照，换文件不能全部生效（第 4 点），`publish` 只报告 `RESTART_REQUIRED`。发布这种快照用 `gateway-control restart`。重启会让这个池中断（第 5 点），所以它是单独的一条命令，什么时候做由人定。

它依次做：

1. `publish` 前四步的检查，只是没有"补记"那个例外：放着的不是记录的那一份，一律先对账。另有两种情况也拒绝：这份快照的 `config` 段与网关启动时的相同，用不着重启，让改用 `publish`；池里跑的是另一个构建，重启换不了镜像。
2. 核对 `--container` 指的那个容器：它在跑，并且把这个池的配置目录挂在网关读配置的位置上。不是，就什么都不做，退出码 1。
3. 把文件换上去，等网关报告期望摘要。这一步网关不重启，快照里启动设置之外的部分已经生效。网关加载不了：把上一份放回去，结局 `RESTORED`，不重启。先换文件再重启，为的是不拿一份池里加载不了的文件去重启网关：那样它起不来。
4. 重启网关容器（`docker restart`）。docker 先发终止信号，网关把在途的请求做完再退出，最多等到容器的停止时限。
5. 等网关报告：在跑的是这份快照，`config` 段也是离线加载时的那一套。然后记下这一份，结局 `ACTIVE`。
6. 时限内没有等到：把上一份放回去，再重启一次，等网关带着上一份的设置起来，结局 `RESTORED`；仍等不到是 `UNKNOWN`。

不给 `--snapshot` 时，重启用的是记录里的那一份：对账报告 `RESTART_PENDING` 之后要做的就是这个。

被叫停（SIGINT、SIGTERM、SIGHUP）时：还没重启的，把上一份放回去，不重启；重启一旦开始就做完。网关停到一半没人管，或者带着新设置起来了却没人确认，都比多等几秒糟。

三轮里看到的（`SH-11`）：

- **一次带重启的发布**：发布器用了 4.27、4.27、4.30 秒（离线加载；换上文件之后等 1 秒；重启；重启之后再等 1 秒）。重启时有两个各还剩 1 秒左右的在途请求，都做完了；每秒 20 个的快请求里 23、21、18 个得到 502，前后 1 秒左右，与脚本自己重启网关时量到的相同（第 5 点）。网关换了一个进程，还是那个容器；`front` 没有动。
- **重启途中按 Ctrl-C**。终端上的 Ctrl-C 是发给整个前台进程组的，所以发布器让 `docker restart` 自成一个进程组，信号到不了它。脚本给发布器所在的进程组发 SIGINT，那时网关正在等一个还要 13 秒左右才做完的请求（这个请求从 `front` 的容器里直接发给网关，不经 nginx：nginx 等后端最多 10 秒）。看到的：那个进程组里只有发布器；发布器做完才退出（前后 16.23、16.98、16.53 秒），结局 `ACTIVE`；docker 对网关容器只做了一次重启，没有强杀；那个请求 14 秒后得到 200。docker 等了 13 秒，超过它默认的 10 秒：不给时限时，它用的是容器自己设的停止时限，这里是 60 秒。  
  对照（跑了一遍）：把"自成一个进程组"那一行去掉，docker 命令行和发布器一起收到了信号。命令行退出了，守护进程照样把那次重启做完；发布器却当成重启失败，把上一份放回去并又发了一次重启，结局成了 `RESTORED`：一次本来会成功的发布被收了回去。
- **用不着重启的快照，池里加载不了的快照，指错了容器**：分别是 `REFUSED`、`RESTORED`（没有重启）、退出码 1。这三次网关都没有重启。
- **docker 刚把网关重新起来，发布器就被 SIGKILL**：文件是新的，网关已经带着新设置起来，记录里仍是上一份。脚本是等网关在回读口上答得上话才杀发布器的（原因见第 1 点末尾、第 14 点）。对账把记录的那一份放回去，路由回到了那一份，启动设置却还是新的：结局 `RESTART_PENDING`，退出码 6，列出了那一项。不给快照的 `restart` 再重启一次：文件不用再换，结局 `ACTIVE`，启动设置回来了，之后对账是 `IN_SYNC`。这是把它收回去。要把它做完，就拿同一份快照再 `publish` 一次：网关已经带着新设置起来了，只差补记。后一条路在真的网关上只对不用重启的快照走过（`SH-10`）。
- **一份离线加载得了、网关拿它却起不来的快照**。它把指标端口设成了 `front` 占着的那个。离线加载的容器里没有 `front`，加载得了；池里的网关换上文件时也报告加载成功，因为启动设置这时不生效；重启之后它起不来，自己说的是 `Error: stats server starts` 和 `Address already in use (os error 98)`。发布器读不到网关，等满时限（这一次设的是 5 秒，默认 10 秒），把上一份放回去再重启一次，网关回来了，结局 `RESTORED`，前后 9.36、8.44、8.54 秒。docker 的事件里是两次重启，中间网关自己退出了一次。从第一次重启到网关回来，这个池是断的。

要知道的：

- **离线加载和换文件都通过，仍不等于重启之后起得来。** 启动设置只在启动时生效，离线加载的容器又不是池的环境。兜底的是重启之后的回读和放回去再重启，代价是多中断一阵。
- **中断多久取决于在途的请求**（第 5 点），最长到网关的 `connectionTerminationDeadline` 和容器的停止时限里短的那个。容器的停止时限更短时，到时 docker 直接杀掉网关，在途的请求被切断；这种情况没有测。`--stop-timeout` 可以另给一个停止时限，只有单元测试。
- **docker 的两样行为只在 29.8.1 上看过**：不给时限时用容器自己设的停止时限；命令行中途被杀掉，守护进程照样把重启做完。
- **容器没有重启策略。** 有重启策略时，网关起不来 docker 会自己反复去起它，发布器这时的表现没有测。

前四条命令里没有在真的网关上走到的分支，只有单元测试（`internal/gatewayconfig`、`cmd/gateway-control`；看守的见第 14 点末尾）：

- 离线加载出来的、或池里的网关报告的存储模式不是 `readOnly`；池里的构建与离线加载的不同。
- 发布或重启没有生效，放回上一份之后仍然对不上（`UNKNOWN`）；得到了确认却记不下来。
- 第一次动一个没有记录的池时记下的第一条；记录是别的格式（记录损坏只在 `place` 上跑过，`SH-13`）。
- 对账时网关换过构建（`UNCONFIRMED`；没有记录的那一种在 `SH-01` 里跑过）；文件是对的，网关在跑的却不是它；放回去时写不进去。
- 目录里已经是这份快照、网关却没有在跑它时的 `restart`；重启的命令返回了，答话的还是旧进程。
- `place`：没有记录而放着的文件又读不成一份配置；记录的那一份放不回去（`UNKNOWN`）。

### 11. 启动的先后：先把记录的那一份放到位，回读对上了才收请求

机器重启的时候没有人在场。那时目录里放着的可能是发布器死在半路留下的一份没有人确认过的文件（第 9 点）：网关加载得了它，池就带着一份没人确认过的配置收请求；加载不了，网关起不来。所以部署文件给启动定了先后（`deploy/compose/compose.yml` 的 `depends_on`），`docker compose up -d` 照着做：

1. `netns` 启动：占住网络命名空间和本机上的两个端口。这时两个端口后面都还没有人。
2. `place` 跑完：`gateway-control place` 拿记录去比目录里放着的文件，不是记录的那一份就把那一份放回去（做法与发布时换文件相同）。它不读网关，不接网络，不用 docker。结局是 `IN_PLACE`；还没有记录时是 `NO_RECORD`，什么都不写。它以非零码结束，后面几步都不做。它和 `netns` 是一起开始的，这两个之间没有先后。
3. 网关启动：要 `netns` 起来了，`place` 也以退出码 0 跑完了；中间还有 `egress` 这一步，也要以 0 跑完（第 16 点）。
4. `confirm` 跑完：就是 `gateway-control reconcile`（第 9 点），从 compose 的网络上读回读口，最多等网关 `CONFIRM_TIMEOUT`（默认 60 秒，这里设成了 10 秒）。
5. `confirm` 的退出码是 0，`front` 才启动。在那之前业务端口后面没有人，请求进不来。

七个容器都不设重启策略：由 docker 自己起来的网关不经过第 2 步。容器死了，把它们起回来的是看守，它跑的也是这条启动命令（第 14 点）。机器开机时跑 `docker compose up -d` 的是一个 systemd 单元（`deploy/compose/idp-gateway-pool.service`）；这个单元没有装到哪台机器上跑过，它里面写的命令在 `SH-19` 里原样跑过，见"没有覆盖的"。

三轮里看到的（`SH-12`）。每轮断电四次，每次都把三个常驻容器同时强行杀掉，再跑启动命令，一共 12 次启动；这期间脚本每 0.05 秒往业务端口发一个请求。

- **先后**。12 次都是：`place` 跑完，网关才启动；网关启动了，`confirm` 才跑；`confirm` 跑完，`front` 才启动。从启动命令开始算，`netns` 启动在 0.17 到 0.31 秒，`place` 跑完在 0.23 到 0.46 秒，网关启动在 0.91 到 0.98 秒，`confirm` 跑完在 1.09 到 1.20 秒，`front` 启动在 1.59 到 1.69 秒，命令返回在 1.65 到 1.76 秒。`netns` 和 `place` 之间没有先后：12 次里有 8 次，`place` 比 `netns` 启动还早跑完 0.01 到 0.02 秒。
- **`confirm` 跑完之前没有请求得到应答**。第一个应答到达是在 1.67 到 1.81 秒，比 `confirm` 跑完晚 0.57 到 0.64 秒；在它之前，每条路由上落空的请求每次有 33 到 35 个。比的是应答到达的时刻，各时刻是同一台机器上的时钟。
- **断电之前放着的不是记录的那一份**，三种各三次：
  - 发布器刚把一份多一条路由的快照换上去就被强行杀掉，网关已经在跑这一份，然后断电。`place` 把记录的那一份放回去，原因写的是 `what was in place (2355e744cd75) was not the snapshot last confirmed on this pool`。
  - 有人绕过发布器放了一份网关加载不了的文件，然后断电。同上。不经 `place` 的话网关拿这份文件是起不来的（`SH-10`）。
  - 配置文件被删掉，然后断电。原因写的是 `there was no configuration file in place`。

  三种情况下网关都是带着记录的那一份起来的，`confirm` 是 `IN_SYNC`，没有再写文件；没有人确认过的那条路由，启动期间和之后一次都没有答过 200。
- **好好的池上再跑一次启动命令**：`place` 和 `confirm` 各又跑了一遍（`IN_PLACE`、`IN_SYNC`），什么都没有写，三个常驻容器没有动。

对不上的时候（`SH-01`、`SH-13`）：

| 启动时的情况 | 看到的 |
|---|---|
| 还没有记录（`SH-01`） | `place` 是 `NO_RECORD`，网关从放着的文件起来；`confirm` 是 `UNCONFIRMED`（退出码 3），命令以非零码结束，说 `service "confirm" didn't complete successfully: exit 3`；`front` 没有启动 |
| 记录读不成样子（脚本把它截掉了一半） | `place` 以退出码 1 结束，说 `the record of the last confirmed snapshot (…) is damaged`，什么都没有写；网关没有启动，`confirm` 没有跑，`front` 没有启动 |
| 网关起不来（脚本拿走了它回读口的私钥） | `place` 照常；网关启动了又退出，自己说的是 ``failed to read from file `/work/tls/gateway-readback.key`: No such file or directory (os error 2)``；`confirm` 等满 10 秒，结局 `UNKNOWN`（退出码 5），什么都没有写；命令用了 11.6 到 11.8 秒，以非零码结束；`front` 没有启动 |
| 一次发布正占着这个池（脚本占着配置目录的锁） | `place` 以退出码 1 结束，说 `another publication to this pool is in progress`；`confirm` 没有跑，在跑的三个容器没有被动过 |

前三种情况下业务端口上都没有人应答。把毛病去掉之后再跑启动命令，都照常起来了。

要知道的：

- **对不上，这个池就不通，直到有人来处理。** 这是有意的：宁可不通，也不带着一份说不清的配置收请求。看守不改这一条：它隔一阵再跑一次启动命令，对不上照样不开 `front`（第 14 点）。启动命令这时以非零码结束。谁来看见：看守的指标里池不是完整的，规则 `GatewayPoolNotWhole` 连着 2 分钟就该叫人（第 15 点）。叫到谁、怎么叫，没有做。
- **先后是量出来的，量时刻查不出每一条依赖。** 对照（在定稿的脚本上各跑了一遍，改的是部署文件，跑完改回）：
  - 去掉"`front` 等 `confirm`"：`SH-01`、`SH-12`、`SH-13`、`SH-14` 都不通过。没有记录时 `front` 照样启动了。四次断电之后的启动里有三次，`front` 启动在 `confirm` 跑完之前，第一个应答比 `confirm` 跑完早到 0.14 到 0.16 秒；另一次 `front` 启动在 `confirm` 跑完之后 0.01 秒，先后碰巧没有乱。
  - 去掉"网关等 `place`"：`SH-13` 和 `SH-14` 不通过（记录坏了，网关照样启动；头一次安装时 `place` 没有跑）。`SH-12` 却通过了：四次里 `place` 都比网关启动早跑完 0.01 到 0.15 秒，先后碰巧还是对的。所以这一条依赖靠的是 `SH-13`、`SH-14` 和离线的契约测试（`tests/contracts/test_single_host_deployment.py`），不是 `SH-12` 量到的时刻。
  - 多映射一个端口：`SH-01` 不通过。把 `front` 的停止信号改成 SIGTERM：`SH-14` 不通过，停的时候在途的那个请求被切断了，没有得到应答。
- **机器忙的时候启动得慢。** 这台机器上别的项目也在跑测试的时候（1 分钟平均负载 5 到 12），启动的先后没有动过的部署文件跑过两遍：定稿的工作区上又跑的那一轮（见"结果"），和上面只动了端口和停止信号的那一遍对照。八次断电之后的启动里，第一个应答到达有六次在 1.77 到 1.97 秒，另两次是 4.78 和 6.52 秒：一次是 `place` 跑完之后过了 3.6 秒网关才启动，一次是 `confirm` 在网关启动之后过了 3.9 秒才跑完。先后都没有乱。所以上面的 1.7 到 1.8 秒只说明量级。
- **`netns` 刚起来的那一会儿发出的请求会悬 1 秒左右。** 更早的一遍对照里量到过（去掉"网关等 `place`"的那一种，`front` 因此开得早）：启动命令开始后 0.35 秒发出的一个请求，1.37 秒才得到应答。所以脚本比的是应答到达的时刻，各个请求各发各的，不等前一个回来；上面的对照是这样改了之后重跑的。
- **`place` 只管文件。** 网关在跑的时候叫它，它也只是把文件放回去；网关在跑什么由 `confirm` 看。

### 12. 部署文件的其余部分：再跑一次启动命令，停，`netns`，头一次安装

三轮里看到的（`SH-14`；`netns` 的那一条在 `SH-13`）：

- **在跑着的池上跑启动命令，就是对一次账。** 发布器刚把一份快照换上去就被强行杀掉，网关在跑那一份。这时 `docker compose up -d`：`place` 把记录的那一份放回去，网关重新加载，`confirm` 是 `IN_SYNC`，命令的退出码是 0；没有人确认过的那条路由没有了，三个常驻容器都没有重启。三轮都是这样。`confirm` 要是赶在网关重新加载之前去读，会自己再放一次，结局是 `RESTORED`（退出码 4），命令也就以非零码结束，这时再跑一次是 0。未改动的部署文件上没有碰到过；上面"去掉网关等 `place`"的对照里两步同时跑，碰到了。
- **单独重启 `front`**（`docker compose restart front`）：`front` 换了一个进程，网关和 `netns` 没有动，请求照常。
- **停**（`docker compose stop`）的时候有一个耗时 4 秒的请求在途，还剩 3 秒左右。docker 先给 `front` 发 SIGQUIT，`front` 把这个请求做完才退出；然后给网关发 SIGTERM，网关退出；最后是 `netns`。那个请求得到 200，`front` 和网关的退出码都是 0。停用了 3.58 到 3.66 秒。之后再跑启动命令，整个池照第 11 点的先后起来。
- **`netns` 这个容器单独死了**（脚本把它杀掉）：网关和 `front` 还在跑，业务端口和回读口上却都没有人应答了。这时只跑启动命令修不好：`netns` 重新起来了，网关和 `front` 没有被动过，仍接在原来那个命名空间里；`confirm` 读不到网关，等满时限，结局 `UNKNOWN`，命令用了 11.5 到 11.6 秒，以非零码结束。先 `docker compose stop` 再 `docker compose up -d`，整个池重新起来。看守遇到这种情况做的就是这件事，只是它停的是接在里面的那两个（`SH-16`，第 14 点）。
- **头一次安装**。一个全新的池：没有容器，配置目录是空的。
  1. 把第一份快照放到 `config.yaml`，`docker compose up -d agentgateway`：退出码 0，`place` 是 `NO_RECORD`，网关起来了；`confirm` 和 `front` 的容器都还没有，业务端口上没有人应答。
  2. 用发布器把同一份快照 `publish` 一次：`ACTIVE`，文件没有再写，这个池有了第一条记录，记的是这一份，带着启动设置。
  3. 再跑 `docker compose up -d`：`place` 是 `IN_PLACE`，`confirm` 是 `IN_SYNC`，`front` 启动，请求照常。

要知道的：

- **不经启动命令的重启不经过 `place`。** `docker restart`、`docker compose restart agentgateway` 重启的网关，读到的是目录里当时放着的文件。`SH-10` 里就是这样：有人放了一份坏文件，之后网关被重启，起不来。
- **网关或 `front` 自己崩了，docker 不会去起它们。** 起回来的是看守，它跑的就是启动命令（第 14 点）。看守没有在跑时，要有人再跑一次启动命令。
- **`docker compose stop` 不带服务名时停的是整个项目。** 这套用例里项目还有 `echo`，脚本停的是部署文件里的七个；`echo` 是被 docker 等了 2 秒之后强行杀掉的，一起停的话那个在途的请求就做不完。各容器收到的信号和先后，两种停法相同（单独试过一次）。

### 13. 后端的名字在网关第一次用到它时解析不了，那条路由就一直答 503

启动的先后与这一条有关：网关起来的时候，它要找的后端不一定已经在了。三轮里看到的（`SH-15`），三轮相同：

- 后端不在，它的名字在 compose 的网络里也就解析不了。这时重启网关，发一个请求：503，应答正文是 `dns resolution failed`。
- 把后端起起来，从网关所在的网络命名空间里按名字连得上它了。20 秒之后再发请求：仍是 503，`dns resolution failed`。
- 重启网关：0.05 秒之后请求得到 200。
- 对照：网关启动时名字解析不了，但在第一个请求到来之前解析得了了。这个请求得到 200。所以网关不是在启动时解析后端的名字，是第一次用到它时才解析；第一次解析不了，就记住了这个结果。

用例之外单独试过一次的：名字解析得了之后等了 240 秒，仍是 503；一个解析过的后端后来没了又回来，3.7 秒之后请求恢复。

要知道的：

- **多久之后会自己恢复，没有量到**；会不会自己恢复也不知道。没有去读上游的源码，这里写的只是看到的行为。
- **测的是名字不存在。** 解析器够不着、解析超时的时候是不是也这样，没有测。
- 按这个性质推断（没有测）：机器开机时解析器比网关晚就绪，或者某个 Provider 的域名在头一个请求到来时刚好解析不了，那条路由会一直 503 到有人重启网关。启动的先后管不了这件事：`confirm` 看的是网关加载了哪一份配置，不看后端。

### 14. 看守：容器死了跑启动命令把它们起回来，平时定时对账

前面留着两件没有人做的事：平时没有谁去对账（第 9 点），网关或 `front` 崩了没有谁把它们起回来（第 12 点）。`gateway-control keep` 是常驻的，做的就是这两件。它没有另造做法：把容器起回来，跑的是启动一个池的那条命令，第 11 点的先后因此照旧；对账就是 `reconcile`（第 9 点）。

它每隔一阵看一眼（默认 5 秒），每一眼依次做：

1. 问 docker 这个池的三个常驻容器各是什么样子。
2. 三个都在跑（`whole`）：到了该对账的时候（默认一分钟一次）对一次账，别的不做。
3. 有没在跑的（`down`）：先试着占一下配置目录的锁。占不到，说明一次发布正在进行，这一眼什么都不做（`busy`）。占到了就放开，跑启动命令 `docker compose up -d`。
4. `netns` 没在跑，网关或 `front` 却在跑（`orphaned`）：它们接着的命名空间已经不在了，只跑启动命令修不好（第 12 点）。同样先看锁；然后先 `docker compose stop front agentgateway`，再跑启动命令；`egress` 不用它停，启动命令会在新的命名空间里把这一步重新跑一遍（第 16 点）。
5. 启动命令跑完再看一次三个容器，网关在跑就对一次账。三个都在跑才算修好。
6. 没修好：隔得越来越久再试，间隔是看一眼的间隔乘 2、4、8……，默认最长 5 分钟。等着的时候它照样看；网关在跑的话照样对账。对账从对不上变成对得上，它不等到原定的时候，下一眼就再试。修好了，或者看到三个都在跑，间隔从头算。

它不做的：不直接启动或重启哪个容器，只跑上面两条 docker compose 命令；不重启在跑着的网关；对账的结局是 `RESTART_PENDING`、`UNKNOWN`、`UNCONFIRMED` 时只写出来。

它写的是一行一份的 JSON，有事才写：动过容器的，往回放过文件的，以及池的样子或对账的结局与上一次写的不同的。各项的意思见 [`deploy/compose/README.md`](../../../deploy/compose/README.md) 的"看守"。它的退出码不说池的事：被叫停时把手上的那一步做完，以 0 结束（跑过的是 SIGTERM；SIGINT 和 SIGHUP 走的是同一段代码）；一开始就装不起来是 1（只有单元测试）；命令行或变量文件写得不对是 2。

三轮里看到的（`SH-16`）。头三步看守用的是默认的间隔，环境里带着部署文件的各个变量，与它的单元里的相同；之后为了省时间 1 秒看一眼。

- **好好的池上它只写一行**：`whole`，对账 `IN_SYNC`，没有动手。之后 7 秒它没有再出声，容器没有动，`place` 和 `confirm` 没有再跑。
- **网关被强行杀掉**（`docker kill`）。看守下一眼看到，写的那一行是：`down`，依据 `the gateway is not running (exited (137))`，做了 `start`，修好了，对账 `IN_SYNC`。网关是经启动命令起来的：`place` 先跑完（`IN_PLACE`），网关才启动，然后是 `confirm`。网关换了一个进程，还是那个容器；`netns` 和 `front` 没有被动过。每秒 20 个的快请求里没有得到 200 的是 104、105、106 个，前后 5.2 到 5.3 秒，得到的都是 `front` 答的 502；之后照常。这 5 秒多里，大头是看一眼的间隔。
- **`front` 被强行杀掉**：同样由启动命令起回来，网关和 `netns` 没有被动过。到这里七个容器都还是原来那七个：看守带着部署文件的变量跑启动命令，没有重建哪一个。
- **`netns` 单独被强行杀掉**。看守写的是 `orphaned`，依据是网关和 `front` 各一句 `… is running but the container that holds its network namespace is not`，做了 `stop+start`。docker 记下的事件三轮相同：`front` 收到 SIGQUIT 退出，然后网关收到 SIGTERM 退出，都是自己退出的；然后启动命令照它的先后来。三个常驻容器都换了进程，还是那三个容器。
- **三个常驻容器同时被强行杀掉，这时才启动看守**。它第一眼就跑启动命令。从看守启动算起：`place` 跑完在 0.37 到 0.41 秒，网关启动在 1.04 到 1.08 秒，`confirm` 跑完在 1.24 到 1.29 秒，`front` 启动在 1.73 到 1.78 秒，第一个应答到达在 1.81 到 1.87 秒；在那之前落空的请求每次 36 到 37 个。先后与开机时的相同（第 11 点），`confirm` 跑完之前没有请求得到应答。
- **一次发布正占着这个池时网关死了**。脚本占着配置目录的锁，杀掉网关，又往目录里放了一份没人确认过的文件：一次发布做到一半就是这个样子。看守写了一行 `down`、`busy`，没有动手；之后它又看了四眼，没有再写，网关还是没在跑，那份文件没有被动过。锁一放开它就跑启动命令：`place` 把记录的那一份放回去，说出原来放着的是哪一份，网关带着记录的那一份起来。没人确认过的那条路由从头到尾没有答过 200：网关死着时是 `front` 的 502（112 到 130 个），回来之后是 404。

三轮里看到的（`SH-17`），看守 1 秒看一眼，5 秒对一次账：

- **发布器刚把一份快照换上去就被 SIGKILL**（第 9 点里要人来对账的那种情况）。看守在下一次对账时把记录的那一份放回去，结局 `RESTORED`，原因里有原来放着的是哪一份；那一行写出来是在发布器被杀掉之后 2.34、2.34、5.23 秒。它没有动容器，三个常驻容器都没有重启。这期间 553 个快请求和 30 个慢请求全部得到 200。
- **有人绕过发布器放了一份网关加载不了的文件，或者把配置文件删了**：都在下一次对账时收回去，`RESTORED`。前一种的原因里带着网关自己说的那句话，后一种写的是 `there was no configuration file in place`。
- **正常的发布它不碰**。看守在跑时用发布器发布一份新快照：`ACTIVE`。之后 12 秒看守又对了两次账还多，这一份还在生效，记录是它。
- **带重启的发布它不插手**。看守在跑时做一次 `restart`：`ACTIVE`，docker 对网关容器只做了这一次重启。这期间看守写了两行：一行 `whole`、`busy`（轮到它对账时池正被发布器占着），一行 `IN_SYNC`。
- **带重启的发布让网关停了 5 秒多**（一份网关拿它起不来的快照，第 10 点）。发布器用了 8.41 到 8.45 秒，结局 `RESTORED`；docker 的事件是两次重启，中间网关自己退出了一次。看守这期间看到网关没在跑：写的是 `down`、`busy`，依据 `the gateway is not running (exited (1))`，没有动手，`place` 和 `confirm` 没有跑。发布器做完之后它的对账是 `IN_SYNC`。看守要是在这时去跑启动命令，就是和发布器抢着起网关：对照见下。
- **带重启的发布做到一半，发布器被 SIGKILL**，网关已经带着新设置起来了。看守在下一次对账时把记录的那一份放回去，报告 `RESTART_PENDING`，指出是 `terminationMaxDeadline` 这一项。它自己不重启网关：又过了 7 秒，网关还是那个进程，启动设置还是新的那一套。脚本跑了不给快照的 `restart`（`ACTIVE`），看守的下一次对账是 `IN_SYNC`。

  这一条原来是一看到网关重启就杀发布器，偶发不通过：单独循环跑这一段，40 遍里 2 遍（完整套件里 1 次），看守先写一行 `UNKNOWN`（原因里先是回读口 `connection reset by peer`，然后是放回去的那一份没有得到确认，等了 10 秒），下一次对账把同一份再放一遍，才是 `RESTART_PENDING`，这时那一行的 `previous` 已经是记录的那一份，检查对不上。原因见第 1 点：杀的时刻正落在网关刚启动、看不到换上去的文件的那几毫秒附近，看守又正好在对账。现在脚本等到网关在回读口上答得上话（看到重启之后 0.02 到 0.05 秒，中位 0.03 秒）才杀发布器，同一段循环跑 80 遍，看守的第一行都是 `RESTART_PENDING`，没有一遍 `UNKNOWN`。发布器重启网关之后至少要过 1 秒才认读到的结果，所以这时杀仍然是做到一半。改的是脚本杀发布器的时刻；检查的条件没有放宽，看守的代码没有改。

三轮里看到的（`SH-18`），看守 1 秒看一眼：

要知道的：

- **网关崩了，池要断几秒。** 断多久主要看看守多久看一眼：默认 5 秒时量到 5.2 到 5.3 秒。`front` 这期间开着，调用方得到的是 502。把间隔改短，断得短，问 docker 也问得勤；默认值是执笔时取的，没有对着真实的要求调过。
- **它只跑启动命令，所以起回来的池仍然是对上了才开门。** 对不上（没有记录，记录坏了，读不到网关），`front` 就不开，它隔一阵再试，写在自己的输出里。
- **它写的那些行没有人看，它说的事就没有人知道。** 修不好，`RESTART_PENDING`，`UNKNOWN`：都在它的输出里，也在它给出的指标里（`SH-20`）。什么时候该叫人写在部署目录的规则里，一个真的 Prometheus 读真的看守时响过其中几条（`SH-21`）。叫到谁不在这个仓库里。安稳的时候它不出声，指标仍在走。
- **它和发布器用同一把锁，谁先占到谁做。** 池被发布器占着时看守不动手，这在三轮里每轮都看到。反过来，看守对账的那一下占着锁（账对得上时 0.01 秒左右，第 9 点），这时到来的 `publish`、`restart`、`reconcile` 和启动命令里的两步会以退出码 1 结束，说 `another publication to this pool is in progress`，什么都没做，要再跑一次。脚本为此在跑发布器的命令时留了重试；三轮里碰没碰到没有记。
- **发布器死在半路留下的那一份，它一律收回去。** 第 9 点说没做完的发布有两条出路：再发布同一份把它做完，或者对账把它收回去。看守在跑时，最迟到下一次对账它就被收回去了；要把它做完，再发布一次。
- **看守写什么行与时刻有关。** 同一步在三轮里写的行数不一样：带重启的发布让网关停着的那一次，一轮比另两轮多一行 `whole`、`busy`。检查看的是它有没有动手，不是行数。

只有单元测试的（`internal/gatewayconfig/application`、`cmd/gateway-control`）：

- 记录读不成样子：对不了账，只报告，不动文件。
- 再试的间隔到 5 分钟封顶，和默认的 10、20、40 秒这一串；账对上之后的那一次再试又没修好，间隔不从头算。
- `netns` 被重新启动过、网关和 `front` 一直在跑（它们是在 `netns` 这一次启动之前启动的）：也当成 `orphaned`。跑过的是 `netns` 死着的那一种。

### 15. 告警：看守给出指标，规则决定什么时候该叫人

`SH-20` 和 `SH-21`。看守加上 `--metrics-listen` 之后，每看完一眼在那个地址的 `/metrics` 上给出 Prometheus 文本。数里没有配置的内容，也没有凭证；没有设防，够得着这个地址的都读得到。部署目录里的 `idp-gateway-pool.rules.yml` 是八条：`GatewayKeeperDown`（读不到看守，1 分钟，这一条是底）、`GatewayKeeperStalled`（超过 10 分钟没有看完一眼）、`GatewayKeeperLookFailing`（连着 2 分钟没看成）、`GatewayPoolNotWhole`（三个常驻容器不是都在跑，连着 2 分钟）、`GatewayPoolNotConfirmed`（对账连着 5 分钟是 `UNKNOWN` 或 `UNCONFIRMED`）、`GatewayPoolRestartPending`（连着 5 分钟是 `RESTART_PENDING`）、`GatewayPoolBroughtBack`（过去 15 分钟里跑过启动命令）、`GatewayPoolSnapshotPutBack`（过去 15 分钟里把记录的那一份放回去过）。这些时长是执笔时取的，没有对着真实的要求调过。叫到谁、怎么送，不在这个仓库里。

2026-11-17，docker 29.8.1，compose 5.5.1，Prometheus 3.14.0（按摘要引用的镜像），Go 1.26.8。跑之前这台机器的时钟已对准：内核 tick 是 10000，单调时钟按硬件速度走，墙上时钟不跳。连跑三轮都是 21/21，每轮 669 到 686 秒。`GatewayKeeperDown` 从看守进程停下算起，三轮是 61.1、61.1、61.0 秒。套件用 `time.monotonic()` 量，接受 60 到 75 秒。更早在同一棵树上量到 54 到 56 秒，是这台 WSL 的单调时钟被调慢了（`systemd-timesyncd` 在拨墙上时钟），不是规则提前响，也不是从第一次抓取失败的样本另起一分钟。精确的 1 分钟由 `promtool test rules` 对着造的数把关。

对着真的看守响过的是三条：往回放文件（`GatewayPoolSnapshotPutBack`，不等时长）、把网关起回来（`GatewayPoolBroughtBack`）、看守停了（`GatewayKeeperDown`）。`GatewayPoolNotWhole` 看到了 pending，网关在 2 分钟之内回来，没有响。没有对着真的看守让它响过的：`GatewayPoolRestartPending`、`GatewayPoolNotConfirmed`、`GatewayKeeperLookFailing`、`GatewayKeeperStalled`。

Prometheus 容器的 `/prometheus` 是 tmpfs。进程不是 root 时，这个 tmpfs 要写成运行它的用户的 uid 和 gid，不然它一启动就以 1 退出，什么都读不到。测试里的 Prometheus 每秒读一次；平时的 Prometheus 是 15 秒。两次读之间发生又过去的事它看不到，除了那两条数次数的。

这两条没有做对照（把做法改坏几处，看有没有用例不通过）。`units.py` 仍是 6/6：看守单元的命令行末尾是 `--metrics-listen`，值取自 `.env`。

### 16. 出口的规则：网关启动之前装好，`egress-watch` 守着

锁定的网关按名字找后端，名字后来指到哪里它就去哪里，配置里没有开关能拦住。部署文件因此在网关所在的网络命名空间里装规则，只许新的外出连接去配置里写着的地址：`egress` 在网关启动之前装一遍，`egress-watch` 每两秒重装一遍。为什么这样做、规则是什么、留下的限制，见 [`deploy/compose/README.md`](../../../deploy/compose/README.md) 的"出口的规则"和 [`tests/integration/egressnet/README.md`](../egressnet/README.md)。

启动的先后里多出来的部分（`deploy/compose/compose.yml` 的 `depends_on`）：`netns` 起来了、`place` 也以退出码 0 跑完了，才是 `egress`；`egress` 以退出码 0 跑完，网关才启动；`egress-watch` 在 `egress` 跑完之后启动，别的都不等它。

三轮里看到的（`SH-22`），三轮的检查项相同，没有不通过的：

- **两个容器的身份**。`egress` 和 `egress-watch` 都是 `0:0`，多出来的 capability 只有 `CAP_NET_ADMIN`，去掉的是 `ALL`。三轮相同。
- **从池的网络命名空间里连各处**（`connect` 的结果，0 是连上了，113 和 13 是被规则拒绝）。后端的名字 `echo` 解析到 192.168.32.2。连得上的三处：`192.168.32.2:8000`、`127.0.0.1:8081`、`127.0.0.1:15000`，都是 0。被拒绝的：`192.168.32.2:8001`（后端那个地址的另一个端口）113，`127.0.0.1:15020`（网关的指标端口，它在听，配置里没有写它）113，`192.0.2.1:443`（一个不相干的地址）113，`[::1]:15020` 13。三轮相同。
- **钉着的两处**：`echo:8000` 钉在 192.168.32.2，`127.0.0.1:15000` 钉在 127.0.0.1。三轮相同。
- **`egress-watch` 重写规则的 8 秒里没有空档**。这 8 秒里连后端那个地址的另一个端口，三轮各是 3761、3756、3763 次，每一次都是 113。
- **`forget`**：`docker compose run --rm --no-deps egress forget`，退出码 0，说了 `pinned 127.0.0.1:15000 -> 127.0.0.1` 和 `pinned echo:8000 -> 192.168.32.2`；之后钉着的没有变，请求照常。三轮相同。
- **断电之后**。三个常驻容器同时被强行杀掉，`egress-watch` 在 0.06 秒时已经停了，退出码 137；三轮相同。再跑启动命令：退出码 0，`egress` 在这次启动里重新跑了，在网关启动之前以 0 跑完，`egress-watch` 在新的 `netns` 之后起来，请求照常。新的命名空间里：`192.168.32.2:8000` 是 0，`192.168.32.2:8001` 和 `127.0.0.1:15020` 是 113，钉着的还是那两处。
- **`egress` 读不了配置**。`egress` 读配置靠的是文件对所有人可读；配置文件是 0644（发布器写的就是这个）。把它改成 0600 再跑 `docker compose up -d`：命令的退出码是 1，最后说 `service "egress" didn't complete successfully: exit 1`；`egress` 容器的退出码是 1，在标准错误上说 `sed: /work/config/config.yaml: Permission denied` 和 `pin-egress: cannot read /work/config/config.yaml`。在跑的只有 `netns`；`egress`、网关、`confirm`、`front`、`egress-watch` 都没有在跑，业务端口上没有人应答。`place` 在这次 `up` 里照常以 0 跑完（`IN_PLACE`），在 `egress` 之前；配置文件没有被动过，内容、属主、修改时刻都不变，模式还是 0600。三轮相同。
- **改回 0644 之后**：再跑启动命令，退出码 0，`egress` 重新跑了并以 0 跑完，网关在它之后才启动，`confirm` 是 `IN_SYNC`，请求照常。池又是完整的：三个常驻容器和 `echo` 都在跑，`egress-watch` 在跑，钉着的和之前一样。

只在套件之外看过一次（2026-11-18，一次，同一个部署文件的池，真的看守 `gateway-control keep --interval 1s`），套件里没有检查看着它：看守修好一个 `orphaned` 的池之后，规则在不在。`netns` 单独被 `docker kill`，看守写的是 `orphaned`，做了先停后启动，修好了，对账 `IN_SYNC`。它停的只有 `front` 和网关（`docker compose stop front agentgateway`）。之后各容器的启动时刻：`netns` 14:32:30.899，`egress` 14:32:31.686，`egress-watch` 14:32:32.278，网关 14:32:32.349，`front` 14:32:33.065：`egress` 这一步在新的 `netns` 之后、网关之前重新跑了，以 0 跑完。之后从池的网络命名空间里：钉着的还是那两处（`echo:8000` 钉在后端的地址上，`127.0.0.1:15000`），后端连得上，后端那个地址的另一个端口和 `192.0.2.1:443` 都被规则拒绝（113），经 `front` 的请求得到 200。

`SH-22` 的对照（把做法改坏几处，看有没有检查不通过）没有留下记录，当作没有做。

## 没有覆盖的

- 发布器的几个只有单元测试的分支（见第 10 点末尾），看守的几个（见第 14 点末尾）。
- **真的重启一台机器，或者重启 docker。** 这里的断电是把三个常驻容器同时强行杀掉。docker 守护进程重启之后各容器是什么状态、两个 systemd 单元在开机过程中跑得是不是时候，都没有看过。
- **两个 systemd 单元装在一台机器上的样子。** 没有装过。做过的是三样：用 `systemd-analyze verify` 查写法；它们之间的关系，在用户级的 systemd 里用替身命令跑（`units.py`）；它们里面写的命令，不经 systemd 原样跑（`SH-19`）。没有看过的：系统级的 systemd，看守换了账号（`User=`）之后用不用得了 docker，与 `docker.service` 的先后，开机和关机。池的单元以 root 跑启动命令、看守以另一个账号跑同一条命令时，容器会不会被重建，也没有看过：`SH-19` 里两条命令是同一个用户跑的。
- 看守修好一个 `orphaned` 的池之后，出口的规则在不在：只在套件之外看过一次（第 16 点），没有检查看着它。`egress` 失败只试过读不了配置这一种（`SH-22`）；别的失败方式，比如 iptables 装不上，没有试。`egress-watch` 死了而 `netns` 还在时会怎样，没有试。
- 看守的对账正好落在网关启动的那几毫秒里的情形：套件现在碰不到（杀发布器的时刻改到网关答得上话之后）。见过的 3 次里，它都是下一次对账把同一份再放一遍收拾好的；没有哪一项检查看着这条路。
- 看守没有跑到的：docker 守护进程重启或崩溃时它会怎样；它正跑着启动命令时被强行杀掉；它在跑时有人手工重启网关容器，或者手工跑的启动命令与它跑的那一条同时进行；默认的对账间隔（一分钟）和再试的间隔封顶（5 分钟）。
- 启动时对不上、看守修不好、启动设置还差一次重启：规则能说出来（`SH-20`、`SH-21`）。告警送到谁那里、Prometheus 自己停了由谁发现，没有做。
- 发布器在哪里、以什么身份运行。它要用 docker 命令起临时容器、重启网关容器，看守要用 docker compose；这里它们和网关是同一个本机用户，`place` 和 `confirm` 在容器里用的也是这个用户，两者不同时文件的属主和权限怎么定没有测。`restart` 核对容器的挂载时比的是 docker 报告的路径，发布器要是跑在容器里，两边的路径不一样。发布器的证书怎么签发和轮换没有设计。
- 离线加载那边挂哪个证书目录。挂池的那个，两边引用的文件一致，但临时容器也拿到了池的私钥；另备一套，就可能出现 `SH-09` 里"离线加载得了、池里加载不了"的情况。
- 带 JWT、ExtAuthZ 和真实 PDP 的配置。JWKS 随快照下发也没有在这里跑：这里的快照只有一个配置文件，多个文件怎么一起换没有测。
- 有重启策略的容器上会怎样：docker 自己把网关起起来时读到什么，带重启的发布失败之后是什么样。部署文件写明了不设重启策略。
- 长连接和流。这里最长的请求是 14 秒；SSE、gRPC 流、WebSocket 在重启和停的时候会怎样没有测，在途的请求超过终止时限或容器的停止时限时会怎样也没有测。
- 换镜像（升级 agentgateway）。换了构建之后记录要重新做一次（把同一份快照再发布一次），在那之前启动时 `confirm` 是 `UNCONFIRMED`、`front` 不启动：这些只有单元测试。
- 解析器够不着或解析超时的时候，网关怎么对待后端的名字；第 13 点里的 503 多久之后会自己恢复。
- 部署文件里的日志和资源上限用的是 docker 的默认值，没有定也没有测。启动时本机上还没有镜像、镜像仓库又够不着会怎样，没有试过。
- 证书轮换。
- 别的挂载方式。测的是 WSL2 里本机 ext4 上的目录直接挂载；Docker Desktop 的文件共享、网络文件系统、命名卷都没有测，文件变化的通知在那些上面不一定一样。
- 一台机器上的多个池，池之间的隔离。每个池要有自己的临时容器名字、端口和放候选配置的目录；两个池共用时会怎样没有测。
- 别的 docker 版本；arm64。
