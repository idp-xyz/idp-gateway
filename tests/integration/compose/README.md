# 单机上发布配置：换掉挂载目录里的文件，网关不重启

运行平台的第一期是单机上的 docker compose（[ADR-0010](../../../docs/adr/ADR-0010.md) 第 10 条）。单机上一个池只有一个网关实例，没有别的副本可以轮着换，所以发布不重启网关：发布器把网关容器挂载的目录里的配置文件整份换掉，网关自己重载，发布器再经回读口确认它在跑的是哪一份。这里在本机用 docker compose 验证这套做法。

> 这是机制验证，不是验收，通过不改变验收矩阵里任何用例的 `NOT_RUN`。  
> 配置是一份只有几条路由的小文件；没有 JWT、ExtAuthZ 和凭证，那些在黑盒套件里。`SH-01` 到 `SH-08` 由这个脚本扮演发布器，看的是网关和这种发布方式本身；`SH-09` 跑的是真的发布器 `cmd/gateway-control`。

## 怎么跑

```bash
.venv/bin/python tests/integration/compose/run.py     # 两分钟左右；自己起，跑完自己拆
```

需要 docker、docker compose 和 Go（脚本现场构建 `cmd/gateway-control`）。

- compose 项目叫 `idp-gateway-compose`。脚本只动它的容器和网络，以及一个叫 `idp-gateway-compose-scratch` 的临时容器。
- 用到三个镜像，都按摘要引用，本机没有时由 docker 去拉：锁定的上游 agentgateway 镜像（摘要取自 `deploy/agentgateway/agentgateway.lock.json`）、与黑盒套件相同的前置 nginx、一个带 Python 的工具镜像。
- 占用本机回环上的 `27618` 到 `27620`，所以不能和黑盒套件、Gatekeeper 联调、Kubernetes 套件同时跑。
- 证书每次运行现做，跑完删除。逐项结果写在 `.run/result.json`，不入库。

## 部署的样子

`compose.yml` 里三个容器：

| 容器 | 是什么 | 端口 |
|---|---|---|
| `front` | nginx，与黑盒套件同一个镜像、同一份配置，只换了端口。对外收业务请求的只有它 | 8080，映射到本机回环的 27620 |
| `agentgateway` | 锁定的上游镜像，与 `front` 共用一个网络命名空间（相当于 Kubernetes 上的同一个 Pod）。收业务请求的监听、管理、指标和就绪端口都只绑回环；另开一个回读口 | 8081、15000、15020、15021（回环）；8443（回读口），映射到本机回环的 27619 |
| `echo` | 路由的后端 | 8000，只在 compose 的网络里 |

- **配置**：本机上的一个目录，只读挂进网关容器。挂的是目录，不是 `config.yaml` 这一个文件。
- **发布**：发布器在这个目录里写一个临时文件，落盘，再改名盖掉 `config.yaml`。改名是原子的，网关读到的要么是旧的整份，要么是新的整份。
- **回读**：发布器从本机连回读口，出示自己的客户端证书，读 `/config_dump` 和 `/api/runtime`。写法与黑盒套件的 `P1-RB-03` 相同。发布器的证书不在网关容器里。
- **证书**：另一个只读挂载的目录，里面是回读口的服务端证书、网关去问 PDP 用的客户端证书和 CA。
- 网关容器的根文件系统只读，不带任何 capability，以运行脚本的那个本机用户的身份运行；会话密钥经环境变量 `SESSION_KEY` 给。
- **真的发布器**（`SH-09`）：`gateway-control publish` 直接在本机上运行，与脚本是同一个用户。它用本机的 docker 命令另起一个临时容器做离线加载；那个容器的回读口映射到本机回环的 27618，挂的证书目录是另外现做的一套（另一个 CA），比池的那个多一个文件。

## 结果

2026-11-11，docker 29.8.1（WSL2 里的 Ubuntu 24.04，不是 Docker Desktop），compose 5.5.1，agentgateway 1.7.0（锁定摘要的上游镜像），Go 1.26.8：9 个用例、73 项检查全部通过，同一份脚本连跑三轮都是 9/9。前 7 个用例在加进后两个之前也连跑过三轮，数字与这三轮相近。

| 用例 | 内容 | 结果 |
|---|---|---|
| SH-01 | 网关在容器里从挂载的目录启动。跑的是按摘要引用的锁定镜像，报告的版本和提交与锁定文件一致。发布器从本机经回读口读到：配置已加载，存储模式 `readOnly`，摘要等于发布前在另一个容器里算出的期望值。本机上只映射了 `front` 的端口和回读口，都只在回环上；从同一个网络上的另一个容器，连不上网关的业务监听、管理、指标和就绪端口。带两个 `Host` 头的请求在 `front` 就被拒绝。回读口不回答别的调用方，上面也没有管理地址的其余接口 | PASS |
| SH-02 | 发布一份多一条路由的快照：改名换文件，网关报告的摘要变成新快照的期望值，新路由生效；网关还是那个容器、那个进程；期间没有一个请求失败 | PASS |
| SH-03 | 一份网关加载不了的快照：离线加载先拒绝它并给出原因。硬换上去：网关经回读口报告加载失败和原因，在跑的仍是上一份，被拒绝的文件里的路由没有生效，没有重启，没有请求失败。把上一份放回去之后报告加载成功 | PASS |
| SH-04 | 回滚到更早的那份快照：同样是换文件，摘要回到那份快照的期望值，没有重启，没有请求失败 | PASS |
| SH-05 | 对照：另起一个网关容器，只把 `config.yaml` 这一个文件挂进去。就地改写这个文件，容器里看得到；写临时文件再改名，本机上的文件已经是另一份，容器里的网关 5 秒后还在跑原来那份 | PASS |
| SH-06 | 一份只在 `config` 段与上一份不同的快照：期望摘要相同。换上去之后路由部分生效、网关报告加载成功，`config` 段却仍是启动时的值。重启网关容器之后才是新值；重启时在途的请求做完了，`front` 没有动 | PASS |
| SH-07 | 重启网关时新来的请求被拒绝多久。没有在途的请求时重启一次；有两个各还剩 3 秒左右的在途请求时再重启一次：在途的请求都做完了，它们做完之前新来的请求全部被拒绝 | PASS |
| SH-08 | 网关解析配置文件之前先做环境变量替换。另起一个网关容器加载一份正文里带 `$` 的文件：`$名字` 换成了那个容器里环境变量的值，`${名字:-默认值}` 在没有这个变量时换成默认值，`$$` 成了一个 `$`，反斜杠不起转义的作用，后面不跟名字的 `$` 原样留着。`$SESSION_KEY` 一样被换：会话密钥进了运行配置，从回读口读得到。引用一个没有的环境变量，整份文件加载失败，离线加载也拒绝它 | PASS |
| SH-09 | 真的发布器 `gateway-control publish`，对着同一个池。发布一份新快照：结局 `ACTIVE`，新路由生效，网关没有重启，期间没有请求失败；再发布同一份，不再写文件。网关加载不了的快照和带环境变量引用的快照：`REFUSED`。`config` 段与网关启动时不同的快照：`RESTART_REQUIRED`。这三种池都没有被碰过。一份离线加载得了、池里加载不了的快照：发布器换上去，读到网关报告加载失败，把上一份放回去，结局 `RESTORED`，期间没有请求失败。发布器刚把文件换上去就收到 SIGTERM：它先把上一份放回去并得到确认才退出，结局也是 `RESTORED`。有人绕过发布器放了一份坏文件时：`POOL_NOT_READY`，目录里的文件它不动。两次发布同时进行，晚到的那次什么都不做。发布器用过之后没有留下容器和临时文件 | PASS |

## 看清的事

### 1. 改名换文件，0.3 秒左右生效，期间没有请求失败

三轮里从改名到回读口报告出结果，一共量了 12 次：0.28 到 0.35 秒。

流量从本机经 `front` 的端口发出：每秒 20 个快请求，每个一条新连接；另有两条线各自接连发耗时 2 秒的请求。三轮里换文件的三个用例（`SH-02` 至 `SH-04`，共 12 次换文件）期间一共 1296 个快请求和 78 个慢请求，全部得到 200。

这不是碰巧。上游在锁定提交上的源码（`crates/agentgateway/src/util.rs`、`state_manager.rs`）里，配置文件是一个普通文件时网关监视的是这个文件本身，变化先攒 250 毫秒；文件被改名替换之后它重新加载，并对新文件重新建立监视。上游自己有一条"反复改名替换之后仍然重载"的测试（`file_config_reloads_after_repeated_rename_replacement`）。

### 2. 加载不了的文件在两个地方被挡住，但不能让它留在盘上

- **发布之前**。发布器用同一个镜像另起一个容器加载这份快照。加载不了，进程以非零码退出并说出原因，这份快照就不该往下发。
- **硬换上去**。0.3 秒后网关经回读口报告这次加载失败和原因（与离线加载给出的原因相同），继续用上一份；整份文件都不生效，里面没有毛病的那条路由也不生效。

第二种情况下网关看上去没事，但这时目录里的文件是坏的那一份，网关在跑的是上一份。它一旦重启（崩溃、主机重启、换镜像），读到的就是那份坏文件，起不来：离线加载那一步看到的正是网关启动时遇到这份文件就退出。所以发布器读到"加载失败"之后要把上一份放回去，不能停在这里。放回去 0.3 秒后网关报告加载成功。

真的发布器做的就是这两步，见第 8 点。

### 3. 要挂目录，不能只挂 `config.yaml`

只挂一个文件时，容器拿到的是那个文件本身，而不是"目录里叫这个名字的文件"。发布器改名换上去的是另一个文件，容器里的还是原来那个：`SH-05` 里本机上的文件已经换了，网关 5 秒后仍在跑旧的，也不报错。就地改写同一个文件容器里倒是看得到（0.34 到 0.35 秒后重载），但就地改写不是原子的，网关可能读到写了一半的文件。

### 4. `config` 段的改动要重启网关，回读的摘要看不出来

`config` 段的设置只在启动时读取。`SH-06` 换上一份只改了 `config` 段里一项的文件：网关报告加载成功，路由部分也确实换了，那一项却还是启动时的值。摘要是不含 `config` 段的（见第 6 点），所以这份快照和上一份的期望摘要相同，回读看不出 `config` 段有没有生效。发布器得自己比：新快照的 `config` 段和网关启动时用的那份不一样，这次发布就要重启网关。

真的发布器比的是两边 `/config_dump` 里的 `config` 段：离线加载这份快照得到的，和池里的网关报告的。不一样就不发布，结局是 `RESTART_REQUIRED`，并列出不同的项。`dns` 和工作线程数这两项随运行环境变，不比。

### 5. 单机上重启网关，新来的请求被拒绝；拒绝多久取决于在途的请求还要多久

单机上只有这一个实例，重启期间新来的请求没有别处可去：`front` 连不上网关，答 502（应答正文是 nginx 自己的错误页）。三轮里量到的：

| 重启时在途的请求 | 重启命令用时 | 每秒 20 个的快请求里得到 502 的 |
|---|---|---|
| 没有（`SH-07`） | 0.27、0.29、0.27 秒 | 3、3、3 个 |
| 两个，各还剩 1 秒左右（`SH-06`） | 1.21、1.20、1.20 秒 | 22、21、21 个 |
| 两个，各还剩 3 秒左右（`SH-07`） | 3.18、3.18、3.19 秒 | 60、61、60 个 |

网关收到终止信号就不再接新连接，等在途的请求做完才退出；在途的请求都做完了，没有被切断。所以新请求被拒绝的时间，差不多就是在途的请求里最长的那个还要多久；没有在途的请求时是 0.15 秒左右。

它最多等多久由 `connectionTerminationDeadline` 定，这里设的是 45 秒；这里最长只测到 3 秒。45 这个数是从 Kubernetes 套件沿用的，没有对着真实的请求时长调过。在单机上它有两头：定得长，重启时新请求可能被拒绝得久；定得短，在途的请求会被切断。

### 6. 期望摘要可以在另一个容器里算出来

池里的网关经回读口报告的摘要，等于发布前另起一个容器加载同一份快照得到的摘要；那个容器用的是另一套证书。两边相等的条件与 Kubernetes 套件里看到的相同：算摘要时去掉 `config` 段（两边不同的项是 `dns`），并把证书正文换成占位。

发布器（Go）和这个脚本（Python）各自实现了这个算法。`SH-09` 里两边对同一个网关算出的摘要相同。

### 7. 网关解析配置文件之前，先拿环境变量替换正文里的 `$名字`

锁定的版本读到配置文件之后、解析之前，把整份正文过一遍替换（上游 `crates/agentgateway/src/types/local.rs` 的 `expand_env`，用的是 `shellexpand`）。用的是加载这份文件的那个进程的环境。替换在解析之前，所以不分键、值还是注释；上游为此专门绕开了自己那行写模式地址的注释。`SH-08` 里看到的：

| 正文里写的 | 网关拿到的 |
|---|---|
| `$HOSTNAME` | 这个环境变量的值（容器的主机名） |
| `${NO_SUCH_VARIABLE:-fallback}` | 没有这个变量，是 `fallback` |
| `$$HOSTNAME` | `$HOSTNAME`：`$$` 是字面的 `$` |
| `\$HOSTNAME` | 反斜杠加上环境变量的值：反斜杠不起转义的作用 |
| 后面不跟名字的 `$` | 原样 |
| `$NO_SUCH_VARIABLE` | 整份文件加载失败：`error looking key 'NO_SUCH_VARIABLE' up: environment variable not found` |
| `$SESSION_KEY` | 会话密钥 |

用例之外单独试过的：`${名字}` 同样被换；`$1` 被当成名字叫 `1` 的变量，没有这个变量，整份文件加载失败。

这对发布意味着三件事：

- **带这种写法的快照不是自成一体的。** 同一份文件，离线加载的容器里和池里的网关上可以是两份不同的配置，期望摘要就说明不了什么；也可以一边加载得了、另一边加载不了。
- **会话密钥可以被写进运行配置。** 会话密钥是经环境变量给网关的。快照里写一个 `$SESSION_KEY`，它就成了运行配置里的一个值，能读回读口的都读得到。
- **值里一个没有转义的 `$` 能让整份文件加载不了。** 正则替换里的 `$1` 就是。以后由 RouteIntent 编译出配置时，值里的 `$` 要写成 `$$`。

所以发布器拒绝正文里带这类引用的快照，结局是 `REFUSED`，不加载，也不碰池。它查的是正文的字面，比网关认的宽：`$` 后面跟着字母、数字、下划线、非 ASCII 字节或 `{` 的都算，`$$` 成对跳过。它只管得了经它发布的文件；它依据的是锁定版本的写法，换版本时要重新确认（`deploy/agentgateway/README.md`）。

### 8. 真的发布器对着真的网关

`SH-09` 跑的是 `gateway-control publish`，对着前面的用例用的同一个池。它发布一份快照时依次做：

1. 正文里有对环境变量的引用：拒绝（第 7 点）。
2. 用同一个镜像另起一个临时容器加载这份快照，得到期望摘要。网关加载不了，或加载出来存储模式不是 `readOnly`：拒绝。
3. 经回读口读池里的网关。它上一次加载失败，或存储模式不是 `readOnly`：池不干净，不发布。它的构建或 `config` 段与离线加载的不同：要重启，不发布。
4. 目录里已经是这份快照、网关也报告它在生效：什么都不写。否则把文件换上去（临时文件、落盘、改名），等网关经回读口报告期望摘要。
5. 没有生效（网关报告加载失败，或 10 秒内没有报告期望摘要）：把上一份放回去，再等网关报告它在跑的又是发布之前的那一份。

结果以 JSON 写到标准输出，退出码说明池现在的状态：

| 结局 | 退出码 | 池 |
|---|---|---|
| `ACTIVE` | 0 | 这份快照正在生效 |
| `REFUSED`、`RESTART_REQUIRED`、`POOL_NOT_READY` | 3 | 没有被碰过 |
| `RESTORED` | 4 | 换上去过，没有生效；上一份已经放回去并得到确认 |
| `UNKNOWN` | 5 | 换上去过，没有生效，也没能确认放回去了；要对账 |
| 没有结局，出了错 | 1 | 没有被碰过，原因在标准错误上 |
| 没有结局，命令行写得不对 | 2 | 什么都没做 |

三轮里看到的：

- **发布一份新快照**：发布器用了 1.85、1.92、1.99 秒。其中要另起一个容器做离线加载；换上文件之后它至少等 1 秒才认读到的结果，因为网关攒 250 毫秒才重载，新旧两份的运行配置相同时，更早读到的"已生效"说明不了它加载过新文件。期间 477 个快请求和 24 个慢请求全部得到 200，网关没有重启。
- **一份离线加载得了、池里加载不了的快照**：它引用的一个文件只在离线加载那边的证书目录里有。发布器换上去，读到网关报告加载失败，把上一份放回去，前后用了 3.08、2.97、2.99 秒；这期间 542 个快请求和 30 个慢请求全部得到 200。它给的原因是池里的网关自己说的：`routes[4]: read resource file /work/tls/only-in-staging.crt at line 65 column 3`。离线加载通过不等于池里加载得了，兜底的是放回去这一步。
- **被叫停时先把上一份放回去**。脚本等发布器把一份没有毛病的快照换上去，立刻给它发 SIGTERM。它没有立刻退出：把上一份放回去，等网关报告在跑的又是发布之前的那一份，然后以 `RESTORED` 结束，原因写的是 `interrupted while waiting for the gateway: context canceled`。SIGINT 和 SIGHUP 走的是同一段代码，没有另发。
- **池不干净时它不动手**。脚本绕过发布器往目录里放了一份坏文件，网关正报告加载失败：发布器的结局是 `POOL_NOT_READY`，那份坏文件它没有动。把池收拾回来（对账）还没有做，这里是脚本自己把上一份放回去的。
- **同一个池同时只有一次发布**。晚到的那次以退出码 1 结束，什么都没做。互斥靠配置目录里的一个锁文件 `.config.yaml.lock`；它一直留在目录里，网关不受它影响。
- **用过之后不留东西**：临时容器不在了，放候选配置的目录是空的。

上面五步里没有在真的网关上走到的分支，只有单元测试（`internal/gatewayconfig/application`、`cmd/gateway-control`）：离线加载出来的、或池里的网关报告的存储模式不是 `readOnly`；池里的构建与离线加载的不同；放回上一份之后仍然对不上，也就是 `UNKNOWN`。

## 没有覆盖的

- 发布器的几个只有单元测试的分支（见上），其中有 `UNKNOWN` 这个结局。
- 发布器换上文件之后被强行杀掉（SIGKILL、断电）。它来不及把上一份放回去，留下的状态要靠对账。
- 对账。发布器启动时核对目录里的文件和网关在跑的那份（ADR-0010 要求的），以及池不干净、结局未知之后怎么收拾，都还没有做。
- 发布器在哪里、以什么身份运行。它要用 docker 命令起临时容器；这里它和网关是同一个本机用户，两者不同时文件的属主和权限怎么定没有测。发布器的证书怎么签发和轮换没有设计。
- 离线加载那边挂哪个证书目录。挂池的那个，两边引用的文件一致，但临时容器也拿到了池的私钥；另备一套，就可能出现 `SH-09` 里"离线加载得了、池里加载不了"的情况。
- 带 JWT、ExtAuthZ 和真实 PDP 的配置。JWKS 随快照下发也没有在这里跑：这里的快照只有一个配置文件，多个文件怎么一起换没有测。
- 主机重启或 docker 重启之后容器会不会自己起来。`compose.yml` 里没有写重启策略。
- 长连接和流。这里最长的请求是 6 秒；SSE、gRPC 流、WebSocket 在重启时会怎样没有测，在途的请求超过终止时限时会怎样也没有测。
- 换镜像（升级 agentgateway）。
- 证书轮换。
- 别的挂载方式。测的是 WSL2 里本机 ext4 上的目录直接挂载；Docker Desktop 的文件共享、网络文件系统、命名卷都没有测，文件变化的通知在那些上面不一定一样。
- 一台机器上的多个池，池之间的隔离。
- arm64。
