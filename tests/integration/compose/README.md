# 单机上发布配置：换掉挂载目录里的文件，网关不重启

运行平台的第一期是单机上的 docker compose（[ADR-0010](../../../docs/adr/ADR-0010.md) 第 10 条）。单机上一个池只有一个网关实例，没有别的副本可以轮着换，所以发布不重启网关：发布器把网关容器挂载的目录里的配置文件整份换掉，网关自己重载，发布器再经回读口确认它在跑的是哪一份。这里在本机用 docker compose 验证这套做法。

> 这是机制验证，不是验收，通过不改变验收矩阵里任何用例的 `NOT_RUN`。  
> 配置是一份只有几条路由的小文件；没有 JWT、ExtAuthZ 和凭证，那些在黑盒套件里。`SH-01` 到 `SH-08` 由这个脚本扮演发布器，看的是网关和这种发布方式本身；`SH-09` 到 `SH-11` 跑的是真的发布器 `cmd/gateway-control` 的三条命令：`publish`、`reconcile`、`restart`。

## 怎么跑

```bash
.venv/bin/python tests/integration/compose/run.py     # 三分半到四分钟；自己起，跑完自己拆
```

需要 docker、docker compose 和 Go（脚本现场构建 `cmd/gateway-control`）。

- compose 项目叫 `idp-gateway-compose`。脚本只动它的容器和网络，以及一个叫 `idp-gateway-compose-scratch` 的临时容器。
- 用到三个镜像，都按摘要引用，本机没有时由 docker 去拉：锁定的上游 agentgateway 镜像（摘要取自 `deploy/agentgateway/agentgateway.lock.json`）、与黑盒套件相同的前置 nginx、一个带 Python 的工具镜像。
- 占用本机回环上的 `27618` 到 `27620`，所以不能和黑盒套件、Gatekeeper 联调、Kubernetes 套件同时跑。
- 证书每次运行现做，跑完删除。逐项结果写在 `.run/result.json`，不入库。

## 部署的样子

`compose.yml` 里三个容器：

| 容器 | 是什么 | 端口 |
|---|---|---|
| `front` | nginx，与黑盒套件同一个镜像、同一份配置，只换了端口。对外收业务请求的只有它 | 8080，映射到本机回环的 27620 |
| `agentgateway` | 锁定的上游镜像，与 `front` 共用一个网络命名空间（相当于 Kubernetes 上的同一个 Pod）。收业务请求的监听、管理、指标和就绪端口都只绑回环；另开一个回读口 | 8081、15000、15020、15021（回环）；8443（回读口），映射到本机回环的 27619 |
| `echo` | 路由的后端 | 8000，只在 compose 的网络里 |

- **配置**：本机上的一个目录，只读挂进网关容器。挂的是目录，不是 `config.yaml` 这一个文件。
- **发布**：发布器在这个目录里写一个临时文件，落盘，再改名盖掉 `config.yaml`。改名是原子的，网关读到的要么是旧的整份，要么是新的整份。
- **回读**：发布器从本机连回读口，出示自己的客户端证书，读 `/config_dump` 和 `/api/runtime`。写法与黑盒套件的 `P1-RB-03` 相同。发布器的证书不在网关容器里。
- **证书**：另一个只读挂载的目录，里面是回读口的服务端证书、网关去问 PDP 用的客户端证书和 CA。
- 网关容器的根文件系统只读，不带任何 capability，以运行脚本的那个本机用户的身份运行；会话密钥经环境变量 `SESSION_KEY` 给。它的停止时限设的是 60 秒（`stop_grace_period`），没有写重启策略。
- **真的发布器**（`SH-09` 到 `SH-11`）：`gateway-control` 直接在本机上运行，与脚本是同一个用户。`publish` 和 `restart` 用本机的 docker 命令另起一个临时容器做离线加载；那个容器的回读口映射到本机回环的 27618，挂的证书目录是另外现做的一套（另一个 CA），比池的那个多一个文件。`restart` 还用 docker 命令重启网关容器。`reconcile` 不用 docker。发布器在配置目录里留两个自己的文件：锁文件 `.config.yaml.lock` 和记录 `.config.yaml.confirmed`（第 9 点）。

## 结果

2026-11-12，docker 29.8.1（WSL2 里的 Ubuntu 24.04，不是 Docker Desktop），compose 5.5.1，agentgateway 1.7.0（锁定摘要的上游镜像），Go 1.26.8：11 个用例、108 项检查全部通过，同一份脚本连跑三轮都是 11/11，每轮 208 到 213 秒。下面引用的数字都出自这三轮。前 9 个用例在加进后两个之前也连跑过三轮（2026-11-11），数字与这三轮相近。

## 看清的事

### 1. 改名换文件，0.3 秒左右生效，期间没有请求失败

三轮里从改名到回读口报告出结果，一共量了 12 次：0.29 到 0.36 秒。

流量从本机经 `front` 的端口发出：每秒 20 个快请求，每个一条新连接；另有两条线各自接连发耗时 2 秒的请求。三轮里换文件的三个用例（`SH-02` 至 `SH-04`，共 12 次换文件）期间一共 1300 个快请求和 78 个慢请求，全部得到 200。

这不是碰巧。上游在锁定提交上的源码（`crates/agentgateway/src/util.rs`、`state_manager.rs`）里，配置文件是一个普通文件时网关监视的是这个文件本身，变化先攒 250 毫秒；文件被改名替换之后它重新加载，并对新文件重新建立监视。上游自己有一条"反复改名替换之后仍然重载"的测试（`file_config_reloads_after_repeated_rename_replacement`）。

### 2. 加载不了的文件在两个地方被挡住，但不能让它留在盘上

- **发布之前**。发布器用同一个镜像另起一个容器加载这份快照。加载不了，进程以非零码退出并说出原因，这份快照就不该往下发。
- **硬换上去**。0.3 秒后网关经回读口报告这次加载失败和原因（与离线加载给出的原因相同），继续用上一份；整份文件都不生效，里面没有毛病的那条路由也不生效。

第二种情况下网关看上去没事，但这时目录里的文件是坏的那一份，网关在跑的是上一份。它一旦重启（崩溃、主机重启、换镜像），读到的就是那份坏文件，起不来：离线加载那一步看到的正是网关启动时遇到这份文件就退出。所以发布器读到"加载失败"之后要把上一份放回去，不能停在这里。放回去 0.3 秒后网关报告加载成功。

真的发布器做的就是这两步，见第 8 点。它自己死在这两步之间时怎么办，见第 9 点。

### 3. 要挂目录，不能只挂 `config.yaml`

只挂一个文件时，容器拿到的是那个文件本身，而不是"目录里叫这个名字的文件"。发布器改名换上去的是另一个文件，容器里的还是原来那个：`SH-05` 里本机上的文件已经换了，网关 5 秒后仍在跑旧的，也不报错。就地改写同一个文件容器里倒是看得到（0.29 到 0.35 秒后重载），但就地改写不是原子的，网关可能读到写了一半的文件。

### 4. `config` 段的改动要重启网关，回读的摘要看不出来

`config` 段的设置只在启动时读取。`SH-06` 换上一份只改了 `config` 段里一项的文件：网关报告加载成功，路由部分也确实换了，那一项却还是启动时的值。摘要是不含 `config` 段的（见第 6 点），所以这份快照和上一份的期望摘要相同，回读看不出 `config` 段有没有生效。发布器得自己比：新快照的 `config` 段和网关启动时用的那份不一样，这次发布就要重启网关。

真的发布器比的是两边 `/config_dump` 里的 `config` 段：离线加载这份快照得到的，和池里的网关报告的。不一样，`publish` 就不发布，结局是 `RESTART_REQUIRED`，并列出不同的项；这种快照由 `restart` 发布（第 10 点）。`dns` 和工作线程数这两项随运行环境变，不比。

### 5. 单机上重启网关，新来的请求被拒绝；拒绝多久取决于在途的请求还要多久

单机上只有这一个实例，重启期间新来的请求没有别处可去：`front` 连不上网关，答 502（应答正文是 nginx 自己的错误页）。三轮里量到的：

| 重启时在途的请求 | 重启命令用时 | 每秒 20 个的快请求里得到 502 的 |
|---|---|---|
| 没有（`SH-07`） | 0.31、0.31、0.27 秒 | 3、3、3 个 |
| 两个，各还剩 1 秒左右（`SH-06`） | 1.20、1.18、1.16 秒 | 21、20、20 个 |
| 两个，各还剩 3 秒左右（`SH-07`） | 3.18、3.18、3.19 秒 | 58、60、61 个 |

网关收到终止信号就不再接新连接，等在途的请求做完才退出；在途的请求都做完了，没有被切断。所以新请求被拒绝的时间，差不多就是在途的请求里最长的那个还要多久；没有在途的请求时是 0.15 秒左右（更忙的那一轮是 0.4 秒）。

它最多等多久由 `connectionTerminationDeadline` 定，这里设的是 45 到 49 秒（用例拿这一项当那种只在启动时生效的设置来改）；等得最久的一次是 13 秒左右（`SH-11`，第 10 点）。45 这个数是从 Kubernetes 套件沿用的，没有对着真实的请求时长调过。在单机上它有两头：定得长，重启时新请求可能被拒绝得久；定得短，在途的请求会被切断。

### 6. 期望摘要可以在另一个容器里算出来

池里的网关经回读口报告的摘要，等于发布前另起一个容器加载同一份快照得到的摘要；那个容器用的是另一套证书。两边相等的条件与 Kubernetes 套件里看到的相同：算摘要时去掉 `config` 段（两边不同的项是 `dns`），并把证书正文换成占位。

发布器（Go）和这个脚本（Python）各自实现了这个算法。`SH-09` 里两边对同一个网关算出的摘要相同。

### 7. 网关解析配置文件之前，先拿环境变量替换正文里的 `$名字`

锁定的版本读到配置文件之后、解析之前，把整份正文过一遍替换（上游 `crates/agentgateway/src/types/local.rs` 的 `expand_env`，用的是 `shellexpand`）。用的是加载这份文件的那个进程的环境。替换在解析之前，所以不分键、值还是注释；上游为此专门绕开了自己那行写模式地址的注释。`SH-08` 里看到的：

| 正文里写的 | 网关拿到的 |
|---|---|
| `$HOSTNAME` | 这个环境变量的值（容器的主机名） |
| `${NO_SUCH_VARIABLE:-fallback}` | 没有这个变量，是 `fallback` |
| `$$HOSTNAME` | `$HOSTNAME`：`$$` 是字面的 `$` |
| `\$HOSTNAME` | 反斜杠加上环境变量的值：反斜杠不起转义的作用 |
| 后面不跟名字的 `$` | 原样 |
| `$NO_SUCH_VARIABLE` | 整份文件加载失败：`error looking key 'NO_SUCH_VARIABLE' up: environment variable not found` |
| `$SESSION_KEY` | 会话密钥 |

用例之外单独试过的：`${名字}` 同样被换；`$1` 被当成名字叫 `1` 的变量，没有这个变量，整份文件加载失败。

这对发布意味着三件事：

- **带这种写法的快照不是自成一体的。** 同一份文件，离线加载的容器里和池里的网关上可以是两份不同的配置，期望摘要就说明不了什么；也可以一边加载得了、另一边加载不了。
- **会话密钥可以被写进运行配置。** 会话密钥是经环境变量给网关的。快照里写一个 `$SESSION_KEY`，它就成了运行配置里的一个值，能读回读口的都读得到。
- **值里一个没有转义的 `$` 能让整份文件加载不了。** 正则替换里的 `$1` 就是。以后由 RouteIntent 编译出配置时，值里的 `$` 要写成 `$$`。

所以发布器拒绝正文里带这类引用的快照，结局是 `REFUSED`，不加载，也不碰池。它查的是正文的字面，比网关认的宽：`$` 后面跟着字母、数字、下划线、非 ASCII 字节或 `{` 的都算，`$$` 成对跳过。它只管得了经它发布的文件；它依据的是锁定版本的写法，换版本时要重新确认（`deploy/agentgateway/README.md`）。

### 8. 真的发布器对着真的网关

`SH-09` 到 `SH-11` 跑的是 `gateway-control`，对着前面的用例用的同一个池。它有三条命令：`publish` 发布一份快照，网关不重启（本点）；`reconcile` 对账（第 9 点）；`restart` 发布一份要重启网关才能全部生效的快照（第 10 点）。

`publish` 发布一份快照时依次做：

1. 正文里有对环境变量的引用：拒绝（第 7 点）。
2. 用同一个镜像另起一个临时容器加载这份快照，得到期望摘要。网关加载不了，或加载出来存储模式不是 `readOnly`：拒绝。
3. 经回读口读池里的网关。它上一次加载失败，或存储模式不是 `readOnly`：池不干净，不发布。它的构建与离线加载的不同：要重启，不发布。
4. 目录里放着的不是记录里的那一份（第 9 点）：池不干净，不发布，要先对账。只有一种情况它自己补得上：放着的正是要发布的这一份，网关也报告它在生效，这时只补记。
5. 这份快照的 `config` 段与池里的网关启动时的不同：要重启，不发布（第 4 点）。
6. 目录里已经是这份快照、网关也报告它在生效：什么都不写。否则把文件换上去（临时文件、落盘、改名），等网关经回读口报告期望摘要，然后把这一份记成这个池上最后一次得到确认的。
7. 没有生效（网关报告加载失败，或 10 秒内没有报告期望摘要）：把上一份放回去，再等网关报告它在跑的又是发布之前的那一份。

三条命令的结果都以 JSON 写到标准输出，退出码说明池现在的状态：

| 结局 | 退出码 | 哪条命令 | 池 |
|---|---|---|---|
| `ACTIVE` | 0 | `publish`、`restart` | 这份快照正在生效，并且记下来了 |
| `IN_SYNC` | 0 | `reconcile` | 就是记录的样子，什么都没有写 |
| `REFUSED`、`POOL_NOT_READY` | 3 | `publish`、`restart` | 没有被碰过 |
| `RESTART_REQUIRED` | 3 | `publish` | 没有被碰过 |
| `UNCONFIRMED` | 3 | `reconcile` | 没有可以拿来对的记录，什么都没做 |
| `RESTORED` | 4 | 三条都有 | 发布时：换上去过，没有生效，上一份已经放回去并得到确认。对账时：池和记录对不上，记录的那一份已经放回去并得到确认 |
| `UNKNOWN` | 5 | 三条都有 | 没能确认网关在跑的是哪一份。发布时：换上去过，没有生效，也没能确认放回去了。对账时：记录的那一份在目录里，却没能读到网关在跑它 |
| `RESTART_PENDING` | 6 | `reconcile` | 文件和运行配置都对得上，网关的启动设置却不是确认时的那一套；要重启（第 10 点） |
| 没有结局，出了错 | 1 | | 配置没有被动过，原因在标准错误上 |
| 没有结局，命令行写得不对 | 2 | | 什么都没做 |

`UNKNOWN` 不是成功也不是失败：先看网关是不是还在跑，再对一次账。

三轮里看到的（`SH-09`）：

- **发布一份新快照**：发布器用了 2.28、2.00、1.98 秒。其中要另起一个容器做离线加载；换上文件之后它至少等 1 秒才认读到的结果，因为网关攒 250 毫秒才重载，新旧两份的运行配置相同时，更早读到的"已生效"说明不了它加载过新文件。期间 486 个快请求和 26 个慢请求全部得到 200，网关没有重启。
- **一份离线加载得了、池里加载不了的快照**：它引用的一个文件只在离线加载那边的证书目录里有。发布器换上去，读到网关报告加载失败，把上一份放回去，前后用了 3.06、2.99、3.18 秒；这期间 546 个快请求和 30 个慢请求全部得到 200。它给的原因是池里的网关自己说的：`routes[4]: read resource file /work/tls/only-in-staging.crt at line 65 column 3`。离线加载通过不等于池里加载得了，兜底的是放回去这一步。
- **被叫停时先把上一份放回去**。脚本等发布器把一份没有毛病的快照换上去，立刻给它发 SIGTERM。它没有立刻退出：把上一份放回去，等网关报告在跑的又是发布之前的那一份，然后以 `RESTORED` 结束，原因写的是 `interrupted while waiting for the gateway: context canceled`。SIGINT 和 SIGHUP 走的是同一段代码；`publish` 上没有另发，`SH-11` 给 `restart` 发的是 SIGINT。
- **池不干净时它不动手**。脚本绕过发布器往目录里放了一份坏文件，网关正报告加载失败：发布器的结局是 `POOL_NOT_READY`，那份坏文件它没有动。把池收拾回来是 `reconcile` 的事（第 9 点）；这一条里是脚本自己把上一份放回去的。
- **同一个池同时只有一次发布**。晚到的那次以退出码 1 结束，什么都没做。互斥靠配置目录里的一个锁文件 `.config.yaml.lock`；它一直留在目录里，网关不受它影响。三条命令占的是同一把锁；实际跑过的是两次 `publish` 同时进行，别的组合只有单元测试。
- **用过之后不留东西**：临时容器不在了，放候选配置的目录是空的，配置目录里除了配置文件只有锁文件和记录。

### 9. 发布器死在半路：记录，和对账

发布器被叫停时会先把上一份放回去（第 8 点）；被强行杀掉（SIGKILL、断电、机器重启）时来不及。它要是死在换上文件之后，目录里留下的就是一份没有人确认过的文件：网关加载得了，池就在跑一份没人确认过的配置；加载不了，网关下次重启就起不来（第 2 点）。要收拾，先得知道该放着的是哪一份。

**记录。** 每次发布得到网关确认之后，发布器把配置目录里的一个文件 `.config.yaml.confirmed` 整份换掉（做法与换配置文件相同）。这个文件只有属主能读写，里面是：

- 得到确认的那份快照的全文和它的 SHA-256；
- 网关当时报告的运行配置摘要，和它的构建（版本、提交）；
- 网关当时的启动设置，也就是 `/config_dump` 的 `config` 段，除去随运行环境变的 `dns` 和工作线程数。每一项只记值的 SHA-256，不记值：对账只要知道它们变没变，而这些值有一部分取自网关进程的环境；
- 记下的时刻。

它和配置文件在同一个目录里，所以也只读地挂进了网关容器；里面除了快照的全文只有几个摘要。它是单机下发这一层自己的东西，只有最后一条，只说"这个目录里该放着哪一份"。它不是发布的记录：发布过哪些、谁批准的，不在这里。

第一次对一个还没有记录的池动手之前，`publish` 和 `restart` 先把当时放在那里的文件和网关当时报告的记成第一条，这一条不带启动设置。这样第一次发布做到一半死了，也知道该放回哪一份。记下的内容只有单元测试核对过。

有了记录：

- **`publish` 和 `restart` 动手之前先核对。** 目录里放着的不是记录的那一份（上一次发布没有做完，或者有人绕过发布器写了这个文件），它们不动手，结局是 `POOL_NOT_READY`，原因里说要先对账。
- **没做完的发布有两条出路。** 再发布同一份：放着的正是它、网关也报告它在生效，`publish` 只补记，不再写文件，结局 `ACTIVE`。或者对账，把它收回去。
- **`gateway-control reconcile` 对账**：拿记录去对池现在的样子。它不做离线加载，不用 docker；依据是记录，不是重新算出来的期望值。

| 目录里的文件 | 网关 | 对账做什么 | 结局 |
|---|---|---|---|
| 是记录的那一份 | 报告在跑的是它 | 什么都不写 | `IN_SYNC` |
| 不是记录的那一份，或者没有文件 | 不论报告什么，读不到也一样 | 把记录的那一份放回去，等网关报告在跑的是它 | `RESTORED`；等不到是 `UNKNOWN` |
| 是记录的那一份 | 报告上一次加载失败，或者在跑的不是它 | 再放一次：换文件会让网关重新加载。等法同上 | 同上 |
| 是记录的那一份 | 读不到 | 不写，等到时限 | 读到了按上面几行办；一直读不到是 `UNKNOWN` |
| 是记录的那一份 | 报告加载成功，但构建不是做记录时的那个 | 什么都不做：摘要里有版本，两个构建的没法比 | `UNCONFIRMED` |
| 没有记录 | | 什么都不做 | `UNCONFIRMED` |

文件和运行配置对上之后（本来就对上的，和放回去之后对上的都算），它再比启动设置。不是确认时的那一套，说明网关带着别的文件重启过：结局改成 `RESTART_PENDING`，列出不同的项。对账自己不重启网关，也不启动网关。

三轮里看到的（`SH-10`；最后一条在 `SH-11`）：

- **池就是记录的样子**：0.01 秒，`IN_SYNC`，文件没有被重写。
- **发布器刚把一份没有毛病的快照换上去就被 SIGKILL**。文件留在那里，网关加载了它，新路由已经在答话；记录里仍是上一份。这时发布另一份：`POOL_NOT_READY`，文件它没有动。对账：把记录的那一份放回去，1.07、1.06、1.06 秒之后以 `RESTORED` 结束（其中 1 秒是换上文件之后至少要等的），没有人确认过的那条路由没有了。期间 426 个快请求和 24 个慢请求全部得到 200，网关没有重启。
- **同样被杀掉之后，把同一份快照再发布一次**：`ACTIVE`，文件没有再写，记录跟上了。
- **有人绕过发布器放了一份网关加载不了的文件**：对账把记录的那一份放回去，`RESTORED`，原因里带着网关自己说的那句话。
- **有人把配置文件删了**：网关不退出，报告 ``failed to read from file `config/config.yaml`: No such file or directory (os error 2)``，继续跑原来那份。对账把文件放回去，`RESTORED`。文件被删过之后网关仍然看得到它变了：之后的发布照常生效。
- **发布器在离线加载时被 SIGKILL**：留下一个临时容器和一个放候选配置的目录；池没有被碰过，对账是 `IN_SYNC`。下一次发布先把这两样清掉，照常成功。
- **网关带着一份坏文件重启，起不来**（坏文件是脚本放的，网关容器是脚本重启的）。这时对账：记录的那一份放回去了，可是读不到网关，等满时限（这一次设的是 3 秒），结局是 `UNKNOWN`。再对一次：文件已经是对的，它不再写，等满时限，仍是 `UNKNOWN`。脚本把网关容器起起来之后，网关读到的是放回去的那一份，对账是 `IN_SYNC`。
- **带重启的发布做到一半被 SIGKILL**：对账之后是 `RESTART_PENDING`，见第 10 点。

要知道的：

- **没有谁会自动去对账。** `gateway-control` 是一条命令，不是常驻的服务。发布器被强行杀掉之后、机器重启之后，要有人或者定时任务来跑 `reconcile`。在那之前，`publish` 和 `restart` 会拒绝动手，但留在目录里的仍是那份没人确认过的文件。
- **对账会把绕过发布器的改动收回去。** 这是它的本意：这个目录只有发布器写。
- **对账不启动网关，也不重启网关。** 网关没有在跑时它只管把文件放对。
- **记录读不成样子时三条命令都停下来。** 文件坏了，或者是更新的版本写的格式：退出码 1，什么都不做，要人来看。只有单元测试。
- **记录跟着配置目录走。** 目录没了，记录也没了；这时对账是 `UNCONFIRMED`，下一次发布把当时放在那里的当成起点。

### 10. 带重启的发布：先换文件，网关加载得了再重启

`config` 段与网关启动时不同的快照，换文件不能全部生效（第 4 点），`publish` 只报告 `RESTART_REQUIRED`。发布这种快照用 `gateway-control restart`。重启会让这个池中断（第 5 点），所以它是单独的一条命令，什么时候做由人定。

它依次做：

1. `publish` 前四步的检查，只是没有"补记"那个例外：放着的不是记录的那一份，一律先对账。另有两种情况也拒绝：这份快照的 `config` 段与网关启动时的相同，用不着重启，让改用 `publish`；池里跑的是另一个构建，重启换不了镜像。
2. 核对 `--container` 指的那个容器：它在跑，并且把这个池的配置目录挂在网关读配置的位置上。不是，就什么都不做，退出码 1。
3. 把文件换上去，等网关报告期望摘要。这一步网关不重启，快照里启动设置之外的部分已经生效。网关加载不了：把上一份放回去，结局 `RESTORED`，不重启。先换文件再重启，为的是不拿一份池里加载不了的文件去重启网关：那样它起不来。
4. 重启网关容器（`docker restart`）。docker 先发终止信号，网关把在途的请求做完再退出，最多等到容器的停止时限。
5. 等网关报告：在跑的是这份快照，`config` 段也是离线加载时的那一套。然后记下这一份，结局 `ACTIVE`。
6. 时限内没有等到：把上一份放回去，再重启一次，等网关带着上一份的设置起来，结局 `RESTORED`；仍等不到是 `UNKNOWN`。

不给 `--snapshot` 时，重启用的是记录里的那一份：对账报告 `RESTART_PENDING` 之后要做的就是这个。

被叫停（SIGINT、SIGTERM、SIGHUP）时：还没重启的，把上一份放回去，不重启；重启一旦开始就做完。网关停到一半没人管，或者带着新设置起来了却没人确认，都比多等几秒糟。

三轮里看到的（`SH-11`）：

- **一次带重启的发布**：发布器用了 4.27、4.27、4.30 秒（离线加载；换上文件之后等 1 秒；重启；重启之后再等 1 秒）。重启时有两个各还剩 1 秒左右的在途请求，都做完了；每秒 20 个的快请求里 23、21、18 个得到 502，前后 1 秒左右，与脚本自己重启网关时量到的相同（第 5 点）。网关换了一个进程，还是那个容器；`front` 没有动。
- **重启途中按 Ctrl-C**。终端上的 Ctrl-C 是发给整个前台进程组的，所以发布器让 `docker restart` 自成一个进程组，信号到不了它。脚本给发布器所在的进程组发 SIGINT，那时网关正在等一个还要 13 秒左右才做完的请求（这个请求从 `front` 的容器里直接发给网关，不经 nginx：nginx 等后端最多 10 秒）。看到的：那个进程组里只有发布器；发布器做完才退出（前后 16.23、16.98、16.53 秒），结局 `ACTIVE`；docker 对网关容器只做了一次重启，没有强杀；那个请求 14 秒后得到 200。docker 等了 13 秒，超过它默认的 10 秒：不给时限时，它用的是容器自己设的停止时限，这里是 60 秒。  
  对照（跑了一遍）：把"自成一个进程组"那一行去掉，docker 命令行和发布器一起收到了信号。命令行退出了，守护进程照样把那次重启做完；发布器却当成重启失败，把上一份放回去并又发了一次重启，结局成了 `RESTORED`：一次本来会成功的发布被收了回去。
- **用不着重启的快照，池里加载不了的快照，指错了容器**：分别是 `REFUSED`、`RESTORED`（没有重启）、退出码 1。这三次网关都没有重启。
- **docker 刚把网关重新起来，发布器就被 SIGKILL**：文件是新的，网关已经带着新设置起来，记录里仍是上一份。对账把记录的那一份放回去，路由回到了那一份，启动设置却还是新的：结局 `RESTART_PENDING`，退出码 6，列出了那一项。不给快照的 `restart` 再重启一次：文件不用再换，结局 `ACTIVE`，启动设置回来了，之后对账是 `IN_SYNC`。这是把它收回去。要把它做完，就拿同一份快照再 `publish` 一次：网关已经带着新设置起来了，只差补记。后一条路在真的网关上只对不用重启的快照走过（`SH-10`）。
- **一份离线加载得了、网关拿它却起不来的快照**。它把指标端口设成了 `front` 占着的那个。离线加载的容器里没有 `front`，加载得了；池里的网关换上文件时也报告加载成功，因为启动设置这时不生效；重启之后它起不来，自己说的是 `Error: stats server starts` 和 `Address already in use (os error 98)`。发布器读不到网关，等满时限（这一次设的是 5 秒，默认 10 秒），把上一份放回去再重启一次，网关回来了，结局 `RESTORED`，前后 9.36、8.44、8.54 秒。docker 的事件里是两次重启，中间网关自己退出了一次。从第一次重启到网关回来，这个池是断的。

要知道的：

- **离线加载和换文件都通过，仍不等于重启之后起得来。** 启动设置只在启动时生效，离线加载的容器又不是池的环境。兜底的是重启之后的回读和放回去再重启，代价是多中断一阵。
- **中断多久取决于在途的请求**（第 5 点），最长到网关的 `connectionTerminationDeadline` 和容器的停止时限里短的那个。容器的停止时限更短时，到时 docker 直接杀掉网关，在途的请求被切断；这种情况没有测。`--stop-timeout` 可以另给一个停止时限，只有单元测试。
- **docker 的两样行为只在 29.8.1 上看过**：不给时限时用容器自己设的停止时限；命令行中途被杀掉，守护进程照样把重启做完。
- **容器没有重启策略。** 有重启策略时，网关起不来 docker 会自己反复去起它，发布器这时的表现没有测。

三条命令里没有在真的网关上走到的分支，只有单元测试（`internal/gatewayconfig`、`cmd/gateway-control`）：

- 离线加载出来的、或池里的网关报告的存储模式不是 `readOnly`；池里的构建与离线加载的不同。
- 发布或重启没有生效，放回上一份之后仍然对不上（`UNKNOWN`）；得到了确认却记不下来。
- 第一次动一个没有记录的池时记下的第一条；记录损坏，或者是别的格式。
- 对账时没有记录，或者网关换过构建（`UNCONFIRMED`）；文件是对的，网关在跑的却不是它；放回去时写不进去。
- 目录里已经是这份快照、网关却没有在跑它时的 `restart`；重启的命令返回了，答话的还是旧进程。

## 没有覆盖的

- 发布器的几个只有单元测试的分支（见第 10 点末尾）。
- 谁来跑对账，什么时候跑。机器重启之后先对账、再让网关收请求，这个顺序现在没有东西保证。
- 发布器在哪里、以什么身份运行。它要用 docker 命令起临时容器、重启网关容器；这里它和网关是同一个本机用户，两者不同时文件的属主和权限怎么定没有测。`restart` 核对容器的挂载时比的是 docker 报告的路径，发布器要是跑在容器里，两边的路径不一样。发布器的证书怎么签发和轮换没有设计。
- 离线加载那边挂哪个证书目录。挂池的那个，两边引用的文件一致，但临时容器也拿到了池的私钥；另备一套，就可能出现 `SH-09` 里"离线加载得了、池里加载不了"的情况。
- 带 JWT、ExtAuthZ 和真实 PDP 的配置。JWKS 随快照下发也没有在这里跑：这里的快照只有一个配置文件，多个文件怎么一起换没有测。
- 主机重启或 docker 重启之后容器会不会自己起来；有重启策略的容器上，带重启的发布失败之后是什么样。`compose.yml` 里没有写重启策略。
- 长连接和流。这里最长的请求是 14 秒；SSE、gRPC 流、WebSocket 在重启时会怎样没有测，在途的请求超过终止时限或容器的停止时限时会怎样也没有测。
- 换镜像（升级 agentgateway）。换了构建之后记录要重新做一次（把同一份快照再发布一次），这一步只有单元测试。
- 证书轮换。
- 别的挂载方式。测的是 WSL2 里本机 ext4 上的目录直接挂载；Docker Desktop 的文件共享、网络文件系统、命名卷都没有测，文件变化的通知在那些上面不一定一样。
- 一台机器上的多个池，池之间的隔离。每个池要有自己的临时容器名字、端口和放候选配置的目录；两个池共用时会怎样没有测。
- 别的 docker 版本；arm64。
