0. 执行结论

本项目不是自研通用代理引擎，而是以 agentgateway 开源数据面为首选候选，为多个 IDP 产品建设可审计的 Ingress / Egress / AI Gateway 部署与配置能力。Gatekeeper 是内部身份、第三方账户授权和外部凭证治理权威；API Fabric 拥有 API 契约与治理发布权；Gateway 为访问策略执行点（PEP）；领域上下文保留对象级授权、业务状态、Port/ACL。

1. 使用者、边界与流程

使用者：内部业务产品服务账户、外部 API 客户、开发者、平台运维、安全管理员、API Fabric 审批人与 Gatekeeper 凭证管理员。实际人工 UI 不在本期必交范围；同版增补的 Gateway Console 原型与 75 条 UX 用例已使 STD-CP4 适用（Manifest user_interface=true），其扩展在 P1 PoC 结论落地前冻结，见 governance/README.md。

网络信任域：公网入口、内部业务入口、内部第三方出口、AI 入口、控制面与密钥域独立定义。一个统一产品名称或配置标准不意味着单一公共故障域。内部服务间通信不默认强制经中心网关；如组织决定全部强制走 Internal Gateway，须另补服务拓扑、延迟预算、容灾和可用性 ADR。

MVP 请求生命周期：应用携带 Gatekeeper 信任域签发的服务身份，调用受管理的 Egress 逻辑路径；网关验证 JWT 和请求级授权；可选凭证适配从获授权账户生成外发凭证；仅向已登记 upstream 透传请求；领域 ACL 将提供商响应翻译成内部结果。非幂等操作不会被代理层盲目自动重试。

非目标：BIP/ESB、EDI/SFTP 编排、跨系统业务映射、Workflow Engine、商业化 API 订阅计费、通用 Service Mesh、独立 IAM/IdP、业务领域对象授权、替代 Fabric、重写 agentgateway Rust 核心。

GW-FR-047 MUST 第三方账户授权撤销与缓存失效遵守高风险时限 撤销跨实例生效与 Gatekeeper 断连 fail-closed 可测

6. Gateway Operations UI/UX 范围补充（G01 · V1.0 同版更新）

本项目需要 IDP Internal Engineering Portal 下的轻量 Gateway Operations 模块，不新增独立 Gateway Portal。其六个页面：Dashboard、API Routes、Access Policies、Traffic Explorer、Config Releases、Gateway Instances。权威职责：路由由 Gateway 发布投影提供，授权由 Gatekeeper 提供，契约发布由 Fabric 提供，Trace 由遥测平台提供。

  • GW-UX-001～006：六个核心管理视图的只读展示、检索、筛选、健康和变化审计；统计必须标注来源、环境、时间窗及数据新鲜度。
  • GW-UX-007～012：角色矩阵、审批与部署职责分离、配置只读对比及安全操作；不能通过 UI 直接绕过策略审批和 Gatekeeper 权威。
  • GW-UX-013～020：租户与账户权限投影、脱敏 Trace、故障状态、空值/超时/过期状态、禁用明文凭证。
  • GW-UX-021～030：受控实例运维、生产状态回读、审计、可访问性、安全回归与响应式交互。

设计规格：Gateway Operations UX Spec；原型：离线 18 页统一 Console 演示；75 条 UX 验收矩阵：CSV。现有 50 FR / 19 NFR 有对应追溯，全部正式运行验收 NOT_RUN；UX 补充作为单独追溯域，不得宣称完成正式验收。

同版设计增补：统一 Gateway Console

附加需求：对照 agentgateway 官方开源 UI 提供单一入口，覆盖 Traffic、LLM、MCP、Tools；围绕第三方 API 接入、权限、凭证引用、发布和故障处置提供业务意图引导；不引入另一个可绕过发布流程的生产配置编辑器。

详情参见 portal/spec/Agentgateway_UI_Capability_Matrix_V1.0.md（自本工程根目录）。

同版增补：可诊断的第三方 API 调用（Message Inspector）

Gateway Operations 对外部第三方 API 不得只展示状态码与 Trace ID。用户能够在权限范围内依据同一 Trace 对照：客户端入站、Gateway 完成认证/路由转换后的外发请求、第三方返回、Gateway 下游返回。要求 Header 与 Body 默认不保存敏感原文，提供脱敏样例及可观测性完整度标识；对于未捕获或无法还原阶段必须明确标识。403/401 的 NOT_SENT 与 504 写操作的 UNKNOWN 是 P0 诊断能力。本项作为现有观测/安全需求的细化要求，正式编号与 FR 追溯需由需求负责人审核，不可假定原 50 FR 已全部覆盖新增实现。对应正式 UX 用例 GW-UX-AT-055..062 均 NOT_RUN。

7. 生产阻断缺口的正式需求收敛（V1.0 同版）

最小交付能力与非目标：

  1. 运行时核心：真实 JWT/ExtAuthZ、出站安全、健康/熔断/连接保护、账户配额、受控发布、四阶段诊断是生产门槛。原型演示和离线校验不等于真实代理行为。
  2. 合同面：Ingress/Egress/AI 独立判定；contracts/gateway/route-intent.schema.json 为中立意图，原生 agentgateway 配置须使用固定版本 Schema 和二进制独立验证。
  3. 身份面：Gatekeeper 仍是身份、第三方账户与授权权威；Credential Broker 只将最小短时用途材料交给经过认证的网关工作负载。
  4. 流量面：ProviderAccount 配额和并发隔离是共享出站账户的 MUST；精确全局配额必须验证所选协调器与第三方计费/限额边界，不得把本地桶称为全局精确。
  5. 用户体验：Console 应提供“配置/授权/流量/报文/发布”关联诊断，但生产配置写入仍由唯一受控 Publisher 管理；原生 UI 保留受控排障能力。

Message Inspector：请求与响应配对验收边界

Gateway Console 的一次 Trace 必须按客户端 ↔ Gateway及Gateway ↔ 上游两条通信链路呈现对应 Request/Response 四个观察点，而不是只查看响应或只查看单侧流水。每个观测报文分别显示 Method / Request Target / HTTP Version（请求）、Status / gRPC Status（响应）、Headers / Metadata、Body 样本、捕获状态、脱敏状态、截断标记、大小、Trace ID 与关联请求 ID。

  • 401/403/429 前置拒绝：标记 NOT_SENT，上游响应为 NOT_OBSERVED/NOT_REACHED，不得捏造第三方响应。
  • 504：必须区分 Gateway 生成的下游 504 与未观测到的上游响应；针对可能已发出并产生副作用的写操作，业务结果为 UNKNOWN，不可自动重试。
  • 支持上下游 Request 的路径/Header 变化对照与上游/下游 Response 的状态、错误结构变化对照；不得泄露注入的凭证。
  • 正文采集默认关闭，仅按经审批策略启用；未捕获、无正文、采集失败、因策略禁止和截断属于不同状态，不可混用。
  • 原型使用合成脱敏数据；正式上线须经过服务端 Gatekeeper 授权、租户范围校验、采集时脱敏、审计及负载测试。

0. 不可混淆的三个平面

  • Governance Plane — IDP API Fabric：Provider/Consumer API Catalog、不可变契约版本、Release/PublicationSlot、审核与门户，不参与正常 API 请求转发。Fabric 的 PublicationSlot = Target × APIAsset 不等于 Gateway 的路由资源；必须通过明确的绑定关系和受控发布适配。

4. 三条流量路径

A 公网 Ingress：Client → WAF/Edge（按需）→ Ingress agentgateway Pool → CargoPai / Parcel API；验证来自 Gatekeeper 的身份；产品保留业务授权。不能把“查看 API 文档”的 Grant 直接当成生产调用权限。

B 内部 Egress：Product Port/ACL → Egress agentgateway Pool → Provider API；Gateway 只代理已登记的 Provider/Operation，并与 Gatekeeper 的 Credential Broker 协作。对于非 HTTP 协议需经产品特定 Connector 或网络出口策略；不是所有 TCP/EDI/SFTP 都必须通过这条路径。

C AI traffic：TELOS HOST/Execution → AI agentgateway Pool → Model/MCP/A2A；Agent 执行/Tool 审批由 TELOS 或对应领域负责，不依赖 Gateway 自己完成所有 AI 授权。

D 内部服务间调用（不是以上三条）：按信任域使用 mTLS / 服务身份及端到端授权。需要统一服务流量治理时可另立 Internal Gateway 池的明确决议，而不是悄然将所有内部流量导向 Egress。

5. 部署拓扑、故障域和环境

  • 独立 ingress-prod、egress-prod、ai-prod 以及相应 Test/Dev；每池多副本、独立凭证和网络访问规则。
  • 内部 Egress 仅开放受认证的内网入口；其出站网络设置应限制上游域名及目标 IP/端口。各区域采用各自负载均衡，非全局统一单实例。
  • 生产变更必须固定 agentgateway 镜像 digest、外部授权服务版本与配置摘要，先在隔离池预发布再逐步提升流量。
  • 网络上只能访问批准的第三方 Upstream 或内部受控服务；对于重定向、DNS 重绑定、内网 IP 与 IPv6 映射必须跨应用及网络层验证。
  • Runtime 可使用最后一份有效且未被安全撤销的配置继续服务，但动态强制授权缺失时仍按风险策略拒绝，不用“配置可用”推导“授权可用”。

6. 技术拓扑及协议约束

agentgateway 1.7.x 官方提供 HTTP/TCP 路由、JWT/JWKS、ExtAuthZ、Backend Authentication、HTTP CONNECT Egress、LLM/MCP/A2A 等能力。技术功能存在 ≠ 在我们选定部署形态下完成验证。不同安全模型必须按协议逐项实测：

  • 显式 L7 HTTP Routing：代理能够处理方法/路径/Header、Header 清洗/受控上游 Token 注入，是第三方账户委托访问的默认候选。
  • CONNECT Tunnel：在保持 TLS 端到端加密时不具备完整 HTTP 报文可见性；不能承诺执行任意 Header 注入或 URI 级 API 权限。官方说明 Tunnel/Route 模式应用策略不同，需要分别测试。
  • gRPC：跨协议元数据、流式行为、状态码、限流、授权在所选 agentgateway 版本和入口模式下执行实测，不能将 REST 测试等价为 gRPC 通过。

G03 — 路由、配置发布与流量策略治理

0. 设计目标与系统事实

统一地址不是开放代理：业务产品调用逻辑入口 https://egress-api.idp.internal/providers/{provider}/...（规划占位），Router 查找已登记 Provider Operation；任何用户输入目标 URL、Host、IP、端口的接口都不纳入 MVP。地址仅是名字空间，绝不能由字符串拼接推导上游 URL。

单一配置事实权威：Gateway 的正式 Desired Snapshot 由受控 Gateway Config/Publisher 持有，引用 Fabric 的批准记录。运行时 agentgateway 的观察状态仅是 Applied/Observed Evidence，不是另一个可变批准源。Fabric API Catalog 的文档可见性不自动转换为运行时 Route 可用性。

2. 路由解析规则

Ingress：按域名、已批准路径、方法、可选 Header 及权重匹配，不允许公共路径吞并内部管理路由；先 TLS/客户端验证，再授权、再请求转发。API 请求对业务对象的最终权限在业务服务验证。

Egress：按 provider_id + operation_id + environment 解析固定 Upstream；账户标识由 Gateway 可信上下文和 Gatekeeper 授权解析。Provider Account 可不出现在 URL；若出现，也只是申请使用的 ID，必须重新授权。任何主机名替换、跨环境或重定向改变目的地都需重新匹配允许目标。

AI：TELOS 流量使用独立网关实例和独立策略；MCP/A2A 版本、安全握手和 Tool 访问权限不得用 REST 通用授权替代。

3. 配置发布状态机

DRAFT → VALIDATED → APPROVED → STAGED → APPLYING → OBSERVING → ACTIVE
  │        │          │         │         │          │           │
  └─REJECTED / CANCELED   └──FAILED / PARTIAL / UNKNOWN──RECONCILE/ROLLBACK
ACTIVE → WITHDRAW_REQUESTED → REVOKING → REVOKED
ACTIVE → SUPERSEDED（被更新的 ACTIVE 发布取代，含回滚发布）

状态语义：

  • APPROVED 是授权发布的事实，不意味着 agentgateway 已接收配置。
  • STAGED 表示已生成目标版本且签名/静态检查通过，并非已生效。
  • APPLYING 向目标池开始发布，部分实例成功时记录 PARTIAL。
  • OBSERVING 各实例回读摘要和健康；在所有预期实例达到规定健康策略前不标 ACTIVE。
  • ACTIVE 必须包含 snapshot_digest、已完成的观察证据和目标池集合。
  • ROLLBACK 创建新受控事件，指向上一个已批准有效 Snapshot；不得静默篡改历史。
  • 凭证撤销属于独立安全状态，不能因为旧路由配置仍有效就允许访问被撤销账户。

4. 发布算法与并发一致性

  1. Fabric 发出具名已批准 RoutePublicationIntent：信封携带 idempotency_key/release_ref/target_id，内嵌的 intent（RouteIntent）携带 approval_ref/expected_generation 与 API 资产引用（api_asset_ref 或 contract_ref）；契约见 contracts/fabric/route-publication-intent.openapi.yaml。
  2. Gateway Publisher 服务端复核调用主体权限、来源和签名/可信通道，不把任意客户端的 Approval Flag 当权威事实。
  3. 将结构化意图与受控策略仓库合成完整 Snapshot；校验引用存在、上游目标白名单、TLS 要求、JWT 绑定、Header 策略及敏感字段。
  4. 产生确定性内容摘要，采用 CAS/乐观版本切换 Desired Generation；保存不可变制品和审计。
  5. 先在受限 canary pool 验证，再按批次应用到副本；记录 deployment_id, instance_id, desired_digest, observed_digest, health, apply_time。
  6. 健康与一致性条件满足才标 ACTIVE。超时不认定失败或成功，标记 UNKNOWN 后 Reconcile。
  7. 对安全严重变更（撤销、Block）即刻触发拒绝策略/隔离，不应等待普通发布慢速最终一致；若达不到撤销窗口，阻断影响范围。

一致性：跨 Fabric/Gateway/Secret Manager 不宣称单事务 Exactly Once。使用幂等命令 + 乐观版本 + Outbox/持久工作队列 + 对账，补偿不能伪造已发生的外部请求从未发生。

5. Header、URI 与转发契约

入站允许：仅按提供商允许的 HTTP Headers 传播 Content-Type、业务 Idempotency-Key 等；Traceparent 保持关联但清洗不受信任的 Baggage；禁止将 Authorization（IDP JWT）、Cookie、X-Forwarded-* 等未经边界验证的身份标头传给第三方。

出站生成：Provider Access Token 或签名只能由通过授权的 Credential Broker / Gateway 可信组件附加。Host/:authority/SNI 严格匹配批准上游，防止 Host header injection。第三方响应中的 Set-Cookie、跳转和 Hop-by-Hop Header 按 API 契约单独处理，不可无条件向业务客户端暴露。

URI 改写：逻辑 URI 与 Provider URI 的映射属于配置策略；Path 编码、百分号、双斜线、点段、尾斜线、Query 重复键都必须有负向用例。任何上游重定向不允许绕过原目的地验证。

写操作：禁止 Gateway 默认对 POST/PATCH 以及其他无幂等保证操作进行自动重试；允许 Idempotency-Key 只代表业务协议和提供商确实支持，不能因 Header 存在就认定安全。

6. 限流、熔断与实时授权策略

按 pool → provider → provider_account → tenant/service → operation 定义配额域。全局限流依赖专门协调服务时，必须验证多副本一致性和协调器故障行为；本地限流不可被标记为全局精确配额。429 必须明确来源（Gateway/Provider），勿把供应商余额和内部配额混为一谈。对 ExtAuthZ 高风险操作以 fail-closed 为默认；读取缓存允许使用时间窗必须由安全负责人批准，且缓存键包含全部授权输入。

10.1 真实发布流水线强制阶段

  1. 读取已批准、具名、具权限的 Intent；CAS 校验 expected_generation。
  2. 预检模型与引用、上游网络许可和租户权限；拒绝重叠路由或不确定优先级。
  3. 使用固定版本映射器编译到 agentgateway native config；由其对应版本 Schema + CLI + 启动检查执行真实兼容性校验。
  4. 构建包含镜像 digest/原生配置 hash/策略版本/审批 ID 的不可变签名 Snapshot。
  5. Canary → 分批发布 → 实例回读与健康判定；不能以“写入配置文件成功”代表已生效。
  6. 部分失败记录真实副本清单和 PARTIAL；回滚仅指向先前已批准快照，仍需再次观察健康及授权拒绝效果。
  7. 安全撤销、强制封禁与正常配置发布分开：最迟生效时限和失败策略必须具名批准。

10.2 ProviderAccount 流量与健康策略（正式设计）

gateway/policies/traffic-policy.schema.json 规定配额维度、协调方式、超时、并发、连接和熔断意图。运维应看到 gateway_429 与 provider_429 不同来源。

  • 单 ProviderAccount 的共享额度，应按账户硬上限与各租户/应用子配额同时判断；对全局一致性有要求的场景使用经验证的协调器。
  • 协调器不可用，必须按配置明确 REJECT 或保守本地上限，绝不无上限放行。
  • 针对供应商返回 429，应读取和验证合法的 Retry-After/配额响应；不应把本地限流机制假称供应商配额权威。
  • 熔断/健康检查必须区分连接错误与正常业务 4xx；不得因正常权限拒绝触发整家供应商下线。
  • 写操作重试一律须业务幂等和供应商契约批准，不得因 Gateway timeout 自动重放。

10.3 协议兼容矩阵

参考 tests/protocol-compatibility.csv，各能力的执行状态初始为 NOT_RUN。对 gRPC 需测 HTTP/2、unary、client/server/bidi streams、metadata/trailer/status；对 HTTP 测 chunked、SSE、二进制、大包、HEAD/OPTIONS、路径规范化和编码；超时取消和连接清理亦需验证。支持清单应随 agentgateway 镜像 digest 固定。

请求 / 响应映射的证据和变更边界

每次受管 L7 代理调用视作两个逻辑通信 Hop：Caller ↔ Gateway 与 Gateway ↔ Upstream。Gateway 能够改变外发 Request 的目标路径、Host、Header、认证材料，以及返回给 Caller 的 Response 状态、Header 和错误体。因此仅展示“第三方 HTTP 200”不足以判断客户端是否收到了 HTTP 200；两条 Hop 必须分别呈现 Request 与 Response，并在单一 Trace 下关联。

  • 采集阶段必须声明是转换前还是转换后的报文；请求签名、凭证注入、编码与代理转码的顺序必须通过固定 agentgateway 版本的真实 PoC 验证。
  • NOT_SENT 表示网关确认未进行上游发送；NOT_OBSERVED 仅表示观测不到响应，不等于上游业务未执行。
  • 路径重写、敏感 Header 删除、Provider Request ID 与客户端 Correlation ID 应形成脱敏差异摘要。不能从默认 Access Log 推导原始 Request/Response Body。
  • 对响应改写必须保留业务领域的解释权：Gateway 允许协议/安全错误规范化，领域 ACL 负责业务语义和幂等恢复。
G04 / 信任与安全

G04 — 统一认证、第三方凭证治理与多租户安全

编号 G04 · Identity, Authorization, Credential Security · 版本 V1.0 · 状态 DESIGN_DRAFT / Threat Model Proposed / PenTest NOT_RUN
重大约束 Gatekeeper 为身份与授权权威；Secret Manager 管密钥材料；agentgateway 为 PEP 和可信上游认证执行点，不是任意第三方 Token 的发行方。

0. 核心安全判定

三道不可混淆的判定：

  1. Caller Authentication：IDP Workload/外部客户端是谁？JWT/JWKS/mTLS 校验证书及信任发行方、audience、有效期、算法等。
  2. Access Authorization：这个 Caller 能否对指定租户、Provider、Account、Operation、Environment 发出请求？由 Gatekeeper PDP 判定，Gateway 执行。
  3. Upstream Authentication：外部 Provider 如何认可我们？API Key、OAuth Client Credentials、授权码 Token、HMAC、mTLS、签名等由其自己定义；Gatekeeper Credential Broker 管理可用授权凭证，Gateway 按经批准的模式使用。

禁止的捷径：仅验证 IDP JWT 就放行全部 Provider；相信 X-Account-ID 或 X-Tenant-ID 作为授权事实；把内部 IDP JWT 原样传给 FedEx；把第三方 Secret 广泛下发给每个业务服务。

1. 信任域与参与主体

2. Gatekeeper 最小扩展模型

候选逻辑对象：

ExternalProvider(provider_id, auth_mode, issuer?, environment_profiles)
ProviderAccount(account_id, provider_id, tenant_id, environment, status)
CredentialReference(credential_id, account_id, secret_ref, version, rotated_at)
ExternalAccessGrant(grant_id, principal_id, tenant_id, provider_id, account_id,
                    operation_ids, scopes, valid_from, valid_to, status)
TokenLease(lease_id, account_id, oauth_client_id, audience, scope_set,
           token_fingerprint, expires_at, refreshed_at)
  • ProviderAccount 和 CredentialReference 明确分离；secret_ref 是安全存储引用而非密钥明文。

  • TokenLease 是受控缓存事实，不是 Provider 的权威授权状态；撤销后不能因为 Lease 未到期就忽略撤销策略。
  • 对外展示只能是脱敏账户元数据（后四位/别名），不暴露 Bearer Token、客户端密钥和私钥。
  • 不同客户共用同一物理 Provider 账户时必须明确共享授权合同边界，不得默认跨租户共享。

3. 判定函数与策略

ALLOW = TrustedCaller ∧ AudienceValid ∧ TenantBound ∧ ActiveGrant ∧
        ProviderAccountActive ∧ EnvironmentMatch ∧ OperationAllowed ∧
        RouteAllowlisted ∧ CredentialAllowed ∧ NoExplicitDeny

UNKNOWN / INDETERMINATE 对于凭证使用、非幂等操作、客户隐私 API 均拒绝。统一鉴权优先在 Gateway 前端执行，并在选定上游后必要时做 Backend-level ExtAuthZ 以限定上游账户。不得仅因为 ExtAuthZ 允许，就在上游路由改变后继续使用前一账户的 Token。

AuthZ 输入来源：principal 只能来自已验签身份与可信服务间通道，tenant/account/operation 由 Route Registry、令牌绑定和 Broker 的权威数据共同求得；若 Adapter 提交 account_id，视为待校验申请而非事实。scope 必须满足实际目标 API 的最小权限，不得由调用方任意提权。

授权缓存：如果采用 Envoy gRPC extAuthz 缓存，官方特别提醒缓存 Key 包含全部决策使用的属性；Token、租户、目标账户、路由、操作、环境、策略版本、撤销代次都应评估。高风险请求初期关闭跨请求决策缓存或采用极短有效期并验证撤销传播。HTTP ExtAuthZ 与 gRPC ExtAuthZ 缓存能力不相同。

4. 第三方凭证与 Token 生命周期

Client Credentials：Gateway / Broker 使用相应 Provider 授予的 OAuth Client 认证并从该 Provider 获取 Access Token；不能把内部 JWT 直接交换成第三方 Token，除非第三方正式支持 RFC 8693 Token Exchange 或其他指定授权协议。Token 缓存键至少包含 Provider × Account × Environment × Client × Scope/Audience × Secret Version；并发刷新采用 Singleflight/租约，失败不得复用已撤销的 Token。

API Key：存储在 Secret Manager；受控 Broker 或 Gateway BackendAuth 引用，不可写入 URI 或普通日志。固定配置内 Key 适合单账户固定路由，不自动解决多租户动态凭证选择。

HMAC / 签名：某些 Provider 要求对时间戳、路径、Body 签名。HTTP 代理在路由/重写之后才可能签名最终字节；不允许错误使用改变 Body 后的原签名。需要专用 Provider Signer 时可部署受限 Go 签名适配器，不将任意代码执行机制放入 Gateway 核心。

mTLS：客户端与 Gateway、Gateway 与 Provider、Gateway 与 Gatekeeper 是三条不同的 TLS 信任链。证书和私钥保存在独立安全目录/Secret Manager，定期轮换并演练吊销。

Credential Broker 返回模式（需 PoC 比较）：

  • 模式 A：Gatekeeper 经可信 ExtAuthZ 返回受限 Header 注入信息（可能包含短期 Provider Token）。只允许 Gateway 授权通道处理，必须禁止日志泄密并验证缓存风险。
  • 模式 B：Gateway 通过受限本地 Broker/Sidecar 获取 Token 并注入，减少网络传播面，但增加独立部署和通信契约。
  • 模式 C：固定 Secret 引用通过 agentgateway BackendAuth；适合固定账户，不适合动态租户账户。
  • P1 PoC 结果（agentgateway 1.6.0 与 1.7.0 + Mock Gatekeeper/Provider，非正式验收）：模式 A 经 HTTP ExtAuthZ 响应头注入跑通并做到双租户账户隔离，网关到 PDP 为工作负载 mTLS；模式 B 用 Mock 本地 Broker 跑通，隔离相同，代价是多一个持有凭证的本地组件；模式 C 跑通，但所有租户共用同一账户。见 P1 PoC 报告 与 ADR-0008。

最初版本不能假设动态凭证插入对所有协议都可原生实现；必须以真实版本和 extAuthz 回包机制实测，必要时在受控 sidecar 实现，严禁因此开放任意 Header 注入。

7. 接口契约与访问矩阵

  • contracts/gatekeeper/openapi.yaml 定义 Gateway Control API 的建议命令形态，供 OpenAPI 检查及跨域讨论；不是 Envoy extAuthz 线协议的替代定义。
  • contracts/gatekeeper/authz-decision.schema.json 是中立决策制品结构与 Mock 的共同输入输出定义，仅用于内部逻辑校验与示例，不承诺 agentgateway 原生接受此 JSON。
  • 真实 Gateway ↔ PDP 使用官方 Envoy gRPC ExtAuthZ 或官方 HTTP ExtAuthZ 模式之一，由 GatewayAuthzAdapter 将 Gatekeeper 决策安全映射到被验证的协议。
  • HTTP ExtAuthZ 2xx 表示允许，非 2xx 表示拒绝；不等于允许把响应 Header 任意插入后端请求。必须按白名单选择输出 Header 并验证具体配置支持。

8. 数据保护、密钥运维与审计

审计中保留稳定 trace_id、principal_subject_hash、service_id、tenant_id、provider_id、account_ref_hash、operation_id、policy_version、decision_code、config_digest；拒绝记录 Token/Key、密码、PII、未脱敏 Body。审计保留期与区域数据合规按照真实部署法域、客户合同和数据分类在上线前确认，不编造统一全球法定义务。

绝不允许管理 UI/开发者门户的查看权限直接继承为第三方账户使用权。Gatekeeper 授权包含 principal + action + resource + environment + purpose，并有时间有效性；紧急吊销变更应具有优先通道和效果验证。

9. PoC 必须证明的核心结论

  1. 两租户、两 Provider Account 的 Token 隔离；撤销 A 不影响 B，A 不能读/使用 B 的 Token。
  2. Gateway 收到内部 JWT、第三方 API 只收到 Provider Token；内网 Hook、Header 不能伪造租户。
  3. 同一操作支持固定 Key 和动态 OAuth 两种鉴权，确认 agentgateway 真实兼容路径。
  4. HTTP L7 与 CONNECT 在所选模式下具有明确协议能力边界；证书和 SNI 正确。
  5. Gatekeeper、Secret、Provider 授权服务器、网关实例分别故障时按默认拒绝与恢复策略执行。
  6. 关键授权绕过和 SSRF 用例经过动态负向测试，不能用代码评审替代。

资料： JWT · External AuthZ · Backend Auth · OAuth 2.0 BCP RFC 9700 · JWT BCP RFC 8725。

10. Gateway Operations UI 安全与权限（G04 · V1.0 同版更新）

  • Gatekeeper 不可用时高风险操作默认拒绝，不得沿用过期的允许结果。业务网关数据面不得因 UI 停机而停止已有合法流量。

同版增补：报文诊断数据安全边界

  • 认证、授权与凭证可在 Gateway 中运行，但绝不可默认将第三方 Token、JWT、HMAC 签名材料、Cookie、身份证明、个人地址、医疗/支付等信息写入报文日志；捕获策略应在采集和导出边界先删敏感字段。
  • Gatekeeper 单独决定 gateway.message.read_sanitized、gateway.message.export、gateway.diagnostic_capture.manage 是否允许，结合服务身份、租户、目的、时间范围与数据分级执行；真实授权必须在后端，不以角色下拉框为准。
  • 使用不可变审计关联每次报文读取、导出及临时捕获启停；提供保留期、加密、租户级访问隔离、删除与成本上限。导出是另一个授权操作，不是读权限的默认附属能力。
  • 需要看外发变更后报文时必须通过安全的捕获路径取得确切事实，不得从原始请求推断 Gateway 确实转发了相同数据。对捕获错误或 ExtProc 故障采用经批准的失败策略，不得静默关闭强制的鉴权/安全策略。

11. 多租户 CredentialUse / Token Broker 执行契约与撤销

Gateway 的内部授权与 Provider 认证是两个不同的交易。Gatekeeper PDP 先确认 Caller+Tenant+DelegatedUser（如有）+ ProviderAccount+Operation+Environment，并签发短有效期决策；Broker 仅接收绑定此决策与网关工作负载身份的 CredentialUse 请求。

认证类别 原则 必须做的负向验收
OAuth2 Client Credentials 向第三方授权服务器请求 Token；缓存按 provider/account/client/scope/audience/env/secret-version 隔离 交叉租户、过期 Token、并发刷新、撤销后拒绝
OAuth2 Authorization Code 处理授权用户/租户委托与刷新令牌保护；禁止用户 Token 自动转换成服务 Token 不同委托人、过期授权、用户撤销
API Key 从 Secret Manager 受控引用；只在 Gateway 上游发送阶段附加 改 Host/Route/Account 后绝不沿用
HMAC / 私有签名 签名确切的最终外发方法/路径/query/body/hash；必要时独立可信 Signer 签名前后 Body 变更、时钟偏移、重放和密钥泄露
mTLS 客户端证书/私钥仅存于受控工作负载/密钥设施 错误证书、链不受信、过期/撤销、跨租户复用

gateway/policies/credential-binding.schema.json 是使用授权意图，绝不允许存真实 Token。不应默认让 agentgateway 原生处理所有类型；必须经选定版本的真实能力对照，必要时开发独立、只执行最小权限签名/注入的扩展。

撤销：账户禁用和 AccessGrant 撤销独立于慢速 Route 发布；必须保证新 CredentialUse 无法越过最新撤销代次。缓存必须绑定 PolicyVersion/RevocationEpoch 并有硬 TTL；对高风险请求默认实时 PDP 判断，PDP/Broker/Secret 不可用时拒绝新增凭证注入，不得自动 fail-open。

11.1 业务人员委托与服务身份绑定

  • 对用户代表组织调用第三方 API，必须记录已验证的真实 User、Service、Tenant、Authorization Grant 及代理委托范围；没有委托上下文的后台作业须通过明确的服务授权策略，不得伪装成某个用户。
  • 客户端 Header X-Tenant-ID、X-Provider-Account、X-User-ID 不能直接成为决策权威。可信上下文由 Gateway 在验签/受保护连接后构建。
  • Broker 响应的凭证只能送达受保护 Gateway 执行边界，不得传入业务响应、异常文本、OpenTelemetry Baggage 或普通审计日志。
  • 上游路由重写完成后才能确定 HMAC 签名输入；变化后必须重新做一致性判定，防止跨账户复用凭证。

11.2 安全按需诊断

gateway/policies/diagnostic-capture.schema.json 与 contracts/gateway/diagnostic-event.schema.json 定义 CaptureGrant 与四阶段证据。默认只收集元数据；如需正文，CaptureGrant 必须具备 Route、Tenant、用途、审批人、开始/结束时间、保留期、消息大小上限和脱敏规则，并且开始时刻严格早于到期时刻（见离线语义校验及真实服务端验收）。

所有捕获和导出都需要后端 ABAC 与不可变审计；对二进制/gRPC Streaming 只记录有界元数据而不承诺完整正文。开发者无权借由 Agentgateway 原生 UI 或日志绕过这层保护。

Message Inspector 请求 / 响应成对诊断的安全界限

成对报文展示不是授权的例外。Request Headers、Response Headers、Request Body、Response Body 四类证据均需按主体、租户、应用、环境、路由与用途独立授权；前端 Viewer 的按钮隐藏绝不能替代服务端策略校验。

默认不捕获 Body；当审批后采集时，必须在持久化、Telemetry Export、索引和导出前进行字段删除或不可逆脱敏，覆盖 Authorization、Proxy-Authorization、Cookie/Set-Cookie、API Key、Token、Secret、敏感 Query 参数、地址电话和其他 PII。正文采样需按大小、时间和数据类别限制；二进制及流式协议仅展示元数据，除非明确批准受控解码。

任何 NOT_OBSERVED 不得替换为“空 HTTP 200”；任何下游 Gateway 生成的 504 不得记录为第三方返回的 HTTP 504。报文的时间戳、采集点位置与脱敏策略版本属于审计证据。

5. 容量与性能验证设计

比较三个基线：Direct → Provider Mock、Gateway L7（只代理）→ Mock、Gateway L7（JWT+ExtAuthZ+Credential）→ Mock。所有测量在同一上游延迟分布、同网络/硬件/连接池配置下进行，报告 p50/p95/p99、吞吐、CPU、内存、连接数、错误分类、Token Broker 刷新峰值。包含以下工作负载：

  • A. 读接口小 JSON（Tracking/Rate Quote），读写比例可调。
  • B. 大文件与高并发流（label PDF、manifest），检查 Body 流式行为及限制。
  • C. 写操作（创建面单/订舱 Mock），严格禁止代理重放。
  • D. gRPC unary 和 streaming，检验消息顺序、Metadata、deadline、status。
  • E. 故障状态：Broker 抖动、DNS 失败、提供商 429、半开连接、进程关闭、网关池滚动升级。

阈值治理：基于生产使用量、第三方 SLA、业务端到端超时预算确定绝对/相对延迟与可用性阈值；当前所有数值仅作测量计划。没有真实负载数据就不要宣称“网关性能比直连更好”。

信号分层：默认 agentgateway access log → OpenTelemetry Collector → 脱敏/过滤后日志存储；OpenTelemetry trace → Tempo/Jaeger 类 Trace 存储；请求计数、P95/P99、拒绝原因经指标通道采集。日志主要记录 method/route/status/latency/decision/trace_id/provider_request_id，不默认启用完整 Body。

条件捕获：在受控测试/故障分析中，官方 CEL 提供 request.body / response.body，但 Body 缓冲限制、截断及 Streaming 语义须遵循运行版本。若需精准比较 Gateway 认证注入/URI Rewrite 前后信息，评估经过验证的 ExtProc 或等价事件观测点；ExtProc 是处理器并可能增加延迟及失败依赖，不应为了常规日志而强制所有 API 同步调用 ExtProc。

诊断呈现：按 Trace ID + Hop + Config Revision + Provider Request ID 关联四阶段证据，每阶段保留 CAPTURED/NOT_CAPTURED/TRUNCATED/NOT_SENT/TIMEOUT/REDACTED；Request/Response Header 与 Body 仅展示经服务端授权和脱敏后的有限内容。gRPC 应单独支持方法、Metadata、Status、Trailer 与分帧/流式限制。

故障分类：401（身份）、403（账户授权）、429（网关与提供商不同限额）、502（上游）、504（已发送写请求的结果未知）、TLS/DNS（连接层）、Schema/业务码（域适配层）。应显示故障阶段而非笼统“网关错误”。

性能与隐私验收：测量开启/关闭捕获时的 CPU、内存、请求/响应 P95/P99、带宽、存储成本；限制单报文大小和采样率；日志注入与跨租户读取负面用例必须通过。默认 Body 捕获为关闭；任何生产临时捕获需自动过期与审计。

每个请求至少关联：trace_id,request_id,route_id,config_digest,authz_decision_id,provider_request_id（如存在）、tenant_ref（可见范围内）、provider_account_ref（脱敏）及 failure_origin。区别不可信客户端自报字段与网关实际观察值。

11.3 Runbook 与紧急响应

参考 operations/incident-runbook.md：401/403 排查 Gatekeeper 信任与授权，429 区分本地与 Provider，502/504 分辨 DNS/TLS/连接超时和真实上游返回；504 写操作不可默认重放。

  • 快照发布：固定二进制/镜像 digest、固定 schema、SBOM/签名、可回滚 artifact；预检→Canary→批量→回读→观察→ACTIVE。
  • 变更失败：按故障域停更、恢复上一个批准快照、核验 observed digest；安全撤销不能因配置回滚而逆向放行。
  • Gateway 数据面故障：按池故障注入验证；不允许 Fabric/Console 不可用导致现存请求无条件失败。对需要在线 PDP 的高风险新授权可 fail-closed。
  • 隐私事件：立即停用 Capture Session、隔离存储、审计访问路径、按适用法域执行通知与清理。

双 Hop Request / Response 观测实现规范

在与 agentgateway 固定版本进行真实验证后，BFF 的 Message Inspector Read Model 应按两个 Hop 将四个 Observation 组织在一条 Trace 中：INGRESS_REQUEST、EGRESS_REQUEST、UPSTREAM_RESPONSE、DOWNSTREAM_RESPONSE。响应与请求按 Trace ID、Route ID、Config Digest、Tenant Ref、Client Request ID 和 Provider Request ID 关联。

每份观测记录需要显式的 capture_status（包含 METADATA_ONLY、CAPTURED_SANITIZED、NOT_SENT、NOT_OBSERVED、TRUNCATED、NOT_CAPTURED）、正文长度和截断标记。按 HTTP Method/Target、响应 Status、Headers、Body、Content-Type、HTTP/gRPC Metadata 和 Trailers 分类输出，避免将捕获未发生误显示成空报文。

生产默认只记录元数据，Body 捕获按审批设置 TTL、范围、大小、采样、加密存储与到期删除。UI 侧任何复制、导出与查询都必须经服务器端 ABAC 校验并审计。真正的性能开销与采集能力需要在代理配置、ExtProc/Telemetry 顺序及大包/流式协议测试中确认，不能由离线 UI 推断。

2. 重点验收场景

  1. JWT 严格验证：同一服务身份的合法 JWT 可在允许环境访问，错误 iss/aud/alg/签名/过期/撤销场景拒绝。Gateway 必须鉴别 Token 类型与客户端权威。
  2. 跨租户隔离：相同 Provider 多账户并存，A 不能访问 B；改变 Header/URI/account ID 无法绕过 Gatekeeper 的复合授权。
  3. 第三方凭证处理：Gateway 执行认证，第三方只收到其认可 Token；不记录或转发内部 JWT；失效/刷新/吊销时反应在规定窗口内。
  4. 出站 L7 正确透传：对 Path/Query/Body/Header/Status 按允许契约观察，异常字符、URI 规范化、重定向不形成新的未授权目标。
  5. CONNECT 对照：以官方 Tunnel 与 Route 模式分别测量可见信息，验证不误用 CONNECT 实现动态 HTTP 认证注入。
  6. gRPC：Unary 与 Stream 的 deadline/metadata/status，识别认证中间件在流内能否保证安全。
  7. 运行可靠性：Gatekeeper PDP、JWKS、Token Broker、DNS、Provider、Gateway 分别故障，确认 Fail Closed、无写请求重放、配置可回退。
  8. 部署一致性：同一 GatewayPool 多副本的 Desired 和 Observed 摘要一致，部分成功必须显示 PARTIAL/UNKNOWN。
  9. Provider 限流：多租户与共享 Account 配额不互相挤占、可明确区分 Provider 429 与 Gateway 429。
  10. 运营审计：能通过 Trace 和 Snapshot 信息重构授权事实、上游状态及发布责任；日志中没有 Secret/Token。

tests/acceptance_matrix.csv 提供逐条 ID、FR 映射、前置条件、预期结果、状态与证据占位标记；没有运行过的行保持 NOT_RUN，不把自带 Mock 逻辑测试伪装成运行验证。

key.expression 的做法：ExtAuthZ 的 metadata 把 PDP 响应里的 authorization 头读进 extauthz.credential，再由 backendAuth.key.expression 写到上游请求，不再用 includeResponseHeaders。这条路由的写法是先在单独的试验里试出来的，试验中看到三点（不在证据文件里；证据文件证明的是现在这条路由的行为）：

  • backend 上的 authorization 规则先于 backendAuth 执行。照搬模式 A 路由上"必须有 Authorization 头"的规则，每个请求都会被拒（这时头还没写上）；要改成判断 extauthz.credential。写错的后果是全部拒绝，不是放行。
  • 不加这条规则时，PDP 放行却没给凭证的请求会被不带凭证地转发，与"默认配置不安全的地方"第 3 项相同。
  • metadata 也读得到响应体（json(response.body)），所以凭证可以不放在头里。契约目前规定凭证正文不出现在任何响应体里，本 PoC 没有改这一点。

模式 B 跑下来暴露的三件事：

  • 回环端口上，密钥文件是唯一的屏障。Broker 在回环地址上监听，网关用一个密钥文件证明自己；本机任何能读到这个文件的进程都能向 Broker 要到凭证（P1-MB-04 的对照项）。真实部署要靠 Unix Socket 或 Pod 内网络隔离，这一点没有测。
  • 多了一处持有凭证的地方。Broker 的本地存储里有该网关池用得到的全部账户凭证，它如何下发、轮换、吊销，设计里还没有。
  • 决策契约缺一个字段。DecisionRequest 原先没有地方放"调用方 Token 是为哪个环境签发的"，Broker 无从转达，PDP 也就拒绝不了 PROD Token 用在 TEST 池上。已在 contracts/gatekeeper/openapi.yaml 里加上可选的 token_environment（提案）。

默认配置不安全的地方

下面六项不配置就是不安全的，都是跑出来的，不是读文档读出来的。前五项的默认行为是在 1.6.0 上观察到的；1.7.0 上验证的是处理之后的配置同样有效，没有重测不处理时的默认行为。第 6 项是 1.7.0 新出现的。第 1、2 项是第一次运行的失败项；第 3、4 项是随后对照 G03 §5 把期望收紧才暴露的；第 5 项的"默认行为"来自一次单独的探测（一条不带任何策略的路由，把 Cookie、X-Forwarded-*、Forwarded、Authorization、Host 全部原样转发），这次探测不在证据文件里，证据文件只证明处理之后这些头不再到达 Provider。现在的 agentgateway.poc.yaml 已逐项处理。

  1. Host 原样转发。上游收到的是调用方发来的 Host: egress-api.idp.test。必须为每条路由配置 urlRewrite.authority。
  2. 路径不做规范性检查。%252e%252e（双重编码）、%00、;x=1 被原样转发到上游。现在由两层拦截：路由 authorization 规则只放行由非保留字符组成、段不以点开头的路径；PDP 参考实现（scripts/policy_reference.py）用同一条规则。无 PDP 的模式 C 路由证明了网关这一层单独有效。带 ExtAuthZ 的路由上 PDP 先被调用，这些请求是被 PDP 拒绝的。
  3. PDP 放行但没给凭证时，请求照样转发（不带任何凭证）。现在在 backend 上加了 authorization 规则，没有 Authorization 头就由网关拒绝。
  4. Provider 的 Location、Set-Cookie 原样回给调用方。网关不跟随 302，但会把跳转目标交给调用方。现在用 responseHeaderModifier.remove 去掉。
  5. 调用方的 Cookie、X-Forwarded-*、Forwarded 原样传给 Provider。现在用 requestHeaderModifier.remove 去掉。
  6. （仅 1.7.0）没有会话密钥时，网关启动会改写自己的配置文件。config.session.key 未设置时，1.7.0 生成一个密钥并写回启动它的那个文件；1.6.0 不会。第一次在 1.7.0 上运行时，仓库里受版本管理的 agentgateway.poc.yaml 就这样被加了三行（已还原，没有提交）。对按摘要审批、部署后回读对账的配置发布（G03）来说，这意味着运行中的文件不再是批准的那个文件，而且里面多了一个密钥。处理：用环境变量 SESSION_KEY 提供密钥，实测可阻止改写；run_poc.py 另外只让网关从 .run/ 下的副本启动，仓库里的文件它碰不到。P1-CF-01 检查网关运行时所用的文件与仓库里的逐字节一致；证据的 start_without_session_key_rewrites_config_file 记录了每个版本在不提供密钥时的实际行为（1.6.0 为 false，1.7.0 为 true）。另外两个单独试过、不在证据文件里的观察：配置文件只读时 1.7.0 只记一条警告然后照常启动；session.key: disabled 只有 1.7.0 接受，1.6.0 会拒绝整份配置，所以两个版本共用的文件里不能这样写。

未解决

  • P1-SS-04 FAIL：带两个 Host 头的请求被接受（RFC 9112 §3.2 要求 400）。1.6.0 与 1.7.0 行为相同。网关用第一个做路由，第二个不会到达上游；上游 Host 已被第 1 项改写，所以没有形成越权，但请求本身应当被拒。配置层面没有办法：两个版本的配置 Schema 里都没有相关开关；CEL 规则里也识别不出来，request.headers["host"] 取不到值，request.host 只反映第一个（这是在两个版本上单独试验的结果，不在证据文件里）。需要在入口前置组件处理，或向上游提出。
  • 请求头是"删黑名单"而不是"放白名单"。G03 §5 要求只传播 Provider 允许的头。本 PoC 只做到了按名字删除，调用方的任意自定义头（如 X-Client-Trace）仍会到达 Provider。
  • 监听地址无法限制。1.6.0 和 1.7.0 的配置 Schema 都没有监听器的绑定地址字段，27611 对本机所有网卡开放（两份证据里都记录为 *:27611）。管理、指标、就绪端口可以也已经绑到 127.0.0.1。
  • PDP 不可用与策略拒绝无法区分。PDP 超时或不在时调用方得到 403，与正常拒绝相同；PDP 返回 500 时调用方得到 500。PDP 证书不被信任、网关自己的证书不被接受时同样是 403。G01 的失败来源区分（GW-FR-043）在这一点上没有满足。
  • mTLS 证明的是"谁在调用 PDP"，不是"调用方 Token 里写了什么"。租户和服务身份仍然是网关转述的：PDP 相信它们，是因为对面是网关。网关被攻破等于这些声明可以伪造，这一点 mTLS 不改变。
  • 规范路径规则很严：不允许 %，所以路径段里不能有需要编码的字符。真实 Provider 的 Operation 如果需要，得按 Operation 单独登记放宽，不能全局放开。

没有覆盖

Gatekeeper 是 Mock（没有真实身份源、授权库、Secret Manager、Provider 令牌端点），没有对接过任何 Gatekeeper 实现；Provider 是回环 Mock；本地 Broker 是 Mock，存储是一个 JSON 文件。mTLS 只在网关到 PDP、Broker 到 PDP 两段上是真的，CA 和证书每次运行临时生成：没有 SPIFFE Workload API，没有证书轮换和吊销；调用方到网关、网关到 Provider 是明文 HTTP。单进程，没有多副本、配置滚动、限流、负载；没有 gRPC ExtAuthZ、决策缓存、CONNECT、gRPC 上游、HMAC 签名、对 Provider 的 mTLS；没有 DNS 重绑定和网络层出口 ACL。完整列表在证据文件的 scope_limits。

ADR-0008 / 架构决策

ADR-0008 — 出站凭证经 HTTP ExtAuthZ 响应头按请求注入

状态：Proposed（待具名批准） · 版本 V1.0 · 日期 2026-11-10
本 ADR 为设计建议，不是已经执行的技术审批、生产基线或运行验收。

背景

G04 §4 列出三种 Credential Broker 返回模式并要求用 PoC 比较；ADR-0001、ADR-0003、ADR-0004 都以"动态凭证注入经实测可行"为前提保持 Proposed。Gatekeeper 契约里的 credentials/prepare 返回不透明的 secure_binding_handle，但没有定义网关如何把它兑换成凭证。

推荐决策

  1. 需要按租户/账户选择凭证的出站路由采用模式 A：网关验证调用方 JWT 后调用 Gatekeeper 的 HTTP ExtAuthZ 端点；允许响应的 Authorization 头即本次请求的 Provider 凭证，网关只把这一个头写到上游请求。
  2. 凭证兑换只有这一条路。Gatekeeper 不提供"用句柄换凭证正文"的接口：credentials/materialize 不实现，secure_binding_handle 不签发。credentials/prepare 只返回计划，不返回秘密。
  3. 可信上下文由网关从已验签 JWT 与路由常量构造；调用方只能提交账户申请（X-Provider-Account），由 PDP 对照授权复核。
  4. 模式 A 用复制响应头（includeResponseHeaders）实现，不用 1.7.0 的 backendAuth.key.expression：两者实测结果相同，后者把配置绑在 1.7.0 上而没有换来安全上的好处。例外只有一种：Provider 要求凭证放在请求头以外的位置（如查询参数），复制响应头做不到，届时按路由单独评估并补测。
  5. 网关到 Gatekeeper 用工作负载 mTLS：网关出示自己的证书并固定 CA 与对端名字，Gatekeeper 从客户端证书取调用方身份，只对网关身份下发凭证。
  6. 模式 C（网关固定凭证）仅用于单账户固定路由；模式 B 暂不采用，保留为回退方案。
  7. 线上契约见 contracts/gatekeeper/openapi.yaml 的 /v1/extauthz/check，网关侧必须配置的项见 poc/p1/README.md 的"默认配置不安全的地方"。

为什么这样决定

poc/p1 在 agentgateway 1.6.0 和 1.7.0 上用同一份配置跑通了模式 A：双租户双账户隔离、撤销即时生效、伪造上下文无效、内部 JWT 不到第三方、PDP 故障默认拒绝、非幂等写不重放（1.7.0 上 50 个用例 49 个通过；1.6.0 上跑了 47 个、46 个通过；证据在 poc/p1/evidence/）。模式 C 同时跑通，但两个租户以同一账户到达 Provider，不满足多租户要求。一次往返同时完成授权与凭证下发，不需要第二个接口，也就没有可被重放或转交的句柄。

网关到 Gatekeeper 的 mTLS 在两个版本上都跑通：没有工作负载 CA 签发的证书连不上，同一信任域里不是网关的身份拿不到凭证，冒充 Gatekeeper 的服务收不到网关的请求。

被考虑的替代方案

  • 模式 B（本地 Broker/Sidecar）。已测，可行：隔离、撤销、默认拒绝与模式 A 相同，而且 Provider 凭证不出现在 Gatekeeper 的任何响应里。没有采用，是因为它多出一个进程、一份放着全部账户凭证的本地存储（下发、轮换、吊销都没有设计），以及一段只能靠部署环境来限制访问的本地通信；换来的"凭证不过网络"在网关与 Gatekeeper 之间已有 mTLS 的前提下收益有限。
  • backendAuth.key.expression。已测，可行，结果与复制响应头相同；只有 1.7.0 接受。
  • 模式 C 作为默认（不能按租户选账户）；保留 prepare + 句柄兑换（多一次往返，且句柄的绑定与兑换语义从未定义）。

成本与剩余风险

  • 证据来自 Mock Gatekeeper、Mock Provider、单进程。没有对接过任何 Gatekeeper 实现：验证的是网关一侧和一个按契约写的 Mock。mTLS 用的是每次运行临时生成的 CA，证书的签发、轮换、吊销未验证；多副本、负载下的行为未验证。
  • 验证了 1.6.0 和 1.7.0，两个版本都能跑的用例结果逐条相同；具体版本与镜像 digest 尚未锁定，换版本必须用同一套 PoC 重跑。1.7.0 在没有会话密钥时会改写自己的配置文件，部署时必须经 SESSION_KEY 提供密钥（见 poc/p1/README.md）。
  • mTLS 让 Gatekeeper 确认对面是网关，但租户与服务身份仍是网关转述的；网关被攻破时这些声明可以伪造。
  • 每个请求同步依赖 PDP，延迟与可用性预算未测；决策缓存未启用也未测。
  • Provider 凭证经过网关进程内存和 PDP 响应。PoC 里网关默认配置下的日志没有出现凭证、调用方 JWT 或密钥；追踪、指标以及改过日志字段之后的行为没有验证。
  • 只覆盖 Header 注入。HMAC 签名、mTLS 客户端身份、OAuth 授权码委托仍是设计提案。
  • PoC 的遗留问题（重复 Host 头被接受、请求头只能按黑名单删除、监听地址不可限制、PDP 不可用与拒绝不可区分）在批准前需要处置或接受。

变更与回退条件

需由架构负责人、对应产品 Owner、安全负责人及运行负责人具名复核；在相关 PoC、负向测试、容量与灾备验证未完成前保持 Proposed。若最终锁定的版本上同一 PoC 不通过，重新评估本决策。若真实 Gatekeeper 的延迟/可用性无法满足受批准目标，按以下顺序评估，而非自动维持本决策：先评估 gRPC ExtAuthZ 加短时效决策缓存（agentgateway 文档写明缓存只支持 gRPC 协议，HTTP 协议每个请求都会调用 PDP；缓存会让撤销最多延后一个 TTL；两者本 PoC 均未测），仍不满足再评估模式 B。
