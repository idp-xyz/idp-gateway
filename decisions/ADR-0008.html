DECISIONS / ADR-0008

ADR-0008 — 出站凭证经 HTTP ExtAuthZ 响应头按请求注入

状态：Proposed（待具名批准） · 版本 V1.0 · 日期 2026-11-10
本 ADR 为设计建议，不是已经执行的技术审批、生产基线或运行验收。

背景

G04 §4 列出三种 Credential Broker 返回模式并要求用 PoC 比较；ADR-0001、ADR-0003、ADR-0004 都以"动态凭证注入经实测可行"为前提保持 Proposed。Gatekeeper 契约里的 credentials/prepare 返回不透明的 secure_binding_handle，但没有定义网关如何把它兑换成凭证。

推荐决策

  1. 需要按租户/账户选择凭证的出站路由采用模式 A：网关验证调用方 JWT 后调用 Gatekeeper 的 HTTP ExtAuthZ 端点；允许响应的 Authorization 头即本次请求的 Provider 凭证，网关只把这一个头写到上游请求。
  2. 凭证兑换只有这一条路。Gatekeeper 不提供"用句柄换凭证正文"的接口：credentials/materialize 不实现，secure_binding_handle 不签发。credentials/prepare 只返回计划，不返回秘密。
  3. 可信上下文由网关从已验签 JWT 与路由常量构造；调用方只能提交账户申请（X-Provider-Account），由 PDP 对照授权复核。
  4. 模式 A 用复制响应头（includeResponseHeaders）实现，不用 1.7.0 的 backendAuth.key.expression：两者实测结果相同，后者把配置绑在 1.7.0 上而没有换来安全上的好处。
  5. 网关到 Gatekeeper 用工作负载 mTLS：网关出示自己的证书并固定 CA 与对端名字，Gatekeeper 从客户端证书取调用方身份，只对网关身份下发凭证。
  6. 模式 C（网关固定凭证）仅用于单账户固定路由；模式 B 暂不采用，保留为回退方案。
  7. 线上契约见 contracts/gatekeeper/openapi.yaml 的 /v1/extauthz/check，网关侧必须配置的项见 poc/p1/README.md 的"默认配置不安全的地方"。

为什么这样决定

poc/p1 在 agentgateway 1.6.0 和 1.7.0 上用同一份配置跑通了模式 A：双租户双账户隔离、撤销即时生效、伪造上下文无效、内部 JWT 不到第三方、PDP 故障默认拒绝、非幂等写不重放（1.7.0 上 50 个用例 49 个通过；1.6.0 上跑了 47 个、46 个通过；证据在 poc/p1/evidence/）。模式 C 同时跑通，但两个租户以同一账户到达 Provider，不满足多租户要求。一次往返同时完成授权与凭证下发，不需要第二个接口，也就没有可被重放或转交的句柄。

网关到 Gatekeeper 的 mTLS 在两个版本上都跑通：没有工作负载 CA 签发的证书连不上，同一信任域里不是网关的身份拿不到凭证，冒充 Gatekeeper 的服务收不到网关的请求。

被考虑的替代方案

  • 模式 B（本地 Broker/Sidecar）。已测，可行：隔离、撤销、默认拒绝与模式 A 相同，而且 Provider 凭证不出现在 Gatekeeper 的任何响应里。没有采用，是因为它多出一个进程、一份放着全部账户凭证的本地存储（下发、轮换、吊销都没有设计），以及一段只能靠部署环境来限制访问的本地通信；换来的"凭证不过网络"在网关与 Gatekeeper 之间已有 mTLS 的前提下收益有限。
  • backendAuth.key.expression。已测，可行，结果与复制响应头相同；只有 1.7.0 接受。
  • 模式 C 作为默认（不能按租户选账户）；保留 prepare + 句柄兑换（多一次往返，且句柄的绑定与兑换语义从未定义）。

成本与剩余风险

  • 证据来自 Mock Gatekeeper、Mock Provider、单进程。没有对接过任何 Gatekeeper 实现：验证的是网关一侧和一个按契约写的 Mock。mTLS 用的是每次运行临时生成的 CA，证书的签发、轮换、吊销未验证；多副本、负载下的行为未验证。
  • 验证了 1.6.0 和 1.7.0，两个版本都能跑的用例结果逐条相同；具体版本与镜像 digest 尚未锁定，换版本必须用同一套 PoC 重跑。1.7.0 在没有会话密钥时会改写自己的配置文件，部署时必须经 SESSION_KEY 提供密钥（见 poc/p1/README.md）。
  • mTLS 让 Gatekeeper 确认对面是网关，但租户与服务身份仍是网关转述的；网关被攻破时这些声明可以伪造。
  • 每个请求同步依赖 PDP，延迟与可用性预算未测；决策缓存未启用也未测。
  • Provider 凭证经过网关进程内存和 PDP 响应。PoC 里网关默认配置下的日志没有出现凭证、调用方 JWT 或密钥；追踪、指标以及改过日志字段之后的行为没有验证。
  • 只覆盖 Header 注入。HMAC 签名、mTLS 客户端身份、OAuth 授权码委托仍是设计提案。
  • PoC 的遗留问题（重复 Host 头被接受、请求头只能按黑名单删除、监听地址不可限制、PDP 不可用与拒绝不可区分）在批准前需要处置或接受。

变更与回退条件

需由架构负责人、对应产品 Owner、安全负责人及运行负责人具名复核；在相关 PoC、负向测试、容量与灾备验证未完成前保持 Proposed。若最终锁定的版本上同一 PoC 不通过，或真实 Gatekeeper 的延迟/可用性无法满足受批准目标，重新评估模式 B，而非自动维持本决策。
