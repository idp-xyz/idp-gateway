阶段 0：开工前须由仓库所有者拍板的 3 项范围决策

按照本仓库治理规程（不设执行人/批准人分离，由仓库所有者拍板、以可核验证据为准），开工前先定好以下 3 项边界，避免阶段 1 与阶段 2 出现架构返工：

Decision 0-1 · UI 与采集范围

ADR-0018/0019 定态与 18 页台边界

确定 ADR-0018（观测/审计）与 ADR-0019（回环应急台）是否转为 Accepted；同时明确冻结中的 18 页完整 Console（ui_ux_expansion）与正文采集（GW-GAP-07）是否移出生产一期。

建议：生产一期保持 18 页台冻结、关闭正文采集；配置走 Fabric，应急走现有 gateway-console，显著缩小 STD-CP4 验收范围。
Decision 0-2 · 运行底座选型

Kubernetes 多副本 vs 多机 Compose

决定生产多副本底座形态。直接决定安全域隔离载体（K8s NetworkPolicy vs 多机 pin-egress.sh）、发布器下发机制以及是否同步启动 ADR-0013 的 PostgreSQL + idp-bento-go 持久化升级。

建议：完整生产发布首选 Kubernetes 分池部署（Ingress / Egress / AI 独立 Namespace）+ PostgreSQL/Outbox 控制面持久化。
Decision 0-3 · 顺丰令牌协调模式

顺丰多副本互踢治理策略

顺丰国际协议“取新令牌即作废旧令牌”（ADR-0014）。若生产一期启用多副本 gateway-authz，各实例独立换票会互相作废线上令牌，且重启会踢掉在途请求。

建议：多副本生产必选“集中令牌租约协调器”；若一期急于上线可先将顺丰池锁定主备单活，二期补跨实例协调。
§ 01

五阶段关键路径与双轨并行全景图

为了避免外部 Gatekeeper 排期阻塞本仓库研发，计划采用“阶段 0 拍板 → 阶段 1 双轨并行 → 阶段 2 合流生产化 → 阶段 3 逐层验证 → 阶段 4 灰度放量”的推进拓扑。任一阶段均设有刚性退出门槛，禁止跳过 D3 直接切流生产。

§ 02

阶段 1 · 轨道 A：生产 Gatekeeper 5 项前置与 KMS 托管

之前跑通的 13/13 Gatekeeper 联调依赖本机只读检出基础上的 3 处局部补丁（provider_account 模型补丁、全局 TOKEN_AUDIENCE 开关、前置临时 pdp-mtls nginx）。若不完成生产侧变更就直接指向 gk.idp.xyz，系统会因零信任默认拒绝机制直接拦截流量。

A3 · KMS / Secret Manager 接管策略（不破坏既有零依赖与测试基线） gateway-authz 已将凭证读取抽象为 ports.CredentialSource。接入生产 KMS / Secret Manager 时新增受控适配器（负责只写录入句柄读取、版本化 key_version 轮换与内存 ports.Secret 封装），保留现有 0600 文件源专供离线与黑盒测试，从而在不引入回归风险的前提下彻底消除生产手工分发密钥文件。
§ 03

阶段 1 · 轨道 B：API Fabric 发布闭环与状态机实现

按 ADR-0006 与仓库既定顺序，Fabric 对接是本仓库的下一项核心开发工作。动代码前先起草 ADR-0020 提案经你点头，再按“契约对齐 → mTLS 适配器与状态机 → 可选持久化升级 → 集成与干净树黑盒验证”四步交付。

打通 route-intent.schema.json、credential-binding.schema.json 与 internal/routecompile 的统一输入映射：

  • Tier 1 标准声明模板：API_KEY（支持默认 Authorization、白名单头名与 Query 参数，自动启用 extauthz.credential + backendAuth 防夹带路径）、OAUTH2_CLIENT_CREDENTIALS、HTTP Basic、MTLS_CLIENT_CERT。
  • Tier 2 命名适配器：WANB_DEVELOPER_TOKEN 与 SF_INTL_ENVELOPE（强绑定 request_signer_ref）；UI 只传类型与结构化字段。
  • 硬校验延续：拒绝密钥明文、${ENV} 引用、非 HTTPS 的 PROD 上游、危险头名与自由脚本表达式。

按 contracts/fabric/route-publication-intent.openapi.yaml 在控制面暴露受控 HTTP 接口（零外部 Go 依赖或仅在持久化层按规程引入）：

  • 工作负载身份隔离：仅接受具备 Fabric 工作负载客户端证书的 mTLS 连接，拒绝未授权身份与双 Host 头。
  • 并发与幂等保护：相同 idempotency_key + 相同正文返回原结果；同键异体或 expected_generation 失配返回 409；Schema 或编译器预检失败返回 422。
  • 单一配置权威：编排 compile → agentgateway --validate-only → publish → reconcile，GET /status 分离呈现 desired_digest 与 observed_digest。

对应 ADR-0009 第 4 条与 ADR-0013 第 9 条，在进入多池/多实例生产前替换单机 releases.log 文件历史：

  • 先锁定 idp-bento-go 的实际可用版本/提交号，新增 tests/bentocontract 契约测试；
  • 实现 PostgreSQL + Outbox 存储适配器与显式迁移命令，落库发布意图、幂等键、CAS 代次、不可变快照摘要与各副本观测记录；
  • 严禁跨数据库直读 Fabric 或 Gatekeeper 私表（保持领域边界清洁）。

严格遵守项目测试与对照规程，杜绝“校验通过但运行时失效”的假绿：

  • 新增 tests/integration/fabric/ 套件：用 Fabric 替身驱动全链（正常发布到 ACTIVE、重复键幂等、同键异体 409、CAS 冲突 409、非法 Intent 422、漂移 UNKNOWN 对账、回滚、无 mTLS 401）并配安全负向对照；
  • 所有 Go 改动先提交代码，再在干净工作区重跑 tests/acceptance/blackbox/run.py（保持 97/97）并单独提交证据文件。
§ 04

阶段 2：多副本分池高可用、短板治理与生产上游收口

当前 deploy/compose/ 是单机单点结构（宿主机或 Docker 停即中断），且存在 3 项已记录在 ADR 中的多副本短板。阶段 2 将轨道 A 与轨道 B 的成果落到高可用底座上，完成生产化收口。

§ 05

阶段 3：D3 生产候选真实验证与 11 项故障演练

按 docs/G06_Testing_and_Acceptance.md §11.1，生产候选验证必须在同构预发布环境按 A → F 顺序逐层举证，不能跳步，也不能用离线静态检查或单机替身结果替代多副本与真实负载证据。所有证据文件必须记录镜像摘要、Gatekeeper/本仓库 commit、策略摘要、环境与时钟元数据。
