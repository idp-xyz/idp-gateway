# ADR-0021 — 工作负载 mTLS 证书与 CA 文件热重载（workloadtls）

> **状态**：Proposed · **版本** V1.0 · **日期** 2026-11-24  
> 本 ADR 为设计建议，不是已经执行的技术审批、生产基线或运行验收。实现和当天的测试记在文末「做出来了（V1.0）」，不是验收通过。执笔的是 AI 编码助手。  
> 2026-11-24 仓库所有者在 ADR-0020 定为 Accepted 之后指示继续推进阶段 2 短板治理。本篇是其中第 3 项：工作负载 mTLS 的证书和 CA 不必重启进程就能换。这是开工的许可，不是决定。状态保持 Proposed。正式门禁仍为 `NOT_RUN`。

## 背景

`internal/platform/workloadtls` 给 `gateway-authz`、`provider-signer`、`gateway-fabric`、`gateway-control`、`gateway-console` 做双向 TLS。身份是证书 subjectAltName 里的一个 URI。服务端要求并验证客户端证书，`PeerIdentity` 只从 `VerifiedChains` 里取这一个 URI。客户端出示自己的证书，并按给定的 CA 和名字验证服务端。系统根证书不参与。

在这一步之前，证书和 CA 只在进程启动时读一次。文件后来被换掉，要等下一次进程才看得见。`IssuePublisherCert` 能把新叶子写到磁盘上，正在跑的发布器或网关侧客户端仍拿着旧的那一对。证书到期、CA 轮换、或者叶子被换掉，都要重启进程。重启会拆掉已经建立的连接，也会打断正在判定的请求。

登记表、开发者令牌和配额已经按同一习惯热重载：用 `os.SameFile`、修改时间、大小判断文件有没有换；读不成就留上一份，同一份坏文件只记一次，日志里没有正文。证书比那些 JSON 多一个约束：私钥和证书可能分两次换完，中间那一次对不上，不能把空证书换上去，也不能放行没有证书的连接。

这里仍不接 SPIFFE Workload API，也不查 CRL 或 OCSP。

## 推荐决策

1. **函数签名保持不变，另给带日志的入口。** `ServerConfig(certFile, keyFile, clientCAFile)` 和 `ClientConfig(certFile, keyFile, serverCAFile, serverName)` 的参数和返回值不动。它们分别调用 `ServerConfigWithLogger` 和 `ClientConfigWithLogger`，logger 传 nil。nil 时用 `slog.New(slog.DiscardHandler)`，不写日志。长驻进程把现有的 `*slog.Logger` 传进去。`gateway-fabric` 原先没有 logger，这里建一个 JSON logger 写到原来的 stderr；不在启动时多打一行，避免碰既有输出。

2. **启动时仍然失败即拒绝启动。** 文件不存在、证书和私钥不配对、CA 文件里没有证书、或文件超过 4 MiB，`ServerConfig` / `ClientConfig` 立刻返回错误。这一点和改之前一样。

3. **每次新建的 TLS 握手才看文件。** `keyPairReloader` 盯证书和私钥两个 `os.FileInfo`，`caReloader` 盯 CA 那一个。和上一次尝试（不论成功还是失败）比的是 `os.SameFile`、`ModTime().Equal`、`Size()` 和 `Mode()`。没变就不读。变了就按 4 MiB 上限重读。读不成、配对失败、或 CA 里没有证书：留下上一份有效的证书或 CA 池，把这次看到的文件状态记下来，同一状态只记一条错误。日志只有路径和固定类别（`not found`、`permission denied`、`too large`、`no certificate`、`rejected`），不写私钥，不写 PEM 正文。

   证书和私钥分两次换时，第一次握手看见新证书配旧私钥，加载失败，留下旧的一对，并记住这一对文件状态。私钥文件随后换完，状态变了，下一次握手重新加载，用上新的一对。已经成功的那一对不会被清成空证书。

4. **服务端换叶子，也换信任客户端的 CA。** 返回的 `*tls.Config` 仍带上启动时的 `MinVersion: tls.VersionTLS12`、`Certificates`、`ClientAuth: tls.RequireAndVerifyClientCert`、`ClientCAs`，给已经在检查这些字段的代码用。另外设置 `GetConfigForClient`：每次握手返回一份新的 `*tls.Config`，证书和 `ClientCAs` 是此刻的文件，`MinVersion` 和 `ClientAuth` 固定。`NextProtos` 从原配置抄一份，`http.Server` 启动时加上的 `h2` 不会丢。客户端证书仍由 `crypto/tls` 验证，`r.TLS.VerifiedChains` 照旧填充，`PeerIdentity` 不用改。

5. **客户端换叶子，也换信任服务端的 CA。** 返回的 `*tls.Config` 仍带上启动时的 `MinVersion`、`Certificates`、`RootCAs`、`ServerName`。`readback.New` 和 `revokerclient.New` 把 `Clone()` 出来的 `Certificates` 或 `RootCAs` 置空后仍会拒绝。`(*tls.Config).Clone()` 会带走 `GetClientCertificate`、`VerifyConnection`、`InsecureSkipVerify`、`ServerName`、`RootCAs` 和 `Certificates`。

   `GetClientCertificate` 在每次新建连接时返回此刻的叶子。返回的是副本，调用方改这个指针改不到缓存里的那一份。

   服务端 CA 的热重载不能靠构造时那个 `RootCAs`：默认校验只用那一个池，文件换了会在自定义校验之前失败。因此按 `crypto/tls` 的做法，`InsecureSkipVerify: true` 和 `VerifyConnection` 必须一起设。`VerifyConnection` 做完这些才让握手继续：

   - `cs.ServerName` 为空：拒绝。不用拨号地址顶上，也不信任系统根。
   - `cs.PeerCertificates` 为空：拒绝。
   - 用 `cs.PeerCertificates[1:]` 做中间证书池，用此刻的 `serverCA` 做根。
   - `PeerCertificates[0].Verify`，`DNSName` 是 `cs.ServerName`，`KeyUsages` 是 `ExtKeyUsageServerAuth`。失败就中断握手。

6. **三个常驻进程接上带日志的入口。** `gateway-authz` 的监听证书和 Gatekeeper PDP 客户端、`provider-signer` 的监听证书、`gateway-fabric` 的监听证书以及发布器 / authz 客户端，改为 `ServerConfigWithLogger` / `ClientConfigWithLogger`。`gateway-control` 和 `gateway-console` 是短命令或另一次连接，仍用原来的 `ServerConfig` / `ClientConfig`；这两个函数已经会热重载，只是不写日志。

7. **已经建立的连接不拆。** 文件换了，正在用的那条 TLS 连接继续用握手里的那一对证书。新证书和新 CA 从下一次新建的握手开始生效。调用方要自己关空闲连接，或本来就不用 keep-alive。

## 为什么这样决定

重启才能换工作负载证书，会把判定和签名的在途请求一起停掉。文件替换已经是这个仓库换登记表和令牌的办法，证书沿用同一种「坏文件留上一份」。

服务端用 `GetConfigForClient`，是因为客户端 CA 和叶子都要在同一次握手里换成新的，而且 `ClientAuth` 必须仍是 `RequireAndVerifyClientCert`，`VerifiedChains` 才会被填上。只换 `GetCertificate` 换不了 `ClientCAs`。

客户端用 `InsecureSkipVerify` 加 `VerifyConnection`，是因为标准库的默认校验绑死构造时的 `RootCAs`。把这个标志单独打开、又不做 `VerifyConnection`，会接受任意服务端证书。对照 A 把 `VerifyConnection` 改成直接 `return nil` 之后，错主机名和错 CA 的握手都成功了。所以这两个字段要成对出现，不能只留一个。

`Certificates` 和 `RootCAs` 仍放上启动时的值，是因为 `readback` 和 `revokerclient` 在连接之前就检查这两个字段。热重载不能把这些检查弄成永远失败，也不能让它们看见空配置就启动。

## 被考虑的替代方案

- **换文件就重启进程。** 不选。这一步要的就是不重启。
- **接 SPIFFE Workload API，由它推送新证书。** 不选。本仓库这一期仍从文件读，不增加工作负载 API 的进程和依赖。`go.mod` 仍然没有 `require`。
- **在握手路径上查 CRL 或 OCSP。** 不选。吊销仍不在这一步。文件换掉不是吊销；旧叶子在到期之前，对仍信任它的 CA 来说还是一张有效证书。
- **只热重载叶子，CA 仍要重启。** 不选。客户端信任的服务端 CA 和服务端信任的客户端 CA 都是文件，轮换时同样不该重启。
- **坏文件时清空证书或清空 CA 池。** 不选。清空之后服务端握不成手，或者客户端不再出示证书，等于把这一跳停掉。对照 B 把证书清成空的之后，保活测试失败：服务端是 `tls: handshake failure`，客户端是 `tls: certificate required`。
- **用第三方的文件监视库。** 不选。`os.Stat` 在握手时做就够，而且和令牌文件是同一种判断。

## 成本与剩余风险

- 已经握完手的连接继续用旧证书，直到它自己关掉。操作员把文件换掉，不等于已经把旧连接上的身份换掉。
- 换叶子文件不会吊销旧叶子。不查 CRL / OCSP。要让旧叶子立刻不能再握手，得换掉信任它的那个 CA 文件，并且对端来的是新握手。
- 就地改写、但 inode、修改时间、大小和权限都没变时，看不出文件变了。换文件要写临时文件再改名，和开发者令牌那一条相同。
- `InsecureSkipVerify: true` 单独存在是危险的。它只有和 `VerifyConnection` 同时在时才成立。以后改这个配置的人如果拿掉回调、留下这个标志，错 CA 和错主机名都会被接受。对照 A 就是这个失败。
- 校验的名字来自 `ConnectionState.ServerName`（写进 SNI 的那个）。字面 IP 不会放进 SNI，这个字段会是空的，握手被拒绝。现有调用给的是 DNS 名。
- 单次读取上限是 4 MiB。再大的文件，启动时拒绝启动；运行中则留下上一份。
- 热重载在握手路径上，读文件时拿着该重载器的锁。文件在本地盘上，这个成本是一次 `stat`，有变化时再读一小段 PEM。
- 本篇不是决定。正式门禁仍是 `NOT_RUN`。黑盒没有为这一步单独重跑。

## 做出来了（V1.0）

2026-11-24 按上面写进 `internal/platform/workloadtls`。`ServerConfig` / `ClientConfig` 仍是原来的签名。`gateway-authz`、`provider-signer`、`gateway-fabric` 改调带 logger 的入口。`go.mod` 没有 `require`。没有改 `contracts/` 和 `deploy/`。

测试在 `internal/platform/workloadtls/reload_test.go`，与原有的 `workloadtls_test.go` 一起跑，含 `-race`：

- 服务端不停机，原子换上新序列号的叶子后，新连接看到新序列号。
- 服务端不停机，把客户端 CA 换成 CA2 后，CA1 签发的客户端证书被拒，CA2 签发的立刻成功，`PeerIdentity` 是新 URI。
- 客户端不停机。`IssuePublisherCert` 把叶子从 `spiffe://idp.test/gateway-control/publisher` 轮换成 `spiffe://idp.test/gateway-control/publisher-next` 之后，下一次新连接上服务端看到新 URI 和新序列号。
- 客户端不停机。服务端改用 CA2 的证书后，客户端的 `serverCA` 文件还是 CA1 时握手失败；把该文件原子换成 CA2 后立刻成功；主机名改成 `other.idp.test` 仍然被拒。
- 先只换证书文件（和旧私钥不配对），握手仍用旧序列号；再换私钥，下一次握手用新序列号。
- 垃圾 PEM、空文件、删除文件：服务端和客户端都继续用上一份完成握手。同一坏状态只记一条错误。日志里没有 `PRIVATE KEY`、`BEGIN CERTIFICATE` 或测试放进文件的标记。
- 8 路并发握手，同时轮换服务端和客户端叶子。`-race` 没有报告。
- 一条已经建立的连接在文件换掉之后仍可再用，拨号次数不变；关掉空闲连接之后，下一次拨号才看到新序列号。
- 超过 4 MiB 的证书、私钥或 CA，启动时拒绝。

`readback`、`revokerclient`、`gatekeeper` 以及 `gateway-console`、`gateway-control` 的既有测试仍走原来的 `ClientConfig` / `ServerConfig`。返回的配置仍带初始的 `Certificates`、`RootCAs` 或 `ClientCAs`，`Clone()` 保留回调。

## 没有做的

- 不查 CRL，不查 OCSP，不维护吊销列表。
- 不接 SPIFFE Workload API，也不从环境变量或网络拉取证书。
- 不主动拆掉已经建立的 TLS 连接。
- 不把 `gateway-control`、`gateway-console` 的短命令改成带 logger 的入口。它们调用的 `ClientConfig` / `ServerConfig` 已经会在下一次握手重读。
- 没有改 `contracts/`、`deploy/`、`go.mod`。

## 变更与回退条件

需由仓库所有者复核和决定；在此之前保持 Proposed。执笔的是 AI 编码助手，这不是决定。

所有者不接受时，撤回本篇，并还原 `internal/platform/workloadtls` 以及 `cmd/gateway-authz`、`cmd/provider-signer`、`cmd/gateway-fabric` 里这几处调用。`ServerConfig` 和 `ClientConfig` 的签名没有变，调用方不必改。

出现下面任一情况就停，先还原，不带着半套校验发布：

- `VerifyConnection` 不在了，`InsecureSkipVerify` 还在。错主机名或错 CA 的握手会成功。
- 坏文件把证书或 CA 池换成空的。保活测试会从「仍用上一份」变成握手失败。
- 热重载之后 `PeerIdentity` 读到空串，而证书里明明有一个 URI。那说明 `VerifiedChains` 没有填上。

以后若要查吊销或改接 Workload API，另写一篇。不要在这个重载器里悄悄加上其中一样。
