## 背景

RouteIntent 的预检当时只有 [scripts/preflight_intents.py](../../scripts/preflight_intents.py)。万邦和顺丰的 `agentgateway.yaml`、`policy.example.json` 是手写的，没有编译器。

## 推荐决策

1. **限界上下文 `internal/routecompile`。** 只用标准库。`domain` 不做 I/O，不跑网关二进制，不读文件。
2. **预检移植成 Go。** 覆盖 INGRESS、EGRESS、AI 三条，与脚本对齐：模式、规范路径、承运商登记表的允许名单、保留的主机和后缀、拒绝 IP 字面量、SNI 相符、重定向必须是 `DENY`、TLS 校验、`gatekeeper:` 绑定、拒绝敏感键、精确路径冲突、前缀重叠。对照文件是 [invalid-route-intents.json](../../tests/contracts/invalid-route-intents.json)，以及 `contracts/gateway/route-intent.example.json`、`route-intent.ingress.example.json`、`route-intent.ai.example.json`。
3. **编译做出站配置；V1.1 起同一条命令也编译入口规格。** 输入是一份编译规格。规格里没有密钥，也不许环境变量引用。出站输出两样，都是确定的，只用标准库：锁定的 agentgateway 1.7.0 能用的 YAML，和 `gateway-authz` 的登记表 JSON。入口写出网关 YAML 和一份没有承运商操作的策略文件，见下面 V1.1。万邦和顺丰的出站黄金文件不因此改。
4. **安全缓解写在编译里，不靠手写时记得住。** 提交 `e78d62e` 的说明列出这些：只读存储（`readOnly`）、回环上的 `bindAddress`、不设会话密钥、没有环境变量引用、`networkAuthorization`、评审过的请求头白名单、按名字精确删除的头、失败关闭的后端授权前缀、不重试，以及回读路由。可选的 `frontend_limits`（`maxConcurrentRequests`、`maxConnections`）和按路由的 `localRateLimit`。不写就不出现在配置里。
5. **两条例外只在编译规格里显式打开，而且很窄。** 明文沙箱主机：环境是 `PROD` 时拒绝。池内签名器（`internal_backend_host`）：`upstream_tls` 仍必须是 `VERIFY_REQUIRED`，并且规格里写了 `backend_tls`。两条不能同时设。预检默认不带这些例外，与脚本一样严。
6. **先用锁定的二进制校验，再写文件。** 适配器在临时目录里跑 `agentgateway --validate-only`。给了 `--lock-file` 就对照 [agentgateway.lock.json](../../deploy/agentgateway/agentgateway.lock.json) 核对二进制的 SHA-256。校验不通过，输出文件不写。
7. **命令是 `gateway-control compile`。** `--spec` 做编译。`--preflight-only` 只做预检。`sync-jwks` 和已有命令不改。
8. **手写文件仍是黄金基线。** [wanbexpress/compile-spec.json](../../deploy/providers/wanbexpress/compile-spec.json) 和 [sfintl/compile-spec.json](../../deploy/providers/sfintl/compile-spec.json) 各 4 条路由。顺丰的规格含 `sfintl-labels-print`。已有的 `agentgateway.yaml` 和 `policy.example.json` 不改。

## 为什么这样决定

手写的两份配置已经对着替身和沙箱跑过。编译器要先证明自己编出来的和这两份相同，再谈用它替换手写。预检进 Go 之后，控制面不必再靠仓库外的 Python 才能拒绝一份意图。`go.mod` 不加依赖。当时入口和 AI 的编译、Fabric 的批准、登记表的动态下发都不在这一步里。入口的编译见 V1.1。AI、Fabric 的批准、登记表的动态下发仍然不做。

## 被考虑的替代方案

- **继续只手写，等第三家承运商再做编译器。** 2026-11-19 定过推后。2026-11-20 的开工许可把这一项包括进来。不选继续等。
- **编译器直接覆盖手写文件。** 没有采用。手写文件留着当黄金基线，编译结果与它们比。
- **预检仍只留 Python。** 不选。开发计划 4.3 写的是移植成 Go。脚本还在，契约测试仍用它的反例。

## 入口编译规格（V1.1）

2026-11-21 定了入口编译的输入。主机名、JWT 的签发者和受众、后端地址都是规格里的字段，不写进编译器。

`gateway-control compile --spec` 现在接受这份入口文档，写出网关 YAML，以及一份没有承运商操作的策略文件。监听端口、回读端口、管理地址、签发者、受众、主机名、上游和超时都来自规格。示例在测试跑过时用锁定的 agentgateway 二进制做过校验。没有另外部署一个入口池，也没有新的验收用例。

### 没有做的

- AI 的编译。预检覆盖 INGRESS、EGRESS、AI 三类。入口按这份规格编译；AI 当时不编译。2026-11-23 的 V1.2 做了 LLM 这一支。

- 手写的 `agentgateway.yaml` 和 `policy.example.json` 没有被编译产物换掉。

## MCP 与 A2A 的编译（V1.4）

2026-11-23。V1.2 里「只编译 LLM，编译拒绝 MCP 和 A2A」那一句不改。MCP 和 A2A 的编译以本节为准。上一节末尾「MCP、A2A 和 Fabric 的发布批准仍然不做」里，MCP 和 A2A 的编译以本节为准。Fabric 的发布批准仍然不做。这不是验收通过。

### 设计之前量过的

同一天在锁定的 agentgateway 1.7.0 上量过，二进制 SHA-256 是 `c7ef326b7b5702451e94bab55ff484d600d5abdc5344a4cdf7c72fc0bcff9e24`。回环，替身，一次一个网关进程。没有加固时，MCP 的 initialize、notifications/initialized、tools/list、tools/call 能走通；调用方的 JWT 不到目标；Cookie、X-Forwarded-For、X-Provider-Account 和未登记的头会到目标；比路由前缀深一段的路径也会被转到同一个后端。路径规则 `request.path == "<前缀>"` 放在路由上，深一段变成 403。请求头白名单放在路由的 `transformations.request.replace` 上，那四个头不再到达，会话仍然通。白名单少了 `mcp-session-id` 或 `mcp-protocol-version`，initialize 之后是 400。少了 `accept`，每个请求都是 406。所以白名单是 `accept`、`content-type`、`mcp-protocol-version`、`mcp-session-id`、`traceparent`。`urlRewrite.authority.full` 改的是目标看到的 Host。目标 `backendTLS` 用证书、私钥、根和 `hostname`：证书来自另一套 CA、名字对不上、没有进程在听，initialize 都是 HTTP 500，JSON-RPC 是 -32603，正文是 `failed to send message`，目标应用收到 0 次。

A2A 是普通路由上的 `policies.a2a: {}`。没有这项时，卡片里的 `url` 是 agent 自己的地址。有这项时，`url` 被改成 `http://<请求的 Host><路由前缀>`。调用方送 `X-Forwarded-Proto: https`，方案仍是 `http`。agent 证书来自另一套 CA 时，调用方得到 503，正文是 `upstream connection failed`，agent 应用收到 0 次。

### 编出来的形状

一份文档仍然是一个池、一个意图。`intent.ai_protocol` 选支。`LLM` 与 V1.2 相同：要有 `provider` 和 `models`，不能有 `mcp` 或 `a2a`。`MCP` 要有一个 `mcp.target`，不能有 `provider`、`models` 或 `a2a`。`A2A` 要有 `a2a.agent`，不能有 `provider`、`models` 或 `mcp`。另一支的字段出现就拒绝，不忽略。未知字段仍拒绝。

MCP 目标和 A2A agent 的地址同一套规则。`host` 是 DNS 名时必须 TLS，证书名是 `tls_hostname`，没有就用 `host`。`host` 是 `127.0.0.1` 时，`PROD` 拒绝；`DEV` 和 `TEST` 上，没有 `tls_hostname` 是明文，有就是 TLS。别的 IP 字面量和 `localhost` 都拒绝。TLS 用这个池自己的 `tls/gateway.crt`、`tls/gateway.key`、`tls/ca.crt`，和入口的 `backendTLS` 一样。公网 CA 签发的上游证书这一步不支持。MCP 和 A2A 都没有凭证字段，也没有 API 密钥。

MCP 编一条路由，名字是 `<池名>-mcp`。`pathPrefix` 是池的 `path_prefix`，方法是 POST、GET、DELETE。路由上有精确路径规则、上面那份请求头白名单、`urlRewrite.authority`、`responseHeaderModifier` 去掉 `location` 和 `set-cookie`。不写 `timeout`。后端是一个 `mcp.targets` 条目。明文回环的目标不写 `policies`。目标名匹配 `^[a-z][a-z0-9-]{1,31}$`，不许下划线。这一步只编译一个目标。

A2A 编一条路由，名字是 `<池名>-a2a`。方法是 GET 和 POST。路由上有 `a2a: {}`，一条同时绑方法和路径的规则：POST 精确在 `<path_prefix>`，或 GET 精确在 `<path_prefix>/.well-known/agent-card.json`。`urlRewrite` 改 authority，并把路径前缀换成 agent 的 `path_prefix`（`/` 或一条规范路径）。应答去掉 `location` 和 `set-cookie`。`timeout.requestTimeout` 用 `route_timeout`。后端是 `host: <host>:<port>`，TLS 时带 `backendTLS`，请求头白名单是 `accept`、`content-type`、`traceparent`。

监听仍是严格 JWT。回读路由与 LLM 共用 `readBackRoute`。策略 JSON 的版本是 `ai`，默认 DENY，没有承运商操作。`RouteCount` 是 1。预检意图里的 `ai_protocol` 是 MCP 或 A2A。输出里没有环境变量引用，也没有会话密钥。

### LLM 这一支补上的策略

V1.2（commit `7695527`）编出的顶层 `llm` 没有 `policies`。V1.2 只量了两件事：没有 JWT 是 401，相符的 JWT 得到 200。同一天在锁定的 agentgateway 1.7.0 上再量这份输出，二进制 SHA-256 仍是 `c7ef326b7b5702451e94bab55ff484d600d5abdc5344a4cdf7c72fc0bcff9e24`。四件事是开着的：

1. 不绑池的 `public_hostname`。`Host: other.example` 和 `Host: ai.example:8080` 都是 200，请求到达供应商，供应商看到调用方的 Host。
2. 调用方的 `Cookie`、`X-Forwarded-For`、`X-Provider-Account` 和未登记的头被转到模型供应商。调用方的 JWT 不到：供应商看到的 `Authorization` 是密钥文件里的密钥。
3. 前缀下任意 POST，只要 JSON 里点了规格列出的模型，就带着池的 API 密钥转到同一条供应商路径。`POST /llm/other` 到了 `/v1/other`；`POST /llm/v1/embeddings` 到了 `/v1/embeddings`；末尾斜杠和查询串按原样转发。没有 JSON 正文的 GET 或 DELETE 是 400，不转发。`POST /llm/v1/models` 是 501，正文是 `Route 'Models' not implemented`，不转发。
4. 供应商的 `Location` 和 `Set-Cookie` 回到调用方。

现在 LLM 这一支编出 `llm.policies`。没有新的规格字段。`llm` 里的键序是 `gateways`、`pathPrefix`、`policies`、`providers`、`models`。`providers` 和 `models` 与原来相同。

- 一条授权规则，用 `request.host`。不用 `request.headers["host"]`：那种写法在这份 1.7.0 上把每个请求都拒成 403。规则是 `request.host == "<public_hostname>"`，并且（POST 精确在 `<path_prefix>/v1/chat/completions`，或 GET 精确在 `<path_prefix>/v1/models`）。主机名和前缀来自规格，不是编译器里的常量。
- `transformations.request.replace` 与入口的请求头白名单同一句：`accept`、`content-type`、`traceparent`。
- `transformations.response.remove` 是 `location` 和 `set-cookie`。

这一步只放行这两个端点。messages、responses、embeddings 故意不在规则里。

套件加上这些 LLM 用例之后，主模式连跑两次，都是 17 个用例、87 项检查通过。套件自己记的用时是 8.21 秒和 8.41 秒。第二次启动前等上一轮留下的 TIME-WAIT，等了 60.3 秒，这 60.3 秒不在 8.41 秒里。看到的：

- AUTH-LLM：另一个 Host 是 403，替身收到 0 次。AUTH-MCP 和 AUTH-A2A 的另一个 Host 仍是 404，替身收到 0 次。
- LLM-01：相符的 JWT，聊天仍是 200。替身看到的路径是 `/v1/chat/completions`，`Authorization` 里有密钥文件的内容。替身看到的头是 `accept`、`authorization`、`content-length`、`content-type`、`host`、`traceparent`。Cookie、X-Forwarded-For、X-Provider-Account、X-Not-Registered 不到替身。替身的应答带 `Location` 和 `Set-Cookie`，调用方这两项都是空。
- LLM-MODELS：`GET /llm/v1/models` 是 200，正文里有 `example-model`。替身收到 0 次。
- LLM-PATHS：`POST /llm/other`、`POST /llm/v1/embeddings`、带斜杠的 `POST /llm/v1/chat/completions/`、`GET /llm/v1/chat/completions`、`POST /llm/v1/models` 都是 403，替身收到 0 次。
- LLM-UNKNOWN：规格里没有的模型名是 404，替身收到 0 次。
- 只记录、不作为通过条件：聊天路径上带查询串 `?x=1`，调用方得到 200，替身收到的路径是 `/v1/chat/completions?x=1`。

`--control llm-no-policies` 去掉编译结果里的 `llm.policies`，跑一次。17 个用例里 3 个不通过（14/17），87 项检查里 79 项通过，用时 8.05 秒，启动前等了 59.0 秒。看到的与描述相符的部分：另一个 Host 是 200，替身收到这一次，路径是 `/v1/chat/completions`；调用方的 Cookie、X-Forwarded-For、X-Provider-Account、X-Not-Registered 到达替身；`Location: https://llm.standin.test/elsewhere` 和 `Set-Cookie: llm=1` 回到调用方；`POST /llm/other` 和 `POST /llm/v1/embeddings` 都是 200，替身路径是 `/v1/other` 和 `/v1/embeddings`，`Authorization` 是密钥文件里的密钥。带斜杠的 `POST /llm/v1/chat/completions/` 同样是 200，替身路径是 `/v1/chat/completions/`，也带着这把密钥。和「这些请求被拒、替身收不到」不完全一样的两处：`GET /llm/v1/chat/completions` 是 400，正文是 `LLM request body must be valid JSON`，替身收到 0 次；`POST /llm/v1/models` 是 501，正文是 `Route 'Models' not implemented`，替身收到 0 次。描述没有改成去贴合这两处。

同一轮把原来的四个对照又各跑了一次。失败的样子与上表相同，用例数已是 17：`mcp-no-allowlist` 16/17 用例、86/87 项，用时 8.27 秒；`mcp-no-path-rule` 16/17、86/87，用时 8.05 秒；`a2a-no-policy` 16/17、86/87，用时 8.02 秒；`no-readback-route` 14/17、81/87，用时 8.19 秒。这四次启动前各等了约 59 到 60 秒的 TIME-WAIT。

还开着，或这一步没有量的：

- 聊天路径上的查询串会被转到供应商。出站路由也会把查询串转出去。`request.path` 不含查询串，所以这条规则挡不住它。
- Host 带端口时，这条规则拒绝。调用方是经 front 进来的，front 送的 host 不带端口。
- 流式 completions（`"stream": true`）没有量。
- 只放行聊天补全和模型列表这两个端点。

### 没有做的，也没有量的

- 只编译一个 MCP 目标。几个目标时工具名会带目标名前缀，这一步不编。
- 公网 CA 签发的上游证书。TLS 只用这个池自己的那套。
- DNS 名的上游只做过 `gateway-control compile` 的 `--validate-only`。没有跑 `--in-image`，也没有在容器里用 DNS 名连过替身。
- 旧的 `sse`、`stdio`、`openapi` 目标。
- MCP 上的长连接和超时。路由上不写 `timeout`。
- 几个网关实例共用 MCP 会话。会话号是加密的，要同一把 `SESSION_KEY`，没有试。
- 卡片在 TLS 终结之后仍广告 `http://`。调用方送 `X-Forwarded-Proto: https` 也不改方案。
- A2A 的流式调用。
- 没有把 AI 池跑在 `deploy/compose` 上。
- Fabric 的发布批准仍然不做。

## 成本与剩余风险

- 编译规格和手写文件以后可能分叉。契约测试只对得上字段，对不上「编出来的字节与黄金文件结构相同」。后一条在 Go 测试里。
- 明文沙箱例外和池内签名器例外打开错了，会编出不该有的上游。`PROD` 拒绝明文沙箱。签名器那一条仍要 `VERIFY_REQUIRED` 和 `backend_tls`。
- 原生校验依赖本机有那份锁定的二进制，并且 SHA-256 对得上。对不上就不写输出文件。
