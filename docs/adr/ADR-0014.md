# ADR-0014 — 要改写正文的承运商协议由受限的签名适配器承担（第一家：顺丰国际）

> **状态**：Proposed（由仓库所有者决定） · **版本** V1.1 · **日期** 2026-11-20（V1.0：2026-11-20）  
> 本 ADR 为设计建议，不是已经执行的技术审批、生产基线或运行验收。它是[开发计划](../development-plan.md) 2.6 和 [G04](../G04_Identity_and_Security.md) 第 4 节预留的那件事的提案：承运商要签名、要改写正文时，由谁来做，放在哪里。执笔的是 AI 编码助手。  
> 来历：2026-11-20，仓库所有者选定顺丰国际为第二家承运商（开发计划 1.1）。"加密和签名放在哪里"列了三个做法给仓库所有者；仓库所有者没有在其中点选，要的是按经验给出最专业的做法。所以本篇的推荐是执笔者（AI 编码助手）的判断，不是仓库所有者的决定。动代码之前，等仓库所有者看过本篇。  
> 2026-11-20，仓库所有者看过本篇之后定的：五项都照推荐的做（第 2 项同时覆盖明文的令牌端点和签名适配器到承运商的明文地址，各是一个默认关着、按主机名放开的例外）。这是开工的许可，不是决定；状态保持 Proposed。当天按这个许可做了第零步、第一步和第二步；第三步没有做。

## 背景

[ADR-0008](ADR-0008.md) 把出站凭证收成一条路：网关验证调用方之后调用 ExtAuthZ，允许响应里的 `Authorization` 头就是这次请求的承运商凭证，网关只把这一个响应头写到上游。[ADR-0011](ADR-0011.md) 让凭证正文由 `gateway-authz` 持有；写本篇时已有的三种来源（`--credentials`、`--developer-tokens`、`--oauth-clients`）给出的，都是要写进 `Authorization` 的一整段值。万邦那一家就是这样接上的。ADR-0008 的"成本与剩余风险"写明：只覆盖 Header 注入，HMAC 签名仍是设计提案。开发计划 2.6 和 G04 第 4 节也预留过这件事：要签名时用一个受限的签名适配器，不把任意代码放进网关核心。

顺丰国际开放平台的协议（来源是它公开的[对接文档](https://openapi-portal.sf.global/)；沙箱 `http://api-ifsp-sit.sf.global` 只有明文 HTTP，正式环境是 `https://api-ifsp.sf.global`）有三样装不进"复制一个 `Authorization` 头"：

1. **正文整体加密。** 请求正文只有密文这一个字符串，不包 JSON，不加换行（文档的常见问题：否则答"签名验证错误"）。应答里的业务数据也是密文，解开才是业务 JSON。
2. **签名盖着密文，另有四个头。** 请求头有 `appKey`、`token`、`timestamp`（Unix 毫秒）、`nonce`、`signature`、`msgType`、`lang`。签名是令牌、时间戳、随机数、密文四个字符串按字典序排序、拼接之后取的 SHA-256，写成小写十六进制；方法和路径不在签名里。
3. **所有操作同一个地址。** 都是 `POST /openapi/api/dispatch`，靠请求头 `msgType` 区分。

第三样好办：网关按路径分路由，每条路由写死一个操作。前两样不行：必须有一个地方拿着密钥，改写请求正文，再把应答解开。

协议的其余几处，后面用得上：

- **加密**照文档里官方的 Go 样例。`encodingAesKey`（43 个字符）后面补一个 `=`，做 base64 解码，得 32 字节的密钥；AES-256-CBC，IV 取密钥的前 16 字节；明文是 16 个随机字符、4 字节大端的正文长度、正文、appKey，按 32 字节的块做 PKCS#7 填充；密文做标准 base64。解密反过来，并核对末尾的 appKey 是自己的。官方样例取随机字符用 `math/rand`，这里不照抄，用 `crypto/rand`。
- **应答的信封**是 `apiResultCode`、`apiErrorMsg`、`apiResultData`、`apiTimestamp`。`apiResultCode` 为 0 时，`apiResultData` 是密文字符串，解密后是这个操作的业务 JSON，里面另有自己的 `success`、`code`、`msg`。
- **访问令牌**另取：`GET /openapi/api/token?appKey=…&appSecret=…`，appSecret 在查询串里。应答里有 `expireIn`（秒）和 `accessToken`。文档写：有效 2 小时；取了新令牌，旧令牌就失效；建议过期前 5 到 10 分钟换；一个客户有几套系统时，要么每套各申请一套密钥，要么自己在几套之间同步同一个令牌。常见问题页另写：测试环境为了方便，令牌是固定的。
- **第一步用得上的三个操作**（`msgType`）：`IECS_CREATE_ORDER`（创建；`customerOrderNo` 要求唯一；文档写创建之后不能修改，要改只能先取消再重建）、`IECS_CANCEL_ORDER`（取消，揽收前才能取消）、`IECS_QUERY_AGENTNO`（服务商单号查询，只读，一次最多 100 个，同一个单号 500 毫秒限一次）。面单（`IECS_PRINT_ORDER`）这一步不做。

2026-11-20 对沙箱做了一次只读探测：三个请求，都是文档写明的正常用法，没有创建任何订单；从开发机直连，不经代理，名字解析到的是公网地址；用的是文档"测试环境授权信息"一页公开给出的那一套凭证。

- 取令牌两次：都是 HTTP 200、`apiResultCode` 为 0、`expireIn` 为 7200，两次是同一个令牌（与常见问题页"测试环境令牌固定"一致），各约 0.1 到 0.15 秒。
- 用 `IECS_QUERY_AGENTNO` 查一个不存在的订单号：HTTP 200、`apiResultCode` 为 0，`apiResultData` 按上面的算法解得开，是业务 JSON：`success` 为真，`successData` 为空，`wrongData` 里一条 `status` 为 `4001`（未找到对应的代理单号）。约 0.4 秒。应答头里有 Kong 的头。承运商应答里的时间比本机快约 0.9 秒。
- 所以加密、签名、解密的算法在沙箱上是对的。沙箱上验不了的有两样：令牌 2 小时过期、取了新的旧的失效；到承运商的 TLS。探测用的程序和凭证都在仓库之外，没有入库。

## 推荐决策

1. **新增一个进程：受限的签名适配器。** 暂名 `provider-signer`，二进制 `cmd/provider-signer`，上下文 `internal/providersigner`，分包照 [ADR-0009](ADR-0009.md) 第 2 条。它是请求路径上的第三个二进制，只用标准库（`crypto/aes`、`crypto/cipher`、`crypto/sha256` 等），`go.mod` 仍然没有依赖。它是网关的一个后端：网关照常验证调用方 JWT、问 `gateway-authz`、按名单重建请求头，然后把调用方的明文 JSON 转给它；它加密、签名、调承运商、解密应答，把明文交回网关。ADR-0009 第 3 条写的是"请求路径和控制面是两个二进制"，它的正文这次不动；本篇被接受之后，再给 ADR-0009 记一笔，与 ADR-0011 第 2 条对 ADR-0003 和 ADR-0008 的做法相同。

2. **凭证仍然只由 `gateway-authz` 持有**（ADR-0011 第 1 条不改）。适配器没有凭证文件，不把任何秘密落盘。
   - `gateway-authz` 多第四种凭证来源，启动参数暂名 `--sf-openapi-apps`。文件的键仍是凭证句柄；值里有令牌端点所在的地址、`app_key`、`app_secret`、`encoding_aes_key`、`key_version`（字段名以实现时为准）。文件的规矩与前三种相同：0600 或更严，换文件后整份重读，坏文件不替换上一份，一个句柄只能在一个文件里，不认识的字段拒绝。
   - 访问令牌向承运商取。缓存和并发照 ADR-0011 第 4 条和 V1.2：按句柄隔离，同一个键并发只取一次，过期之前换新，取不到就拒绝、不用旧的。提前多少换新，实现时取值。
   - 放行时交出的 `Authorization` 是 `Sf-OpenApi ` 加 appKey、分号、访问令牌、分号、AES 密钥。三样都是不含分号和空白的可见 ASCII，写法与万邦那一种同构。整段值放在 `ports.Secret` 里：日志、错误、JSON 里都是占位符。`ports.CredentialSource` 这个端口不改；网关仍只复制 `authorization` 这一个响应头，ADR-0008 第 1、4 条不改；后端上"PDP 放行却没给凭证就拒绝"那条规则的前缀换成 `Sf-OpenApi `，理由同 ADR-0011 第 3 条。
   - 这一家特有的两点。其一，appSecret 在取令牌请求的查询串里，所以这个地址不能进日志和错误信息：Go 的 `*url.Error` 会带着完整的 URL，要剥掉。其二，承运商写明"取了新令牌，旧的就失效"，所以一套密钥只能有一个取令牌的地方：这套密钥要专给这个网关用（顺丰自己的建议也是每套系统各申请一套）。多个 `gateway-authz` 实例各取各的，会互相作废。这是已知的限制，实现时记入开发计划第 5 节"多实例"一项，这一步不解决。
   - 令牌端点的地址默认只许 `https`。沙箱只有明文 HTTP，而且不是回环地址，照 ADR-0011 V1.2 对 OAuth 令牌端点的规矩是不许的。这里给一个只按主机名放开的启动参数例外，默认关着，只为沙箱开。这一条列在"要仓库所有者定的"里。

3. **适配器只做这几件事，别的都不做。**
   - 只收双向 TLS，只认网关的工作负载身份，与 `gateway-authz` 认网关的做法相同（`internal/platform/workloadtls`）。
   - 一张写死的操作表：路径和方法对到 `msgType`。第一步三个：创建订单 `IECS_CREATE_ORDER`、取消订单 `IECS_CANCEL_ORDER`、服务商单号查询 `IECS_QUERY_AGENTNO`。`msgType` 从不取自调用方；表里没有的路径或方法直接拒绝，不联系承运商。具体路径实现时定。
   - 承运商的地址是启动参数，不取自请求。向承运商发的 URL 由这个常量拼出，调用方的路径和查询串到不了承运商（万邦那一家"查询串原样带到承运商"的情形，这里不会出现）。不跟随重定向，不用环境变量里的代理，应答正文有上限，有超时且短于网关路由的 9 秒，不重试：写操作超时或断连，结果是未知，不重放，与万邦相同。上限和超时的取值，实现时定。
   - 请求：从 `Authorization` 里取出 appKey、令牌、AES 密钥，取不出就拒绝，不联系承运商。正文是调用方的明文 JSON，有大小上限，必须是一个 JSON 对象，原样（逐字节）作为明文加密，不重新序列化。时间戳取当前毫秒；随机数和加密用的 16 个随机字符都用 `crypto/rand`。`lang` 是部署时的常量，不取自调用方。
   - 应答：承运商答的是文档里的信封、`apiResultCode` 为 0、`apiResultData` 是字符串时，解密，核对末尾的 appKey，确认是合法 JSON，然后把 `apiResultData` 换成解密出来的 JSON 值，其余字段不动。`apiResultCode` 不是 0 时，信封原样交回，不解密。其余情况（不是 JSON、解不开、appKey 对不上、超过上限）一律答 502 和适配器自己的一个小 JSON 错误，不把密文或解了一半的内容交出去。这样调用方和网关两头看到的都是明文。业务上成没成，要看 `apiResultCode` 为 0 并且解密后的 `success` 为真；HTTP 200 不等于业务成功，这一点与万邦相同，要写进给调用方的说明。
   - 日志：每次调用一行，写哪个操作、`msgType`、上游状态、`apiResultCode`、用时、大小。正文、凭证、令牌、签名、密文都不进日志。

4. **这一家的网关配置照开发计划 3.2 的做法手写。** 每个操作一条路由，形状与万邦的相同（`deploy/providers/wanbexpress/agentgateway.yaml`）：路径形状的规则、`extAuthz` 加路由常量、只复制 `authorization`、请求头名单、后端规则的前缀 `Sf-OpenApi `、不重试、9 秒超时。后端是池里按名字找的适配器，这一跳是双向 TLS，网关出示自己的证书。带客户端证书的 `backendTLS` 用在路由的后端上：写本篇时本仓库的配置里它只用在 `extAuthz.policies` 下面，也就是网关到 `gateway-authz` 那一跳，路由的后端上没有试过。这是动手的第一件事（第 6 条）。2026-11-20 第零步在锁定的 1.7.0 上试过，网关会出示客户端证书，见文末 V1.1。网关看到的是明文，所以访问日志里取客单号和承运商单号的做法（开发计划 3.3）照旧可用，字段名换成这一家的，实现时核对。

5. **出口。** 到承运商的连接现在由适配器发起，不是网关。适配器有自己的网络命名空间，装与网关那一个相同的规则（[ADR-0010](ADR-0010.md) V1.8）：新的外出连接只许去它的配置里写着的地址。做法是给适配器一份带 `host: 名字:端口` 的小配置文件，让同一个 `pin-egress.sh` 不改就能在它的命名空间里用：脚本读哪份文件（`CONFIG`）、回环上另外放行什么（`LOOP_ALLOW`，适配器这边是空）都是环境变量。这在适配器的命名空间里没有试过，第三步核对。网关到适配器这一跳按名字找，所以和到 `gateway-authz` 一样，本来就在网关那一侧被钉住的地址里（`deploy/compose/gateway-authz.yml` 的注释）。`gateway-authz` 到承运商令牌端点这一段的出口规则，这一步不做，与 ADR-0011 V1.2"没有做的"最后一条（OAuth 令牌端点）是同一件事。

6. **分四步做，先做能消掉最大未知数的。**
   - 第零步：在联调架子上用一个最小的回显后端，确认锁定的 1.7.0 能对路由的后端出示客户端证书。不行就停下来报告，不往下建。
   - 第一步：Go 代码（加解密和签名、适配器、`gateway-authz` 的新来源）和单元测试；一个照沙箱今天的样子做的替身；联调架子上的套件；黑盒原有用例的结果不变。`internal/architecture` 里"请求路径只用标准库"的测试看的是一份写死的包清单，新的 `internal/providersigner` 和 `cmd/provider-signer` 要加进去。
   - 第二步：联调架子对着真实沙箱。先只读的查询，再创建加取消；测试订单的 `customerOrderNo` 带 `IDPGW-` 前缀，建了的都取消，取消不掉的单号写在结果里；证据入库，证据里没有凭证。
   - 第三步：进单机池：叠加的 compose 文件、经 `gateway-control publish` 发布、适配器的出口规则、池上的套件。

7. **原有的不改。** 黑盒套件原有用例的期望不改；`gateway-authz` 原有三种凭证来源的行为不变；万邦的配置不动。

## 为什么这样决定

网关的整条既有防线都不用改：JWT、ExtAuthZ、请求头名单、路径形状、访问日志、超时。网关前后看到的都是普通的明文 JSON，它的配置与这一家的协议没有关系，只是后端换成了适配器。凭证仍走一个 `Authorization` 头，所以开发计划 2.6 第一条说的"只认 `Authorization` 这一处"也不用放开。

秘密仍然只有一个存放处。适配器没有凭证文件；撤销照旧在判定里生效：被撤销的账户拿不到凭证，适配器也就无从加密。

适配器小，只用标准库，上游地址是常量，操作是一张写死的表，能逐行评审。这是 G04 第 4 节预留的做法：专用的签名适配器，不把任意代码放进网关核心。`go.mod` 不用加依赖。

## 被考虑的替代方案

- **用 agentgateway 的 ExtProc 改写正文。** 好处是出站连接仍由网关发起，出口规则、到承运商的 TLS、访问日志都不用另做。没有采用：ExtProc 是 gRPC，要给 `go.mod` 加 gRPC 和 protobuf 依赖；锁定的 1.7.0 上请求和应答两个方向的正文替换都没有试过（二进制里找得到 `extProc`、`includeRequestBody` 这些字样，本仓库没有用过）；每个请求同步多依赖一个处理器，G05 对此有保留（原话针对常规日志：ExtProc 是处理器，可能增加延迟和失败依赖；这里不是日志，顾虑相同，适配器也是同步的一跳，见"成本与剩余风险"）。以后有好几家只需要签名、不需要改写协议形状时再看。
- **调用方自己加密，网关只注入令牌和签名。** 调用方要持有 AES 密钥，那是承运商给的凭证，与"调用方不持有承运商凭证"相悖；网关看不到正文；每个调用方都要实现一遍加解密。不选。
- **在网关配置里用表达式做。** 表达式里没有 AES，做不到。
- **把加密和签名放进 `gateway-authz` 进程。** PDP 就上了正文的数据路径，判定和转发成了同一个故障面。不选。
- **适配器自己放一份凭证。** 等于 ADR-0008 里没采用的模式 B：第二个存着凭证的地方，下发、轮换、撤销都要另做一套。不选。代价是 AES 密钥和令牌每个请求经过网关的内存和网关到适配器的那一跳；已有的令牌本来就是这样走的。
- **做成通用的签名框架或插件机制。** 现在只有一家要它，不做。下一家要签名时再加一个包。

## 成本与剩余风险

- 多一个进程、多一跳、多一张证书、多一个故障点。适配器不可用时，这一家的请求全部失败。2026-11-20 起这个进程在仓库里（`cmd/provider-signer`）。
- 到承运商的连接、TLS、超时在适配器里，不在网关里。黑盒报告"默认配置不安全的地方"的九项，在这份配置上对过，表在 [deploy/providers/sfintl/README.md](../../deploy/providers/sfintl/README.md)。第 6、7、8 项这份配置上没有用例，只有契约测试。第 1 项没有判承运商看到的 `host` 的值。第 5、9 项没有「去掉名单」的对照：签名器本来就不转发调用方的头。到承运商的 TLS 仍没有验。
- 长期有效的 AES 密钥，每个请求经过一次网关的内存和网关到适配器的那一跳。能读到这些进程的人能读到它。
- 沙箱只有明文 HTTP。appSecret 在取令牌请求的查询串里，明文过公网；只因为它本来就是文档公开给出的那一套，才可接受。2026-11-20 经网关的那一遍，取令牌和业务请求都是明文：头里的令牌也在其中，正文是密文。到承运商的 TLS 没有验（沙箱没有）。
- 沙箱的凭证是所有人共用的：别人看得到，也取消得了我们的测试订单。只有一个账户。两个账户的隔离在替身的 SF-05 上看到了（green 用 green 的应用；green 取消不了 blue 的单是替身的假设，检查文字里写了）。沙箱上 green 没有账户，被拒。
- 沙箱令牌是固定的，令牌"过期"和"被作废"在沙箱上验不了。替身的 SF-13 看到了作废，以及把寿命改成 5 秒之后换新。第二遍沙箱里 `gateway-authz` 取了三次令牌（SF-09 把进程换了两次，每个新进程取一次）；沙箱令牌固定，没有作废。
- 令牌在别处被作废之后，`gateway-authz` 继续交出缓存里的那一枚，直到应用文件里的 `key_version` 改掉。SF-13 在替身上量到：作废之后的请求是 HTTP 200，承运商的 `apiResultCode` 500，原样交回；接着几次仍是；改掉 `key_version`（旁边写新文件再改名）之后才重新取。适配器没有回头告诉 `gateway-authz` 的路。
- 换新令牌的那一刻，旧令牌即刻失效（文档写的）；已经带着旧令牌在路上的请求会被承运商拒绝。这一步没有处理。在途的那一个请求没有单独量。
- 多个 `gateway-authz` 实例各取各的令牌，会互相作废；一次重启也是一次新的取令牌，生产上同样作废前一枚。记在开发计划第 5 节，这一步不解决。沙箱令牌是固定的，这一条验不了。同一个 `app_key` 写在两个句柄下，启动时拒绝，以后重读文件时也拒绝（`TestTheSameAppKeyUnderTwoHandlesIsRefused`）；比较是逐字节的，只差大小写不算同一个。
- 带客户端证书的 `backendTLS` 用在路由后端上：2026-11-20 第零步在锁定的 1.7.0 上试过，会出示客户端证书。那个程序不在仓库里。联调架子上，做成的请求都经过这一跳；去掉三处 `backendTLS`（`--mutate no-backend-tls`）调用方得到 HTTP 400；`hostname` 写错（`wrong-signer-name`）得到 HTTP 503；签名器改认另一个身份（`signer-other-identity`）时答 403 `caller_not_allowed`。SF-15 不带证书、用另一个 CA 的证书、用另一个身份，直接打签名器。
- 签名里有时间戳，承运商容忍多大的时钟差不知道。只读探测时它的时间比本机快约 0.9 秒。2026-11-20 经网关的沙箱那一遍，承运商的 `Date` 比这台机器慢 0.1 秒（证据里 `offset_seconds` 为 -0.1，精度 1 秒）。
- 承运商对随机数重复的态度不知道；替身会比沙箱严。
- 出口规则只认名字第一次解析到的地址（ADR-0010 V1.8 留下的限制）。2026-11-20 那一遍，`api-ifsp-sit.sf.global` 解析到 156.59.125.28，签名器和 `gateway-authz` 只连了 156.59.125.28:80。名字会不会换地址，只看了这一次。签名器自己的出口规则没有做（第三步）。
- `gateway-authz` 到令牌端点这一段没有出口规则。第 5 条写了这一步不做。
- 取令牌失败只记一个类别：`timeout`、`unreachable`、`status N`、`code N`、`bad_answer`。请求地址里有应用密钥，日志里不写地址。2026-11-20 第一遍沙箱，前两次取令牌是 `unreachable`（127 毫秒、78 毫秒），分不出更细的原因。
- `provider-signer` 不拒绝不短于路由 9 秒的 `--carrier-timeout`。默认是 8 秒。对照 `signer-long-timeout` 给 20 秒，调用方在 9.0 秒得到网关自己的 504，正文不是签名器的 `carrier_timeout`。
- 签名器发给承运商的请求，除了它自己设的八个头，还有 Go 默认的 `User-Agent`（`Go-http-client/1.1`）和 `Accept-Encoding: gzip`。替身记下的头名里有 `user-agent` 和 `accept-encoding`（SF-03，只记名字，不判值）。
- 与 ADR-0009 第 3 条的"两个二进制"不一致。那一条的决定没有改。2026-11-20 在它下面记了一笔；本篇仍是 Proposed。
- 第三步没有做：单机池（叠加的 compose 文件、经 `gateway-control publish` 发布、签名器自己的出口规则、池上的套件和 SF-11）。面单（`IECS_PRINT_ORDER`）没有做。

## 要仓库所有者定的

下面五项请仓库所有者逐条说"照推荐的做"，或者"这一条换成别的"。推荐是执笔者的判断，不是决定。

**2026-11-20，仓库所有者看过本篇之后定的：五项都照推荐的做**（第 2 项同时覆盖明文的令牌端点，和签名适配器到承运商的明文地址；两处各是一个默认关着、按主机名放开的例外）。这是开工的许可，不是对本 ADR 的决定；状态保持 Proposed。下面各项的原文留着，供以后重看。

1. **接不接受请求路径上多一个进程。** 推荐接受。理由见"为什么这样决定"；代价见"成本与剩余风险"第一条。不接受时，撤回本篇；ExtProc 是被考虑过的另一条路，但它在锁定的 1.7.0 上没有试过。
2. **沙箱的明文令牌端点。** 默认只许 `https`，按主机名给沙箱开一个启动参数的例外，默认关着。推荐这样做。本篇的设计只写了令牌端点；适配器到沙箱的业务地址同样是明文 HTTP，执笔者推荐它适用同一个规矩（默认只许 `https`，同一类按主机名放开的例外，默认关着），这也要在这一项里一并定。
3. **第一步只做创建、取消、服务商单号查询三个操作，面单以后。** 推荐这样做。
4. **适配器有自己的网络命名空间和出口规则（复用 `pin-egress.sh`），放在第三步。** 推荐这样做。
5. **名字：进程 `provider-signer`，承运商标识 `sfintl`。** 推荐，可改。

## 做出来了：第零步到第二步（V1.1）

2026-11-20。仓库所有者当天回答五项都照推荐的做。写代码、验证和执笔的是 AI 编码助手。**这不是对本 ADR 的决定**，状态保持 Proposed。第三步没有做。推荐决策的各条没有改写；做出来与正文不同的地方写在下面。

### 第零步

仓库之外的一个临时程序：自己的证书，一个要求并核验客户端证书、把看到的回显出来的后端，锁定的网关，每种情况一条路由。这个程序不在仓库里。结果：锁定的 1.7.0 上，路由后端的 `backendTLS` 带 `cert`、`key`、`root`、`hostname` 时，网关出示自己的客户端证书。

仓库里对得上的是联调架子。做成的请求都经过网关到签名器这一跳。去掉三处 `backendTLS`（`--mutate no-backend-tls`），调用方得到 HTTP 400。`hostname` 写成 `wrong.idp.test`（`wrong-signer-name`），得到 HTTP 503。签名器的 `--gateway-identity` 换成另一个身份（`signer-other-identity`），签名器答 403 `caller_not_allowed`。SF-15 直接打签名器：不带证书，另一个 CA 的证书，另一个身份。

### 与推荐决策正文不同的地方

- 第 3 条写超时短于网关路由的 9 秒。默认 8 秒，是短于。程序不拒绝更长的值。对照 `signer-long-timeout`（20 秒）：调用方在 9.0 秒得到网关自己的 504，正文不是签名器的 `carrier_timeout`。
- 第 3 条写 `apiResultCode` 不是 0 时信封原样交回，是 0 且 `apiResultData` 是字符串时解密，列出来的其余情况答 502。实现里还有一种：`apiResultCode` 为 0 而没有 `apiResultData`，或它是 null，正文原样交回（`ok_no_data`），不答 502。解开成功时信封按成员名的字节序重写，其余成员的值仍是原来的原始字节。
- 第 1 条写本篇被接受之后再给 ADR-0009 记一笔。2026-11-20 在 ADR-0009 第 3 条下记了一笔，本篇仍是 Proposed。ADR-0009 决定的那一句没有改。
