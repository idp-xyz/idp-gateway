ADR-0001 至 0007 随原始设计基线交付。ADR-0008 是其后依据 [P1 PoC 报告](../../tests/acceptance/blackbox/README.md) 的实测结果提出的。ADR-0010 回答 ADR-0009 留下的部署形态问题，依据同一份报告里的配置回读用例和 [kind 集群上的发布验证](../../tests/integration/kubernetes/README.md)；它在 2026-11-11 做过一次技术复核并据此修订为 V1.1，那次复核不是具名批准。同日的 V1.2 记入了仓库所有者对运行平台的决定（先单机 docker compose，以后再上 Kubernetes）和[单机上的发布验证](../../tests/integration/compose/README.md)；这也不是具名批准。V1.3 记入写单机发布器（`cmd/gateway-control`）时看清的一条规则：快照里不能有对环境变量的引用；同样不是具名批准。2026-11-12 的 V1.4 记入发布器新增的对账和带重启的发布；同日的 V1.5 记入[单机的部署文件](../../deploy/compose/README.md)和它规定的启动先后（网关启动之前先把确认过的那一份配置放到位，回读对上了才收请求）；同日的 V1.6 记入看守（`gateway-control keep`）：池里的容器死了由它跑启动命令起回来，平时由它定时对账；2026-11-17 的 V1.7 记入告警：看守每看完一眼给出指标，由一份 Prometheus 规则决定什么时候该叫人。这四次同样不是具名批准。同日的 ADR-0011 提议出站凭证正文由 gateway-authz 持有、按账户现取；这也是提案，ADR-0003 与 ADR-0008 的正文没有改。仓库所有者在 2026-11-18 同意照它动手，那是开工的许可，不是具名批准。同日的 V1.1 记入它的第一步（固定令牌加每个请求一个随机数）的实现和对着替身的验证；承运商的沙箱没有被调用。同日的 ADR-0012 提议撤销状态存在哪里、谁能改，回答 ADR-0009 留下的另一半；仓库所有者当天同意照它动手，同样是开工的许可，不是具名批准。它的 V1.1 记入实现和在黑盒套件里的验证。2026-11-18 的 ADR-0011 V1.2 记入它的第二步（OAuth2 客户端凭证，向令牌端点取令牌、按账户缓存）的实现和对着替身令牌端点的验证；那是 2026-11-18 在 V1.1 那一步之后做的第二步，没有对着任何真实的令牌端点，同样不是具名批准。2026-11-18 的 ADR-0010 V1.8 记入出口的规则（网关所在的网络命名空间里，新的外出连接只许去配置里写着的地址，池因此多了两个服务）；它补记的是开发计划 3.1 已经做了的事，同样不是具名批准。2026-11-19 的 ADR-0012 V1.2 记入操作员撤销账户用的三条命令（`gateway-control revoke`、`restore`、`revocations`）：各对着 `gateway-authz` 的撤销接口发一次请求，“不知道”和“撤销已经生效但没有写下去”各是单独的结局；V1.1 写的“操作员的命令没有做”由它取代；没有具名批准，状态仍是 Proposed。2026-11-19 的 ADR-0013 提议发布历史怎么存（应用层一个端口，第一个实现是池旁边的文件，Bento-Go 和 PostgreSQL 等第二台机器或接 Fabric 时再进来）；仓库所有者当天看过，把它列出的六项都定成照推荐的做，那是开工的许可，不是具名批准；写这一句时还没有动手。2026-11-19 的 ADR-0013 V1.1 记入它的两个阶段：Go 代码（`releases`、`release`、`rollback` 三条新命令，`publish`、`restart`、`reconcile`、`keep` 多了 `--history-dir`）和部署（只有看守和操作员的命令碰历史，开机的路上不碰），以及在真的池上的验证；状态仍是 Proposed，没有具名批准。
