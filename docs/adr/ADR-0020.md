# ADR-0020 — API Fabric 发布意图适配器与认证模板编译闭环（gateway-fabric）

> **状态**：Proposed · **版本** V1.0 · **日期** 2026-11-24  
> 本 ADR 为设计建议，不是已经执行的技术审批、生产基线或运行验收。代码还没有写。执笔的是 AI 编码助手。  
> 2026-11-24 仓库所有者定了阶段 0：轨道 B 的 API Fabric 发布适配器先复用现有文件历史和单机池，`go.mod` 保持零第三方依赖，阶段 2 再上 Kubernetes 多副本和 PostgreSQL / Outbox（`idp-bento-go`）；顺丰国际「取新令牌即作废旧令牌」的跨实例令牌租约协调器纳入阶段 2；生产一期保持 18 页 Console 冻结（`scope_freeze.ui_ux_expansion.state` 仍为 `FROZEN`），正文采集 `GW-GAP-07` 仍关闭，新路由与认证方案声明走 API Fabric，应急处置留在现有回环 `gateway-console`。这是范围。本篇仍是 Proposed，点头之后才写代码。

## 背景

[ADR-0006](ADR-0006.md) 把发布批准放在 Fabric，把运行配置和观察到的状态放在本网关。适配器还没有做。契约已经在 [route-publication-intent.openapi.yaml](../../contracts/fabric/route-publication-intent.openapi.yaml)：信封是 `RoutePublicationIntent`，里面一条 [RouteIntent](../../contracts/gateway/route-intent.schema.json)。示例是 [route-publication-intent.example.json](../../contracts/fabric/route-publication-intent.example.json)。契约里的 `servers.url` 写的是 `https://gateway-control.idp.internal`，那是草案里的控制面名字；路径只有两个。

编译器已经在 [ADR-0016](ADR-0016.md)。`internal/routecompile/domain.Compile` 吃一份 `CompileSpec`：一个 `PoolSpec`、一个 `ProviderSpec`、一份 `AccessSpec`、多条 `RouteSpec`。`emitGateway` 让每条业务路由都用这一个 `Provider`。万邦和顺丰今天是两份规格（`deploy/providers/wanbexpress/compile-spec.json`、`deploy/providers/sfintl/compile-spec.json`），池名都可以叫 `egress-test`，编出来是两份 YAML，不是一份。入口是 `CompileIngress`，AI 是 `CompileAI`。`gateway-control compile` 按文档里的 `traffic_class` 分流。`ParseSpec` 拒绝未知字段、`${…}` / `$` 加大写字母的环境变量引用，以及真值的敏感键。

发布和历史已经在 [ADR-0010](ADR-0010.md)、[ADR-0013](ADR-0013.md)。池锁是配置目录上的 `flock`（`internal/gatewayconfig/adapters/directory/hold_unix.go` 的 `Hold`，已被占着时不等）。历史目录 0700，快照 0600，写临时文件、刷盘、改名。`domain.ReleaseState` 写进日志的是 `STAGED`、`APPLYING`、`OBSERVING`、`ACTIVE`、`FAILED`、`UNKNOWN`，另有 `OVERTAKEN`；`SUPERSEDED` 是读的时候推出来的。`History.Begin` 写下去的起始行不填 `route_intent`。`domain.Release` 上那个字段的注释仍是「现在永远为空」。日志解析只认 `Known()` 里的状态；把契约的 `DRAFT` 或 `APPROVED` 写进 `releases.log`，下一次读会当成历史损坏。

登记表是缺口。`internal/egressauthz/adapters/filestore/policy.go` 的 `LoadPolicy` 把文件读进 `domain.Policy`。`cmd/gateway-authz` 只在启动时调用一次。`application.New` 写明：登记表在进程生命周期内不变，换登记表要换进程。`Decide` 用的是构造时那一份。同一包里的开发者令牌和配额不是这样：`developer_tokens.go` 的 `sameFile` 用 `os.SameFile`、修改时间相等、大小相等判断文件没有换；读不成就留上一份，记一条不含正文的错误。`ratelimits.go` 同一形状。

回读对得上的摘要是 `domain.PublishedDigest`（网关 `/config_dump` 里由发布文件决定的那一部分）。`Observation.Confirms` 要求这份摘要相等、加载成功、存储是只读。YAML 字节的 SHA-256（`CompiledArtifacts.GatewaySHA256`、`Snapshot.ID()`）是另一回事，发布器不用它跟回读比。

`go.mod` 只有模块名和 Go 版本，没有 `require`。`internal/architecture/boundaries_test.go` 的 `TestContextsAreLayered` 禁止一个限界上下文的包导入另一个上下文。`domain` 不能做 I/O，也不能导入 `net`、`net/http`、`os`、`database/sql` 那些被点名的包。Bento-Go 只允许出现在上下文的 `adapters` 和 `cmd`。请求路径的清单里没有控制面。

认证方案的契约是 [credential-binding.schema.json](../../contracts/gateway/policies/credential-binding.schema.json)：`auth_scheme` 是 `API_KEY`、`OAUTH2_CLIENT_CREDENTIALS`、`OAUTH2_AUTHORIZATION_CODE`、`HMAC_REQUEST_SIGNING`、`MTLS_CLIENT_CERT`；`account_resolution` 只能是 `GATEKEEPER_AUTHORIZED_ACCOUNT`；`request_signer_ref` 匹配 `^signer:[a-z0-9/_-]+$`；`additionalProperties` 是 false，模式里没有密钥字段。编译器不读这份绑定。它读的是 `ProviderSpec` 上的 `credential_scheme`（一个词加一个结尾空格）、`credential_header`、`credential_query_parameter`。默认位置复制 `Authorization` 响应头。[ADR-0008](ADR-0008.md) V1.1：别的请求头或查询参数改为读进 `extauthz.credential`，核对方案前缀，去掉前缀，再由 `backendAuth` 放上去；两样不能一起写。万邦的方案词是 `Hc-OweDeveloper `（[ADR-0011](ADR-0011.md)）。顺丰的方案词是 `Sf-OpenApi `，上游是 `provider-signer`，`upstream_tls` 仍是 `VERIFY_REQUIRED` 并且规格里有 `backend_tls`（[ADR-0014](ADR-0014.md)）。RouteIntent 上没有 `auth_scheme`、`credential_header`、`rewrite_path_prefix`、`route_id`、`path_match_mode`。这些字段今天在编译规格里，不在 Fabric 能合法送出的意图里。

## 推荐决策

1. **新二进制 `cmd/gateway-fabric`，新上下文 `internal/fabricpub`。** 四层是 `domain`、`ports`、`application`、`adapters`。`domain` 只有规则：状态怎么迁、正文怎么规范化、意图怎么并进一份 `CompileSpec` 的输入、哪些字段算冲突。它不做 I/O，不导入 `routecompile`、`gatewayconfig`、`egressauthz`。跨上下文只发生在 `cmd/gateway-fabric` 的装配里：`ports` 上的编译端口和发布端口由 `main` 接到现有的 `internal/routecompile` 和 `internal/gatewayconfig`。`adapters` 只放本上下文的 HTTP 和 `--state-dir` 文件。这样过 `TestContextsAreLayered` 和 `TestDomainIsPureRules`。不改 `cmd/gateway-control` 的命令分支，不改 `deploy/compose/compose.yml` 的服务和路径，不往 `go.mod` 加 `require`。`gateway-fabric` 这一期不写进 compose，也不写进 systemd，由下面的套件自己拉起。

2. **按契约听 mTLS，只做那两个路径。** 服务端用 `internal/platform/workloadtls.ServerConfig`：TLS 1.2 起，`RequireAndVerifyClientCert`。`--fabric-identity` 是唯一允许的客户端 SPIFFE URI，取法与 `gateway-authz` 的 `--revoker-identity`、发布器证书相同：`PeerIdentity` 在没有 URI 或不止一个 URI 时是空串。空串或与 `--fabric-identity` 不同的 URI，HTTP 401，不读进池。没有客户端证书，或证书不是配置的 CA 签发的，握手完不成，到不了 HTTP。套件两样都覆盖；能形成 HTTP 应答的那一笔是 401。两个 `Host` 头在进处理函数之前就是 400，处理函数里若仍看到多于一个 `Host` 也是 400，与 `cmd/gateway-console` 相同；两种情况都不读正文、不改状态。正文超过 1 MiB（与配额文件的读取上限同量级）是 422，应答不回显正文。

   `POST /v1/route-intents` 受理时是 202，JSON 正好是 `intent_id`、`release_ref`、`state`。`intent_id` 用内嵌 RouteIntent 的 `intent_id`（`^gwi-[a-z0-9-]{3,64}$`），不另造一个。`release_ref` 原样抄信封。`state` 是 `DRAFT`。`GET /v1/route-intents/{intent_id}/status` 是 200，JSON 永远带上 `intent_id`、`release_ref`、`desired_digest`、`observed_digest`、`state`。契约把后两个标成非必须；本进程仍写出这两个键，还没有的用空串。没有这条 `intent_id` 是 404，正文不回显路径。`state` 只许契约 `ReleaseState` 的 16 个词：`DRAFT`、`VALIDATED`、`APPROVED`、`STAGED`、`APPLYING`、`OBSERVING`、`ACTIVE`、`REJECTED`、`CANCELED`、`FAILED`、`PARTIAL`、`UNKNOWN`、`SUPERSEDED`、`WITHDRAW_REQUESTED`、`REVOKING`、`REVOKED`。不写 `RECEIVED`。不写控制台标签 `REVIEW`、`ROLLOUT`、`RECONCILED`、`REVERTED`。不把 `gatewayconfig` 的 `OVERTAKEN` 写进这个字段。

3. **幂等和代次在落记录之前做完。** 比较用的是规范化正文：解码后按键名排序再编码，数组保持顺序。同一个对象里同一个键出现两次，422。未知字段、九个敏感键的真值（`password`、`client_secret`、`secret_value`、`api_key`、`access_token`、`refresh_token`、`private_key`、`authorization`、`bearer_token`，与 `preflight.go` 的 `sensitiveKeys` 相同）、信封或 RouteIntent 不满足模式、环境变量引用，都是 422。同一 `idempotency_key` 加上规范化后相同的正文，返回第一次的 202，三个字段原样，包括 `state: DRAFT`；当时的进度用 GET 看。同键、规范化后不同的正文，409，池不动，键仍绑在第一次的正文上。`expected_generation` 与 `--state-dir` 里该池的当前代次不一致，409，并且不占用这个键，改对代次之后可以再用。池已有一条还没了结的发布（不是 `ACTIVE`、`REJECTED`、`FAILED`、`SUPERSEDED`，也不是已经交给对账的 `UNKNOWN` / `PARTIAL`）时，另一把键也是 409。代次从 0 起，只在一条发布变成 `ACTIVE` 时加一。422 和这两种 409 都不改代次、不改策略文件、不改网关快照、不追加历史。

4. **一条意图并进该池当前的整份规格，再编译。** `--pool-base` 是只读 JSON，形状就是今天的出站 `CompileSpec`（`pool`、`provider`、`access`、`routes`），用 `ParseSpec` 的规则读：未知字段、环境变量引用、敏感键都拒绝。里面没有密钥。`routes` 是目录，不是已经生效的集合：每条给出编译器要、而 RouteIntent 没有的 `route_id`、`path_match_mode`、`rewrite_path_prefix`。`route_id` 须符合编译器现有的小写令牌（字母开头，其余只许小写、数字、连字符，最长 64）。`--state-dir` 必须已经存在，0700，本进程不替敲错的路径建目录。其下文件 0600。锁用 `flock`；写入是临时文件、`fsync`、原子改名、再刷目录，与历史适配器同一套。目录里存该池当前有效意图、每条发布的 16 词状态、幂等键到第一次 202 的映射、池代次。

   合并在 `domain` 里做完，再由 `cmd` 调用 `Compile`。有效集里同一 `intent_id` 换成这一条；没有就加上。`operation_id` 加那一个方法必须对上目录里的一条。`allowed_methods` 多于一个是 422，因为 `RouteSpec.Method` 是一个方法。`logical_path`、`credential_binding_ref`、`upstream_hostname`、`upstream_port` 必须与目录行和 `provider` 一致，意图不能改写重写前缀，也不能把上游换成目录里没有的主机。`gateway_pool` 必须等于 `pool.name`，并且过 `domain.ValidatePool`。信封的 `target_id` 必须等于 `--target-id`。对不上是 422。然后对合并后的整份规格做预检和 `Compile`。`PROD` 上的 `PLAIN_HTTP_SANDBOX_EXCEPTION` 由现有的 `plainHTTPAllowed` 拒绝。通过之后用锁定的 `agentgateway 1.7.0 --validate-only`，给了 `--lock-file` 就按 `deploy/agentgateway/agentgateway.lock.json` 核对二进制 SHA-256。校验失败是 422，输出文件不写，池不动。编出来的 YAML 是这一份 pool-base 上全部有效意图，加上编译器自己的回读路由，不是只含刚才那一条的片段。

   一份 `CompileSpec` 只有一个 `Provider`。一期一个进程配一份 `--pool-base`，也就是一家承运商、一种流量类。万邦和顺丰继续各是一个编译目标。第二个提供商或入口 / AI 规格不在这一份进程里混编。

5. **认证方案只做绑定元数据到现有编译字段的核对，不搬密钥。** 绑定是只读 JSON，符合 `credential-binding.schema.json`，由 `--bindings` 给出，按 `intent.credential_binding_ref` 查找。找不到、多出来的字段、或出现敏感键，422。绑定里的 `provider_id`、`environment`、`authorized_credential_ref` 必须与 pool-base 的提供商一致。`account_resolution` 只能是模式里的那个常量；意图的 `provider_account_strategy` 只能是 `GATEKEEPER_DECISION_BINDING`（编译器的 `routeIssues` 已经拒绝别的）。

   一期按已经在编译器和请求路径里跑通的几种核对：

   | 绑定 `auth_scheme` | pool-base 必须已经是 |
   |---|---|
   | `API_KEY` | `credential_scheme` 是一个词加一个结尾空格。不写 `credential_header`、也不写 `credential_query_parameter` 时，走默认的 `Authorization` 复制。写了自定义头或查询参数时，沿用 ADR-0008 V1.1：`extauthz.credential` 加 `backendAuth`，两样不能同时写。 |
   | `OAUTH2_CLIENT_CREDENTIALS` | 同上的放置规则。绑定可以带 `audience`、`scope_set`、`token_ttl_max_seconds`。密钥仍在 `gateway-authz` 的 `--oauth-clients` 文件里，本进程不读。 |
   | `MTLS_CLIENT_CERT` | `backend_tls` 只有主机名，`upstream_tls` 是 `VERIFY_REQUIRED`。证书文件留在池的 `tls_dir`。 |
   | 万邦这种命名适配器 | `provider_id` 与方案词 `Hc-OweDeveloper ` 对上。开发者令牌文件仍由 `gateway-authz` 按现有热重载去读。 |
   | 顺丰这种命名适配器 | 绑定带 `request_signer_ref`。pool-base 的 `internal_backend_host`、`VERIFY_REQUIRED`、`backend_tls` 和方案词 `Sf-OpenApi ` 对上。 |

   `OAUTH2_AUTHORIZATION_CODE`，以及没有 `request_signer_ref` 的 `HMAC_REQUEST_SIGNING`，一期 422。不接受意图或绑定里的自由头拼接脚本，也不接受意图往 `set_request_headers` 里加键。密钥明文、`${ENV}` 引用继续拒绝。顺丰「取新令牌即作废旧令牌」的跨实例协调不在这一期；多个 `gateway-authz` 仍会各取各的令牌。那是阶段 2 的协调器。

6. **状态机记在 `--state-dir`，发布器只经手它已经会记的那一段。** 同步检查（第 3、4、5 条）全部在 202 之前做完，并且持有状态目录的锁，不持有池锁。通过之后才写下 `DRAFT` 并返回 202。契约对 202 的说明是还没有应用；同步的 422 对应契约里「信封或 RouteIntent 校验或预检失败」，编译和 `--validate-only` 算在同一次拒绝里，免得一份二进制不接受的配置先变成一条发布。

   异步协程按这个顺序记状态：`DRAFT` → `VALIDATED` → `APPROVED` → `STAGED` → `APPLYING` → `OBSERVING` → `ACTIVE`。`VALIDATED` 表示同步的预检、编译和 `--validate-only` 已经过了，不再做第二次。`APPROVED` 只表示意图里已有长度合格的 `approval_ref`。2026-11-19 仓库所有者定过：本项目不另设批准人。本进程不把 `APPROVED` 当成网关已经接上配置。G03 第 3 节也是这么写的。

   从 `STAGED` 起拿池锁（`Hold`，非阻塞）。拿不到就保持原状态，稍后重试，不另造 409。然后：

   - 先把编译出的登记表 JSON 原子换上 `gateway-authz` 正在读的那份策略文件，再发布快照。顺序是为了网关开始放行这条路由时，PDP 已经能认它。新路由在旧登记表上是默认 `DENY`。
   - 热重载补在 `filestore` 的登记表上，形状与 `developer_tokens.go` / `ratelimits.go` 相同：下次判定前看 inode、修改时间、大小；坏文件留上一份，日志只有路径和错误，没有正文。`Decide` 和 `PolicyVersion` 改为先取当前这份。`application.New` 里「进程内不变」那句到时候改掉。
   - 发布器证书今天不是 `gateway-authz` 的调用方（调用方只有网关、broker、撤销者）。推荐允许发布器身份做一次不会放行、也不取凭证的读取，只看应答里已经有的 `policy_version` 是否等于刚写下去的 `version`。对上了才 `publish`。这一条请所有者定，见下面第 3 项。
   - `desired_digest` 从 `STAGED` 起是发布器离线加载得到的运行配置摘要，之后不变。在那之前这个键在，值是空串。`observed_digest` 是回读口报告的摘要，还没有回读就是空串。YAML 的 SHA-256 另存在状态目录里，用来发现快照被改，不拿去和回读比。
   - 只有 `observed_digest` 与 `desired_digest` 都非空且相等，并且满足现有的 `Observation.Confirms`（已同步、存储只读），才把意图标成 `ACTIVE`，池代次加一，同一 `intent_id` 在这个池上的上一条 `ACTIVE` 标成 `SUPERSEDED`。别的 `intent_id` 若仍在合并后的快照里，它们的记录保持 `ACTIVE`。历史日志里的 `SUPERSEDED` 仍由「同一个池上更晚的一条 `ACTIVE`」在读时推出来，两套粒度不一样，都保留。

   失败怎么落：

   | 情形 | `state` |
   |---|---|
   | 同步检查没过 | 不落记录，HTTP 422 或 409 |
   | 已经 202，池和策略文件都还没改，后面的步骤做不成 | `REJECTED` |
   | 动过池，上一份快照确认放回，策略文件也回到上一份 | `FAILED` |
   | 动过之后不能确认已经回到上一份 | `UNKNOWN`，等对账 |
   | 策略文件和快照各落在不同代次，而且换不回同一代 | `PARTIAL`，等对账 |
   | 历史里被收成 `OVERTAKEN` | 对外写 `UNKNOWN`，不写出 `OVERTAKEN` |

   单机只有一个数据面实例。`PARTIAL` 只用于上面那一行，不用来表示「多个副本里成功了一部分」。`CANCELED`、`WITHDRAW_REQUESTED`、`REVOKING`、`REVOKED` 留在词表里，一期没有把它们写出去的路径。对账走现有的 `reconcile`：`UNKNOWN` 或 `PARTIAL` 不另开一条发布，直到对账说清池上到底是哪一份。

7. **一期是文件和单机池，阶段 2 只换端口后面的适配器。** 状态机、HTTP 契约、代次和摘要的含义不变。阶段 2 才把 `ports` 的存储换成 PostgreSQL / Outbox（`go.idp.xyz/idp-bento-go`），导入只出现在 `internal/fabricpub/adapters` 和 `cmd/gateway-fabric`；第一次引入的那个提交按 [ADR-0009](ADR-0009.md) 第 4 条同时带上 `tests/bentocontract` 和显式迁移命令。Kubernetes 多副本也在阶段 2。顺丰的跨实例令牌租约协调器同样在阶段 2，不塞进这个发布适配器。

   撤销和操作封禁继续走 `gateway-authz` 上现有的接口，以及 `gateway-control revoke` / `restore` / `revocations` / `ban` / `unban`，也继续可以由回环上的 `gateway-console` 转发。它们不进这条发布队列，发布进行中也不把撤销表锁住。本进程不实现 `gateway-control rollback`，也不调用它来代替操作员的回滚。`scope_freeze.ui_ux_expansion.state` 保持 `FROZEN`。不改 `portal/prototypes/`，不加 UX 用例，也不把 18 页 Console 放进一期。正文采集继续关着。

## 为什么这样决定

单条 `RoutePublicationIntent` 描述一条路由。数据面上的一份快照是一个池的整份配置。现有 `Compile` 又只能把一家承运商编进一份 YAML。所以一期的闭环是：一份只读的 pool-base 提供监听器、回读口、JWKS 文件、ExtAuthZ、访问范围、TLS 目录、方案词和路由目录；状态目录保存这个池已经生效的意图；新意图并进去之后整份重编、用锁定的 1.7.0 校验、再经现有发布器放到这个单机池上。不在这一步改编译器去接受多家承运商，也不改 RouteIntent 的模式去偷运 `rewrite_path_prefix`。

登记表如果仍只在 `gateway-authz` 启动时读一次，新路由要么要重启 PDP，要么在重启前被默认拒绝。重启会打断正在判定的请求。开发者令牌和配额已经证明同一进程里按文件替换重读、坏文件留上一份是行得通的。策略文件先于快照换上，是为了避免网关已经露出新路由而 PDP 还拿着旧表。

文件和单机池是 2026-11-24 的阶段 0 决定，也是 [ADR-0013](ADR-0013.md) 已经落地的那条路。`go.mod` 保持没有第三方依赖。Bento-Go 和多副本留到阶段 2，端口先留好，免得状态词到时候再改一遍。

对外状态用契约的 16 个词，是因为 G03 第 9 节写明控制台标签不是另一套状态。历史日志吃不下这 16 个词，所以意图状态放在 `--state-dir`，不往 `releases.log` 里写它不认识的状态。

## 被考虑的替代方案

- **在 `gateway-control` 里加 `serve-fabric`。** 能少一个二进制。不选。`gateway-control` 的命令是做完就退出的那一组，compose 套件按这些命令的路径在跑。把一个常驻的 mTLS 服务塞进同一个 `main`，容易碰到那条提前返回的分支。新进程把装配放在新的 `cmd` 里，现有命令一个字不用改。
- **让 `internal/fabricpub` 直接导入 `routecompile` 和 `gatewayconfig`。** 不选。`TestContextsAreLayered` 会失败。
- **先上 PostgreSQL、Outbox 和 Kubernetes。** 不选。阶段 0 已经定了一期走文件和单机池。
- **202 先收下，校验失败再标 `REJECTED`。** 契约对 202 的字面是校验还没发生。那样一份预检或 `--validate-only` 失败的意图也会占一条发布。不选。同步拒绝用 422，202 只表示已经收下、还没往池上应用。若所有者认为 POST 里跑 `--validate-only` 太慢，再改本篇，见变更条件。
- **把登记表热重载做成重启 `gateway-authz`。** 不选。发布一条路由不该打断判定。
- **策略文件和快照谁先写完就把意图标成 `ACTIVE`。** 不选。文件写下去还不是回读确认。
- **在意图里接受自由的头模板或脚本。** 不选。放置方式只有编译器已经实现的那三种，加上万邦和顺丰这两个已经命名的适配器。
- **解开 18 页 Console，或把回滚搬进本进程。** 不选。阶段 0 把这两件事留在原处。

## 验收计划

新套件 `tests/integration/fabric/`。Fabric 一侧是替身客户端，出示 `--fabric-identity` 那张证书。服务端是真实的 `gateway-fabric`。校验和回读用锁定的 `agentgateway 1.7.0`（`--lock-file` 对得上锁文件里的 SHA-256）。PDP 是真实的 `gateway-authz`。至少覆盖：

- 一条合法意图走到 `ACTIVE`：`observed_digest` 等于 `desired_digest`，池代次加一，同一 `intent_id` 的上一条 `ACTIVE` 变为 `SUPERSEDED`。
- 同一键、同一规范化正文再次 POST，得到第一次的 202，`state` 仍是 `DRAFT`；GET 看到的是当前状态。
- 同键异体 409。代次不对 409。池上已有未了结发布时另一把键 409。这三样都不改池。
- 未知字段、敏感键、`PROD` 明文例外、预检失败、编译失败、`--validate-only` 失败：422，策略文件和快照都还是上一份。
- 回读摘要对不上：`UNKNOWN`，然后对账；不把这一条标成 `ACTIVE` 或 `FAILED`。
- 发布进行中，撤销和封禁仍走现有客户端，不排在发布队列后面。
- 没有客户端证书：握手失败。错误的 SPIFFE URI：401。两个 `Host` 头：400。
- 安全负向对照，一次改坏一处：正文里的密钥、`${ENV}`、目录里没有的上游、绑定方案与 pool-base 对不上、坏的登记表文件被换上之后 PDP 仍用上一份。

这一期会改 `internal/egressauthz` 的登记表读取，源码哈希会变。黑盒套件要从干净树重跑。最近一次记录是 97 个用例、97 个通过、752 项检查（提交 `9152cff`，证据 `a6f64b4`，`P1-SS-04` 已按 2026-11-23 的决定改为接受）。重跑要保持 97/97。本篇没有跑过这套，也不把没跑的写成已经通过。compose 套件的路径不改；不把它的既有记录换掉。

## 成本与剩余风险

- 一期一个进程、一个池、一家承运商。池锁只在这一台机器上有效。第二个副本会互相抢同一把锁，或者各写各的目录。多副本要等阶段 2。
- `gateway-control publish` 若和本进程同时写同一个池，靠的是同一把池锁。谁先拿到谁先做。本进程的意图集合不会自动跟一次绕过它的手工发布走。一期应只有一个写入方。
- `gateway-control rollback` 这一期不会把登记表文件一起滚回去。回滚之后，网关快照和 PDP 的登记表可能不在同一代。多出来的登记行是默认拒绝以外的放行条件，对不上的路由仍会被 PDP 拒绝；方向反了就会 `PARTIAL` 或 `UNKNOWN`，等对账。操作员要知道回滚还在原来的命令里，而且它看不见 `--state-dir`。
- 热重载在请求路径上。坏文件必须留上一份。若实现做成「读不成就换成空表」，默认拒绝会变成没有任何登记，或者反过来放宽。验收里的负向对照就是看住这件事。
- 发布器身份若被允许去读 `policy_version`，那个调用必须不能放行、不能取出凭证。做宽了就多了一条发凭证的路。
- `desired_digest` 在 `STAGED` 之前是空串。把它和 YAML 的 SHA-256 比，会永远对不上。`ACTIVE` 只比运行配置摘要。
- 目录里没有的 `operation_id` 发不出来。新操作要先改只读的 `--pool-base`，再由 Fabric 发布。这是 RouteIntent 没有重写前缀的结果。
- 顺丰的令牌在一期仍是每个 `gateway-authz` 进程各取各的。重启也会再取一次。阶段 2 的协调器做之前，生产上多副本会互相作废。
- 数字错误预算和正式 SLO 不在本篇里。ADR-0018 接受之后这两项仍未批准。
- 黑盒 97/97 是要在写代码之后重跑才算数。本篇不提前记成通过。

## 要仓库所有者定的

下面五项请逐条说「照推荐的做」，或者「这一条换成别的」。推荐是执笔者的判断，不是决定。点头之后才写代码。

1. **独立的 `cmd/gateway-fabric`，还是 `gateway-control serve-fabric`。** 推荐独立二进制。现有 CLI 和 compose 套件路径不动，上下文之间的调用只在新的 `cmd` 里装配。
2. **`--pool-base` 加上意图集合并，一个进程一家承运商。** 推荐这样做。`routes` 是目录，提供 `route_id`、`path_match_mode`、`rewrite_path_prefix`；Fabric 的意图只能启用目录里已有的那一条，并入该池当前全部有效意图后整份编译。一家一个进程。不在 RouteIntent 里加字段。
3. **`gateway-authz` 登记表热重载，并且先换策略文件、确认 `policy_version`、再发布快照。** 推荐做。重载与开发者令牌、配额同构；坏文件留上一份。发布器身份只许做一次不放行、不取凭证的版本读取。若这一条不接受，一期就只能在发布后靠下一次判定才看到新表，新路由在那之前是 `DENY`。
4. **一期的流量类先只做 Egress。** 推荐先做 Egress。`CompileIngress` 和 `CompileAI` 留到后面的切片；这一期的进程若读到入口或 AI 规格，启动失败。同步把三种都接上，要另写两套合并规则。
5. **校验和 `--validate-only` 放在 202 之前，失败即 422。** 推荐这样做。202 的正文始终是 `DRAFT`，表示还没往池上应用。若 POST 的时延不能接受，再把原生校验挪到异步，失败记 `REJECTED`，并改本篇。
