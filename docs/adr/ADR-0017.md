# ADR-0017 — 出站流量治理：按账户限流、入口并发上限与承运商被动熔断

> **状态**：Accepted · **版本** V1.0 · **日期** 2026-11-20（2026-11-21 仓库所有者定为 Accepted）

## 背景

开发计划第 5 节把按 Provider 账户的配额和限流（`GW-GAP-09`）、以及过载和熔断（`GW-GAP-05`）列为还没有做。动手之前在锁定的 agentgateway 1.7.0 上量过：

- ExtAuthZ 答 HTTP 429，带 `Retry-After` 和一段 JSON 正文时，网关把这份应答原样交给调用方，不叫后端。
- `frontendPolicies.http.maxConcurrentRequests` 超额是 503。`frontendPolicies.tcp.maxConnections` 生效。路由上的 `localRateLimit` 超额是 429，并带 `Retry-After`。
- 1.7.0 没有能用的、针对静态 `host:` 后端的熔断或异常检测。`health.eviction` 校验得过，失败的静态主机没有被摘掉。

[ADR-0016](ADR-0016.md) 的编译器可以写出 `frontend_limits` 和 `localRateLimit`。它不知道一次请求最后选定的是哪个 Provider 账户。那个账户是 `gateway-authz` 判定之后才有的。

## 推荐决策

1. **按 Provider 账户的限流放在 `gateway-authz`。** 只有它在授权之后知道选定的 `account_id`。启动参数 `--rate-limits <文件>`，可选，默认不给，不给时行为与原来相同。配额文件是 JSON，里面没有秘密。文件换了就整份重读。新文件不合法时保留上一份，并记一条错误。
2. **配额文件是 `version` 加 `buckets`。** 每个桶有 `id`、`provider_id`、`operation_id`、`key_dimensions`、`max_requests`、`window_seconds`，可选 `burst`。不认识的字段拒绝，所以文件里没有 `coordination`。维度与提交说明一致：`provider`、`provider_account`、`tenant`、`operation`、`service`。每条规则都必须有 `provider_account`。出站配额必须含这个维度，见 [traffic-policy.schema.json](../../contracts/gateway/policies/traffic-policy.schema.json)。`burst` 只限制桶的容量，必须在 1 和 `max_requests` 之间；不写时容量就是 `max_requests`。补充速率仍是 `max_requests / window_seconds`。
3. **先查全部命中的规则，再一起扣。** 后一条拒绝时，前面已经查过的规则不扣。进程内的桶最多留 8192 个键，超过之后丢掉闲置的和最久没用的。丢掉的键下一次拿到满的新桶。这是内存上限，不是跨重启的精确配额。桶只在本进程里。行为对得上契约枚举里的 `LOCAL_APPROXIMATE`。`DISTRIBUTED_COORDINATED` 没有实现。
4. **顺序固定。** 策略、撤销、Gatekeeper 的授权，这三样都过了，才查限流。限流在发放凭证之前。没有授权或已被撤销的调用方扣不了这个账户的配额。被限流的请求不取凭证，也不写出 `Authorization`。ExtAuthZ 答 HTTP 429、`Retry-After`、`X-Idp-Decision-Id`，原因码 `RATE_LIMITED`。模式 B 的判定接口仍是 HTTP 200，决定是 `DENY`，原因码 `RATE_LIMITED`，与契约一致。
5. **入口并发和连接上限用数据面已经量过的那几项。** `frontendPolicies.http.maxConcurrentRequests`、`frontendPolicies.tcp.maxConnections`、路由 `localRateLimit`。`gateway-control compile` 能把前两样写成 `frontend_limits`，把后一样写成每条业务路由上的 `localRateLimit`。见 ADR-0016。
6. **承运商的被动熔断放在 `provider-signer`。** 数据面上静态 `host:` 的熔断在 1.7.0 不能用，所以熔断做在真正去连承运商的那个进程里。`--cb-failure-threshold` 默认 0，表示关着。`--cb-open-duration` 默认 30 秒。阈值大于 0 时，打开时长必须大于 0。状态是关闭、打开、半开。打开持续 `OpenDuration`。半开时同时只放一个探测。探测成功回到关闭，探测失败再打开。半开探测若 panic，记成失败，电路重新打开，探测标志不一直占着。
7. **什么算承运商故障，在联系承运商之前才查电路。** 调用方自己的 4xx 不计入，也看不到 503。传输错误、承运商 HTTP 大于等于 500、HTTP 200 但信封读不成，记失败。HTTP 200 且信封读得成，记成功，包括业务拒绝和信封一级的拒绝。承运商的 4xx 记中性，不增加也不清零连续失败。电路打开时答 HTTP 503，`error` 是 `carrier_circuit_open`，不联系承运商。

## 为什么这样决定

账户级的配额必须用判定选定的账户，不能用调用方自己报的账户。这个值只在 `gateway-authz` 里。1.7.0 会把 ExtAuthZ 的 429 原样交回去，所以限流不必再在数据面上做第二套。并发上限和按路由的本地限流，1.7.0 已经做了，编译器把它写进配置。静态主机的熔断 1.7.0 做不到。万邦的后端就是静态 `host:`，不经过 `provider-signer`。这一家有超时、并发上限和按账户限流，数据面上没有熔断。顺丰的后端是 `provider-signer`，熔断做在签名器里，打开时承运商收不到请求。

## 被考虑的替代方案

- **在 agentgateway 里用 `health.eviction` 做熔断。** 校验能过。失败的静态主机没有被摘掉。不选。
- **按账户的限流做在数据面的 `localRateLimit`。** 数据面在 ExtAuthZ 之前不知道选定的账户。不选作账户级配额。它仍用于路由级的本地限流。
- **跨实例共享配额。** 契约里有 `DISTRIBUTED_COORDINATED`。这一步只有本进程的桶。不选。

- 两个构建：`gofmt` 干净，`go build`、`go vet`、`go test -count=1` 各 36 个包通过，`internal/architecture` 通过。`go test -count=1 -race` 覆盖 `egressauthz`、`providersigner`、`gateway-authz`、`provider-signer`，17 个包通过。其中 `TestBurstCapsTheBucket` 看容量被 `burst` 卡住。

- 回环上对着锁定的 agentgateway 1.7.0，端口 28410 到 28450。按账户的 429 带 `Retry-After`，账户之间分开；没有授权的 403 不消耗配额。数据面上 `maxConcurrentRequests` 答 503，`localRateLimit` 答 429。`provider-signer` 在连续两次承运商 503 之后打开，随后的请求是 503 `carrier_circuit_open`，承运商收到 0 次；半开的探测之后恢复。

### 没有做的

- 跨实例的配额协调。桶只在一个进程里，对得上 `LOCAL_APPROXIMATE`。
- 数据面上对静态 `host:` 的熔断。不经过 `provider-signer` 的路由（万邦是这样）没有数据面熔断。
- 这个提交没有跑 compose 套件连跑三轮。

## 成本与剩余风险

- `--rate-limits` 和熔断参数默认关着。不给就没有这些保护。
- 8192 个键的上限会丢掉旧桶。丢掉之后下一次请求拿到满桶。单进程重启也是满桶。这不是跨重启的精确配额。
- 被限流的请求不取凭证，也不写出 `Authorization`。没有授权的请求也不扣配额。
- 签名器的熔断把承运商的 5xx 和读不成的 200 当成故障。HTTP 200 且信封读得成的，包括业务上 `success` 为假，记成健康。熔断没有拿沙箱的取消再跑一遍。
- 万邦这一家没有签名器，也就没有这条熔断。超时、并发上限和按账户限流仍可用。数据面熔断没有。
