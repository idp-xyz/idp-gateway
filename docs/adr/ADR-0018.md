# ADR-0018 — 可选的 Trace、JSONL 审计与 Prometheus 指标

> **状态**：Proposed · **版本** V1.0 · **日期** 2026-11-23  
> 本 ADR 为设计建议，不是已经执行的技术审批、生产基线或运行验收。它补记[开发计划](../development-plan.md)第 5 节里 `GW-FR-017` 和 `GW-GAP-08` 在提交 `ecfff81` 之后这一步。执笔的是 AI 编码助手。  
> 数字错误预算没有批准。本篇不是仓库所有者的决定。状态是 Proposed。

## 背景

开发计划第 5 节把完整的 Trace、审计和 SLO 列为还没有做。2026-11-21 在锁定的 agentgateway 1.7.0 上量过，当时没有 `frontendPolicies.tracing`：调用方送了 `traceparent` 时，上游看到同一个 trace id 和新的 span id；调用方没送时，上游没有 `traceparent`，网关日志里也没有 `trace.id`。那一次的记录留在开发计划里，不改。

[G05](../G05_Engineering_and_Operations.md) 11.2 节写：初始 SLO 目标必须与容量工作负载一起批准；在缺少真实硬件、部署区域和流量模型时，禁止把 99.9%、99.99% 或一个固定的毫秒延迟写成已经达到的事实。这次没有容量工作负载，也没有人批准一个错误预算。

提交 `ecfff81` 加了三样可选的东西，默认都关着：`gateway-authz` 和 `provider-signer` 的 OTLP/HTTP JSON 导出、JSONL 审计、单独明文端口上的 Prometheus 文本；编译器里可选的 `pool.tracing`，写成 `frontendPolicies.tracing`。不写这个字段、不给那三个参数，行为与原来相同。`go.mod` 仍然没有第三方依赖。

## 推荐决策

1. **追踪、审计和指标默认关着。** `pool.tracing` 不写，就不出现在编出来的配置里。`--otlp-traces-url`、`--audit-log`、`--metrics-listen` 不给，就不导出、不写审计、不开指标端口。mTLS 监听上仍然没有 `/metrics`。
2. **数据面的追踪是锁定的 1.7.0 自己的 `frontendPolicies.tracing`。** 编译器把 `host`、`protocol`、`path`、采样和属性写进去。`protocol` 默认 `http`，`path` 默认 `/v1/traces`。采样写成 0 到 1 的无引号小数。这一步量到的数据面 POST 的 `Content-Type` 是 `application/x-protobuf`，不是 JSON。`gateway-authz` 和 `provider-signer` 的导出器在代码里写的是 `application/json`。两边不是同一种正文。
3. **审计是追加的 JSONL，文件权限 0600。** 行里不写令牌、密钥或 `Authorization` 的值。指标在另一个明文地址的 `GET /metrics` 上，Prometheus 文本。数据面的指标在 `statsAddr` 的 `/metrics`，不在管理口：这次管理口的 `/metrics` 是 404。
4. **不设数字错误预算。** 告警可以是运行上的：抓不到指标、OTLP 送出失败或被丢掉、签名器熔断开着、数据面 5xx 比例高于一个写明的初始门槛。这些条目标 `slo: initial`。时长和 0.05 这个比例是写规则时取的，没有对着容量目标调过，也不是签过的 SLO。没有按延迟告警。
5. **收集器不由这个仓库新起一个镜像。** `deploy/compose/observability.yml` 是叠加文件，不改 `compose.yml` 的七个服务，也不写进 systemd 单元。它不启动容器。地址用环境变量指到本机已经在听的 `idp-otel`、`idp-jaeger`、`idp-prometheus`、`idp-grafana`。见过监听的，默认用那个回环地址；没见过有人在听的指标端口，默认是空的，例子只写在注释里。
6. **`pin-egress.sh` 不改。** 它先按 `host: 名字:端口` 摘行，再去掉引号。编译器写的是 `host: 'otel-collector:4318'` 这种带引号的行。以后发布里若有这个名字，出口规则会钉住它。这一步用同一条 `sed` 对编出来的 `host: '127.0.0.1:27706'` 摘过，摘出来了。

## 为什么这样决定

账户和凭证仍然只在 `gateway-authz` 里。追踪不能为了导出失败去拒绝一次已经判定过的调用，所以导出在请求路径旁边，失败只记数。数据面会不会自己造 trace id，取决于有没有 `frontendPolicies.tracing`：2026-11-21 没有这块配置时不造；这一步加上之后，调用方不送 `traceparent` 也会在上游看到一条，并且采样标志是 `01`。两件事都要留着，不能把「不写 tracing」的那一笔改掉。

G05 不许在没有容量工作负载和所有者批准时宣布一个可用性或延迟目标。所以规则里可以有「抓不到」「导出失败」「熔断开着」和「5xx 比例高于一个写明的初始数」，但不能把这个数叫作已经达到或已经批准的 SLO。

## 被考虑的替代方案

- **写成 99.9% 或一个固定毫秒。** 没有容量工作负载，也没有人批准。不选。
- **在叠加文件里再起一个收集器镜像。** 本机已经有 `idp-otel`、`idp-jaeger`、`idp-prometheus`、`idp-grafana` 在听。不新增镜像，也不用浮动标签。
- **把 `/metrics` 加到 mTLS 监听上。** 不做。mTLS 上的 `GET /metrics` 仍是 404。
- **改 `pin-egress.sh` 去认别的写法。** 带引号的 `host:` 行已经摘得出来。不改。
- **默认打开 tracing 或那三个参数。** 不写就必须和以前一样。不选。

## 做出来了（V1.0）

代码在提交 `ecfff81`，当时已经在 `main` 上。这一步没有改产品代码，没有改 `go.mod`，没有改 `pin-egress.sh`。写的是本篇、开发计划里的一笔、`deploy/compose/idp-gateway-slo.rules.yml`、`deploy/observability/idp-gateway-overview.json`、`deploy/compose/observability.yml`，以及 `tests/integration/observability`。写这些和跑验证的是 AI 编码助手。**这不是对本 ADR 的决定**，状态保持 Proposed。

### 验证

锁定二进制 `~/.local/opt/agentgateway/1.7.0/agentgateway` 的 SHA-256 是 `c7ef326b7b5702451e94bab55ff484d600d5abdc5344a4cdf7c72fc0bcff9e24`，与 `deploy/agentgateway/agentgateway.lock.json` 一致。`--version` 报 1.7.0，`git_revision` 是 `26f5aebe99a36a037fe54f8080a608aca5547e15`。

**数据面指标。** 用一份很小的、校验通过的配置把这个二进制起在回环上，请求打完就停。管理口 `127.0.0.1:27702/metrics` 是 404。`statsAddr` `127.0.0.1:27703/metrics` 是 200，`Content-Type` 是 `application/openmetrics-text;version=1.0.0;charset=utf-8;escaping=allow-utf-8`。同一地址的 `/stats/prometheus` 也是 200，正文与 `/metrics` 不完全相同；下面的名字取自 `/metrics`。一笔上游 200 之后见过 `agentgateway_requests_total` 的 `status="200"`。上游没有人听时，同一名字的 `status="503"`，`reason="UpstreamFailure"`。同一次正文里还有 `agentgateway_request_duration_seconds`、`agentgateway_request_processing_seconds`、`agentgateway_response_processing_seconds`、`agentgateway_response_bytes_total`、`agentgateway_upstream_call_duration_seconds`、`agentgateway_upstream_connect_duration_seconds`、`agentgateway_requests_shed_total`、`agentgateway_downstream_connections_total`、`agentgateway_downstream_connections_shed_total`、`agentgateway_downstream_received_bytes_total`、`agentgateway_downstream_sent_bytes_total`、`agentgateway_build_info`、`agentgateway_config_synchronized`、`agentgateway_substrate_request_parking_active`，以及 cgroup、process、tokio 那几组。没有看到数据面自己的 OTLP 失败计数。这次抓取的配置没有打开 tracing，所以没有把「只有打开 tracing 才出现」的名字写进规则。

**gateway-authz 和 provider-signer 的名字**在 `internal/egressauthz/adapters/httpapi/metrics.go` 和 `internal/providersigner/adapters/httpapi/metrics.go`。authz 是 `idp_gateway_authz_decisions_total`、`idp_gateway_authz_decision_duration_seconds`、`idp_gateway_authz_revocation_epoch`、`idp_gateway_authz_otlp_spans_exported_total`、`idp_gateway_authz_otlp_spans_dropped_total`、`idp_gateway_authz_otlp_spans_failed_total`。signer 是 `idp_gateway_signer_calls_total`、`idp_gateway_signer_call_duration_seconds`、`idp_gateway_signer_circuit_open`、`idp_gateway_signer_otlp_spans_exported_total`、`idp_gateway_signer_otlp_spans_dropped_total`、`idp_gateway_signer_otlp_spans_failed_total`。这一步没有另起一个 `provider-signer` 去抓它的 `/metrics`。`gateway-authz` 的活进程抓到过 `idp_gateway_authz_decisions_total`。

**已经在听的收集器。** `docker ps` 看到 `idp-otel` 发布 `127.0.0.1:4317`、`127.0.0.1:4318` 和 `127.0.0.1:13133`；`idp-jaeger` 发布 `127.0.0.1:16686`，容器里的 4317 和 4318 没有到主机；`idp-prometheus` 是 `127.0.0.1:9090`；`idp-grafana` 是 `127.0.0.1:3000`。没有为它们执行 pull、启动、停止或进入容器。本机镜像里看得到带摘要的 otel、jaeger、prometheus 和 grafana，叠加文件没有引用它们。

**回环套件。** `tests/integration/observability/run.py` 用 `gateway-control compile` 编一份小的 AI / A2A 规格，`pool.tracing` 指向套件进程里的回环收集器，再跑锁定的二进制。端口 27701–27709。默认跑了两遍，退出码都是 0。

- A：调用方不送 `traceparent`。上游收到一条 W3C `traceparent`，标志是 `01`。收集器收到 `POST /v1/traces`，`Content-Type` 是 `application/x-protobuf`，正文里有同一个 trace id。
- B：调用方送 `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`。上游和收集器保持这个 trace id。上游的 span id 与调用方的不同。内容类型仍是 `application/x-protobuf`。
- C：收集器不再监听。数据面这一笔仍是 HTTP 200。
- D：同一份规格不写 `tracing`。编出来的文件没有 `tracing:`。上游没有 `traceparent`。2026-11-21 那一条还在。
- authz：`--otlp-traces-url`、`--audit-log`、`--metrics-listen` 各给一次。一次放行。审计是一行 JSONL，权限 0600，行里没有这次用的凭证，也没有 `authorization`、`secret`、`bearer`。明文 `GET /metrics` 里有 `idp_gateway_authz_decisions_total`。mTLS 端口的 `GET /metrics` 是 404，正文里没有这个名字。

删掉 tracing 块的对照 `--control drop-tracing` 跑了一次，退出码 0。上游 `traceparent` 是空的，应答仍是 HTTP 200，收集器收到 0 次 POST。所以 A 看的是那一块 tracing，不是别的。`pin-egress.sh` 里那条 `sed` 从编出来的文件摘出了 `127.0.0.1:27706`（收集器）、`127.0.0.1:27705`（上游）和 `127.0.0.1:27707`（回读用的管理地址）。脚本没有改。

套件退出之后，27701–27709 上没有人在听。看板 JSON 能被解析，9 个面板，uid 是 `idp-gateway-overview`。没有把它导入正在跑的 Grafana。`docker compose -f observability.yml config --quiet` 通过。规则文件能被解析，一组 9 条。没有跑 `promtool`，也没有把规则装进正在跑的 Prometheus。

### 没有做的

- 没有批准数字错误预算，也没有跑容量工作负载。0.05 和各条 `for` 不是 SLO。
- 没有按延迟告警。`agentgateway_request_duration_seconds` 只出现在看板上，不当作目标。
- 没有重跑黑盒套件。
- 没有把看板导入 Grafana，没有把规则交给 Alertmanager。叫到谁不在这个仓库里。
- 没有在打开 tracing 的那次进程上再抓一遍数据面 `/metrics`。
- 没有活抓 `provider-signer` 的 `/metrics`。
- 没有 `docker compose up` 这个叠加文件，也没有改 systemd。
- 没有改产品代码。导出失败不拒绝请求这一条，由套件的 C 和 authz 的放行一起看到；没有再改 `ecfff81`。

## 成本与剩余风险

- 三个参数和 `pool.tracing` 默认关着。不打开就没有导出、没有审计文件、没有这两处指标。2026-11-21 的「不送 `traceparent` 就不生成」只在没有 tracing 配置时成立。
- 数据面送的是 protobuf。按 JSON 去读 `/v1/traces` 会读不到 span。Go 进程送的是 JSON。收集器要两种都收。
- 告警的时长和 0.05 会在很安静时把单独一笔 503 看成很高的比例。这是初始门槛的代价，不是一个被批准的错误预算。
- 容器里的 `127.0.0.1` 不是主机上的 `idp-otel`。叠加文件里的回环默认值只给跑在主机上的进程。网关在 `netns` 里时，tracing 的 `host` 必须是它够得着、并且会被 `pin-egress.sh` 钉住的那个名字。
- `host: 'otel-collector:4318'` 一旦写进发布的配置，出口规则会钉住那个名字第一次解析到的地址。名字后来变了，要人去 `forget`，和别的后端一样。
