# ADR-0010 — 数据面用 standalone 模式，配置由发布器以文件下发

> **状态**：Proposed（待具名批准） · **版本** V1.0 · **日期** 2026-11-11  
> 本 ADR 为设计建议，不是已经执行的技术审批、生产基线或运行验收。

## 背景

ADR-0009 把"控制面的部署形态（standalone 文件下发还是 Kubernetes）"列为未定，它决定 `gateway-control` 怎么写。这句话里其实有两个问题：agentgateway 用哪种模式，以及它跑在什么平台上。

agentgateway 1.7 有两种模式（上游文档的说法）：

- **standalone 模式**：代理从一份配置文件运行，文件由使用者自己管，文件变了自动重载。可以是一个二进制、一个容器，也可以是 Kubernetes 上的一个 Deployment 加一个 ConfigMap。
- **Kubernetes 模式**：多一个控制器。它监视 Gateway API 资源和 agentgateway 自己的 CRD（`AgentgatewayPolicy` 等，API 组 `agentgateway.dev/v1alpha1`），翻译后经 xDS 下发给代理，并自动为每个 Gateway 部署代理。

所以选项是三个：standalone 跑在主机或虚拟机上、standalone 跑在 Kubernetes 上、Kubernetes 模式。

本仓库验证过的全部是 standalone 的配置文件：黑盒套件的 57 个用例、与本机 Gatekeeper 联调的 11 个用例，以及一个 kind 集群里经 ConfigMap 下发的 5 个用例。

## 推荐决策

1. 数据面用 **standalone 模式**。不部署 agentgateway 的 Kubernetes 控制器，不用 Gateway API 资源描述路由。
2. 运行平台是 Kubernetes 时，每个网关池是一个 Deployment 加一个只读挂载的 ConfigMap，外加各自的 Secret 与 NetworkPolicy（ADR-0002）。`gateway-control` 是这个 ConfigMap 的唯一写入方。运行平台不是 Kubernetes 时，同一份文件由 `gateway-control` 分发到各实例，本 ADR 的其余各条不变。
3. 发布的配置必须带 `config.storage.mode: readOnly`，会话密钥经环境变量 `SESSION_KEY` 提供。两者的原因见 `tests/acceptance/blackbox/README.md`"默认配置不安全的地方"第 6、7 项。
4. "这一份配置在某个实例上已经生效"的判据是三条同时成立：
   - 该实例 `/config_dump` **去掉 `config` 段之后**的摘要等于期望值。期望值取自先加载这份文件的实例；
   - `config` 段里发布的文件写了的那几项（`storage.mode`、管理地址等）逐项等于文件里的值；
   - `/api/runtime` 的 `configReload.synchronized` 为 `true`。

   不拿整个 `/config_dump` 算摘要：`config` 段里有随运行环境变的值。不用 `/api/config/effective`。
5. 灰度以池为单位：先发到灰度池，回读通过后再发到其余的池。不在一个池内部分批。回读逐个副本做；ConfigMap 发出之后在约定的时限内没有全部到齐，按 G03 记为未知并对账，不记为成功。
6. `config` 段里的设置只在启动时读取。发布的文件改了其中的项，发布器要滚动重启这个池；判据第二条不满足的实例，就是还没有重启到的。

## 为什么这样决定

- **已有的验证全部沿用。** 黑盒和联调用的就是这种文件，第 3 条的两项处理也已经在其中。
- **G03 的发布模型能直接对上。** 快照就是文件。逐实例回读已经在 1.7.0 上跑过：换文件不用重启，约 0.3 秒生效；加载不了的文件被整份拒绝，网关报告失败和原因并继续用上一份；`/config_dump` 的摘要随配置变、换回后回到原值（`P1-RB-01/02`）。管理接口写不进配置（`P1-CF-02`）。
- **在 Kubernetes 上跑得通。** 一个单节点的 kind 集群里，三个副本从同一个只读挂载的 ConfigMap 启动；ConfigMap 一换，各副本各自重载，不重启，随文件重载的那部分摘要一致；加载不了的文件每个副本各自拒绝并继续用上一份；只在启动时读取的设置要滚动重启才生效，没重启到的实例从 `config` 段看得出来（`tests/integration/kubernetes/README.md`，`K8-01` 至 `K8-05`）。
- **可信组件最少。** 没有集群级的控制器，发布器是运行配置的唯一来源，这正是 G03 §0 和 `GW-FR-046` 要的。
- **分池隔离不共享任何运行组件。** 每个池的 Deployment、ConfigMap、Secret、NetworkPolicy 都是自己的。

## 被考虑的替代方案

- **Kubernetes 模式**。没有采用，原因有三条：
  - 配置换成另一套 API（HTTPRoute 加 `AgentgatewayPolicy`，仍是 `v1alpha1`），字段名也不同。例如外部授权里我们用的 `includeResponseHeaders`，在那边的例子里叫 `allowedResponseHeaders`。现有的处理和用例要全部重写、重测，黑盒运行器（拿一份文件启动一个二进制）也用不上。
  - 集群的 API 成为第二个能改运行配置的入口，"发布器是唯一来源"要另靠集群权限来守。
  - 多一个要监视集群里的路由资源和 Secret 的控制器。上游已发布的 7 条安全公告里有 2 条是它特有的跨命名空间问题（`GHSA-g7j8-wp7h-wmgr`、`GHSA-jwm2-83f3-52xc`），都已在 1.7.0 之前修复。

  它的好处是业务团队可以用 Gateway API 自助配置路由。本项目的路由由 Fabric 批准、发布器下发（ADR-0006），用不上这一点。
- **standalone 模式跑在主机或虚拟机上**。这不是另一个决定，而是平台不同时的同一个决定；多出来的是文件分发和进程托管要自己做。

## 成本与剩余风险

- **运行平台是推断的。** 设计文档没有写明平台。ADR-0002 和 G05 用的是 NetworkPolicy、副本、镜像这些词，本 ADR 据此按 Kubernetes 写了第 2 条。
- **ConfigMap 下发是慢的，各副本也不同步。** kind 集群上量到：常态下变更要 24 到 84 秒才到 Pod，同一次变更里各副本先后相差 4 到 17 秒，这段时间同一个池的副本跑着不同的配置。账户撤销是 `gateway-authz` 在请求路径上判定的（`P1-RV-01`），不靠配置下发；但封掉一条路由这类要改配置的紧急变更，走这条路就得等这么久。G03 §4 要求安全上紧急的变更另有时限，那条路径还没有设计。
- **一个池内分不了批。** ConfigMap 一换，这个池的全部副本都会在一两分钟内换上，先后只差几秒到十几秒。G03 §4 第 5 步和 §10.1 写的是先灰度、再分批，第 5 条把"批"定成了池。要在一个池内部再分批，得把它拆成几个各带一个 ConfigMap 的 Deployment，本 ADR 没有这样做。
- **只在一个单节点的 kind 集群上跑过。** 用的是自己打包的镜像、自己写的清单和一份只有几条路由的小配置。多节点、节点或 kubelet 重启、带密钥和证书文件的真实配置、有流量时换配置，都没有测（清单见 `tests/integration/kubernetes/README.md`）。
- **容器镜像没有锁定。** `deploy/agentgateway/agentgateway.lock.json` 只锁了二进制。上游发布的容器镜像没有核对过，也没有锁 digest。
- **`/config_dump` 的 `config` 段里哪些值随环境变，只知道一项。** CPU 限额不同的两个副本，差别在工作线程数。命名空间不同、节点规格不同时还有哪些项不同，没有试；第 4 条因此只比对文件里写了的那几项。
- **发布器怎么够到每个实例的管理地址，还没有设计。** 管理地址只绑回环，集群上的验证是用 `kubectl exec` 进到 Pod 里读的，发布器不该有这种权限。让管理地址对发布器可达而对别人不可达，是 `gateway-control` 设计里要定的事。
- **`configReload` 没有版本号和加载时间。** 单看 `synchronized: true` 分不清加载的是哪一份，所以第 4 条要求同时比对摘要。
- **跟随上游最新发布版**（`deploy/agentgateway/README.md`）意味着这些行为每次换版本都要重新确认。单实例上的部分在黑盒套件里，Kubernetes 上的部分在 `tests/integration/kubernetes` 里，两者都可以重跑。

## 变更与回退条件

需由架构负责人、对应产品 Owner、安全负责人及运行负责人具名复核。出现下面任何一种情况，重新评估本决策，而不是自动维持：

- 多节点集群或真实配置下的验证表明 ConfigMap 下发做不到 G03 要求的逐实例回读和对账；
- 出现了由业务团队自助管理路由的需求，且 G03"发布器是唯一来源"相应修改；
- 上游不再维护 standalone 模式，或配置文件格式的变化使跟随最新发布版的代价高于改用 Kubernetes 模式。
