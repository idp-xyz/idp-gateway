# ADR-0010 — 数据面用 standalone 模式，配置以不可变快照发布

> **状态**：Proposed（待具名批准） · **版本** V1.2 · **日期** 2026-11-11  
> 本 ADR 为设计建议，不是已经执行的技术审批、生产基线或运行验收。V1.1 是一次技术复核之后的修订；V1.2 记入运行平台的决定（先单机 docker compose，以后再上 Kubernetes）和单机上的验证结果。两次各改了什么写在文末。

## 背景

ADR-0009 把"控制面的部署形态（standalone 文件下发还是 Kubernetes）"列为未定，它决定 `gateway-control` 怎么写。这句话里其实有两个问题：agentgateway 用哪种模式，以及它跑在什么平台上。

agentgateway 1.7 有两种模式（上游文档的说法）：

- **standalone 模式**：代理从一份配置文件运行，文件由使用者自己管，文件变了自动重载。可以是一个二进制、一个容器，也可以是 Kubernetes 上的一个 Deployment 加一个 ConfigMap。
- **Kubernetes 模式**：多一个控制器。它监视 Gateway API 资源和 agentgateway 自己的 CRD（`AgentgatewayPolicy` 等，API 组 `agentgateway.dev/v1alpha1`），翻译后经 xDS 下发给代理，并自动为每个 Gateway 部署代理。

所以选项是三个：standalone 跑在主机或虚拟机上、standalone 跑在 Kubernetes 上、Kubernetes 模式。

本仓库验证过的全部是 standalone 的配置文件：黑盒套件的 59 个用例、与本机 Gatekeeper 联调的 11 个用例、一个 kind 集群里的 4 个用例，以及单机 docker compose 上的 7 个用例。

## 推荐决策

1. 数据面用 **standalone 模式**。不部署 agentgateway 的 Kubernetes 控制器，不用 Gateway API 资源描述路由。
2. **跑上游发布的容器镜像，按摘要引用**（`deploy/agentgateway/agentgateway.lock.json`）。测试启动的就是这个镜像里的二进制。
3. **一份快照是一个不可变的 ConfigMap**，名字里带内容的摘要；一个网关池是一个 Deployment，Pod 模板指着一份快照。发布，是建出新快照的 ConfigMap、把 Pod 模板指过去，由 Deployment 滚动替换副本；回滚，是把 Pod 模板指回上一份。已经在用的 ConfigMap 不改。`gateway-control` 是这些 ConfigMap 和 Pod 模板的唯一写入方。证书、私钥和会话密钥不在快照里，来自各池自己的 Secret。本条和第 6、7 条写的是 Kubernetes 上的做法；单机上的做法见第 10 条。
4. **发布的配置必须带下面几样。** 各自不处理时会怎样，见 `tests/acceptance/blackbox/README.md` 的"默认配置不安全的地方"。
   - `config.storage.mode: readOnly`；会话密钥经环境变量 `SESSION_KEY` 提供（第 6、7 项）。
   - 收业务请求的监听写 `bindAddress: 127.0.0.1`；同一个 Pod 里放一个会拒绝畸形请求的前置代理，Pod 上收业务请求的只有它（第 8 项和 `P1-SS-04`）。
   - 管理地址和指标地址只绑回环。设了 `readOnly`，管理地址照样能关停网关、改日志级别，所以它不对任何别的工作负载开放。
   - `connectionMinTerminationDeadline` 和 `connectionTerminationDeadline`。不设的话，网关收到终止信号后立刻不接新连接，5 秒后切断在途的请求。
5. **回读走网关自己的一个监听**：要求工作负载 CA 签发的客户端证书，只放行发布器的身份，只把 `GET /config_dump` 和 `GET /api/runtime` 转给本机的管理地址。发布器不需要进容器的权限。
6. **"这份快照在某个实例上已经生效"**，是下面三条同时成立：
   - 这个 Pod 的模板指着的是这份快照的 ConfigMap；
   - 经回读口读到的 `/config_dump`，去掉 `config` 段、把证书正文换成占位之后算出的摘要，等于期望值。期望值由发布器在发布之前得到：用同一个镜像在集群外加载这份快照，读它的 `/config_dump`。加载不了的快照在这一步就被拒绝，不往下发；
   - `/api/runtime` 的 `configReload.synchronized` 为 `true`，存储模式为 `readOnly`。

   不用 `/api/config/effective`：它显示的是文件，不是生效的配置。
7. **灰度以池为单位**：先发到灰度池，回读和观察通过后再发到其余的池。池内由 Deployment 一个一个地换（`maxUnavailable: 0`）；新副本起不来，滚动就停在第一个上，原来的副本不动。在约定的时限内没有全部到位，按 G03 记为未知并对账，不记为成功。
8. **身份提供方的验签公钥（JWKS）以文件的形式放在快照里**，不让网关按地址自己去取。换签名密钥是一次发布。
9. **紧急的安全变更不走配置发布。** 撤销一个账户的使用授权由请求路径上的 `gateway-authz` 判定，下一个请求生效；封掉一个 Operation 也放在这里做（待建）。没有 PDP 的路由（模式 C）不在这条路上，封它是一次普通发布。最后的手段是隔离整个池。不为紧急变更另设一条就地改配置的快速通道。各类变更的最迟生效时限需要具名批准（G03 §10.1 第 7 条），本 ADR 不定数值。
10. **运行平台分两期：先在单机上用 docker compose，以后再上 Kubernetes。** 这是仓库所有者 2026-11-11 的决定。第 1、2、4、5、8、9 条两期相同；第 3、6、7 条在单机上相应地是：
    - **一个池**是一组容器：前置代理和网关共用一个网络命名空间，相当于同一个 Pod；本机上只映射前置代理的端口和回读口。池里只有一个网关实例，`connectionMinTerminationDeadline` 不设。
    - **快照**仍是内容不可变、名字带内容摘要的一份文件，由 `gateway-control` 保存。**发布**是把网关容器挂载的目录里的配置文件整份换成这份快照：在同一个目录里写临时文件、落盘、改名。网关自己重载，不重启。**回滚**是把上一份换回去。挂进容器的是目录，不是配置文件本身；这个目录只有 `gateway-control` 写。
    - **"已经生效"**是三条同时成立：目录里的配置文件就是这份快照；经回读口算出的摘要等于期望值（算法和期望值的来历与第 6 条相同，离线加载是另起一个容器）；`configReload.synchronized` 为 `true`，存储模式为 `readOnly`。
    - **没有生效时**，也就是网关报告加载失败，或在约定的时限内没有报告期望的摘要：发布器把上一份快照放回去，再回读一次。放回去之后仍对不上，按 G03 记为未知并对账。网关加载不了的文件不留在目录里。
    - **要重启网关的变更**单独对待：`config` 段与网关启动时不同的快照，以及换镜像。回读的摘要不含 `config` 段，要由发布器比较两份快照来判断。重启会让这个池中断，发布器不把它当作一次普通发布自动去做。
    - **灰度**在有不止一个池时仍以池为单位。一个池只有一个实例，没有池内的分批。
    - **下发是 `gateway-control` 里可以替换的一层。** 快照、期望摘要、回读、"已经生效"的判定和发布的状态不随平台变。先做单机的实现；Kubernetes 的实现（第 3、6、7 条）以后加。

## 为什么这样决定

- **已有的验证全部沿用。** 黑盒和联调用的就是这种配置文件，第 4 条的各项处理都在其中，每一项不处理时的默认行为每次运行都重新观察。
- **不可变快照加滚动替换，比就地改同一个 ConfigMap 可控。** 两种做法都在 kind 集群上跑过，数字见 `tests/integration/kubernetes/README.md`：
  - 就地改：变更 24 到 84 秒后才到 Pod，各副本先后相差 4 到 17 秒；一改，全池都换，中途停不下来。遇到一份加载不了的文件，运行中的副本会拒绝它、继续用上一份；但此后任何副本重启或扩容，新进程读到的是那份坏文件，起不来。
  - 滚动替换：三个副本十来秒换完，期间每秒 20 个请求没有一个失败（`K8-02`、`K8-04`）。加载不了的快照先在集群外被拒绝；硬发下去也只停在第一个新 Pod 上，原来的副本照常服务（`K8-03`）。回滚是同一个动作。
  - `config` 段的设置只在启动时读取。滚动替换时每个新副本都是从这份快照启动的，不会出现"文件改了、设置还是旧的"。
- **单机上换文件而不重启，是因为那里只有一个实例。** 重启它，新来的请求就被拒绝，直到在途的请求做完（`SH-06`、`SH-07`）。换文件 0.3 秒左右生效，三轮 12 次换文件期间的 1305 个快请求和 78 个慢请求没有一个失败（`SH-02` 至 `SH-04`）。数字见 `tests/integration/compose/README.md`。上面反对"就地改"的几条，在单机上是这样：
  - 慢和各副本不同步，来自 kubelet 的同步周期。目录直接挂进容器时没有这一层。
  - "一改全池都换"：单机上一个池本来就只有一个实例。
  - 坏文件留在盘上的隐患还在，靠两处守：发布之前的离线加载；网关报告加载失败之后，发布器把上一份放回去（`SH-03`）。
  - `config` 段换文件不生效这一点也还在（`SH-06`），所以这类变更单独对待。
- **回读不依赖进容器。** 上游镜像里没有 shell，`kubectl exec` 这条路在真实镜像上本来就走不通。回读口在单个实例上（`P1-RB-03`）和集群里从另一个 Pod（`K8-01`）都验证过：发布器读得到，管理地址的其余接口一个都够不着，别的调用方得不到回应。期望摘要是在集群外算的，集群里每个副本报告的都与它相同（`K8-01`、`K8-02`、`K8-04`）。
- **网关启动不依赖身份提供方。** 按地址取 JWKS 时，地址不可达网关就拒绝启动（`tests/integration/gatekeeper/README.md` 第 4 点）。滚动替换下每次发布、每次 Pod 重建都要启动新进程：身份提供方一出故障，池就发布不了，也补不回副本。JWKS 走文件没有这个依赖，信任哪几把密钥也成了快照里看得见、审得了的内容。
- **可信组件最少。** 没有集群级的控制器，发布器是运行配置的唯一来源，这正是 G03 §0 和 `GW-FR-046` 要的。
- **分池隔离不共享任何运行组件。** 每个池的 Deployment、ConfigMap、Secret、NetworkPolicy 都是自己的。

## 被考虑的替代方案

- **Kubernetes 模式**。没有采用，原因有三条：
  - 配置换成另一套 API（HTTPRoute 加 `AgentgatewayPolicy`，仍是 `v1alpha1`），字段名也不同。例如外部授权里我们用的 `includeResponseHeaders`，在那边的例子里叫 `allowedResponseHeaders`。现有的处理和用例要全部重写、重测，黑盒运行器（拿一份文件启动一个二进制）也用不上。
  - 集群的 API 成为第二个能改运行配置的入口，"发布器是唯一来源"要另靠集群权限来守。
  - 多一个要监视集群里的路由资源和 Secret 的控制器。上游已发布的 7 条安全公告里有 2 条是它特有的跨命名空间问题（`GHSA-g7j8-wp7h-wmgr`、`GHSA-jwm2-83f3-52xc`），都已在 1.7.0 之前修复。

  它的好处是业务团队可以用 Gateway API 自助配置路由。本项目的路由由 Fabric 批准、发布器下发（ADR-0006），用不上这一点。
- **就地改同一个 ConfigMap**。这是本 ADR V1.0 的做法；上游的 standalone Helm chart 对不需要重启的设置也是这样做的。没有采用，原因见上一节。它的好处是发布不重启进程。
- **按地址取 JWKS**。省掉同步这一步，换密钥不用发布。没有采用：启动依赖身份提供方；1.7.0 上到了该重取的时候身份提供方答 5xx，网关之后几分钟不再重试（同上，第 4 点）；旧密钥的信任没有时限。
- **把管理地址直接开给发布器**。省掉回读口。没有采用：管理地址没有认证，上面有关停网关和改日志级别的接口；上游的安全策略也写明它不是一道面向不可信调用方的边界。
- **单机上每次发布也重启网关**。与 Kubernetes 上的做法一致，`config` 段不必单独对待。没有采用：只有一个实例，每次发布新来的请求都会被拒绝一段时间，长短取决于在途的请求还要多久（`SH-07`）。
- **单机上起两个网关实例轮着换**。没有采用：前置代理要跟着切换上游，多出一套要验证的机制，而以后要去的平台是 Kubernetes。重启造成的中断不可接受时再评估。
- **不经容器、把二进制直接跑在主机上**。没有采用：第 2 条要部署的是上游镜像，进程托管和隔离也要自己做。

## 成本与剩余风险

- **运行平台分两期，设计文档里没有这个分期。** 设计文档没有写明平台。ADR-0002 和 G05 用的是 NetworkPolicy、副本、镜像这些词，第 3、6、7 条据此按 Kubernetes 写。第一期在单机上跑（第 10 条），这三条用不上，Kubernetes 上的验证也没有再扩大。
- **单机是单点。** 这台机器或它的 docker 停了，经它出去的调用全部中断；网关崩溃或重启期间也一样。G01 要的独立实例池（`GW-FR-016`）和分池多副本（风险 R-04 的缓解手段）在一台机器上做不到：池可以分成几组容器，但共用一台机器和一个 docker。
- **单机上重启网关就是中断。** `config` 段的变更、换镜像、主机或 docker 重启都要重启网关。量到的（`SH-06`、`SH-07`）：没有在途的请求时，新来的请求被拒绝 0.15 秒左右；有在途的请求时一直拒绝到它们做完，最长到 `connectionTerminationDeadline`。测试里这个时限是 45 秒，在途的请求最长只测到还剩 3 秒。这个时限在单机上有两头：定得长，重启时新请求被拒绝得久；定得短，在途的请求被切断。
- **单机上的发布靠网关的文件监视。** 配置文件被改名替换之后网关仍然重载，是在上游源码和它自己的一条测试里看到的实现，换版本时由 `SH-02` 至 `SH-05` 把关。只在 WSL2 里本机 ext4 上的目录挂载测过；别的文件系统和挂载方式上，文件变化的通知不一定一样。
- **单机上，一份网关加载不了的文件留在目录里，网关下次重启就起不来。** 发布器在换上文件之后、放回上一份之前自己停了，留下的就是这种状态。所以 `gateway-control` 启动时要先对账：目录里的文件是不是它记录的那份快照，网关报告的摘要是不是那份快照的期望值。
- **在 Kubernetes 上，每次发布都重启这个池的每一个网关进程。** 长连接和流最迟在 `connectionTerminationDeadline` 被切断。集群上只用最长 2 秒的请求测过；SSE、gRPC 流、WebSocket 用之前要重新评估。发布频繁的池，Pod 更替也频繁。
- **在 Kubernetes 上，不丢请求靠的是一组终止时限**：前置代理先等 8 秒，网关 12 秒内照常接请求、最迟 45 秒退出，Pod 的宽限期 60 秒。这些数是为测试取的，没有对着真实的请求时长和端点摘除的耗时调过。
- **摘要不覆盖的东西。** `/config_dump` 里没有私钥，没有固定凭证文件的内容；JWKS 只列 `kid`，同一个 `kid` 换了密钥摘要不变；证书正文是有意不计入的，所以换了信任的 CA，摘要也看不出来。JWKS 在快照里，靠 ConfigMap 不可变、名字带内容摘要来守；私钥、凭证和信任的 CA 在 Secret 里，靠谁能写那个 Secret 来守。
- **回读口是让网关代理它自己的管理地址。** 上游文档没有把这写成一种用法，换版本时由 `P1-RB-03` 把关。NetworkPolicy 没有测。发布器的证书由谁签发、怎么轮换，它怎么得到各个 Pod 的地址，还没有设计。
- **只在一个单节点的 kind 集群和一台机器的 docker compose 上跑过**，用的是一份没有 JWT、ExtAuthZ 和真实 PDP 的小配置和自己写的清单。多节点、节点故障、自动扩缩、带密钥文件的真实配置都没有测；JWKS 随快照下发只在黑盒套件里跑过（那里 JWKS 就是文件），快照里有多个文件时怎么一起换没有测。单机上没有测的还有主机重启之后的恢复、发布器和网关不是同一个用户时文件的权限，见 `tests/integration/compose/README.md`。
- **镜像的来源只核对到摘要和它自报的提交。** 没有验证签名。依赖漏洞查过一遍，结果和它的限制见 `deploy/agentgateway/README.md` 的核查表。G05 §7 要求的具名批准没有。
- **紧急变更这条路大半还没有建。** 账户级的撤销实测过（`P1-RV-01`；启用 Gatekeeper 授权检查时是 `GK-07`），但产品构建里撤销状态只在内存里，还没有写入它的入口；Operation 级的封禁还不存在。在那之前，封一条路由只能靠一次发布，或隔离整个池。
- **JWKS 走文件，同步要自己做。** 把身份提供方的 JWKS 取下来、发现变化就发一次布，是 `gateway-control` 的事，现在不存在。身份提供方还要先发布新密钥、过一段时间再用它签发；Gatekeeper 现在没有这样的换法（同上，第 4 点）。
- **`config` 段里随环境变的值不比对。** 见到过的有解析器配置和工作线程数。
- **跟随上游最新发布版**（`deploy/agentgateway/README.md`）意味着这些行为每次换版本都要重新确认。四套用例都可以重跑。

## 变更与回退条件

需由架构负责人、对应产品 Owner、安全负责人及运行负责人具名复核。出现下面任何一种情况，重新评估本决策，而不是自动维持：

- 单机阶段的单点，或重启网关时的中断，不可接受：提前进入多机或 Kubernetes 阶段，或者重新评估"起两个实例轮着换"；
- 换版本之后，配置文件被改名替换时网关不再重载（`SH-02` 不通过）；
- 多节点集群或真实配置下的验证表明滚动替换做不到不丢请求，或做不到 G03 要求的逐实例回读和对账；
- 要承载长连接或流式流量，而每次发布切断它们不可接受；
- 出现了由业务团队自助管理路由的需求，且 G03"发布器是唯一来源"相应修改；
- 上游不再维护 standalone 模式，不再允许网关代理自己的管理地址而又没有别的回读办法，或配置文件格式的变化使跟随最新发布版的代价高于改用 Kubernetes 模式。

## 技术复核记录

2026-11-11，应仓库所有者的要求，由 AI 编码助手对 V1.0 做了一次技术复核：逐条核对事实，把没有验证过的补上验证，按结果修订成 V1.1。**这不是具名批准。** 上一节要求的四方具名复核仍然需要，状态保持 Proposed。

| 复核中发现的 | 处置 |
|---|---|
| V1.0 的回读靠 `kubectl exec` 进容器。上游镜像里没有 shell，这条路在真实镜像上走不通；发布器也不该有这种权限 | 第 5 条。`P1-RB-03`、`K8-01` |
| 测的是发布页上的独立二进制，要部署的却是镜像里的另一个构建 | 第 2 条。锁定改为镜像；两个构建上黑盒结果逐项相同 |
| 就地改 ConfigMap：池内分不了批，各副本不同步，坏文件留下"重启就起不来"的隐患 | 第 3、7 条。`K8-02` 至 `K8-04` |
| 设了 `storage.mode: readOnly`，管理地址仍能关停网关、改日志级别 | 第 4 条。管理地址不外露；回读口上这些接口是 404 |
| 仓库里"监听器没有绑定地址字段"的说法是错的 | 第 4 条。`P1-NL-01`；相关文档已更正 |
| 默认的终止时限下，滚动替换会切断在途请求 | 第 4 条。`K8-02`、`K8-04` 带着流量跑 |
| `/config_dump` 里有证书正文；JWKS 只列 `kid`；按地址取 JWKS 时摘要会自己变 | 第 6、8 条 |
| 按地址取 JWKS 时，网关启动依赖身份提供方 | 第 8 条 |
| 紧急变更的路径没有设计 | 第 9 条。已有的和待建的分开写在"成本与剩余风险"里 |

复核没有改变的：用 standalone 模式、不用 Kubernetes 控制器；发布器是运行配置的唯一来源；灰度以池为单位。

当时留给具名批准人的：运行平台是否就是 Kubernetes（已有答复，见下一节）；各类紧急变更的最迟生效时限；镜像不验签是否可以接受；"成本与剩余风险"里的各条是否接受。

## 运行平台的决定（V1.2）

2026-11-11，仓库所有者被问到"最终准备部署在哪种环境"时选的是：**先单机 docker compose，以后再上 Kubernetes。** V1.2 记入这个决定，并把单机上的做法写成第 10 条。做法先在本机验证过（`tests/integration/compose`，7 个用例，连跑三轮都通过）；验证和执笔的是 AI 编码助手。

**这回答的是上一节留下的"运行平台是否就是 Kubernetes"这一个问题，不是对本 ADR 的具名批准。** "变更与回退条件"要求的四方具名复核仍然需要，状态保持 Proposed。

| V1.2 改了什么 | 位置和依据 |
|---|---|
| 运行平台从"推断为 Kubernetes"改为分两期 | 第 10 条；第 3 条末句 |
| 单机上发布不重启网关，换掉挂载目录里的配置文件；挂的必须是目录 | 第 10 条。`SH-02`、`SH-04`、`SH-05` |
| 单机上网关报告加载失败之后，发布器要把上一份放回去 | 第 10 条。`SH-03` |
| `config` 段的变更在单机上要重启网关，重启就是中断 | 第 10 条和"成本与剩余风险"。`SH-06`、`SH-07` |
| 单机是单点 | "成本与剩余风险" |

V1.2 没有改变的：第 1、2、4、5、8、9 条，以及 Kubernetes 上的做法（第 3、6、7 条）。

留给具名批准人的：单机阶段的单点和重启时的中断是否可以接受，什么条件下进入 Kubernetes 阶段；各类紧急变更的最迟生效时限；镜像不验签是否可以接受；"成本与剩余风险"里的其余各条是否接受。
