# ADR-0023 — 撤销、封禁与配额的跨副本协调器（authz-state）

> **状态**：Proposed · **版本** V1.0 · **日期** 2026-11-24  
> 本 ADR 为设计建议，不是已经执行的技术审批、生产基线或运行验收。实现和单测记在文末「做出来了（V1.0）」，不是验收通过。执笔的是 AI 编码助手。  
> 2026-11-24 把阶段 2 短板 2 做成一个可选的、只用标准库的协调进程。那是开工的范围，不是对本篇的决定；状态保持 Proposed。正式门禁仍为 `NOT_RUN`。

## 背景

[ADR-0012](ADR-0012.md) 把撤销和封禁放在 `gateway-authz` 的一份文件里。两个进程打开同一份文件时，`filestore.Revocations` 会在写之前把对方已经写下的表并进来，所以同一台机器上的撤销和封禁能够对上。文件在另一台机器上时，这一份并不会自己走过去。

[ADR-0017](ADR-0017.md) 的配额桶只在本进程里，对得上契约里的 `LOCAL_APPROXIMATE`。`DISTRIBUTED_COORDINATED` 当时没有做。一个副本扣过的额度，另一个副本看不见。

[ADR-0020](ADR-0020.md) 把 Kubernetes 多副本和 PostgreSQL / Outbox 留在阶段 2。这一篇只补短板 2：撤销、封禁和配额可以问同一个可选进程。不传新参数时，判定仍走本地文件和本地桶。`go.mod` 仍然没有 `require`。

## 推荐决策

1. **新进程 `cmd/authz-state`，新上下文 `internal/authzstate`。** 四层是 `domain`、`ports`、`application`、`adapters`。`domain` 只有规则，不做 I/O，不导入 `net`、`os`、`log/slog`。`internal/architecture` 的请求路径清单加上 `internal/authzstate` 和 `cmd/authz-state`：只用标准库，不导入 `database/sql`。

2. **`gateway-authz` 上五个参数要么全给、要么全不给：** `--authz-state-url`（必须是没有用户信息、查询串和片段的 `https`）、`--authz-state-cert`、`--authz-state-key`、`--authz-state-ca`、`--authz-state-name`。都不给：不创建客户端，撤销仍是本地文件，配额仍是本进程的桶，判定与现在相同。都给：必须同时有 `--revocations` 和 `--revoker-identity`。`--rate-limits` 也给了，配额扣费走协调器；没给就不发配额 RPC。客户端用 `workloadtls.ClientConfigWithLogger`。

3. **协调器不持有承运商密钥。** 它在 `--state-file` 里保存的是撤销/封禁文档，JSON 形状与 filestore 相同：`epoch`、`revoked_accounts`、`banned_operations`。文件 0600，拒绝符号链接，拒绝 group/other 可读。配额桶只在内存里。进程重启之后每个键都是满桶。启动日志写明 `quota=memory_only_restart_refills`。这个限制写在日志和本篇里，不藏起来。

4. **改动先落盘，再发布。** 撤销和封禁写盘失败时不发布，HTTP 503；调用方不得放宽，也不得把这次撤销当成集群里已经看得见。恢复和解除也是先写盘，写盘失败就不放宽。代次只在集合真的变化时加一。重复撤销、重复封禁不增加代次。

5. **读是失败关闭的。** 五个参数都在时，`gateway-authz` 的每一次 `View`、`State`、`Epoch`、`Revoked`、`Banned` 都向协调器取一份新快照。连不上、超时、401、5xx、正文读不懂，都是错误。`application.Decide` 已经把 `View` 的错误写成 `REVOCATION_STATE_UNAVAILABLE`（没有结论，不发凭证）。不得用旧快照放行。配额 RPC 的错误走已经有的 `RATE_LIMIT_STATE_UNAVAILABLE`。

6. **带上这五个参数启动时，必须先 GET 一次快照，否则拒绝启动。** 取到之后用 `filestore.Revocations.Adopt` 把这份快照整份写回本地 `--revocations` 文件，这样重启之后文件还在。`Adopt` 在原有的写锁下换掉内存并写文件。本地代次和协调器不同时，留下的是协调器那一份。不带协调参数时，`Load`、`Revoke`、`View` 的行为不改。

7. **HTTP 只认 `--authz-identity` 那一个 SPIFFE URI，每个副本出示同一个。** `POST /v1/authz-state/mutate`、`GET /v1/authz-state/snapshot`、`POST /v1/authz-state/quota`。`GET /healthz` 与 `sf-token-coordinator` 一样，握手之后答 `{"ok":true}`，不看身份。重复的 `Host` 是 400，不读正文。身份为空或不对是 401，不读正文。其它方法 405，`Allow` 按路径给出。`DisallowUnknownFields`，正文上限 64 KiB，不允许尾随 JSON。监听用 `workloadtls.ServerConfigWithLogger`。

8. **配额键不把 NUL 放进 JSON。** `domain.QuotaTable.Charges` 只列出命中的规则，不创建桶，也不扣令牌。每条是内部键的 SHA-256，64 位小写十六进制，外加 `MaxRequests`、`WindowSeconds`、`Capacity`（写了 Burst 就用 Burst，否则用 MaxRequests）。没有命中就是空列表，零次 RPC，与本地一样放行。协调器对同一次请求里的全部扣费全有或全无；拒绝时 `retry_after` 至少为 1，一张桶都不扣。一把键第一次出现时锁住这三个数字；以后参数不同是 409，客户端返回错误，失败关闭，不改用更松的桶。时钟只用服务器的。键最多 8192 个，先丢闲置的，再丢最久没用的，算法与 `domain.quotaBucketCap` 同一条。等待时间用窗口和上限做整数除法，与 `domain.retryAfter` 同一条。

9. **变更正文是 `action`（revoke、restore、ban、lift）、`account_id` 或 `operation_id`、`by`、`reason`。** 空的账户和空的操作拒绝，与 filestore 相同。filestore 不限制原因长度；协调器把原因限在 512 个码位，把 `by` 限在 256 个可见 ASCII 码位。账户和操作不再另加格式，`account-blue`、`tracking.get` 仍然合法。

10. **日志和错误不写配额键的原像，只可能出现 64 位十六进制；不写请求正文。** 撤销原因可以记，记法与 `gateway-authz` 现有的撤销日志相同。这个进程里没有任何应用密钥。

客户端放在 `internal/egressauthz/adapters/authzstate`。它可以导入 filestore 和 workloadtls，不导入 sflease。五个参数都在时，交给服务的 `Revocations` 和 `RevocationLedger` 是这个包装，不是裸的 filestore。配额包装只在地址和 `--rate-limits` 都给出时使用。

## 为什么这样决定

跨机器要共享的是「现在谁被撤销、这个操作封没封、这个账户还剩几次」，不是承运商密钥。密钥仍只在 `gateway-authz` 的凭证文件里。协调器磁盘上是撤销表。泄露这份文件看不到应用密钥，也看不到配额键的原像。

失败关闭和 ADR-0012 的「读不到撤销状态就不出结论」是同一条。用一份过期的本地快照放行，会把已经撤销的账户再放出去。配额问不到也一样：问不到就不是「还有额度」。

文件加内存同时分开两件事。撤销要在重启之后还在，所以先落盘再发布。配额写明是近似的，重启即满，所以不进文件，避免被人当成跨重启的精确额度。

五个参数全没有时不创建客户端。黑盒套件不传这些参数，也不启动这个进程。那条路径仍是本地文件和本地桶。

## 被考虑的替代方案

- **协调器不可用时改读本地文件。** 不选。那就是用旧快照放行。文末的套件把协调器停掉，两边都是 503，不是 200。
- **把配额桶写进 `--state-file`。** 不选。重启之后仍是满桶这一条就会被文件盖住，限制不再看得见。多副本的额度仍要有一个进程在计数；文件本身不提供这个计数。
- **用 PostgreSQL 作为第一版存储。** 不选。阶段 2 的存储换代不在这一篇。`go.mod` 仍没有第三方依赖。端口是 `ports.Store`，以后可以换。
- **每个副本一个 SPIFFE ID。** 不选。同一工作负载的副本通常是同一个 URI。协调器只认 `--authz-identity` 这一个。
- **放行错误身份，只靠网络策略。** 不选。错误身份是 401，而且不读正文。

## 成本与剩余风险

- 协调器是单点。它停着的时候，带上这五个参数的副本下一次判定失败关闭，不会退回本地快照。多个协调器副本不在这一版。
- 配额在重启之后是满的。这是内存上限，不是跨重启的精确额度。启动日志写了这一句。
- 每一次判定都取一份新快照。这一跳的延迟加在请求路径上。本篇没有数字 SLO。
- 以后换成共享存储时，语义应保持：先落盘再发布，写盘失败不发布，读失败不放行。那一次若引入 `idp-bento-go`，按 [ADR-0009](ADR-0009.md) 第 4 条同时带契约测试。
- 没有正式 SLO，也没有数字错误预算。这和 ADR-0018 接受之后仍未批准的那两项是同一件事。
- `gateway-authz` 到协调器的出口规则，这一版没有做。`deploy/` 没有改。
- 不传这五个参数时，判定路径与改之前相同。黑盒没有重跑。

## 变更与回退条件

需由仓库所有者复核和决定；在此之前保持 Proposed。执笔的是 AI 编码助手，这不是决定。

不接受独立进程时，撤回本篇，并去掉这五个参数。不传参数时产品路径仍是本地文件和本地桶，回退不需要改已有的撤销文件格式。若要把「协调器挂了就读本地快照」当成可用性策略，必须先改本篇：那会让已撤销的账户在故障时重新放行。

单测里看到的：

- 两个调用方共用一个协调器：一边撤销 `account-blue`，另一边的快照里有它，代次是 1。
- 恢复时存储注入失败：快照仍是撤销，代次不动。撤销在落盘失败时也不会出现在快照里。
- 配额 `max_requests=1`、窗口 3600 秒：两次扣费恰好一次放行，拒绝时等待 3600 秒，且没有扣另一把键。
- 同一把键后来带了更大的上限是 409；原来的桶仍是满额用尽后的那一只，没有换成更松的。
- 错误 SPIFFE 是 401，重复 `Host` 是 400。两处都不依赖正文能解析，日志里没有塞进正文的标记。
- 协调器端口没有人听：包装的 `View` 返回错误；配额 `Allow` 返回错误。没有命中的规则零次 RPC，仍然放行。
- 状态文件拒绝 0644 和符号链接。`Adopt` 用协调器的代次换掉本地更高的代次。`account-blue` 这种账户名被接受。

### 双副本真实进程套件（仍不是验收）

2026-11-24 加了 `tests/integration/authzstate/`。真实进程：一个 `authz-state`、两个 `gateway-authz`（同一个 SPIFFE URI，五个 `--authz-state-*` 都指向协调器，各自一份撤销文件）。直接 mTLS 打 `/v1/extauthz/check`，不传 `--gatekeeper-url`，没有 agentgateway / Gatekeeper / Docker。端口 27861–27875。凭证是固定 Bearer，没有承运商。状态仍是 Proposed。

默认路径连跑两次，退出码都是 0，每遍 5 个用例、**16/16** 项检查。套件先做 AS-02 再做 AS-01：`account-blue` 的共享配额只有 1 次，仍允许的那次操作要在账户被撤销之前用掉。

- **AS-02**：在 A 上封禁 `tracking.get`；B 对该操作 403 `OPERATION_BANNED`；B 上 `labels.print` 仍是 200；三个进程的 PID 不变。当时代次是 1。
- **AS-01**：在 A 上撤销 `account-blue`；B 的下一次检查是 403 `ACCOUNT_REVOKED`；代次变为 2；A 和 B 的 PID 不变。
- **AS-03**：`account-green`、`max_requests=1`。A 第一次 200，B 接着是 429 `RATE_LIMITED`，应答里没有 `Authorization`。
- **AS-04**：停掉协调器。A 和 B 的下一次检查都是 503 `INDETERMINATE` / `REVOCATION_STATE_UNAVAILABLE`，不是 200，也没有凭证头。两个 authz 的 PID 仍是原来的。
- **cleanup**：27861–27875 上没有人在听。

- `--control no-state`：两个 authz **不带**协调参数，配额仍是 `max_requests=1`。A 和 B 对同一个账户都是 200（4/4，含 cleanup）。本地桶不共享。
