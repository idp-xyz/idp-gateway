# ADR-0013 — 发布历史：先定端口和数据，第一个实现落在池旁边的文件里

> **状态**：Proposed（由仓库所有者决定） · **版本** V1.1 · **日期** 2026-11-19  
> 本 ADR 为设计建议，不是已经执行的技术审批、生产基线或运行验收。它是[开发计划](../development-plan.md)第 4 节第 2 项"发布历史和发布状态"所等的那份提案。执笔的是 AI 编码助手。  
> 按开发计划"每个工作包怎么做"：还没有定的决定先出提案，仓库所有者点头之后才写代码。仓库所有者 2026-11-19 看过之后定了"请所有者定的"六项，都照推荐的做；那是开工的许可，不是决定。写这一句时还没有动手。

## 背景

[开发计划](../development-plan.md)第 4 节第 2 项写的是：现在只记最后一条确认过的快照；要做的是保存快照、记录发布过什么，以及 [G03](../G03_Routing_and_Configuration.md) 第 3 节的状态机和审批；持久化要先定，[ADR-0009](ADR-0009.md) 第 4 条规定控制面的持久化用 Bento-Go，第一次引入时同时带上 `tests/bentocontract` 和显式的迁移命令，版本到时再确认。本篇回答的是"持久化先定什么"，范围是发布历史；审批和 RouteIntent 不在内（见第 10 条）。

现在的情况：

- **一个池只记一条。** 配置目录里有一个文件 `.config.yaml.confirmed`（`internal/gatewayconfig/adapters/directory/record.go`），内容是最后一次得到确认的那份快照的全文（base64）、确认时网关报告的运行配置摘要和构建（版本、源码提交）、启动设置各项的指纹。每次发布得到确认之后整份换掉。它是 `place`（启动时把确认过的那一份放回去）、`reconcile` 和看守（`keep`）的依据（[ADR-0010](ADR-0010.md) 第 10 条）。
- **没有历史。** 发布过什么、谁在什么时候发布的、哪一次失败了被收回去，过后查不到。要回到更早的一份，得有人手里还留着那个快照文件。ADR-0010 的"成本与剩余风险"已经这样写：记录"没有历史，没有谁批准的"。
- **发布器是一个命令行程序。** `gateway-control`（[ADR-0009](ADR-0009.md) 第 3 条）在池所在的那台机器上由操作员或 systemd 单元跑；`publish`、`restart`、`reconcile`、`place` 做完就退出，`keep` 是常驻的，但只守一个池。同一个池同时只有一次操作，靠配置目录里的一把文件锁（`.config.yaml.lock`，`flock`，已被占着时不等，命令以退出码 1 结束，没有 JSON）。
- **快照里没有密钥。** 快照是网关配置的全文，内容不可变，名字是内容的 SHA-256（`domain.Snapshot`）。证书、私钥、会话密钥来自池自己的文件和 Secret；快照里不许有对环境变量的引用，发布器会拒绝（ADR-0010 第 11 条）。所以保存快照全文不等于保存秘密。
- **现有命令的结局是"一次操作的结果"，不是 G03 第 3 节的发布状态。** `publish` 和 `restart` 的结局是 `ACTIVE`、`REFUSED`、`RESTART_REQUIRED`、`POOL_NOT_READY`、`RESTORED`、`UNKNOWN`；`reconcile` 多了 `IN_SYNC`、`UNCONFIRMED`、`RESTART_PENDING`；`place` 多了 `IN_PLACE`、`NO_RECORD`（`internal/gatewayconfig/application`）。ADR-0010 V1.3 写的是"发布的状态机接上来时再对应"。
- **G03 的状态机里有两件这个仓库现在没有的事。** `APPROVED` 的来源是 Fabric 发来的具名已批准发布意图（G03 第 4 节第 1、2 条）。这个仓库没有接 Fabric：开发计划第 6 节"没有排的"里写着"与 API Fabric 的发布对接。只有契约（`contracts/fabric/`）；要等第 4 节的编译器，和 Fabric 一侧"。G03 第 4 节第 4 条还要乐观版本和 Outbox（第 4 节"一致性"一段），那是为多个池、多个写入方和向 Fabric 回报准备的；现在一个池只有一个写入方。
- **Bento-Go 的情况。** ADR-0009 第 4 条的方向是控制面的持久化用 Bento-Go（`go.idp.xyz/idp-bento-go`），并写明"现在不引入：还没有用得到它的代码"。各兄弟项目现在用的是 `v0.1.0-rc.2`（`idp-parcel` 等的 `go.mod`），仍是候选版。该版本的 `README.md` 写明：`domain`、`application`、`repository`、`eventing`、`testkit` 是 `v0.1` 的稳定核心包，`postgres`、`postgres/outbox`、`postgres/inbox` 在 `v0.x` 阶段是实验性适配器；仓库里持久化的适配器只有 PostgreSQL 这一种，没有嵌入式或文件的。它的 `go.mod` 要求 `github.com/jackc/pgx/v5` 和 OpenTelemetry 的 API 包（`otel`、`otel/metric`、`otel/trace`）。本仓库的 `go.mod` 现在只有模块名和 Go 版本，没有任何 `require` 行，也就是没有第三方依赖。
- **运行平台和主机。** 运行平台的决定是先单机 docker compose，以后再上 Kubernetes（ADR-0010 V1.2，第 10 条）。发布器在单机上以什么身份运行，ADR-0010 V1.3 列为没有定的；测试主机还没有定（开发计划 1.5）。

## 推荐决策

1. **存什么：每一次发布是一条记录。** 对着现有的流程（`publish.go`、`restart.go`），一条记录有：
   - 自己的编号（每个池里单调增加的整数）和池的标识（`--pool` 给出的名字）；
   - 快照：内容寻址（SHA-256 即 `domain.Snapshot` 的 ID），全文另存、不可变；动手之前放在那里的那一份（`Previous`）的 ID，以及它的全文（还没有存过时一并存下）；
   - 期望的运行配置摘要（离线加载得到，`Result.Expected`）、网关报告的摘要（`Result.Observed`）、网关的构建（版本、源码提交）；
   - 谁发起的：发布器证书（`--tls-cert`）上的工作负载身份，即 SAN 里唯一的那个 URI（取法同 `workloadtls`）；以及跑这个进程的操作系统账号。这两样都是进程自己报的，没有别人核实；
   - 起止时刻（UTC，RFC 3339）；这一次换没换过文件（`Replaced`）、重启没重启过网关（`Restarted`）、需要重启时哪几项启动设置不同（`Restart`）；
   - 每一步的状态和时刻、结局和原因（`Reason`）；
   - 它取代的上一条（同一个池上更早的那条 `ACTIVE`）；回滚时还有它回到的那一条；
   - 操作员的备注（自由文本，见第 3 条，是否要由所有者定）；
   - 一个留给将来的位置：这份快照由哪个 RouteIntent 编译而来。现在永远为空，填它是开发计划第 4 节第 3 项的事。
2. **状态怎么落：记 G03 状态机里发布器自己经手的那一段。** 记得下来的是 `STAGED`、`APPLYING`、`OBSERVING`、`ACTIVE`、`FAILED`、`UNKNOWN`；`SUPERSEDED` 不另写一行，读的时候按"同一个池上更晚的一条 `ACTIVE`"推出来（这样收尾之后不必再写第二次）。`DRAFT`、`VALIDATED`、`APPROVED` 属于 Fabric 一侧批准的事实，`WITHDRAW_REQUESTED`、`REVOKING`、`REVOKED` 是撤回，这一版都不记、也不造。G03 的 `PARTIAL` 要多个实例才有，一个池只有一个实例，这一版没有。现有命令的结局对到状态上：

   | 命令的结局 | 记成什么 | 说明 |
   |---|---|---|
   | `publish` / `restart`：`ACTIVE`，换过文件 | `STAGED` → `APPLYING` → `OBSERVING` → `ACTIVE` | 离线加载通过记 `STAGED`；换文件之前记 `APPLYING`；换完、等网关报告之前记 `OBSERVING`（这一行写不进去不拦发布，见第 4 条） |
   | `restart`：`ACTIVE`，重启过 | 同上，`APPLYING` 里有两步：换文件（文件已经是这一份时没有这一步）、重启网关 | 重启也是动手，也先写后做；两步各写一行，带步骤名 |
   | `publish`：`ACTIVE`，没有换文件 | `STAGED` → `ACTIVE`，`Replaced` 为假 | 目录里已经是这一份、网关也在跑它，发布器只补记确认（`publish.go` 里 `inPlace` 那一支）。没有 `APPLYING` |
   | `publish`：`ACTIVE`，补完上一次没做完的（`complete`） | `STAGED` → `OBSERVING` → `ACTIVE`，`Replaced` 为假 | 文件是上一次发布换上去的，没来得及记；这一次只等网关报告 |
   | `RESTORED` | `FAILED`，原因里写网关报告的失败 | 上一份已经放回去并得到确认。`FAILED` 的意思就是这个 |
   | `UNKNOWN` | `UNKNOWN` | 换上去了，没有生效，也没能确认放回去。等对账（G03 第 4 节第 6 条） |
   | `POOL_NOT_READY`，发生在补完那一支等网关之后（`complete`） | `FAILED`，`Replaced` 为假 | **对不上一个状态。** 池没有被这一次动过，原来就放着这一份、网关没有报告它在跑。`FAILED` 在这里不是"放回去了"；原因里写清楚 |
   | `REFUSED`、`RESTART_REQUIRED`、`POOL_NOT_READY`，发生在动手之前 | 不记 | 池没有被碰过，也没有哪一次发布开始。这是说得清的一个缺口，见"成本与剩余风险" |
   | `reconcile`：`RESTORED`、`IN_SYNC`、`UNKNOWN`、`UNCONFIRMED`、`RESTART_PENDING`；`place`：`IN_PLACE`、`NO_RECORD`、`UNKNOWN` | 不是发布，不记一条新的 | 唯一的作用见第 4 条：给一条停在半路的补上结局 |
   | `REVOKED`、`LIFTED` 等撤销命令的结局 | 与本篇无关 | 那是 ADR-0012 的另一套状态，不在池的发布历史里 |

   `FAILED` 和 `UNKNOWN` 之外，G03 的 `REJECTED`、`CANCELED` 这一版也不造：加载不了的快照（`REFUSED`）没有开始过发布。

3. **批准这一版不做。** 不加 `--approval-ref` 之类由操作员自己填的字段：G03 第 4 节第 2 条说不把任意客户端的批准标记当权威事实，记一个没人核实的批准号，会被后来的人当成批准过。可以记一个明说是"操作员的备注、未经核实"的自由文本（`--note`，限长，不许有控制字符，写明不要往里放秘密）；要不要这个字段、是不是必填，见"请所有者定的"第 3 项。

4. **先写后做。** 每一步动手之前，先把这一步写进历史并落盘；写不进去，这一步不做，池什么都没有被动（命令以退出码 1 结束，与"出了错，池没有被碰过"相同，不另设结局）。做完之后收尾的那一笔写不进去时，池的状态仍以配置目录里的记录为准，这一条历史停在最后写成的那一步，由下一次对账补上结局：`reconcile` 发现历史里有一条没有结局的，而池的记录（`.config.yaml.confirmed`）说确认的就是它的快照，就补一行 `ACTIVE`；池的状态说明它没有生效（比如对账把上一份放回去了），补 `FAILED`；读不到网关、结局是 `UNKNOWN` 时不补。补结局不"做"任何事，它写不进去不改变 `reconcile` 的结局和退出码，只在标准错误里说一句。这样历史里可能有一条"没有结局"的，但不会有"做了却没有记"的。
   两处要说明。`OBSERVING` 那一行不是动手之前的一步：等网关报告不改池，所以它写不进去时发布照常往下走（等网关、确认、换池的记录），这条历史停在 `APPLYING`，由收尾那一笔或者下一次对账补上；不为了一行日志把一份已经换上去、可能正常的快照收回去。带重启的发布里"重启网关"是动手的一步，它那一行写不进去时不重启；文件这时已经换上去了，照现有"重启之前被叫停"的那条路把上一份放回去（`restart.go`），结局是 `RESTORED` 或 `UNKNOWN`，原因里写历史写不进去。

5. **现有的那份记录不动。** `.config.yaml.confirmed` 仍是 `place`、`reconcile`、看守、开机启动的依据，这几条路都不读历史：机器重启时没有人在场，历史读不成不能让池起不来（ADR-0010 第 10 条"启动的先后"）。历史只用来查和回滚。`publish`、`restart` 先读池的记录再动手这一点也不变。

6. **回滚是一次新的发布。** 新命令按编号从历史里取出那份快照，走的仍是 `publish` 的全套检查和确认（环境变量检查、用现在的镜像离线加载、池要对得上记录、回读确认），记成新的一条，"回到的那一条"指向被取出的编号；不改历史里已有的任何一条（G03 第 3 节："ROLLBACK 创建新受控事件，指向上一个已批准有效 Snapshot；不得静默篡改历史"）。细节：
   - 只能回到到过 `ACTIVE` 的那几条；`FAILED`、`UNKNOWN` 的不行。
   - 目标就是现在放着的那一份：不发布，结局 `REFUSED`（没有什么可回的）。
   - 取出的快照与现在的网关启动设置不同、要重启时，默认结局是 `RESTART_REQUIRED`，与 `publish` 一样；加 `--with-restart` 才走 `restart` 那一条。
   - 读不到历史、快照文件与它的 SHA-256 对不上：退出码 1，池没有被碰过。
   - 老快照用现在的镜像不一定还能加载。那时结局是 `REFUSED`，这是全套检查要的，不绕过。

7. **新的命令**（名字照现有命令的风格起，是提议；`restore` 已经被撤销命令用了，所以回滚叫 `rollback`）：
   - `releases`：列出一个池的发布历史（编号、时刻、结局、快照的短 ID、发起人），只读。
   - `release --id <编号>`：一条的详情和它的每一步，只读。
   - `rollback --to <编号>`：第 6 条。
   这三条和 `publish`、`restart` 共用一个新的参数 `--history-dir`，另有 `--pool <名字>`。`--history-dir` 不给时命令与现在完全相同，没有历史（ADR-0012 里 `--revocations` 同样的做法）；给了就记，`releases`、`release`、`rollback` 必须给。`releases` 另外读池的记录（只读，不占锁）并指出两者对不上（见"成本与剩余风险"）。

8. **放在哪：应用层定一个端口，第一个适配器是文件。**
   - `internal/gatewayconfig/ports` 里多一个端口（名字动手时定）：开始一条、给一条追加一步、按 ID 存取快照、列出、取详情。`application` 只依赖端口；`publish.go`、`restart.go` 和 `reconcile.go` 经它记，不知道后面是文件还是数据库。
   - 第一个适配器 `internal/gatewayconfig/adapters/history`：历史目录在池的目录旁边，与配置目录分开，网关容器不挂它。里面是 `snapshots/<SHA-256>.yaml`（不可变，写临时文件、刷盘、改名，权限 0600）和 `releases.log`（只追加，一行一条状态变化，JSON，写完刷盘；新建文件之后刷目录）。读的时候最后一行没有换行结尾算没写完的，忽略；中间的行读不懂，算历史坏了，报错，不猜。权限只给跑发布器的账号（目录 0700）。
   - 并发仍靠配置目录里现有的那把锁：写历史都发生在 `Hold` 之内，只读的两条命令不占锁。
   - 保留多少由所有者定（"请所有者定的"第 2 项）。
   - 只用标准库，不进 `go.mod` 新依赖；包的依赖方向仍由 `internal/architecture` 的测试守着。

9. **Bento-Go 什么时候进来：这一版不进，条件定好。** ADR-0009 第 4 条的方向不变：控制面的持久化用 Bento-Go。这一版不引入，理由是：
   - 它的存储只有 PostgreSQL。在单机上，为一个命令行程序另起一个数据库，保管它的凭据、做备份，而这台机器本来只靠一个目录和一个 docker 就能把池起来；
   - 它仍是候选版（`v0.1.0-rc.2`），PostgreSQL 适配器标着实验性；这两样会进 `go.mod`，连带 `pgx/v5` 和 OpenTelemetry API；
   - G03 要的乐观并发和 Outbox，是为多个池、多个写入方和向 Fabric 回报准备的，这些现在都还没有：一个池一把锁，一个写入方。
   端口按"以后换适配器"来设计：端口上不出现文件路径、行号这类只有文件才有的东西。**进来的条件**写成可以检验的，出现任何一条就重新评估：
   - 出现第二台机器或第二个池，需要一处看到全部的历史；
   - 开始对接 Fabric 的发布意图（那时才有 `APPROVED` 和幂等键，才用得上乐观版本和 Outbox）；
   - 历史要给发布器之外的进程读。
   到那时按 ADR-0009 第 4 条：`go.mod` 里锁定精确版本（引入时再确认当时的版本），对它的导入只出现在 `adapters` 和装配代码，第一次引入的那个提交同时带上 `tests/bentocontract` 和一个显式的迁移命令；并把文件里的历史导进去（导入是迁移命令的一部分）。

10. **这一版不做的：**
    - 批准和 Fabric（第 3 条）；
    - 撤回的三个状态（`WITHDRAW_REQUESTED`、`REVOKING`、`REVOKED`）；
    - 多个池的汇总；
    - 灰度和分批（一个池只有一个实例，ADR-0010 第 10 条）；
    - Outbox 和事件；
    - 历史的签名或防篡改，只有文件权限；
    - RouteIntent 到快照的出处：那是第 4 节第 3 项的事，这里只给记录留一个位置（第 1 条最后一款）；
    - 动手之前就被挡下的尝试的记录（第 2 条表里"不记"的那几行）。

11. **原有用例的期望不改。** 黑盒和 compose 套件现有用例的结局、退出码、输出都不变；它们不给 `--history-dir`，所以不带历史。历史是多出来的，另写用例：每一步先写后做（造一个写不进去的历史目录，池不被碰）；收尾写不进去、再跑 `reconcile` 补上结局；回滚；`releases` 指出两处对不上；发布器被强行杀掉之后历史停在哪一步。

## 请所有者定的

下面六项需要所有者逐条说"照推荐的做"或者"这一条换成另一个选项"。推荐不是决定。

**2026-11-19，仓库所有者看过本篇之后定的：六项都照推荐的做**（第 1 项 A，第 2 项 A，第 3 项 A，第 4 项照推荐，第 5 项 A，第 6 项"是"）。这是开工的许可，不是对本 ADR 的决定；状态保持 Proposed。第 4 项里"这个账号是谁"仍然没有定。下面各项的原文留着，供以后重看。

1. **存储。**
   - 选项 A（推荐）：端口加文件，Bento-Go 和 PostgreSQL 等第 9 条的条件出现再进来。
   - 选项 B：现在就上 Bento-Go 和 PostgreSQL（ADR-0009 第 4 条的字面做法）。代价见"被考虑的替代方案"第一条。
   - 推荐 A 的理由：单机上多一个数据库及其凭据，换来的乐观并发、Outbox 现在没有人用；而候选版框架和实验性适配器进 `go.mod` 之后退不回去。选 B 时，第 8 条作废，第 9 条改写，其余照旧。

2. **保留多少。**
   - 选项 A（推荐）：全部留着，不写自动删除。
   - 选项 B：只留最近 N 条和它们的快照。
   - 依据：黑盒的评审配置 `tests/acceptance/blackbox/agentgateway.poc.yaml` 是 28995 字节，`deploy/agentgateway/agentgateway.local.example.yaml` 是 1487 字节；真实配置会随路由数增长，没有量过。按 29 KB 估，每天发布 10 次，一年约 3650 份、100 MB 出头（相同内容只存一份，实际更少）；每条日志约 1 KB（估计）。这个量一台机器放得下，没有理由为空间删。反过来，自动删除是新的代码，删错一份快照就让一条历史回不去。选 B 时，N 建议不小于 100，并且只删旧的快照文件、保留日志行（日志上写"快照已清理"，`rollback` 对它答 `REFUSED`）；不删最近一条 `ACTIVE` 和它前面一条。
   - 这个估算是假设，不是测量；所有者若有真实配置的大小，以它为准。

3. **操作员的备注。**
   - 选项 A（推荐）：有 `--note`，不必填，限长（建议 512 字节，与撤销的原因同），未经核实的字样写进 `release` 的输出。
   - 选项 B：必填（像 `revoke --reason`）。
   - 选项 C：不要这个字段。
   - 推荐 A：发布频繁，必填会被敷衍成一个字；回滚时写一句为什么才有用，可以让 `rollback` 一条必填（也在选项 B 之内，由所有者定）。

4. **历史目录放在哪、归谁。** 这牵涉"发布器在单机上以什么身份运行"，ADR-0010 V1.3 起一直列为没有定的。
   - 推荐：与池的配置目录同属一个账号（跑发布器和看守的那个账号），放在它的旁边，目录 0700；网关容器和前置代理不挂载。具体路径跟着 `deploy/compose` 的部署文件定，部署文件里把 `--history-dir` 写死在发布器和看守的命令里，免得有人忘了给。
   - 要所有者定的是：这个账号是谁。在它定之前，本篇只能写"与配置目录同属一个账号"。
   - 备份不在本篇里；历史只在这一台机器上（见"成本与剩余风险"）。

5. **收尾那一笔写不进去时，`publish` 的退出码。** 指的是池确实是 `ACTIVE`、网关也确认了、历史的 `ACTIVE` 那一行写不进去。
   - 选项 A（推荐）：单独一个结局，名字 `ACTIVE_NOT_RECORDED`，退出码 8（0 至 7 已被占用，7 只有撤销命令用）。照撤销命令 `REVOKED_NOT_WRITTEN` 的先例（ADR-0012 V1.2）：生效了、没有记下来，不算成功（脚本不会当作都做完了），也不算什么都没变。标准错误里写明：池已经在跑这份快照，历史停在哪一步，再跑一次同样的命令是安全的（它走"目录里已经是这一份"那一支，补记）。
   - 选项 B：退出码照旧是 0，标准错误里说一句，看守的指标里加一项。好处是脚本和现有的套件不受影响；坏处是审计缺口无声无息。
   - 推荐 A 的理由：历史存在的目的就是"过后查得到"，缺了一条而命令说成功，等于让缺口不被发现。池本身不受影响（第 5 条）。要看到的代价：自动化调用 `publish` 的人要认得这个新的码。
   - 收尾写不进去的另外几种（`RESTORED`、`UNKNOWN`）本来就是非零，沿用原来的结局，只在标准错误里多一句。

6. **这一步之后，第 4 节第 3 项（RouteIntent 编译器）是不是紧接着出提案。**
   - 推荐：是。历史里为出处留了位置，RouteIntent 到快照的对应也是 `GW-GAP-06` 的另一半（开发计划第 4 节第 2、3 项同挂这一条）。这一项的提案可以在本篇定下来之后立刻起草，不必等这一步写完代码。
   - 另一个选项：先做第 4 节别的项（第 1 项真机验证、第 4 项换镜像和发布器的证书），第 3 项推后。发布器证书的签发和轮换本来就悬着（ADR-0010 V1.3），而本篇第 1 条要用到它的身份，所以先做第 4 项也说得通。

## 为什么这样决定

历史要回答的是三件事：谁在什么时候把哪一份放上去了，放上去的结果是什么，现在回得去吗。这三件事用一份只追加的日志加一个按摘要存放的快照目录就答得了，写一条、读一条、列一串，没有查询、没有并发写入方、没有跨表的一致性要求。G03 第 4 节第 4 条要的"保存不可变制品和审计"是这样；乐观版本和 Outbox 是多个写入方才有的问题，一个池一把锁时用不上。

先把端口和数据定下来，是因为数据才是迁不掉的东西：一条记录有哪些字段、状态怎么叫、编号怎么取、回滚指向谁，这些以后换存储也要照着走。存储可以换，数据的样子最好一次定对。所以本篇把第 1、2 条定得细，第 8 条的文件格式定得浅。

不让开机这条路依赖历史，是因为开机时没有人在场。ADR-0010 第 10 条的"启动的先后"让 `place` 不读网关、不接网络、不用 docker，就是为了它尽量少失败；失败了就是池不通（"启动时对不上，这个池就不通，直到有人来处理"）。把历史放进这条路，一个坏掉的日志文件、一个满了的磁盘就能让一台没人看的机器起不来池，而历史是用来查的，不是用来跑的。所以 `.config.yaml.confirmed` 一个字不动，历史是旁边多出来的一份。

先写后做，而不是先做后补记，是因为两种出错方式的代价不一样：前者出错时最多有一条没有结局的记录（对账补，查得出来），后者出错时有"做了却没有记"的发布，而这正是现在的状态，也是要消除的。

回滚做成新的一次发布，是为了不开第二条下发的路：回滚要过的检查和发布一样（现在的镜像还加载得了吗，池对得上记录吗，网关回读对上了吗），分开写就要保持两份一致。G03 也是这样写的。

不替操作员记批准号，是因为这个仓库里没有任何一处能核实它。记下来的东西会被人当成事实。

## 被考虑的替代方案

- **现在就上 Bento-Go 和 PostgreSQL**（ADR-0009 第 4 条的字面做法）。好处：一步到位；乐观并发、Outbox 现成；将来不用迁数据；以后接 Fabric 时不必再动存储。代价：
  - 单机部署多一个数据库，要给它凭据、备份、升级；发布这条路多了一个会坏的依赖：数据库不通时，`publish` 按第 4 条要么不做（发布停摆，包括紧急时回滚），要么绕过历史（那历史就不全）；`place` 无论如何不能依赖它，所以开机那条路还得保留文件，两套存储；
  - 候选版框架和实验性适配器进 `go.mod`，连带 `pgx/v5` 和 OpenTelemetry API，而本仓库现在没有任何第三方依赖；
  - 工作量大得多：迁移命令、`tests/bentocontract`、数据库的测试夹具，都在这一步一起带上（ADR-0009 第 4 条）。
  留给所有者选，见"请所有者定的"第 1 项。
- **不设端口，直接把历史写成文件，将来再说。** 省事。没有采用：将来换存储时要改应用层，而应用层是发布流程所在；端口只多一个接口和一个适配器的边界，这一步的代价很小。
- **什么都不存，继续只留最后一条，回滚靠人手里的快照文件。** 就是现状。代价：发布过什么过后查不到；失败被收回去的那一次不留痕迹；要回到更早的一份，靠有没有人留着文件；`GW-GAP-06` 里"可回退"没有依据可查。不推荐，但它是零成本的，不做也能继续往下做第 3 项。
- **把历史放进现有的记录文件里。** `.config.yaml.confirmed` 是整份换掉的，历史会让它越来越大，而 `place`、`reconcile`、看守每次都要读整个文件；这个文件读不成就是池起不来（ADR-0010："它坏了，发布、对账和放到位的各条命令都停下来等人看"），把历史放进去，历史的任何一处写坏都会变成池的故障，也违反第 5 条。没有采用。
- **历史放在配置目录里，和记录并排。** 网关容器挂载的是配置目录（ADR-0010 第 10 条），历史会被挂进网关容器；而 `pin-egress.sh` 之类的东西也读这个目录。历史里有全部旧的快照，没有理由让网关容器看到。没有采用，放在旁边。
- **用 SQLite。** 一个文件、有事务。没有采用：要引入第三方依赖（Go 的 SQLite 驱动，纯 Go 的或者要 cgo 的），而本篇要的只是追加和按编号读；它也不在 Bento-Go 里，将来迁到 PostgreSQL 时仍是一次迁移。这一条是执笔时想到的，没有人提过。
- **每条发布一个文件。** 追加变成建新文件，列出要读整个目录，崩溃时没有"最后一行没写完"那样简单的规则。没有采用。

## 成本与剩余风险

- **历史和池的记录是两处，可能对不上。** 会对不上的情况：发布时没有给 `--history-dir`；收尾那一笔写不进去而没有再跑过 `reconcile`；历史目录丢了或者换回旧的一份；有人绕过发布器直接改了配置文件（`reconcile` 会把池放回记录的那一份，但那一次历史里没有）；池的记录被删。发现的办法：`releases` 读池的记录，把它的快照 ID 与历史里最后一条 `ACTIVE` 的比，不同就在输出里标出来。谁说了算：池在跑什么，以配置目录里的记录加网关的回读为准；历史只说"发布器记得做过什么"，不说池现在的样子。`rollback` 取历史里的快照，但池的状态检查仍然看池的记录。
- **文件在一台机器上，机器没了历史就没了。** 备份和异地不在本篇里。池的记录也在这一台机器上，所以没有更糟，但历史的价值更依赖它。
- **没有防篡改。** 只有文件权限（0700 / 0600）。有这个账号的人能改日志、改快照文件（读的时候会拿 SHA-256 核对快照，改快照会被发现，改日志不会）。"谁发起的"是进程自己报的证书身份和操作系统账号，拿到证书和目录权限的人能写任何东西。G03 说"不得静默篡改历史"，这一版做到的是：发布器自己不改已有的行；不是别人改不了。
- **将来迁到数据库是一次迁移。** 迁移命令要把日志和快照导进去，编号要保留（作为原编号），导入后文件不再写。第 9 条的条件之一出现时才做。
- **状态名与 G03 的对应只覆盖一段。** 只有 `STAGED` 到 `ACTIVE`、`FAILED`、`UNKNOWN`、`SUPERSEDED`。第 2 条表里有一行对不上（补完那一支的 `POOL_NOT_READY` 记成 `FAILED`，而池其实没有被动过），另有一类不记。Console 的展示和 Fabric 要的词表（`ReleaseState`）以后接上来时，还要再对一次。
- **动手之前就被挡下的尝试没有记录。** 比如 `REFUSED`（快照里有环境变量的引用、离线加载失败）、`RESTART_REQUIRED`、`POOL_NOT_READY`。后果：想查"谁试过发布一份有问题的快照"查不到。不记的理由是它们没有改池、没有开始发布；记下来要在什么都没做之前先写一行，而写不进去时按第 4 条该拒绝一次本来也只会被拒绝的操作。所有者若要它们也记，是第 2 条表的改动，不影响别的条。
- **`--history-dir` 不给时命令照旧，没有历史。** 这是为了第 11 条，代价是有人漏给就有缺口。靠部署文件里写死参数，以及上面第一条的比对发现；没有别的拦截。
- **多一个写盘的步骤。** 一次发布多写三到四行日志和一份快照，每次刷盘；对发布的耗时影响没有量过，预期在毫秒到几十毫秒，发布本身要等网关重载（`DefaultTiming` 里最少等 1 秒，最多 10 秒）。
- **看守每分钟的对账会碰历史。** 只在有一条没有结局的记录时才写，一般情况下只读；读不成时 `reconcile` 的结局不变，只在标准错误里说一句。看守的指标里要不要多一项"历史读不成"，动手时再定，本篇不要求。
- **第 4 条的"补结局"依赖池的记录。** 记录说确认的是这条的快照，就补 `ACTIVE`。极端的情况：同一份快照先后发布了两次，第二次中途被杀，对账看到的记录是第一次留下的，补成了第一次的结局。两条记的是同一份快照，摘要相同，补错的只是那一条的时刻和编号。动手时用"这条的开始时刻晚于池记录里的确认时刻就不补成 `ACTIVE`"一类的条件收紧，并要有测试守着；本篇不展开。
- **身份取自发布器证书。** 发布器的证书由谁签发和轮换仍没有定（ADR-0010 V1.3）。证书里没有 URI 或不止一个时，历史里该项记空，不拒绝发布。

需由仓库所有者复核和决定；在此之前保持 Proposed。执笔的是 AI 编码助手，这不是决定。

出现下面任何一种情况，重新评估本决策，而不是自动维持：

- 第 9 条里的三个条件之一出现（第二台机器或第二个池要一处看全部的历史；开始对接 Fabric 的发布意图；历史要给发布器之外的进程读）：改用 Bento-Go 和 PostgreSQL，第 8 条跟着换，第 1 至 7 条的数据和命令不变；

### V1.0 写的是……，做出来是……

1. **谁给停在半路的发布补结局。** V1.0 第 4 条写"`reconcile` 发现历史里有一条没有结局的……就补"，第 5 条写"`place`、`reconcile`、看守、开机启动的依据，都不读历史"。两句对着"开机时 `confirm` 也是 `reconcile`"没有说清。做出来：**开机这条路完全不碰历史**。`compose.yml` 没有改，`place` 和 `confirm` 不挂历史目录、不给 `--history-dir`（挂进容器会多出一种开机失败的方式：目录不在时 docker 自己建一个 root 的，或者拒绝启动）。补结局由看守每分钟的对账做，不必在开机时做；操作员手工 `reconcile` 带 `--history-dir` 时也做。
2. **`OVERTAKEN`。** V1.0 第 2 条列的状态是 `STAGED`、`APPLYING`、`OBSERVING`、`ACTIVE`、`FAILED`、`UNKNOWN`，`SUPERSEDED` 读时推出来。做出来多了 `OVERTAKEN`，写下去的：只有一个池里**最新**的那一条能按"事实上怎么样了"补结局（池的记录确认它的快照就是 `ACTIVE`，确认的是别的快照就是 `FAILED`）；它之前没有结局的，后来的发布已经开始了，它有没有生效不知道，补 `OVERTAKEN`，不借用 `FAILED`。`rollback` 对 `OVERTAKEN` 的答 `REFUSED`，同 `FAILED`。
3. **补成 `ACTIVE` 的条件。** V1.0"成本与剩余风险"留了一条：同一份快照先后发布两次、第二次中途被杀时会补错，"用这条的开始时刻晚于池记录里的确认时刻就不补成 `ACTIVE`一类的条件收紧"。做出来：池的记录里的确认时刻不早于这一条开始的时刻才补 `ACTIVE`。**确认时刻的精度是秒**（记录里就是秒），所以比的时候开始时刻取到秒；同一秒内的先后分不出（见"没有做的"）。
4. **再跑一次同样的命令补全，只对 `publish`。** V1.0 第 4 条只说"由下一次对账补上结局"，选项 A 的说明里说"再跑一次同样的命令是安全的"。做出来：`publish` 同一份快照，而池的记录已经是它时，给停着的那一条补结局（步骤名 `publish-again`），不另开一条；`restart` 和 `rollback` 停下来的，只由对账补。
5. **历史目录要先建好。** V1.0 第 8 条写"权限只给跑发布器的账号（目录 0700）"。做出来：命令不创建历史目录，目录不在就报错（免得敲错路径把历史写到别处）；目录里的 `snapshots/` 和 `releases.log` 第一次写时由发布器建（0700、0600）。命令不检查历史目录自己的属主和权限，要求 0700、归 `CONTROL_USER` 写在部署说明里，没有谁核对。这个账号是谁，"请所有者定的"第 4 项一直没有定。
6. **池的名字用 compose 的项目名。** V1.0 第 7 条的 `--pool` 是"池的标识"。做出来：看守的单元里是 `idp-gateway-pool`，即 `compose.yml` 的 `name:`，不新增 `.env` 变量；`tests/contracts` 核对单元里的 `--pool` 与 `compose.yml` 的 `name:` 相同、`--history-dir` 是 `${POOL_DIR}/history`，并核对 `compose.yml` 里没有服务提到 `history`。
7. **"把 `--history-dir` 写死在发布器和看守的命令里"只对看守成立。** "请所有者定的"第 4 项这样推荐，为的是免得有人忘了给。部署文件里只有看守的命令（单元）；发布器的 `publish`、`restart` 是操作员手工跑的，部署文件里没有它们的命令，`place` 和 `confirm` 按第 1 项不给。操作员那一头靠说明里的 `$HISTORY` 和 `releases` 的比对（`mismatch`）发现漏给，没有别的拦截。
8. **历史有毛病时，`reconcile` 和看守不停。** V1.0 第 4 条和"成本与剩余风险"写的是：补结局写不进去、读不成时，`reconcile` 的结局和退出码不变，只说一句；看守同理。第一阶段的代码只在一部分情况下这样：
   - 日志坏了（有读不懂的行）：对账照常，标准错误上说一句，有单元测试；
   - 日志读不了（文件权限）：补结局那一步读不到，同样只是警告（第二阶段补了测试）；
   - **目录不存在或不是目录：`reconcile` 和 `keep` 都在打开历史时退出，退出码 1。** `reconcile` 没有对账；`keep` 没有启动，看守的单元会被 systemd 每 5 秒再起一次。第一阶段的 `TestKeepRefusesAMissingHistoryDirectoryWithExitOne` 还把这当成期望。这与第 5 条（"历史读不成不能让池起不来"，看守是守池的）不符。

   第二阶段改了：`reconcile` 和 `keep` 打不开历史时，换成一个每次都失败的历史（`cmd/gateway-control/history.go` 的 `unavailableHistory`）继续：对账的结局和退出码不变，看守照常看、照常对账、照常起容器，只是不补；`reconcile` 的标准错误上、看守启动时的标准错误上说一句，看守之后每次对账补不成时那一行里有 `history_notes`。`publish`、`restart`、`rollback` 不变：写不进历史就不动池。那条旧测试换成三条（看守目录不在、看守日志坏了、`reconcile` 目录不在）和一条日志读不了的。V1.0 说"看守的指标里要不要多一项'历史读不成'，动手时再定"：定了不加，只有输出行里的 `history_notes` 和启动时的一句，没有指标，没有告警规则。
9. **补出来的 `FAILED` 不等于"池没有被动过"。** 带重启的发布做到一半被杀时，网关可能已经带着新的启动设置在跑；对账把记录的那一份放回去，结局是 `RESTART_PENDING`，这一条补成 `FAILED`，原因里带着对账说的启动设置不同。V1.0 第 2 条对 `FAILED` 的说明是"上一份已经放回去并得到确认"；这里放回去的只是文件，启动设置要再做一次不给快照的 `restart`。真的池上看到了（`SH-26`）。

### 验证到哪

- **Go（第一阶段）。** 单元测试覆盖端口和文件适配器（崩溃留下的半行、中间读不懂的行、快照被改、权限）、先写后做的每一步写不进去、`ACTIVE_NOT_RECORDED`、对账补结局的各种情形、回滚的各种拒绝、`releases` 的比对、不给 `--history-dir` 时什么历史都不碰。带竞态检测跑过。第一阶段改坏 24 处，每一处都有 Go 测试不通过。
- **Go（第二阶段）。** 第 8 项的三条新测试和一条日志读不了的；它们对着第一阶段的代码（目录不在就退出）会不通过。没有再做对照。
- **部署文件。** `tests/contracts` 多了两个（现在 154 个）：单元里的 `--history-dir`、`--pool` 与 `compose.yml` 一致，没有服务挂历史；套件里历史目录的位置与部署一致。`units.py` 6/6，看守的单元拿到的参数里多了这两个。
- **compose 套件。** 八个用例、52 项检查（`SH-23` 到 `SH-30`，细节在 compose 套件 README 第 17 点）：不给 `--history-dir` 时什么都不写；带历史发布，日志、快照、权限、`releases`、`release`、`SUPERSEDED`、带重启的一步；历史写不进去时 `publish` 不动池；发布器被杀之后看守补成 `FAILED` 和 `OVERTAKEN`，带重启的发布被杀补成 `FAILED`；收尾那一行去掉之后，看守补成 `ACTIVE`，再发布一次补全；回滚、各种 `REFUSED`、快照被改；漏给参数时 `releases` 指出对不上；历史目录不在、日志坏了时，断电后开机照常，带历史的看守照常工作。现有的 22 个用例只有 `SH-19` 的一项检查因为单元的命令行多了两个参数而改了（命令行不再以 `--metrics-listen` 结尾）；其余的检查一字没改。整套连跑三轮（2026-11-19）：都是 30/30、303 项检查（原有的 251 加新的 52），三轮的检查项逐项相同，每轮 790 到 838 秒。写用例的时候整套另跑过两遍，其中一遍是 29/30：不通过的是 `SH-15` 的一项（后端起来 20 秒之后得到的是 200，而不是 503）。这一条与历史无关，没有改它；事后查到的原因是网关照着解析器给的否定缓存时间办事，那一遍上游解析器没有给出可以缓存的"名字不存在"，见 compose 套件 README 第 17 点末尾，处理在这之后另做。
- **黑盒套件**没有重跑：这一阶段改了 Go（第 8 项），原有的证据会过期，在提交之后重跑。
