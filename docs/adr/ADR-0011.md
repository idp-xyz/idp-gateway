# ADR-0011 — 出站凭证由 gateway-authz 持有，按账户现取

> **状态**：Proposed（待具名批准） · **版本** V1.1 · **日期** 2026-11-18（V1.0：2026-11-17）  
> 本 ADR 为设计建议，不是已经执行的技术审批、生产基线或运行验收。它是[开发计划](../development-plan.md) 1.4 和 2.1 所等的那份提案。  
> 2026-11-18，仓库所有者同意照本篇动手，先做第 3 条。这是开工的许可，不是具名批准；状态保持 Proposed。

## 背景

[ADR-0003](ADR-0003.md)、[G02](../G02_Architecture.md) 11.1 节和 [G04](../G04_Identity_and_Security.md) 第 2 节把第三方凭证的登记和 Token Broker 放在 Gatekeeper。[ADR-0008](ADR-0008.md) 把兑换凭证收成一条路：网关验证调用方之后调用 ExtAuthZ，允许响应里的 `Authorization` 头就是这次请求的 Provider 凭证，网关只把这一个头写到上游。

现在这条路的 ExtAuthZ 由本仓库的 `gateway-authz` 实现。凭证来自一个 JSON 文件，键是凭证句柄（绑定/账户），值是 Bearer 令牌；进程启动时读入，权限不是 0600 或更严就拒绝加载（`internal/egressauthz/adapters/filestore`）。[ADR-0009](ADR-0009.md) 把"凭证从哪里来"列为没有定的，并写明 ADR-0003 与 ADR-0008 里"Gatekeeper 下发凭证"的正文这次不改。

开发计划 1.1 选定的沙箱不是 OAuth2。按它的[对接文档](http://apidoc.wanbexpress.com/How-To-Start/)，`Authorization` 的值是 `Hc-OweDeveloper 账号;令牌;随机数`。令牌是事先向它申请的固定令牌。随机数不能为空；文档写明以后的版本会限定同一个客户在一段时间内不能重复，所以要每个请求换一个。现在的文件给出的是一个固定的 `Bearer` 值，做不到这件事。[G04](../G04_Identity_and_Security.md) 第 9 节另外要求同一操作上固定凭证和动态 OAuth 两种都证明；这一家用不到第二种，所以第二种不在 P2 的必经路上，但仍然要做。

## 推荐决策

1. **凭证正文由 `gateway-authz` 持有。** 判定通过之后，由它把这次请求的 `Authorization` 值放进 ExtAuthZ 的允许响应。网关仍然只复制这一个头，ADR-0008 的第 1、4 条不改。Gatekeeper 继续只回答"这个调用方此刻能不能用这个账户"（`ports.Grants`），不提供凭证正文。账户能不能用和凭证正文是两件事，端口已经分开。

2. **ADR-0003 和 ADR-0008 的正文这次不动。** 两篇都还是 Proposed。本篇被接受之后，再各出一个新版本，把"Gatekeeper 下发凭证正文"收成"Gatekeeper 决定账户能不能用，凭证正文在 `gateway-authz`"。`contracts/gatekeeper/openapi.yaml` 现在由本仓库实现，它的归属也留到那时再改，与 ADR-0009 的写法相同。具名批准人不接受本篇的话，开发计划 2.1 按拒绝的理由改，照本篇写下的代码跟着改或撤掉。

3. **第一步是固定令牌加每个请求一个随机数。** 这是 P2 要的。现有的 `--credentials` 和 Bearer 文件保持原样，黑盒套件继续用它。
   - 另给一个文件，由单独的启动参数指出。权限同样必须是 0600 或更严，否则不启动。JSON 对象的键仍是凭证句柄。值是对象，有两个字段：`account`（承运商账号）和 `token`（开发者令牌）。文件里不存放随机数。
   - `account` 和 `token` 只能是可见 ASCII，不能为空，不能含空白、分号或控制字符，否则不启动。拼出来的整段头放进 `ports.Secret`：日志、错误信息和 JSON 里都是占位符，只有写到上游请求时才取出原值。
   - 每个请求用 `crypto/rand` 新生成一个随机数，不落盘，不写进日志。头的值是 `Hc-OweDeveloper `，接着账号、分号、令牌、分号、随机数，随机数之后没有分号。文档规定随机数只能用字母、数字、短横线和下划线。这里取 16 个随机字节，写成 32 位十六进制字符，与文档示例的长度相同。
   - 网关一侧要跟着改一处。评审过的配置里，凭证由 PDP 按请求给出的各条路由，后端上都有一条规则，只放行以 `Bearer ` 开头的 `Authorization`：它是黑盒报告"默认配置不安全的地方"第 3 项的处理，PDP 放行却没给凭证时由网关拒绝。这一家的头以 `Hc-OweDeveloper ` 开头，照搬这条规则，请求会全部被网关拒绝。这一家的路由上，规则的前缀换成 `Hc-OweDeveloper `，规则本身留着。这是开发计划 3.2 那份配置的事，写在这里是因为它由本篇的头格式决定。
   - 两个文件可以同时给。同一个句柄出现在两个文件里则不启动。只给原来的 Bearer 文件时，行为与现在相同。
   - 换令牌用换文件，不靠重启，也不靠环境变量。进程在要用这份文件时看到修改时间变了，就整份重读。换文件的做法是写临时文件再改名，让修改时间一定变。新文件读不成或校验不过，继续用上一份读成的，并记一条不含账号和令牌的错误。启动时文件就读不成，则不启动。凭证不进网关的配置快照，也不靠快照里的环境变量引用带进去：快照的全文记在发布器的记录里，运行中的配置从回读口读得到（`tests/integration/compose` 的 `SH-10`、`SH-08`）；环境变量引用另由 ADR-0010 第 11 条禁止。Secret Manager 这一步不接。

4. **第二步是 OAuth2 客户端凭证，对着替身令牌端点。** 不在 1.1 那一家的必经路上。[G04](../G04_Identity_and_Security.md) 第 4 节的缓存键至少包含 Provider、账户、环境、客户端、scope 或 audience、密钥版本。同一个账户同时来的请求只向令牌端点发一次。取不到、超时或答错，这次请求拒绝，不用过期的令牌，也不用上一枚顶上。过期之前换新；提前多少在实现时取一个值，写进测试，不写成业务要求。客户端密钥与第一步同一个规矩：单独的文件、0600、不进快照、不进日志。句柄仍然只能出现在一个文件里。令牌端点写在这份文件里：不是回环地址上的 `http`，就必须是 `https`。被撤销的账户不得交出缓存里的令牌；撤销状态存在哪里、谁能写，是另一篇提案，本篇不定。

5. **两个账户不串用，按句柄保证。** 沙箱目前只有一个测试账号。两个账户各拿各的令牌，先用文件里的两条记录对着替身证明。第二个沙箱账号要到之后，才在沙箱上做这一条。本篇不把"现在就有第二个沙箱账号"当作开工条件。

6. **黑盒套件原有用例的期望不改。** 新来源另写用例。Bearer 文件的格式不变。

## 为什么这样决定

Gatekeeper 的模型里现在还没有 Provider 账户这个类型，Broker 在它那边仍是基线里的提案。P2 要的这一个头，每次请求都不一样，无论放在哪一个进程里都得现做。`gateway-authz` 已经在这条请求上，端口也已经把"凭证正文"和"账户授权"分开，所以正文先放在这里，少一次往返。以后改由 Gatekeeper 的 Broker 提供时，换的是 `CredentialSource` 的实现，网关复制响应头的那一段不用改。

这一家不是 OAuth2。先做令牌端点，沙箱要的头仍然发不出去。固定令牌和动态 OAuth 分成两个实现，是因为 [G04](../G04_Identity_and_Security.md) 第 9 节要两种都证明，而不是因为这一家同时用两种。

随机数不能写在文件里，否则就不是每个请求一个。现有实现在启动时读一次，换令牌要重启；重启会把判定停掉。改成看到修改时间变了就整份重读，写坏的文件不替换上一份，是为了避免一份写到一半的文件把所有账户的凭证一起丢掉。

## 被考虑的替代方案

- **等 Gatekeeper 的 Broker 来发放凭证正文。** 基线是这样写的。没有采用，是因为那个类型和 Broker 都还没有，而这个头的随机数不论谁来做都是按请求现做。本篇被拒绝时走这一条。
- **模式 B，本机再放一个 Broker。** ADR-0008 已经测过，隔离与模式 A 相同，代价是多一个持有全部凭证的进程。这一家需要的随机数用那个进程做不比在 `gateway-authz` 里做更少，所以不新增这个进程。
- **把随机数写进网关配置，或做一个通用的头模板。** 快照里不能放秘密。通用模板超出这一家的需要；下一家要另一种头时，再加一个 `CredentialSource`。
- **换令牌靠重启。** 能做到"新请求用新令牌"，但每次轮换都中断判定。不选。
- **这一步就接 Secret Manager。** 还没有指定用哪一个。文件能证明头的格式、按句柄隔离和换令牌。指定了实现之后再加一种来源，不改端口。

## 成本与剩余风险

- 令牌集中在 `gateway-authz` 的进程内存和那个文件上。文件权限和 `ports.Secret` 是现在就有的控制。能读到这个进程的人就能读到令牌。
- 就地改文件且落在同一秒时，修改时间可能不变，这一秒里的请求仍用旧令牌。所以换文件要写临时文件再改名。这一条要写进实现旁边的说明。
- 新文件读不成时继续用上一份。换令牌没有生效时，只有那条不含秘密的错误能看出来。这是有意的：不让一份坏文件把凭证清空。
- 沙箱只有明文 HTTP，令牌在到承运商的路上是明文。这是沙箱的限制。本篇不把生产的上游定成明文；生产地址还没有。
- 沙箱只有一个测试账号。两个账户的隔离先在替身上证明。
- 第二步的替身令牌端点不是这一家承运商。两种凭证都证明，靠的是两个实现，不是这一家同时用两种。
- 撤销记在哪里、产品构建里谁能写，本篇没有定。缓存的 OAuth 令牌在撤销之后不得交出，这一条等那篇提案一起实现；第一步的固定令牌没有缓存，撤销之后的下一个请求只要判定读到撤销就不会再要凭证。
- 随机数的取法是照文档定的，还没有拿它对着沙箱的验证授权接口发过一次。
- 后端上那条规则的前缀换了之后，"PDP 放行却没给凭证时由网关拒绝"要在这一家的配置上重新有用例把关。V1.1 起黑盒套件里有一条替身路由带着新前缀，由 `P1-DT-02` 把关；开发计划 3.2 那份对着沙箱的配置是另一份文件，仍要有它自己的用例。

## 变更与回退条件

需由架构负责人、对应产品 Owner、安全负责人及运行负责人具名复核；在此之前保持 Proposed。执笔的是 AI 编码助手，这不是具名批准。

若具名批准人决定凭证正文仍由 Gatekeeper 的 Broker 发放，撤回本篇，开发计划 2.1 改按那个决定写。若沙箱拒绝本篇取的随机数，只改取法。若指定了 Secret Manager，加一种来源，不把文件这一步删掉：没有接上 Secret Manager 的环境仍要能用文件跑测试。

## 第一步做出来了：固定令牌加每个请求一个随机数（V1.1）

2026-11-18。照第 3 条写了代码，对着替身验证过。写代码、验证和执笔的是 AI 编码助手。**这不是对本 ADR 的具名批准**，状态保持 Proposed。承运商的沙箱没有被调用。

做了什么：

- `internal/egressauthz/adapters/filestore` 多了一个凭证来源，读开发者令牌文件，每次放行时用 `crypto/rand` 现做 16 个字节、写成 32 个十六进制字符的随机数，拼成 `Hc-OweDeveloper 账号;令牌;随机数`。端口（`ports.CredentialSource`）没有改。
- `gateway-authz` 多了一个启动参数 `--developer-tokens`。它和 `--credentials` 至少给一个；只给 `--credentials` 时行为与以前相同。
- 黑盒套件多了一条替身路由和五个用例（`P1-DT-01` 至 `05`）。Mock Provider 按承运商文档查这种头的格式。

第 3 条没有写到、写代码时定下来的，留给具名批准人一并看：

- **`--credentials` 不再是必给的**，两个文件至少给一个。只用得到开发者令牌的部署不必为此放一份空的 Bearer 文件。
- **怎样算"文件变了"**。第 3 条写的是修改时间。实现里另外看两样：大小，和它是不是同一个文件。改名换上来的是另一个文件，修改时间碰巧相同也看得出来。就地改写成一样长的内容而修改时间又没有变，仍然看不出来；有一条单元测试专门记着这一点。
- **同一份坏文件只读一次、只记一次。** 它再被换掉之前，每个请求不重读它。文件不见了也只记一次，继续用上一份。
- **读文件比第 3 条写的严三处**：同一个句柄在一个文件里写了两次，有不认识的字段，对象后面还有内容，都拒绝。
- **几个凭证来源依次问。** 前一个说没有这个账户的凭证，才问后一个；前一个出了别的错，不拿后一个顶上。
- **替身比文档严。** 承运商的文档说以后的版本会限定随机数不能重复；Mock Provider 现在就拒绝用过的随机数。

验证（2026-11-18，Go 1.26.8，agentgateway 1.7.0，锁定的镜像）：

- 单元测试：头的格式；连取 500 次随机数互不相同；文件的权限和各种写坏的内容（错误信息里没有账号和令牌）；换文件之后重读；坏文件、别人可读的文件、带着已被占用的句柄的文件换上来之后继续用上一份；一边换文件一边有 8 路并发在取凭证。带竞态检测跑过。
- `cmd/gateway-authz`：两种文件一起给时各走各的；只给开发者令牌文件也能启动；该拒绝启动的六种情况；服务日志里没有账号和令牌。产品构建和验收构建都跑过。
- 对照：把新代码改坏 19 处，每一处都有测试不通过。
- 黑盒：新的五个用例通过，共 41 项检查。原有 59 个用例的 326 项检查与此前逐项相同，失败的仍只有 `P1-SS-04`。没有改坏的工作区上先后跑了三遍，都是 63/64。对照改坏七处（两处在网关配置，五处在 `gateway-authz`），每一处都有 `P1-DT` 用例不通过，别的用例不受影响。细节在 [黑盒报告](../../tests/acceptance/blackbox/README.md) 的"不是 Bearer 的凭证"。
- `tests/contracts` 多了一条：路由上后端规则认的那个词，要和 `gateway-authz` 源码里的是同一个。

黑盒里看清的两件事：

- **规则的前缀确实要换。** 把替身路由上的前缀留成 `Bearer `，这条路由的请求全部被网关拒绝。
- **调用方塞不进自己的凭证。** 调用方在自己的 Token 旁边再放一个这种头：Provider 两种顺序下都没有收到它。放在 Token 后面，Provider 收到的只有 PDP 给的那一个；PDP 没给凭证时网关照样拒绝。放在 Token 前面，网关答 401。

没有做的：

- 没有对着承运商的沙箱发过请求。替身接受这个头，不等于承运商接受；随机数的取法也还没有在沙箱上试过。
- 第 4 条（OAuth2 客户端凭证）没有开始。撤销记在哪里的提案没有写。Secret Manager 没有接。
- 与本机 Gatekeeper 的联调套件（`tests/integration/gatekeeper`）没有重跑。它用的是同一个 Mock Provider 和只带 `--credentials` 的产品构建；这两样的原有行为由上面的测试和黑盒原有用例把关，那套联调本身这次没有跑。
- 开发计划 3.2 那份对着沙箱的网关配置还没有写。
