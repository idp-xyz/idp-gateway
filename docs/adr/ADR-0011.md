# ADR-0011 — 出站凭证由 gateway-authz 持有，按账户现取

> **状态**：Accepted · **版本** V1.2 · **日期** 2026-11-18（V1.0：2026-11-17；V1.1：2026-11-18）（2026-11-21 仓库所有者定为 Accepted）  
> 本 ADR 为设计建议，不是已经执行的技术审批、生产基线或运行验收。它是[开发计划](../development-plan.md) 1.4 和 2.1 所等的那份提案。  
> 2026-11-18，仓库所有者同意照本篇动手，先做第 3 条；第 3 条做完之后，又同意做第 4 条。这是开工的许可，不是决定；状态保持 Proposed。

> 2026-11-21，仓库所有者把本篇定为 Accepted。此前各节里「这不是对本 ADR 的决定，状态保持 Proposed」是当时的记录，不改。

## 背景

[ADR-0003](ADR-0003.md)、[G02](../G02_Architecture.md) 11.1 节和 [G04](../G04_Identity_and_Security.md) 第 2 节把第三方凭证的登记和 Token Broker 放在 Gatekeeper。[ADR-0008](ADR-0008.md) 把兑换凭证收成一条路：网关验证调用方之后调用 ExtAuthZ，允许响应里的 `Authorization` 头就是这次请求的 Provider 凭证，网关只把这一个头写到上游。

现在这条路的 ExtAuthZ 由本仓库的 `gateway-authz` 实现。凭证来自一个 JSON 文件，键是凭证句柄（绑定/账户），值是 Bearer 令牌；进程启动时读入，权限不是 0600 或更严就拒绝加载（`internal/egressauthz/adapters/filestore`）。[ADR-0009](ADR-0009.md) 把"凭证从哪里来"列为没有定的，并写明 ADR-0003 与 ADR-0008 里"Gatekeeper 下发凭证"的正文这次不改。

开发计划 1.1 选定的沙箱不是 OAuth2。按它的[对接文档](http://apidoc.wanbexpress.com/How-To-Start/)，`Authorization` 的值是 `Hc-OweDeveloper 账号;令牌;随机数`。令牌是事先向它申请的固定令牌。随机数不能为空；文档写明以后的版本会限定同一个客户在一段时间内不能重复，所以要每个请求换一个。现在的文件给出的是一个固定的 `Bearer` 值，做不到这件事。[G04](../G04_Identity_and_Security.md) 第 9 节另外要求同一操作上固定凭证和动态 OAuth 两种都证明；这一家用不到第二种，所以第二种不在 P2 的必经路上，但仍然要做。

## 推荐决策

1. **凭证正文由 `gateway-authz` 持有。** 判定通过之后，由它把这次请求的 `Authorization` 值放进 ExtAuthZ 的允许响应。网关仍然只复制这一个头，ADR-0008 的第 1、4 条不改。Gatekeeper 继续只回答"这个调用方此刻能不能用这个账户"（`ports.Grants`），不提供凭证正文。账户能不能用和凭证正文是两件事，端口已经分开。

2. **ADR-0003 和 ADR-0008 的正文这次不动。** 两篇都还是 Proposed。本篇被接受之后，再各出一个新版本，把"Gatekeeper 下发凭证正文"收成"Gatekeeper 决定账户能不能用，凭证正文在 `gateway-authz`"。`contracts/gatekeeper/openapi.yaml` 现在由本仓库实现，它的归属也留到那时再改，与 ADR-0009 的写法相同。仓库所有者不接受本篇的话，开发计划 2.1 按拒绝的理由改，照本篇写下的代码跟着改或撤掉。

3. **第一步是固定令牌加每个请求一个随机数。** 这是 P2 要的。现有的 `--credentials` 和 Bearer 文件保持原样，黑盒套件继续用它。
   - 另给一个文件，由单独的启动参数指出。权限同样必须是 0600 或更严，否则不启动。JSON 对象的键仍是凭证句柄。值是对象，有两个字段：`account`（承运商账号）和 `token`（开发者令牌）。文件里不存放随机数。
   - `account` 和 `token` 只能是可见 ASCII，不能为空，不能含空白、分号或控制字符，否则不启动。拼出来的整段头放进 `ports.Secret`：日志、错误信息和 JSON 里都是占位符，只有写到上游请求时才取出原值。
   - 每个请求用 `crypto/rand` 新生成一个随机数，不落盘，不写进日志。头的值是 `Hc-OweDeveloper `，接着账号、分号、令牌、分号、随机数，随机数之后没有分号。文档规定随机数只能用字母、数字、短横线和下划线。这里取 16 个随机字节，写成 32 位十六进制字符，与文档示例的长度相同。
   - 网关一侧要跟着改一处。评审过的配置里，凭证由 PDP 按请求给出的各条路由，后端上都有一条规则，只放行以 `Bearer ` 开头的 `Authorization`：它是黑盒报告"默认配置不安全的地方"第 3 项的处理，PDP 放行却没给凭证时由网关拒绝。这一家的头以 `Hc-OweDeveloper ` 开头，照搬这条规则，请求会全部被网关拒绝。这一家的路由上，规则的前缀换成 `Hc-OweDeveloper `，规则本身留着。这是开发计划 3.2 那份配置的事，写在这里是因为它由本篇的头格式决定。
   - 两个文件可以同时给。同一个句柄出现在两个文件里则不启动。只给原来的 Bearer 文件时，行为与现在相同。
   - 换令牌用换文件，不靠重启，也不靠环境变量。进程在要用这份文件时看到修改时间变了，就整份重读。换文件的做法是写临时文件再改名，让修改时间一定变。新文件读不成或校验不过，继续用上一份读成的，并记一条不含账号和令牌的错误。启动时文件就读不成，则不启动。凭证不进网关的配置快照，也不靠快照里的环境变量引用带进去：快照的全文记在发布器的记录里，运行中的配置从回读口读得到（`tests/integration/compose` 的 `SH-10`、`SH-08`）；环境变量引用另由 ADR-0010 第 11 条禁止。Secret Manager 这一步不接。

4. **第二步是 OAuth2 客户端凭证，对着替身令牌端点。** 不在 1.1 那一家的必经路上。[G04](../G04_Identity_and_Security.md) 第 4 节的缓存键至少包含 Provider、账户、环境、客户端、scope 或 audience、密钥版本。同一个账户同时来的请求只向令牌端点发一次。取不到、超时或答错，这次请求拒绝，不用过期的令牌，也不用上一枚顶上。过期之前换新；提前多少在实现时取一个值，写进测试，不写成业务要求。客户端密钥与第一步同一个规矩：单独的文件、0600、不进快照、不进日志。句柄仍然只能出现在一个文件里。令牌端点写在这份文件里：不是回环地址上的 `http`，就必须是 `https`。被撤销的账户不得交出缓存里的令牌；撤销状态存在哪里、谁能写，是另一篇提案，本篇不定。

5. **两个账户不串用，按句柄保证。** 沙箱目前只有一个测试账号。两个账户各拿各的令牌，先用文件里的两条记录对着替身证明。第二个沙箱账号要到之后，才在沙箱上做这一条。本篇不把"现在就有第二个沙箱账号"当作开工条件。

6. **黑盒套件原有用例的期望不改。** 新来源另写用例。Bearer 文件的格式不变。

## 为什么这样决定

Gatekeeper 的模型里现在还没有 Provider 账户这个类型，Broker 在它那边仍是基线里的提案。P2 要的这一个头，每次请求都不一样，无论放在哪一个进程里都得现做。`gateway-authz` 已经在这条请求上，端口也已经把"凭证正文"和"账户授权"分开，所以正文先放在这里，少一次往返。以后改由 Gatekeeper 的 Broker 提供时，换的是 `CredentialSource` 的实现，网关复制响应头的那一段不用改。

这一家不是 OAuth2。先做令牌端点，沙箱要的头仍然发不出去。固定令牌和动态 OAuth 分成两个实现，是因为 [G04](../G04_Identity_and_Security.md) 第 9 节要两种都证明，而不是因为这一家同时用两种。

随机数不能写在文件里，否则就不是每个请求一个。现有实现在启动时读一次，换令牌要重启；重启会把判定停掉。改成看到修改时间变了就整份重读，写坏的文件不替换上一份，是为了避免一份写到一半的文件把所有账户的凭证一起丢掉。

## 被考虑的替代方案

- **等 Gatekeeper 的 Broker 来发放凭证正文。** 基线是这样写的。没有采用，是因为那个类型和 Broker 都还没有，而这个头的随机数不论谁来做都是按请求现做。本篇被拒绝时走这一条。
- **模式 B，本机再放一个 Broker。** ADR-0008 已经测过，隔离与模式 A 相同，代价是多一个持有全部凭证的进程。这一家需要的随机数用那个进程做不比在 `gateway-authz` 里做更少，所以不新增这个进程。
- **把随机数写进网关配置，或做一个通用的头模板。** 快照里不能放秘密。通用模板超出这一家的需要；下一家要另一种头时，再加一个 `CredentialSource`。
- **换令牌靠重启。** 能做到"新请求用新令牌"，但每次轮换都中断判定。不选。
- **这一步就接 Secret Manager。** 还没有指定用哪一个。文件能证明头的格式、按句柄隔离和换令牌。指定了实现之后再加一种来源，不改端口。

## 成本与剩余风险

- 令牌集中在 `gateway-authz` 的进程内存和那个文件上。文件权限和 `ports.Secret` 是现在就有的控制。能读到这个进程的人就能读到令牌。
- 就地改文件且落在同一秒时，修改时间可能不变，这一秒里的请求仍用旧令牌。所以换文件要写临时文件再改名。这一条要写进实现旁边的说明。
- 新文件读不成时继续用上一份。换令牌没有生效时，只有那条不含秘密的错误能看出来。这是有意的：不让一份坏文件把凭证清空。
- 沙箱只有明文 HTTP，令牌在到承运商的路上是明文。这是沙箱的限制。本篇不把生产的上游定成明文；生产地址还没有。
- 沙箱只有一个测试账号。两个账户的隔离先在替身上证明。
- 第二步的替身令牌端点不是这一家承运商。两种凭证都证明，靠的是两个实现，不是这一家同时用两种。
- 撤销记在哪里、产品构建里谁能写，本篇没有定。缓存的 OAuth 令牌在撤销之后不得交出，这一条等那篇提案一起实现；第一步的固定令牌没有缓存，撤销之后的下一个请求只要判定读到撤销就不会再要凭证。
- 随机数的取法是照文档定的，还没有拿它对着沙箱的验证授权接口发过一次。
- 后端上那条规则的前缀换了之后，"PDP 放行却没给凭证时由网关拒绝"要在这一家的配置上重新有用例把关。V1.1 起黑盒套件里有一条替身路由带着新前缀，由 `P1-DT-02` 把关；开发计划 3.2 那份对着沙箱的配置是另一份文件，仍要有它自己的用例。

## 变更与回退条件

需由仓库所有者复核和决定；在此之前保持 Proposed。执笔的是 AI 编码助手，这不是决定。

若仓库所有者决定凭证正文仍由 Gatekeeper 的 Broker 发放，撤回本篇，开发计划 2.1 改按那个决定写。若沙箱拒绝本篇取的随机数，只改取法。若指定了 Secret Manager，加一种来源，不把文件这一步删掉：没有接上 Secret Manager 的环境仍要能用文件跑测试。

## 第一步做出来了：固定令牌加每个请求一个随机数（V1.1）

2026-11-18。照第 3 条写了代码，对着替身验证过。写代码、验证和执笔的是 AI 编码助手。**这不是对本 ADR 的决定**，状态保持 Proposed。承运商的沙箱没有被调用。

做了什么：

- `internal/egressauthz/adapters/filestore` 多了一个凭证来源，读开发者令牌文件，每次放行时用 `crypto/rand` 现做 16 个字节、写成 32 个十六进制字符的随机数，拼成 `Hc-OweDeveloper 账号;令牌;随机数`。端口（`ports.CredentialSource`）没有改。
- `gateway-authz` 多了一个启动参数 `--developer-tokens`。它和 `--credentials` 至少给一个；只给 `--credentials` 时行为与以前相同。
- 黑盒套件多了一条替身路由和五个用例（`P1-DT-01` 至 `05`）。Mock Provider 按承运商文档查这种头的格式。

第 3 条没有写到、写代码时定下来的，留给仓库所有者一并看：

- **`--credentials` 不再是必给的**，两个文件至少给一个。只用得到开发者令牌的部署不必为此放一份空的 Bearer 文件。
- **怎样算"文件变了"**。第 3 条写的是修改时间。实现里另外看两样：大小，和它是不是同一个文件。改名换上来的是另一个文件，修改时间碰巧相同也看得出来。就地改写成一样长的内容而修改时间又没有变，仍然看不出来；有一条单元测试专门记着这一点。
- **同一份坏文件只读一次、只记一次。** 它再被换掉之前，每个请求不重读它。文件不见了也只记一次，继续用上一份。
- **读文件比第 3 条写的严三处**：同一个句柄在一个文件里写了两次，有不认识的字段，对象后面还有内容，都拒绝。
- **几个凭证来源依次问。** 前一个说没有这个账户的凭证，才问后一个；前一个出了别的错，不拿后一个顶上。
- **替身比文档严。** 承运商的文档说以后的版本会限定随机数不能重复；Mock Provider 现在就拒绝用过的随机数。

验证（2026-11-18，Go 1.26.8，agentgateway 1.7.0，锁定的镜像）：

- 单元测试：头的格式；连取 500 次随机数互不相同；文件的权限和各种写坏的内容（错误信息里没有账号和令牌）；换文件之后重读；坏文件、别人可读的文件、带着已被占用的句柄的文件换上来之后继续用上一份；一边换文件一边有 8 路并发在取凭证。带竞态检测跑过。
- `cmd/gateway-authz`：两种文件一起给时各走各的；只给开发者令牌文件也能启动；该拒绝启动的六种情况；服务日志里没有账号和令牌。产品构建和验收构建都跑过。

- 黑盒：新的五个用例通过，共 41 项检查。原有 59 个用例的 326 项检查与此前逐项相同，失败的仍只有 `P1-SS-04`。没有改坏的工作区上先后跑了三遍，都是 63/64。对照改坏七处（两处在网关配置，五处在 `gateway-authz`），每一处都有 `P1-DT` 用例不通过，别的用例不受影响。细节在 [黑盒报告](../../tests/acceptance/blackbox/README.md) 的"不是 Bearer 的凭证"。

黑盒里看清的两件事：

- **规则的前缀确实要换。** 把替身路由上的前缀留成 `Bearer `，这条路由的请求全部被网关拒绝。

- 第 4 条（OAuth2 客户端凭证）没有开始。撤销记在哪里的提案没有写。Secret Manager 没有接。
- 与本机 Gatekeeper 的联调套件（`tests/integration/gatekeeper`）没有重跑。它用的是同一个 Mock Provider 和只带 `--credentials` 的产品构建；这两样的原有行为由上面的测试和黑盒原有用例把关，那套联调本身这次没有跑。

## 第二步做出来了：OAuth2 客户端凭证，对着替身令牌端点（V1.2）

2026-11-18，V1.1 那一步之后。照第 4 条写了代码，对着替身令牌端点验证过。写代码、验证和执笔的是 AI 编码助手。**这不是对本 ADR 的决定**，状态保持 Proposed。**没有对着任何真实的令牌端点**；Secret Manager 没有接。V1.1 里写的"第 4 条没有开始"现在不再成立（V1.1 一节的正文没有改，它写的是 V1.1 当时的情况）。

做了什么：

- 新的适配器包 `internal/egressauthz/adapters/oauthclient`，实现 `ports.CredentialSource`，端口没有改。它向令牌端点发 `POST`（`application/x-www-form-urlencoded`，正文 `grant_type=client_credentials`，有 `scope`、`audience` 时带上），客户端凭证用 HTTP Basic；不跟随重定向；应答正文最多读 64KB；不使用环境变量里的代理。拿到的令牌以 `Bearer ` 加 `access_token` 放进 `ports.Secret`，经现有的 Bearer 路由交给网关。
- `gateway-authz` 多了两个启动参数：`--oauth-clients`（第三种凭证文件）和 `--oauth-timeout`（默认 800 毫秒，必须大于 0）。三个文件至少给一个；一个句柄只能在其中一个里，启动时和各自被换掉之后重读时都查。
- 黑盒套件没有加网关路由：OAuth 取到的是 Bearer 令牌，走现有问 PDP 的 Bearer 路由（`tracking.get`）。登记表里那条路由多了两个租户、各带一个账户（`tenant-oauth-1`/`account-oauth-1`、`tenant-oauth-2`/`account-oauth-2`），原有租户和账户没有动。替身令牌端点在 Mock Provider 里（同一个进程和端口，路径 `/oauth/token`）。新增 `P1-OA-01` 至 `08`。

客户端凭证文件（权限 0600 或更严；JSON 对象，键是凭证句柄，即凭证绑定加账户；值是下面这个样子，下面的值是假的）：

```json
{
  "gatekeeper:mockcarrier-test/account-oauth-1": {
    "token_endpoint": "https://auth.example.test/oauth/token",
    "client_id": "client-oauth-1",
    "client_secret": "not-a-real-secret",
    "key_version": "2026-11-a",
    "scope": "parcels.read parcels.write",
    "audience": "https://api.example.test"
  }
}
```

`client_id`、`client_secret`、`key_version` 必填、非空；`scope`、`audience` 可选。`client_id`、`client_secret`、`key_version`、`audience` 只能是可见 ASCII（`audience` 不含空白）。`scope` 是一个或多个记号，用单个空格隔开（RFC 6749 第 3.3 节）：每个记号是可见 ASCII，不含双引号和反斜杠；开头、结尾有空格或连着两个空格都不行；空串等于没给。发给令牌端点时整串照原样放进表单的 `scope`。`token_endpoint` 必须是 `https`；只有主机是回环地址的字面量（`127.0.0.0/8` 或 `::1`，`localhost` 不算）时才允许 `http`；不许带用户信息、查询串和片段。文件的读法与前两种文件相同：权限不合格或启动时读不成就不启动；修改时间、大小或文件本身变了就整份重读；新文件读不成或校验不过，继续用上一份并记一条不含秘密的错误（同一份坏文件只记一次）；同一个句柄写两次、有不认识的字段、对象后面还有内容，都拒绝。运维换客户端密钥时，要在改 `client_secret` 的同时改 `key_version`。

缓存和并发：

- 缓存键由句柄、`token_endpoint`、`client_id`、`scope`、`audience`、`key_version` 和客户端密钥的摘要（SHA-256，只在内存里，不进日志和错误）组成。句柄里已经有凭证绑定和账户；Provider 与环境在绑定里。键里有密钥的摘要，所以运维换了密钥却忘了改 `key_version` 时，用旧密钥取来的令牌也不会一直用到过期：密钥一变旧的那一条就不再用，下一个请求用新密钥重新取。`key_version` 照旧必填、照旧在键里，它是运维写明"这是哪一版密钥"的地方；摘要是防忘了改的那一道。文件重读之后，某个句柄的这些值有任何一个变了，旧的一条就被丢掉，下一个请求重新取；不再出现在文件里的句柄的缓存同样丢掉。
- 过期之前换新在请求来的时候做，没有后台任务。令牌剩下的寿命不超过"30 秒和总寿命的十分之一两者里较小的"时，就不再交出它，这个请求去取新的。寿命从请求发出的时刻算起，所以算出的到期时间只会偏早。
- 同一个缓存键同时来的请求只向令牌端点发一次，后来的等先来的那一次的结果；那一次失败，等着的也都拒绝，不各自再发。这一次获取不受发起它的那个请求的 `ctx` 管，受超时管，所以发起的那个请求走了，别的等着的请求照样拿到结果；每个等着的请求自己受自己的 `ctx` 约束。不同的缓存键互不等待。

取不到的时候：

- 连不上、超时、状态不是 200、答错，这次请求拿不到凭证，不用过期的令牌，也不用上一枚顶上，哪怕上一枚还没到期；取失败时缓存里这个键下的令牌同时清掉。下一个请求再去取，没有"失败也缓存"。答对的条件：状态 200；JSON 对象，后面没有别的内容；`access_token` 非空、可见 ASCII、不含空白；`token_type` 不分大小写等于 `Bearer`；`expires_in` 是正整数（带引号的字符串、小数、`null`、缺了，都算答错）；应答正文不超过 64KB。
- 凭证来源返回的错误不是 `ErrCredentialNotHeld`，所以 `gateway-authz` 照现有的做法答 503、`result` 为 `INDETERMINATE`、`reason_code` 为 `CREDENTIAL_UNAVAILABLE`，网关把它原样交给调用方（`P1-FO-02` 已经是这样）。**没有加新的原因码**：调用方分不出"没有这个账户的凭证"和"令牌端点取不到"，两者都是这一个原因码；分得出来的只有 `gateway-authz` 的日志。要分开的话是要加原因码的，那是另一个决定，这里没有做。
- 每次向令牌端点取，记一行：句柄、结果的类别（`ok`、`timeout`、`unreachable`、`status N`、`bad_answer`）、用时、成功时的 `expires_in`。日志、错误信息和应答里没有客户端密钥、访问令牌、Basic 头，也没有令牌端点应答的正文。

第 4 条留给实现、由仓库所有者定了取值的几处（**这些是实现的取值，不是业务要求**）：

| 项 | 取值 |
|---|---|
| 提前换新 | 剩下的寿命不超过 `min(30 秒, 总寿命/10)` 时不再交出。写成 `oauthclient.RefreshLead`，单元测试里逐个取值检查，用可注入的时钟，不靠真的等 |
| 取一次令牌的超时 | `--oauth-timeout`，默认 800 毫秒：评审过的网关配置里 ExtAuthZ 等 PDP 最多 1 秒，取令牌要留在它之内 |
| 客户端认证方式 | 只有 `client_secret_basic`。客户端标识和密钥按 RFC 6749 2.3.1 先做表单编码再做 Basic（可见 ASCII 里字母、数字和 `-._*` 不变） |
| `expires_in` | 必须有，必须是正整数；没有的一律算答错，不替令牌端点猜一个寿命 |
| 缓存键 | 句柄、`token_endpoint`、`client_id`、`scope`、`audience`、`key_version`、客户端密钥的 SHA-256 摘要（评审后加上最后一项） |

写代码时碰到、不在上面也不在第 4 条里，按最保守的一边取了值的几处，留给仓库所有者一并看：

- **`expires_in` 过大**：大于十年的值照样接受，只是按十年算，免得换算成时间时溢出。
- **答错里包括正文超过 64KB**：读到 64KB 再多一个字节就算答错，不再往下读。
- **`localhost` 不算回环**：第 4 条说"回环地址"，所有者给的取值是"回环地址的字面量"。文件的作者写的是什么就是什么，不靠解析；`http://localhost/…` 要写成 `http://127.0.0.1/…`。
- **取令牌不受发起它的请求的 `ctx` 管**，见上；代价是请求都走了的时候，这一次获取仍然会跑到超时为止。
- **`oauthclient` 里读文件的代码是照 `filestore` 抄的，不是复用**：`filestore` 的那几个函数没有导出，为了复用把它们导出，会改动第一步已经验证过的代码。两边现在各有一份，改读法时要两处一起看。唯一动了第一步代码的地方：`DeveloperTokens` 多了 `Holds`，它读的是上一次读成的那一份，不拿锁，因为三个文件要互相问句柄有没有重复，两边重读时各拿着自己的锁互相等就是死锁。

撤销那一条现在是怎么满足的：ADR-0012 之后撤销表已经有了，`application.Service` 的判定本来就是先读撤销再取凭证，被撤销的账户在判定里就被拒绝，走不到凭证来源。所以没有在凭证来源和撤销表之间加任何耦合，`oauthclient` 不认识撤销。证明这一点的是：`oauthclient` 的一条单元测试用真的 `application.Service` 和一张可改的撤销表，先让账户取到并缓存令牌，撤销之后请求被拒绝、令牌端点没有再被问，恢复之后照常、用的还是缓存里的那一枚；黑盒的 `P1-OA-07` 在网关和 `gateway-authz` 的整条路上做同一件事。第 4 条写的"缓存的 OAuth 令牌在撤销之后不得交出"因此成立；它不依赖撤销状态存在哪里。

验证（2026-11-18，Go 1.26.8，agentgateway 1.7.0，锁定的镜像）：

- 单元测试，用 `httptest` 的令牌端点和可注入的时钟：请求的形状（方法、`Content-Type`、Basic、正文）；两个账户各取各的、连着要只取一次；换新的各个边界；并发只取一次（二十四路，带竞态检测跑），那一次失败时等着的全都拒绝、不各自再发；发起的请求走了不影响别的等着的；各种取不到（状态 500、401、201、204、重定向、超时、连不上、十八种答错，其中有应答正文里带着密钥的）各自拒绝，错误信息和日志里没有密钥、令牌、Basic 头、应答正文，端点恢复之后下一个请求照常；上一枚还没到期但已到该换新的时候，端点坏了，请求拒绝；缓存键的每个组成部分变了都重新取，没变的账户不受影响，不再出现的句柄的缓存被丢掉；文件的各种不合格；重读和读不成继续用上一份；令牌端点地址的各种写法。`cmd/gateway-authz`：三种文件各走各的；`--oauth-timeout`；三个文件至少一个；句柄重复（启动时和重读时）；该拒绝启动的十六种情况。
- 对照：把新代码改坏三十一处（一次一处，在仓库的一份副本里，只跑相关的 Go 测试，带 `-race`），三十一处里三十处有测试不通过；没被发现的一处是"取失败时不清缓存里的旧令牌"：它单独改不出行为上的差别（旧令牌此时本来就已经不够交出，之后时间只往前走），算等价的改动，没有为它去改测试。评审后加的两处（`scope` 的校验放开成什么都接受；缓存键去掉密钥摘要）各有测试发现：前一处是 `TestScopeIsOneOrMoreSpaceSeparatedTokens`，后一处是 `TestACachedTokenIsKeyedByEveryPartOfTheKey` 和 `TestChangingOnlyTheSecretFetchesAgainWithTheNewSecret`。头一遍有一处（缓存键里去掉句柄）没被发现，原因是测试里两个账户用的客户端不同，键靠客户端标识就分得开；补了一条两个账户共用一个客户端的测试之后重跑，发现了。

没有做的：

- 没有对着任何真实的令牌端点发过请求，包括开发计划 1.1 提到的、留作候选的那一家（Dragon Open API）。替身答对了不等于真的令牌端点答得一样：它们的 `expires_in` 写法、错误应答、对 `scope`/`audience` 的态度，都要到对着真的才知道。
- 对着 `https` 的令牌端点只在单元测试里试过（用测试服务器的证书）；黑盒里的替身是回环上的明文 `http`。没有试过私有 CA、证书钉扎、对令牌端点的 mTLS。
- 只有 `client_secret_basic`。没有 `client_secret_post`、`private_key_jwt` 和别的认证方式；没有 `refresh_token`、没有别的授权类型。
- Secret Manager 没有接，客户端密钥放在文件里。
- 没有后台刷新：令牌在请求来的时候才换，一个账户长时间没有请求，下一个请求要多等一次取令牌的时间（最长 `--oauth-timeout`）。
- 令牌端点的应答里别的字段（`scope`、`refresh_token` 等）一概不看。
- 取失败之后没有退避，也不记"刚失败过"：令牌端点坏着的时候，每个请求都会再去问一次（同一个键同一时刻仍只有一次在进行），各等到超时为止，最长 `--oauth-timeout`。
- 令牌端点的证书只认系统的根证书，不能另给 CA；私有 CA 的令牌端点现在接不上。
- 多个 `gateway-authz` 实例各有各的缓存，同一个账户会各取各的令牌，令牌端点按客户端限流时要留意。
- 就地改文件且修改时间、大小都没有变时看不出文件变了，和第一步一样；要写临时文件再改名。
- 与本机 Gatekeeper 的联调套件（`tests/integration/gatekeeper`）没有重跑，理由同 V1.1。
- 没有给 `gateway-authz` 到令牌端点这一段加出口规则（ADR-0010 V1.8 的网络命名空间规则只许去配置里写着的地址）；令牌端点的地址不在网关的配置里，真要部署时那份规则要加上它。没有做，也没有试。
