# ADR-0008 — 出站凭证经 HTTP ExtAuthZ 响应头按请求注入

> **状态**：Accepted · **版本** V1.1 · **日期** 2026-11-10（2026-11-21 仓库所有者定为 Accepted；V1.1 于 2026-11-23）  
> 本 ADR 为设计建议，不是已经执行的技术审批、生产基线或运行验收。

2026-11-21，仓库所有者把本篇定为 Accepted。变更条件里「验证未完成前保持 Proposed」到此为止。下面写的是这篇现在覆盖什么、不覆盖什么。

## 现在

已经做出来的是模式 A：ExtAuthZ，把一个 `Authorization` 头复制到上游请求上，账户选择由 PDP 核对。模式 B 没有采用。`credentials/materialize` 仍然没有实现。证据是提交 `4416f89` 的黑盒文件：97 个用例，96 个通过，751 项检查，未通过的只有 `P1-SS-04`。控制台仍然冻结：P1 PoC 的遗留没有收口，仓库所有者也没有决定控制台在交付范围内（[governance/README.md](../governance/README.md) 与 `design-status.json` 的 `scope_freeze`）。接受本篇只满足 `lift_when` 三条里的一条，控制台保持冻结。

## 背景

G04 §4 列出三种 Credential Broker 返回模式并要求用 PoC 比较；ADR-0001、ADR-0003、ADR-0004 都以"动态凭证注入经实测可行"为前提保持 Proposed。Gatekeeper 契约里的 `credentials/prepare` 返回不透明的 `secure_binding_handle`，但没有定义网关如何把它兑换成凭证。

## 推荐决策

1. 需要按租户/账户选择凭证的出站路由采用**模式 A**：网关验证调用方 JWT 后调用 Gatekeeper 的 HTTP ExtAuthZ 端点；允许响应的 `Authorization` 头即本次请求的 Provider 凭证，网关只把这一个头写到上游请求。
2. **凭证兑换只有这一条路**。Gatekeeper 不提供"用句柄换凭证正文"的接口：`credentials/materialize` 不实现，`secure_binding_handle` 不签发。`credentials/prepare` 只返回计划，不返回秘密。
3. 可信上下文由网关从已验签 JWT 与路由常量构造；调用方只能提交账户**申请**（`X-Provider-Account`），由 PDP 对照授权复核。
4. 模式 A 用**复制响应头**（`includeResponseHeaders`）实现，不用 `backendAuth.key.expression`：两者实测结果相同，后者没有换来安全上的好处。这一条原先还有一个理由：后者只有 1.7.0 接受，会把配置绑在 1.7.0 上。目标版本锁定为 1.7.0 之后这个理由不再成立，剩下的只有前一条。例外只有一种：Provider 要求凭证放在请求头以外的位置（如查询参数），复制响应头做不到，届时按路由单独评估并补测。
5. 网关到 Gatekeeper 用工作负载 mTLS：网关出示自己的证书并固定 CA 与对端名字，Gatekeeper 从客户端证书取调用方身份，只对网关身份下发凭证。
6. 模式 C（网关固定凭证）仅用于单账户固定路由；模式 B 暂不采用，保留为回退方案。
7. 线上契约见 `contracts/gatekeeper/openapi.yaml` 的 `/v1/extauthz/check`，网关侧必须配置的项见 `tests/acceptance/blackbox/README.md` 的"默认配置不安全的地方"。

## 为什么这样决定

`tests/acceptance/blackbox` 在 agentgateway 1.7.0 上跑通了模式 A：双租户双账户隔离、撤销即时生效、伪造上下文无效、内部 JWT 不到第三方、PDP 故障默认拒绝、非幂等写不重放（97 个用例 96 个通过，未通过的 `P1-SS-04` 见下面"重复 `Host` 头"一条；证据在 `tests/acceptance/blackbox/evidence/`）。模式 C 同时跑通，但两个租户以同一账户到达 Provider，不满足多租户要求。一次往返同时完成授权与凭证下发，不需要第二个接口，也就没有可被重放或转交的句柄。

网关到 Gatekeeper 的 mTLS 跑通：没有工作负载 CA 签发的证书连不上，同一信任域里不是网关的身份拿不到凭证，冒充 Gatekeeper 的服务收不到网关的请求。

## 被考虑的替代方案

- **模式 B（本地 Broker/Sidecar）**。已测，可行：隔离、撤销、默认拒绝与模式 A 相同，而且 Provider 凭证不出现在 Gatekeeper 的任何响应里。没有采用，是因为它多出一个进程、一份放着全部账户凭证的本地存储（下发、轮换、吊销都没有设计），以及一段只能靠部署环境来限制访问的本地通信；换来的"凭证不过网络"在网关与 Gatekeeper 之间已有 mTLS 的前提下收益有限。
- **`backendAuth.key.expression`**。已测，可行，结果与复制响应头相同。
- 模式 C 作为默认（不能按租户选账户）；保留 `prepare` + 句柄兑换（多一次往返，且句柄的绑定与兑换语义从未定义）。

## 成本与剩余风险

- 证据来自 Mock Gatekeeper、Mock Provider、单进程。**没有对接过任何 Gatekeeper 实现**：验证的是网关一侧和一个按契约写的 Mock。mTLS 用的是每次运行临时生成的 CA，证书的签发、轮换、吊销未验证；多副本、负载下的行为未验证。
- 只在 agentgateway 1.7.0 上验证，即 `deploy/agentgateway/agentgateway.lock.json` 锁定的构建：上游容器镜像（按摘要锁定）里的那个二进制。换版本必须用同一套用例重跑。网关在没有会话密钥时会改写自己的配置文件，部署时必须经 `SESSION_KEY` 提供密钥（见 `tests/acceptance/blackbox/README.md`）。
- mTLS 让 Gatekeeper 确认对面是网关，但租户与服务身份仍是网关转述的；网关被攻破时这些声明可以伪造。
- 每个请求同步依赖 PDP，延迟与可用性预算未测；决策缓存未启用也未测。
- Provider 凭证经过网关进程内存和 PDP 响应。PoC 里网关默认配置下的日志没有出现凭证、调用方 JWT 或密钥；追踪、指标以及改过日志字段之后的行为没有验证。
- 只覆盖 Header 注入。HMAC 签名、mTLS 客户端身份、OAuth 授权码委托仍是设计提案。
- 重复 `Host` 头：锁定的 1.7.0 自己仍然接受（`P1-SS-04`，没有配置开关）。处置是在网关前面放一个会拒绝这类请求的入口组件，PoC 里用 nginx 验证过（`P1-FP-01..04`）。给 agentgateway 上游的报告（`docs/upstream/UPSTREAM_REPORT_duplicate_host.md`）已于 2026-11-11 经私下渠道提交。2026-11-23 查公开记录：修复在 [PR #4401](https://github.com/agentgateway/agentgateway/pull/4401)（2026-11-13 合并，`c511955`，应答 400），OSS 最新正式版仍是 v1.7.0。同一天仓库所有者决定在锁定的 1.7.0 上直接接受两个 `Host` 头：网关监听按第一个处理，前置组件仍答 400。私下公告当天没有再打开。这个处置成立的前提是调用方只能经入口组件到达网关的监听端口。这个端口现在只绑回环（`bindAddress`，`P1-NL-01`），入口组件与网关放在同一个 Pod 里（ADR-0010 第 4 条；`tests/integration/kubernetes` 的 `K8-01`）。正式选用的入口组件需要重新跑同样的用例。
- 请求头和失败来源（2026-11-18，仍不是决定）。评审配置改为只放行登记过的请求头，六条路由用同一份名单；问 PDP 的路由用 `failureMode.denyWithStatus: 503`，策略拒绝仍是 403 加 PDP 的原因，问不到 PDP 时调用方得到网关自己的 503。同一天稍后起，做出了判定的拒绝（403，以及判定不了的 503）还带着这次判定的编号：应答头 `X-Idp-Decision-Id` 和正文的 `decision_id`，与 `gateway-authz` 日志里的是同一个；网关把它写在这次调用的访问日志那一行，上游应答里的同名头在六条路由上一律去掉，所以 Provider 伪造不了。没走到判定就被挡下的请求没有编号。用例是 `P1-CO-06`、`P1-CO-08`，契约在 `contracts/gatekeeper/openapi.yaml`。用例是 `P1-HD-01` 至 `04`、`P1-FO-01/02`，见黑盒报告。留下的：网关访问日志不再用 `reason=ExtAuth` 标出问不到；名单上的表达式求值不了时，没登记的头仍会到 Provider，按名字删除是第二道。

## 凭证不在 Authorization 里的路由（V1.1）

2026-11-23。第 4 条留了一个例外：Provider 要求凭证放在别的位置时，按路由单独评估并补测。这一节是那次评估，量和执笔的是 AI 编码助手。第 4 条的原文不改。凭证在 `Authorization` 里的路由仍然复制响应头，万邦和顺丰两份配置没有变。现在没有哪一家承运商用到这一节。

量的是锁定的 1.7.0（SHA-256 `c7ef326b7b5702451e94bab55ff484d600d5abdc5344a4cdf7c72fc0bcff9e24`），都在回环上，不是验收通过。

量到的三件事：

1. **查询参数放得进去。** `backendAuth.key` 的 `location.queryParameter` 把值追加到查询串上。调用方自带的同名参数被拿掉，带两个也一样；别的参数留着。值按表单的写法转义：空格成 `+`，`+` 成 `%2B`，`&` 成 `%26`，`=` 成 `%3D`，`%` 成 `%25`，`#` 成 `%23`。网关访问日志里的路径是调用方送来的那一份，没有放上去的凭证。
2. **别的请求头不能照搬复制响应头。** PDP 放行并交出凭证时，复制响应头和 `backendAuth` 两种写法都把调用方自带的同名头换掉，带两个也一样。PDP 放行却没有交出凭证时两种写法不一样。复制响应头的写法下，调用方自带的 `x-api-key: Key attacker` 通过了后端上「凭证以方案开头」的那条规则，到了上游。读进 `extauthz.credential`、再由 `backendAuth` 放上去的写法答 403，上游没有收到请求。`Authorization` 没有这个问题：调用方的 JWT 验完就被网关拿掉了，那时请求上的 `Authorization` 只能来自 PDP。`gateway-authz` 不会放行而不交凭证，所以前一种情形现在走不到。但那条规则就是为这种情形留的第二道，不能在别的头上失效。提交 `481119a` 编出来的是复制响应头的写法，这一节把它换掉了。
3. **去掉方案前缀用 `stripPrefix`。** `gateway-authz` 的凭证来源交出的都是带方案的整个值（`Bearer `、`Hc-OweDeveloper `、`Sf-OpenApi `）。放进别的头或查询参数的是去掉方案的值。`substring(n)`、`stripPrefix("…")`、`regexReplace("^…", "")` 三种只去开头的那一段，在六种 PDP 应答上结果相同。`replace("…", "")` 把值里再出现的同样字样一起删掉。`split(" ")[1]` 把带空格的值截断。

定下来的写法在 `internal/routecompile/domain/emit.go`：

- PDP 那一跳不变。凭证只在 `Authorization` 应答头里，契约和 `gateway-authz` 都不改。提交 `481119a` 给登记表加的 `credential_header`，和 `gateway-authz` 按它换应答头的那部分，撤掉了。
- 编译规格里把 `credential_header` 写成别的头名，或者写 `credential_query_parameter`。两样只能选一样。
- 这种路由不写 `includeResponseHeaders`，在 `metadata` 里写 `credential: response.headers["authorization"]`。
- 后端上的规则是 `has(extauthz.credential) && extauthz.credential.startsWith("<方案>") && size(extauthz.credential) > <方案的长度>`。然后是 `backendAuth.key.expression: extauthz.credential.stripPrefix("<方案>")`，`location` 是那个头或那个查询参数。
- 转发给上游的请求头名单里没有 `authorization`。凭证头在名单里，因为名单在 `backendAuth` 之后求值。
- `set_request_headers` 不许写凭证头的名字，也不许写 `authorization`：这些头是在凭证放上去之后才写的，同名的一项会把凭证换成规格里的常量。

编译器写出来的配置在锁定的二进制上跑过。用的是万邦的规格，方案换成 `Bearer `。脚本只换了监听、PDP 和上游的地址，去掉了监听上的 JWT、PDP 那一跳的 TLS 和回读口；后端上的策略在替换前后逐字相同。两份配置都先过了 `--validate-only`。PDP 替身放行，交出什么由请求头 `x-provider-account` 决定。

| 情形 | `credential_query_parameter: api_key` | `credential_header: x-api-key` |
|---|---|---|
| PDP 交出 `Bearer real-credential` | 200，上游收到 `/api/whoami?api_key=real-credential` | 200，上游收到 `x-api-key: real-credential` |
| 调用方自带同名的值，一个或两个 | 200，只剩 PDP 的那一个，别的参数留着 | 200，只剩 PDP 的那一个 |
| PDP 放行但没有交出凭证，调用方自带同名的值 | 403，上游没有收到请求 | 403，上游没有收到请求 |
| PDP 交出的是别的方案（`Basic real-credential`） | 403，上游没有收到请求 | 403，上游没有收到请求 |
| PDP 交出的只有方案，后面是空的 | 403，上游没有收到请求 | 403，上游没有收到请求 |
| 调用方带了 `Authorization` | 200，上游没有收到 `Authorization` | 200，上游没有收到 `Authorization` |
| 比登记的路径深一段 | 403，上游没有收到请求 | 没有量 |

一共十四笔，到了上游的是七笔。这七笔里上游都没有收到 `x-provider-account`，`Host` 是规格里的 `rewrite_authority`，`Accept` 是规格里写的那一个。两次运行的网关日志里都没有出现 `real-credential`。

留下的：

- 查询串里的凭证会进承运商和沿途代理的访问日志。这是这个位置本身带来的，网关管不到。到承运商的那一跳要有 TLS；明文沙箱例外在 `PROD` 本来就被拒绝。
- 空格转成 `+` 是表单的写法。按 RFC 3986 解查询串的一方会把它读成加号。凭证里有空格时，要先对着那一家量。
- 调用方自己写在查询串里的值会进网关的访问日志，包括它自带的那个同名参数。
- 这一节没有黑盒用例，也没有哪一家承运商在用。真要用的时候，按开发计划 3.2 的做法给那一家写配置，对着替身跑通，再连沙箱。
- 凭证放在 Cookie 或请求正文里，没有量。

## 变更与回退条件

需由仓库所有者复核和决定；在相关 PoC、负向测试、容量与灾备验证未完成前保持 Proposed。若最终锁定的版本上同一 PoC 不通过，重新评估本决策。若真实 Gatekeeper 的延迟/可用性无法满足受批准目标，按以下顺序评估，而非自动维持本决策：先评估 gRPC ExtAuthZ 加短时效决策缓存（agentgateway 文档写明缓存只支持 gRPC 协议，HTTP 协议每个请求都会调用 PDP；缓存会让撤销最多延后一个 TTL；两者本 PoC 均未测），仍不满足再评估模式 B。
