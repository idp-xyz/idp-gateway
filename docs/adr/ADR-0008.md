# ADR-0008 — 出站凭证经 HTTP ExtAuthZ 响应头按请求注入

> **状态**：Proposed（待具名批准） · **版本** V1.0 · **日期** 2026-11-10  
> 本 ADR 为设计建议，不是已经执行的技术审批、生产基线或运行验收。

## 背景

G04 §4 列出三种 Credential Broker 返回模式并要求用 PoC 比较；ADR-0001、ADR-0003、ADR-0004 都以"动态凭证注入经实测可行"为前提保持 Proposed。Gatekeeper 契约里的 `credentials/prepare` 返回不透明的 `secure_binding_handle`，但没有定义网关如何把它兑换成凭证。

## 推荐决策

1. 需要按租户/账户选择凭证的出站路由采用**模式 A**：网关验证调用方 JWT 后调用 Gatekeeper 的 HTTP ExtAuthZ 端点；允许响应的 `Authorization` 头即本次请求的 Provider 凭证，网关只把这一个头写到上游请求。
2. **凭证兑换只有这一条路**。Gatekeeper 不提供"用句柄换凭证正文"的接口：`credentials/materialize` 不实现，`secure_binding_handle` 不签发。`credentials/prepare` 只返回计划，不返回秘密。
3. 可信上下文由网关从已验签 JWT 与路由常量构造；调用方只能提交账户**申请**（`X-Provider-Account`），由 PDP 对照授权复核。
4. 模式 A 用**复制响应头**（`includeResponseHeaders`）实现，不用 `backendAuth.key.expression`：两者实测结果相同，后者没有换来安全上的好处。这一条原先还有一个理由：后者只有 1.7.0 接受，会把配置绑在 1.7.0 上。目标版本锁定为 1.7.0 之后这个理由不再成立，剩下的只有前一条。例外只有一种：Provider 要求凭证放在请求头以外的位置（如查询参数），复制响应头做不到，届时按路由单独评估并补测。
5. 网关到 Gatekeeper 用工作负载 mTLS：网关出示自己的证书并固定 CA 与对端名字，Gatekeeper 从客户端证书取调用方身份，只对网关身份下发凭证。
6. 模式 C（网关固定凭证）仅用于单账户固定路由；模式 B 暂不采用，保留为回退方案。
7. 线上契约见 `contracts/gatekeeper/openapi.yaml` 的 `/v1/extauthz/check`，网关侧必须配置的项见 `tests/acceptance/blackbox/README.md` 的"默认配置不安全的地方"。

## 为什么这样决定

`tests/acceptance/blackbox` 在 agentgateway 1.7.0 上跑通了模式 A：双租户双账户隔离、撤销即时生效、伪造上下文无效、内部 JWT 不到第三方、PDP 故障默认拒绝、非幂等写不重放（59 个用例 58 个通过，未通过的 `P1-SS-04` 见下面"重复 `Host` 头"一条；证据在 `tests/acceptance/blackbox/evidence/`）。模式 C 同时跑通，但两个租户以同一账户到达 Provider，不满足多租户要求。一次往返同时完成授权与凭证下发，不需要第二个接口，也就没有可被重放或转交的句柄。

网关到 Gatekeeper 的 mTLS 跑通：没有工作负载 CA 签发的证书连不上，同一信任域里不是网关的身份拿不到凭证，冒充 Gatekeeper 的服务收不到网关的请求。

## 被考虑的替代方案

- **模式 B（本地 Broker/Sidecar）**。已测，可行：隔离、撤销、默认拒绝与模式 A 相同，而且 Provider 凭证不出现在 Gatekeeper 的任何响应里。没有采用，是因为它多出一个进程、一份放着全部账户凭证的本地存储（下发、轮换、吊销都没有设计），以及一段只能靠部署环境来限制访问的本地通信；换来的"凭证不过网络"在网关与 Gatekeeper 之间已有 mTLS 的前提下收益有限。
- **`backendAuth.key.expression`**。已测，可行，结果与复制响应头相同。
- 模式 C 作为默认（不能按租户选账户）；保留 `prepare` + 句柄兑换（多一次往返，且句柄的绑定与兑换语义从未定义）。

## 成本与剩余风险

- 证据来自 Mock Gatekeeper、Mock Provider、单进程。**没有对接过任何 Gatekeeper 实现**：验证的是网关一侧和一个按契约写的 Mock。mTLS 用的是每次运行临时生成的 CA，证书的签发、轮换、吊销未验证；多副本、负载下的行为未验证。
- 只在 agentgateway 1.7.0 上验证，即 `deploy/agentgateway/agentgateway.lock.json` 锁定的构建：上游容器镜像（按摘要锁定）里的那个二进制。换版本必须用同一套用例重跑。网关在没有会话密钥时会改写自己的配置文件，部署时必须经 `SESSION_KEY` 提供密钥（见 `tests/acceptance/blackbox/README.md`）。
- mTLS 让 Gatekeeper 确认对面是网关，但租户与服务身份仍是网关转述的；网关被攻破时这些声明可以伪造。
- 每个请求同步依赖 PDP，延迟与可用性预算未测；决策缓存未启用也未测。
- Provider 凭证经过网关进程内存和 PDP 响应。PoC 里网关默认配置下的日志没有出现凭证、调用方 JWT 或密钥；追踪、指标以及改过日志字段之后的行为没有验证。
- 只覆盖 Header 注入。HMAC 签名、mTLS 客户端身份、OAuth 授权码委托仍是设计提案。
- 重复 `Host` 头：网关自己仍然接受（`P1-SS-04`，没有配置开关）。处置是在网关前面放一个会拒绝这类请求的入口组件，PoC 里用 nginx 验证过（`P1-FP-01..04`）；给 agentgateway 上游的报告已起草（`docs/upstream/UPSTREAM_REPORT_duplicate_host.md`），尚未提交。这个处置成立的前提是调用方只能经入口组件到达网关的监听端口。这个端口现在只绑回环（`bindAddress`，`P1-NL-01`），入口组件与网关放在同一个 Pod 里（ADR-0010 第 4 条；`tests/integration/kubernetes` 的 `K8-01`）。正式选用的入口组件需要重新跑同样的用例。
- PoC 的其余遗留问题（请求头只能按黑名单删除、PDP 不可用与拒绝不可区分）在批准前需要处置或接受。

## 变更与回退条件

需由架构负责人、对应产品 Owner、安全负责人及运行负责人具名复核；在相关 PoC、负向测试、容量与灾备验证未完成前保持 Proposed。若最终锁定的版本上同一 PoC 不通过，重新评估本决策。若真实 Gatekeeper 的延迟/可用性无法满足受批准目标，按以下顺序评估，而非自动维持本决策：先评估 gRPC ExtAuthZ 加短时效决策缓存（agentgateway 文档写明缓存只支持 gRPC 协议，HTTP 协议每个请求都会调用 PDP；缓存会让撤销最多延后一个 TTL；两者本 PoC 均未测），仍不满足再评估模式 B。
